Branch `chore/adr049-d7-transport`, commit b45f9de5a. ADR-049 Decision 7 made ContextTransportProvider async, hoisting `try_broadcast_commit_or_enqueue` OUT of the fail-closed `commit_class_s_keep` closure into a coalesced (≤50ms) Class-C write. Crash-in-window lost the `commit_fault` safety gate + `pending_commits` retry → silent permanent MLS epoch desync.

**Fix (SOUND):** split into `try_broadcast_commit` (async, send-only, returns `Option<BroadcastFailure>`, mutates no state) + `apply_broadcast_failure` (sync, applies enqueue/marker to 3 disjoint Class-C borrows). Durability class = caller's choice. 3 Class-S sites (execute_remove_member, execute_rotate_content_keys, leave_context) apply inside a SECOND `commit_class_s_keep` (fail-closed). 2 best-effort sites (execute_add_member, execute_reset_member) stay coalesced — correct: add/reset are upward/neutral (not downward-auth), so no wrongful-access-retention, and §9.9.4 epoch-behind recovery heals. `failed_at`/`operation` field-source change (now `pending.first_attempt_at`/`pending.operation`) is behavior-preserving (== old captured `now`/`operation`).

**PRIMARY COMPLETENESS GAP (pre-existing, NOT introduced by PR):** `recovery_advance_epoch` (trust_recovery_helpers.rs:221-243, §9.12 post-compromise recovery step 2, reachable prod via identity/recovery.rs ProductionRecoveryBackend::mls_update) advances the MLS epoch and broadcasts the Commit with a bare `tracing::warn!` on failure — NO pending_commits retry, NO commit_fault gate, NOT EVEN coalesced. This is downward-auth (excludes compromised key material) and strictly higher-stakes than the 3 addressed sites; broadcast-drop = remaining members stuck at epoch N still using compromised keys, node believes recovery succeeded. The PR's own invariant ("every epoch-advancing broadcast is fail-closed") is not fully realized while this site exists. Should route through try_broadcast_commit + fail-closed apply_broadcast_failure. INFO: `handle_issue_mls_update_actor`/`Supervisor::issue_mls_update` returns commit bytes to an out-of-layer caller for distribution (no protocol-level retry either, but by-design caller-distributes).

**Question-4 residual (LOW, irreducible):** removal (step1 persist) and fault (step3 persist) are NOT atomic under async transport. `commit_class_s_keep` = KEEP semantics (persist-fail does NOT roll back in-memory mutation → in-mem gate stays active, correct). On SUCCESS path gate is durable (no false-success — invariant holds). Only residue: broadcast-fail + step3-persist-fail + crash-before-recovery yields on-disk {removed, no-gate}; caller got loud PersistenceFailed (not success), in-mem gate active until crash, healable via §9.9.4. Fully closable via pre-enqueue design (persist removal + pending_commit atomically in step1, best-effort dequeue on broadcast success — MLS commits idempotent so a re-sent already-delivered commit is harmless).

**Testing gap (MEDIUM per project std):** commit adds zero tests; no regression asserting a broadcast-failure at the 3 Class-S sites persists commit_fault fail-closed before the handler returns.

## SECOND-ZERO RE-REVIEW (branch chore/adr049-d7-transport, commits 418b1569a + 521d435d2 + e3b30309f) — AIRTIGHT, APPROVE

PRIMARY GAP above is now **CLOSED**. `recovery_advance_epoch` (trust_recovery_helpers.rs:251-260) routes through `try_broadcast_commit(deps, ctx, epoch_output.commit_bytes, &CommitOperation::RecoveryAdvanceEpoch)` → on `Some(failure)` → `keep_broadcast_failure(cell, deps, ctx, failure).await?`. All FOUR downward-auth/forward-secrecy epoch-advancing in-runtime broadcasts (remove/rotate/leave/recovery) now fail-closed. Set is EXHAUSTIVE for the security-critical class.

- **Helper extraction (418b1569a) semantically identical:** `keep_broadcast_failure` wraps `commit_class_s_keep` + `apply_broadcast_failure(view.commit_broadcast_borrows(), …)`. New `ClassSMut::commit_broadcast_borrows()` (class_s.rs:449) returns the SAME 3 disjoint fields (`&mut state.pending_commits/commit_fault/receive_buffer`) the 3 original inline sites hand-built via `rest_mut()`. Byte-equivalent. 3 sites collapsed to one-liners; no semantic change.
- **Point 1 (ordering/abort) SOUND:** crypto advance_epoch is MLS-provider-durable via its own storage (recovery has NO SCP-companion state to persist atomically, unlike rotate whose advance_epoch rides the primary `_keep` because it also mutates access_key_store). Broadcast-fail → `keep_broadcast_failure` persists commit_fault+pending_commits fail-closed; second-persist-fail → `?` returns PersistenceFailed, recovery NOT acked. Keep-direction: in-memory pending_commits entry RETAINED even on persist-fail (test-pinned) → coalesced tick re-attempts persist → drain re-broadcasts. Not worse than the other 3 sites; irreducible ≤50ms residual is identical class-wide.
- **Point 2 (fieldless variant) SOUND:** retry drain `compute_commit_retry_outcomes` (handlers/governance.rs:930) re-sends `pending.commit_bytes` to `pending.routing_id` VARIANT-AGNOSTIC; `operation` used only for `.label()` observability + `.clone()`. Only exhaustive match on CommitOperation is `label()` (arm added). Unit variant serializes cleanly in persisted PendingCommit. Re-broadcast = same N→N+1 bytes, MLS-idempotent for already-advanced members.
- **Point 3 (no deadlock) CONFIRMED:** recovery dispatched via TrustRecoveryCommand::RecoveryAdvanceEpoch (trust_recovery.rs:89) — does NOT call `check_commit_fault`. Only `execute_governance_action` (gov_helpers:5220) + `leave_context` (lifecycle:244) gate on commit_fault. So a recovery-set commit_fault blocks send/lifecycle/governance (correct — those would use compromised keys) but NOT recovery itself. Fail-close cannot deadlock the recovery it guards. (Doc nit: recovery_advance_epoch doc says gate "trips only on a full retry queue" — also trips on MAX_COMMIT_RETRIES exhaustion in drain; harmless to the conclusion.)
- **Point 4 (counter coalesced) CORRECT, do NOT fail-close:** step-4 `state.epoch.mls_epoch` increment stays coalesced. That counter is a best-effort BOOKKEEPING/REPORTING mirror (read at checkpoint at_epoch, query current_epoch) — NOT the encryption-authoritative epoch (sender-key AAD uses the MLS-provider store epoch, per prior memory). A lost increment drifts ≤1, cannot cause desync (retry entry heals membership) or crypto break. Matches rotate/issue_mls_update coalescing. Fail-closing it = over-engineering, no security benefit.
- **Point 5 completeness:** add (gov_helpers:1268, upward-auth) + reset (2490/2503, same-member refresh, Class-M) coalesced BY DESIGN with honest residual notes — not gaps. `issue_mls_update` (handlers/lifecycle.rs:681) advances epoch locally + returns commit_bytes to caller for out-of-layer distribution — NO in-runtime broadcast, genuinely different architecture, correctly not covered (tracked separately). Zero epoch-advancing in-runtime Commit broadcasts remain on warn-and-drop.
- **Testing gap CLOSED:** e3b30309f adds 8 unit tests exercising try_broadcast_commit/apply_broadcast_failure/keep_broadcast_failure directly with real failing transport + failing/succeeding persistence, incl. `keep_broadcast_failure_surfaces_persist_error_and_retains_entry` (PersistenceFailed + keep-direction) and `recovery_advance_epoch_failure_enqueues_recovery_tagged_entry`. Honest module NOTE: full call sites can't be driven under cfg(test) no-crypto (empty commit bytes short-circuit). cargo check + all 5 targeted tests PASS.

Verdict: airtight. Only residuals are LOW/informational and irreducible/pre-existing (≤50ms crash window shared by all 4 sites; degraded-mode double-advance on storage-broken PersistenceFailed, mitigated by in-memory keep-direction).
