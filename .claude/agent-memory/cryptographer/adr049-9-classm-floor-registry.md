# ADR-049 §9 Class-M floor registry doc edit review

Branch `docs/adr049-classm-floor-registry-reconcile`. Reviewed the §9 crash-safety-class edit that reframes MlsCryptoProvider dissolution: per-context crypto moves onto the actor EXCEPT the epoch/replay floors, which stay in a supervisor-owned lock-free floor registry (reduced successor of the provider `contexts` DashMap).

## Verified facts (code-grounded @ provider.rs / lifecycle_helpers.rs / key_protocol_verify.rs)

- **nonce_dedup Class-C = SOUND (does not block).** `NonceDedup` is NOT in `CryptoStateSnapshot` (provider.rs:112-161) — never persisted, reset to `NonceDedup::new()` on every restore. So Class-C (≤50ms rollback) is strictly STRONGER than status quo (full reset on restore). Honoring a replayed sender-key request is benign: signature covers wrapping_pubkey+nonce (compute_request_hash key_protocol_verify.rs:984), so replay re-seals CURRENT sender key to the ORIGINAL requester's own ephemeral wrapping key (attacker can't open it, provider.rs:1827); membership gate (provider.rs:1800 live MLS members()) + block check (:1820) re-run every request independent of nonce_dedup → rollback CANNOT bypass them; no monotonic state advanced.
  - BUT the diff's JUSTIFICATION is wrong-mechanism: "freshness/timestamp check already bounds the window." Freshness (validate_sender_key_request_freshness :478) bounds ABSOLUTE age to REQUEST_FRESHNESS_SECS=NONCE_EXPIRY_SECS=300s and does NOT reject a replay at all. The 50ms bound is the coalesce window, not freshness. Real reason = not-persisted-anyway + benign-reissue. Correct the wording.

- **Epoch high-water Class-M reasoning = airtight.** restore_crypto_state_with_floor_guard (lifecycle_helpers.rs:1728) exports live floors via export_sender_key_epochs (reads sender_key_store.epochs_for_context ONLY, provider.rs:2645) BEFORE destroy+restore, then validate_and_merge_epoch_floors (provider.rs:2705) max-merges (trusted_local=true=Inv2 warm/own; false=Inv3 untrusted import; empty local_floors=cold no-op :2727). Supervisor-ownership is both necessary (actor-owned destroyed on unwind → nothing to export) and sufficient (Arc survives despawn).

## THE FINDING (MEDIUM, top item)
Diff claims live warm-respawn max-merges BOTH epoch high-water AND `recv_sequence_tracker` ("already implements exactly this"). FALSE for recv_sequence_tracker: it is captured by NOTHING (grep: zero max/merge of recv_sequence_tracker in runtime), destroyed on warm respawn and reloaded VERBATIM from coalesced (≤50ms-stale) snapshot. recv_sequence_tracker is a hard intra-epoch replay gate NOT subsumed by the epoch floor (provider.rs:2099 rejects epoch==last && seq<=last_seq). Spec §23.17.3 line 534 lists the receive-side sequence tracker as a retained_floor source Invariant 2 MUST dominate. So warm respawn CAN lower recv_sequence_tracker → re-admit same-epoch replays at sender-key layer (only MLS-layer replay — the documented PRIMARY defense, provider.rs:152 — catches them → DiD degradation, not clean break). Fix: either correct doc to say only epoch high-water is max-merged (tracker = supervisor-owned snapshot-restored DiD), OR extend export/merge to capture live recv_sequence_tracker too.
