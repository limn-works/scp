# SCP-OUT-036 cross-context streaming bridge — Option 1 SOUND (design validation, branch feat/outlet-xctx-036-bridge @88c98c23b)

Decision: §5.4.5:568 "shared-member bridge re-encrypts each chunk per-recipient as it crosses" + §6.2.5:300 "shared-member local SDK seam, never a new relay primitive". Option 1 = runtime bridge is PLAINTEXT in-process forwarder (validate+reassemble+dual-log, no re-sign); per-recipient re-encryption = wrap each chunk as a normal A-context MLS message via EXISTING provider.seal (sender-key AES-256-GCM + MLS group). VERDICT: SOUND.

**Confidentiality (Q1a):** seal = sender-key AES-256-GCM(shared-member's A sender key) then MLS group encrypt under A's group key. Only A MLS members holding current-epoch group secrets + shared-member sender key decrypt; relay sees ciphertext+routing_id only. Identical to every A-context message. Nonce = fresh OsRng 96-bit per seal (encrypt.rs:58), distinct A send_sequence per chunk → no nonce reuse (birthday 2^48 >> any stream). SOUND.

**Equivocation resistance + preserve-not-resign (Q1b/Q3):** operator chunk sig (compute_chunk_sig_preimage, protocol stream.rs:486) commits SHA256("SCP-OUTLET-CHUNK-SIG-V1:"‖len(B.context_id)‖B.context_id‖len(outlet_id)‖outlet_id‖request_id(16)‖seq_be(8)‖caveats_binding(32)‖SHA256(jcs(payload))). Sig is over **B's context_id** → A verifies against B's context_id (from governed interface descriptor), NOT A's. Operator bound to ONE payload per (B,outlet,req,seq); two valid sigs over same tuple w/ different payload_hash = non-repudiable equivocation evidence (manifest leaf covers sig, root is committed artifact). Preserving (NOT re-signing) is REQUIRED — re-signing would make A verify the BRIDGE's sig, destroying operator-accountability/equivocation binding to B.

**Malicious shared-member bridge powers = availability only, never forge-as-success:** cannot forge B's operator sig (no operator key) → any chunk A accepts carries valid B sig. Can drop (gap→A cancels §5.4.5), reorder/dup (chunk-seq dup/gap detection), refuse (DoS — bridge trusted for liveness by §6.2.0 construction). Cross-stream replay closed by request_id (16 random bytes) in sig preimage: old chunk's sig commits old request_id → fails vs new session's request_id. Wire replay into A closed by A recv_sequence_tracker.

**SOUNDNESS CONDITION (normative, must be pinned):** A MUST verify operator sig against operator_pk + B.context_id + caveats_binding bound in the GOVERNED outlet-interface descriptor / stream-open session, NEVER against values the bridge supplies at delivery time. This is the streaming analog of §6.2.4:276 "caller_did channel-authenticated not envelope-asserted". Otherwise a malicious bridge substitutes an operator/context it controls. Recommend adding as explicit normative clause for the streaming bridge.

**Q2 same guarantee as dedicated chunk-level xctx MLS envelope?** YES for confidentiality (same A group keys — no other key material can address A members). Sequence/AAD: A-envelope AAD binds A.context_id/shared-member DID/A epoch/A send_seq (transport ordering); chunk request_id+sequence bound by operator sig (stream ordering) — two disjoint sequence spaces, each covered. Chunk-boundary: 1 chunk = 1 sealed MLS message, AEAD-framed, no concat ambiguity. Metadata (count/timing/size): per-chunk MLS delivery leaks chunk count + inter-chunk cadence to relay/A-observers (sizes normalized by bucket padding) — REAL side channel but INTRINSIC to per-chunk MLS streaming to REMOTE A members (new vs same-context in-process poll_next path), and IDENTICAL under Option 2, so NOT a differentiator; fix would be cover-traffic/batching (orthogonal, applies to both).

**Q4 Option 2 buys nothing — REDUNDANT (reject):** confidentiality=same AEAD+group keys; integrity/equivocation=operator sig (both carry); ordering=chunk seq + A send_seq; replay=recv_sequence_tracker + request_id binding; metadata=identical wire. A dedicated envelope MAC/seq-in-AAD re-checks in weaker envelope form what operator sig already binds soundly → negative value per CLAUDE.md over-engineering guard. POSITIVE of Option 1: InnerEnvelope is itself Ed25519-signed by shared-member DID → clean double-attestation (bridge accountable for forwarding act + operator accountable for content, both non-repudiable for dual-log).
