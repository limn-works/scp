## Verdict details
- Topology (#1): inductive invariant holds — after every member processes an add-Commit (or is adder/joiner), each member's directory = full-membership wk set. Adder learns joiner from KeyPackage; joiner learns existing from AddMemberOutput.wrapping_keys + self locally; BYSTANDERS learn joiner from broadcast Commit's added_wrapping_keys. Mesh completeness is COEXTENSIVE with existing MemberJoined-leaf convergence — no NEW hole. MLS linearizes commits (one per epoch) so no true concurrency; adder-at-epoch-N has processed all prior adds.
- #5c adder-supplied directory worst case = SELF-DoS / member-denied-my-messages (joiner seals its key to wrong/attacker wk → that member can't read joiner; or adder substitutes own wk → adder gets joiner's key = NO new capability since adder is a member + can't impersonate). NOT interception/impersonation. Consistent with established joiner-trusts-adder model (adder already controls welcome/event_log/members replay). Bounded + detectable. ACCEPTABLE.

## REQUIRED invariants the coder MUST honor (else real bugs)
1. members↔directory parallelism: EVERY add_member_record site must insert the wk in lockstep — add_member (adder), join_context_encrypted (joiner: all existing + self), receive_message Commit path (bystander: added_dids ← added_wrapping_keys, 1:1 aligned). STRONG FIX: fold wk INTO the membership structure (HashMap<did,wk>) so skew is impossible by construction rather than two parallel collections.
2. BYSTANDER re-distribution trigger (make-or-break for push completeness #6): receive_message's Commit-add loop (client.rs:706-736, iterates added_dids) MUST also seal the receiver's OWN sender key to each newly-added member. If distribution only fires on adder's add_member + joiner's join, push is INCOMPLETE (e.g., Alice never sends her key to Carol when Bob adds Carol) → pull (SenderKeyRequest, deferred to #1980) would be REQUIRED. With the bystander trigger, push-only is complete for the SYNCHRONOUS dumb-pipe MVP. Async/offline residual (missed push, no re-drive) is a real gap gated on #1980 — document it, don't claim complete.
3. Reject SCP add whose KeyPackage leaf lacks the wrapping ext (extract_wrapping_key returns Option → None must fail-closed for an SCP add), else silent hole (member no one can seal to).
4. Convergence-independence (#3): wk MUST NOT enter the MemberJoined leaf payload (kept Vec::new() at client.rs:412/726). Directory is private crypto state, never a Merkle leaf → event_log_root unperturbed. Coder must NOT try to transport wk via the leaf.
5. Persist member_wrapping_keys in the participant snapshot (snapshot.rs) + restore, else reopened tab can't seal on next add/rotate.

## Recommended hardening (non-blocking)
- Self-certifying directory: parse existing members' wk from the serialized RatchetTree the joiner gets in Welcome (TLS-serialize export_ratchet_tree → parse leaves), removing adder-trust entirely. Blocked by awkward openmls API today; log as future hardening.
- Push wire type: use the PUSH-appropriate SenderKeyDistributionMessage variant, not force-fit SenderKeyResponse's request_nonce (pull) protocol.
