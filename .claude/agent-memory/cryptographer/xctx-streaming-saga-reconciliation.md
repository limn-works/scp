Proposal `~/.claude/plans/xctx-outlet-saga-streaming-reconciliation.md`: keep §6.2.4 saga envelope, make Commit-B drive §6.2.0.5 chunk-bridge, swap receipt field #6 `output_hash`→`stream_manifest_hash` (both Fixed32 in SCP-XCTX-RECEIPT-V1 preimage).

**Why:** two branches built xctx invocation two ways; post tool→outlet rename same op. Reconciliation before re-port.

**How to apply:** verdicts per point —
- P1 (receipt swap) CONDITIONALLY SOUND. Manifest leaf = SHA-256(SCP-OUTLET-CHUNK-V1:||0x00||jcs(chunk)) covers chunk.sig — no circularity (target signs a hash-of-hashes, distinct domain SCP-XCTX-RECEIPT-V1: vs SCP-OUTLET-CHUNK-SIG-V1:). BUT manifest root does NOT bind caller_did/target_context_id/tool_registration_id/nonce — those stay separate preimage fields, so receipt binding preserved ONLY because they remain explicit fields. Gap: nothing in the manifest binds the stream to THIS saga's target_context_id/caveats_binding at the manifest level; a manifest computed over a different stream with matching outer fields would still verify. Recommend binding request_id/caveats_binding into a manifest-level domain OR asserting the chunk seq's per-chunk preimage context_id==target at verify.
- P2 (replay determinism) **BREAK**. §6.2.4 recovery (supervisor.rs redrive_xctx_commit_in_progress ~6764): on crash mid-Commit-B with NO durable capture → target replies ReadyToExecute → recovery does NOT re-invoke, returns NeedsRepair, "initiator retries fresh." Buffered: fresh re-run of DETERMINISTIC executor → same output_hash → same receipt. Streaming executor is NON-DETERMINISTIC (LLM). commit_b_first_execute (supervisor.rs:7557) runs executor supervisor-side, stashes output in ctx.executor_output (IN-MEMORY, dies on crash). Durable capture only at commit_b_settle→commit_b_first_settle (saga.rs:1601): capture+persist Class-S BEFORE ToolInvoked append. Streaming WIDENS the execute→accumulate-all-chunks→persist window vs buffered execute→serde→persist. Crash after streaming N chunks to caller but before durable capture ⇒ retry-fresh re-invokes ⇒ different chunk stream ⇒ different manifest ⇒ divergent receipt AND caller already saw first stream's chunks. Exactly-once broken for the non-deterministic streaming case unless proposal ALSO makes chunks durable incrementally before forwarding (it doesn't spec this; §3 step-3 says "durably capture the chunk sequence" post-hoc). MUST FIX: durable-append-before-forward, or hold-all-chunks-until-terminal-then-atomic-capture-then-release (but that re-buffers, violating SCP-OUT-036 AC[2]).
- P3 (source vs target sig) **BREAK/AMBIGUITY**. Bridge run_cross_context_bridge (outlets.rs:6134) re-signs EVERY chunk under inputs.source_operator_key with fresh seq, accumulates `forwarded` (SOURCE-reissued chunks), build_completion (outlets.rs:6067) computes manifest over `forwarded` = SOURCE sig sequence. Receipt is signed by TARGET (§6.2.4 build_signed_receipt). So receipt(target-signed) commits a manifest-over-SOURCE-operator-signed-chunks. For non-repudiation the target attests to a stream whose per-chunk sigs are the SOURCE operator's re-issue, NOT the target executor's original sigs. The target executor's original chunk sigs are DISCARDED at the bridge. Mismatch: "who signed the receipt" (target) ≠ "whose per-chunk sigs the manifest covers" (source operator). Target vouches for source's re-signature of the target's own output — weird attestation semantics. Also which context_id is in the manifest leaves' per-chunk preimage = source_context_id (re-sign uses inputs.source_context_id), so the receipt's target_context_id field and the manifest's embedded context are DIFFERENT contexts. Needs explicit decision: manifest over target-original or source-reissued; document the attestation meaning.
- P4 (T2 credit / T4 MLS) — T4 MLS re-encryption is CRYPTO-LOAD-BEARING not separable: bridge production seam (outlets.rs:6242) parks target_context_id/stream_epoch/chain_depth; in-process bridge does NOT MLS-encrypt the hop, so shipping streaming saga w/o T4 = plaintext chunk exposure across the context boundary = violates encryption-as-access-control tenet for a CROSS-context wire. Must NOT ship without T4 or explicit same-process-only fence. T2 credit-relay: signed OutletStreamCredit not relayed across bridge (only mpsc backpressure DEFAULT_CREDIT_WINDOW=32). Gap = unbounded-executor-spend beyond signed authorization is BOUNDED by max_billable (caveats.max_calls) at billing, so not unbounded — but the SIGNED end-to-end credit guarantee §6.2.0.5 claims is absent. T2 = real hardening, degradable (billing cap holds); T4 = security hole, blocking for cross-process.
- P5 (V1 redefine vs V2) SOUND to redefine given pre-release (main memory feedback_no_migration_prerelease: no users/data). BUT the shipped invoke_cross_context_saga SDK×4 already emits V1 receipts w/ output_hash semantics; redefining field #6 meaning w/ SAME domain sep SCP-XCTX-RECEIPT-V1: means an old-semantics V1 receipt and new-semantics V1 receipt are indistinguishable by domain tag → if ANY V1 receipt persisted anywhere (test vectors, journals) a verifier can't tell which field #6 means. Pre-release ⇒ purge all. If any durable V1 receipt survives the re-port, MUST bump V2. Recommend V2 for zero ambiguity since it's free pre-release.
