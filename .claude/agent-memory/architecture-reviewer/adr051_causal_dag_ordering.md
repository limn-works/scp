ADR-051 (`.docs/adrs/ADR-051-causal-dag-application-event-ordering.md`) — causal-DAG ordering for per-author application events (`MessageSent`, `ToolInvoked`), establishing convergent canonical Merkle order without a trusted sequencer (Matrix/Git-style: events carry observed-DAG-head hashes; deterministic topo-sort + leaf-hash tie-break linearizes identically for all members).

**Why:** §9.9.3 equivocation detection requires the canonical Merkle log to hold ONLY convergent events (equal-count → equal-root). Per-author `MessageSent`/`ToolInvoked` have no global order → diverge at equal count → must be excluded from the log in the interim. Three subsystems specced as Merkle-verifiable derive from them: velocity consequences (§7.3.7), economic `SenderVelocity`/`ContextMessageRate` (§19.7), `tool_invocation_count` participation fact (§7.3.2). ADR-051 makes the shared *input* convergent (governing theorem: derived fact is automatic+convergent iff its trigger input is convergent).

**Staging:** unification (ADR-011 amendment in `phase-2.md`) lands first (convergent-only log, these two events excluded as local `ContextEvent`s, velocity computed locally); ADR-051 lands second (re-enter as convergent leaves). Interim qualifications recorded at every source: ADR-011 amendment, §7.3.2:147, §7.3.7:727, §19.7:480, §25:363 (75-variant after PseudonymAnnounced removal).

**How to apply (subsystem-completeness checklist for per-author-derived facts):** the ONLY metrics/facts that derive from `MessageSent`/`ToolInvoked` counts are: `ContextMessageRate`, `SenderVelocity` (§19.7 PricingMetric enum), velocity/rate consequence triggers (§7.3.7), `tool_invocation_count` (§7.3.2 step-2 algorithm). Other PricingMetrics (`MemberCount`, `RelayQueueDepth`, `TimeOfDay`, `StorageUsage`) and other participation facts (`participation_duration_secs` from `MemberJoined`, governance/role/attestation/context-creation counts) are convergent or point-in-time — NOT affected. All affected ones ARE qualified in this change. Note: broadcast reuses `MessageSent` (05-contexts.md:1559) and `SenderVelocity` applies per-author in broadcast (§5.14.9.1) — same event, same interim treatment, no separate gap.

**Verdict given (pass 1):** APPROVE. Model is the right permanent choice (sequencer-free convergence; relay-assigned/per-sender/BFT-consensus rejections all sound). Staging is a documented waypoint, not a DOA deferral. ADR altitude is correct (decision+model+consequences, forward-pointing impl).

**Verdict refined (pass 2, fresh read):** CHANGES-NEEDED for ONE completeness gap pass 1 missed — the **ordering** subsystem (pass 1's checklist only covered count-derived *facts*, not ordering). §9.8.3 "Message Ordering" (`.docs/specs/09-security-model.md:724-730`) still asserts application messages have an authoritative canonical order = single-parent Merkle "hash chain" in append order, and "two events referencing the same parent ⇒ forked ⇒ equivocation (§9.9)." This is the OPPOSITE of the DAG end-state (concurrent branches off a shared frontier are NORMAL, deterministically linearized — not equivocation) AND contradicts the interim (app msgs are local `ContextEvent`s, not canonical leaves at all). ADR-051 never cites §9.8.3/§9.8.5; neither was amended. The display/real-time-reorder HALF of §9.8.3 — `(epoch, generation, timestamp)` SDK reconstruction, referenced by §23:157, §16:839/842 — is FINE (ADR-051 preserves delivery reorder explicitly). The genuine gap is only the "Authoritative ordering" / hash-chain / same-parent=fork paragraph (lines 726-730). It needs an ADR-051 qualifying note exactly like §7.3.1/§9.9.3/§19.7 got. Model itself is still sound — this is a spec-coherence fix, not a model defect. Secondary nit: §7.3.2 algorithm step-2 lists `tool_invocation_count` extraction inline with convergent facts without the interim-local caveat (prose above it IS qualified).
