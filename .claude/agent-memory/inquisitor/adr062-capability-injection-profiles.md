Draft ADR-062 "Capability Injection and Application Profiles" (scratchpad, dated 2026-07-12) interrogated against origin/main. Generalizes spec §17.6 storage-selection rule (mandatory/fail-closed/never-default) to every provider capability with a runtime selector (DHT, blob, credentials, custody, attestation, relay). Motivating defects verified real: #627/#1518/#1880 — production-dht enabled on uniffi Cargo.toml:50-51 but NOT scp-ffi/Cargo.toml (:44) or napi (:45), so shipped Python/TS resolve DIDs in-process only.

**Verified facts (origin/main):** BlobStorageBackend enum InMemory-uncfg'd + `impl Default → in_memory()` (storage.rs:561); InMemoryCredentialStore `impl Default` (credentials.rs:559); DhtClient is RPITIT (`impl Future + Send`, dht_client/mod.rs) so dyn is genuinely impossible — enum dispatch is forced, ADR right; `scp_node::DhtMode {Memory,Production}` already in construction.md M1/M2 and used at server.rs:314/426/465 for NODE reach; scp-platform/testing is an UNCONDITIONAL dep edge on scp-ffi (Cargo.toml:51) AND napi (:55) — nullifier types compiled into release, only SELECTION cfg-gated by allow_in_memory_custody.

**THE finding the ADR obscures:** uniffi ALREADY implements DHT selection — but as a cfg TYPE-ALIAS, not the ADR's runtime enum: `#[cfg(not(any(test, allow_in_memory_custody)))] type FfiDhtClient = PkarrDhtClient; #[cfg(any(...))] = InMemoryDhtClient` (uniffi/src/bridge.rs:44-56). So in release uniffi, in-memory DHT is UNREACHABLE and gated behind the SAME flag as custody nullifiers. This CONTRADICTS ADR Axis-B, which classifies in-memory DHT as "legitimate-dev, runtime-selectable, never the only reachable arm." The ADR's open-question-3 frames this as an abstract choice; it is actually a reversal of shipped code the ADR never names. napi is worse: `make_dht_with_signer → DidDht<InMemoryDhtClient>` type-baked into signatures (napi/src/identity.rs:223,246) — not a one-line flip. Three bridges, three DHT strategies = the real architectural gap.

**Ranked premises that don't hold:**
1. "Generalizes an existing pattern" — for DHT it REVERSES uniffi's shipped classification (in-memory DHT = allow_in_memory_custody-gated, absent from release). Unreconciled with code.
2. allow_in_memory_custody already conflates the two axes (gates plaintext custody nullifier AND uniffi's in-memory DHT legitimate-dev). ADR condemns `testing` for exactly this conflation, then builds G1 on allow_in_memory_custody without questioning it. Status-quo cargo-culted.
3. Central §4 rule "inject a capability WITH a selector, feature-gate one WITHOUT" has NO mechanical enforcement — G1 checks nullifier-absence + allowlist membership; §5 semantic matrix checks arm-parity across bindings; NEITHER checks runtime-vs-compile-time selection. "Profiles ≠ features" is review-only prose → rot risk. A "profile" is concretely just a per-use-case flat config struct (HostSiteConfig exists) + a G1 allowlist entry; no Profile type/trait — the "two-layer architectural primitive" framing is overstated.
4. Reusing scp_node::DhtMode at the SDK-CLIENT identity surface: same type, OPPOSITE default semantics (node=address-disclosure→default Memory; client=DID-doc revocation-reachability→required no-default per §6). "Single vocabulary" across two opposite security surfaces is a tension, not a clean win. Minor phantom: ADR sample `DhtMode{Memory, Production{gateways:Vec}}` vs server.rs bare `DhtMode::Production`.

**Conceded SOUND:** dyn-impossible→enum-dispatch (verified RPITIT); G1 NOT redundant with type system (type layer guarantees no silent config selection; G1 catches nullifier PRESENCE in resolved binary feature-graph — the scp-platform/testing unconditional edge is the exact real scenario type system can't see) — BUT G1 cannot pass today (scp-platform/testing unconditional) so its feasibility is fully contingent on Slice-4 decomposing the testing feature; ADR understates this. InMemoryPreRotationCustody nullifier defensible (stores raw `Zeroizing<[u8;32]>` private keys in heap HashMap, pre_rotation_custody.rs:30-43) but ADR never states WHICH property it nullifies — pre-rotation is the taxonomy's softest joint (state-loss AND plaintext-key axes).

**Verdict: SOUND CORE, INTERROGATE FURTHER on 4 premises.** An ADR is warranted (storage precedent makes cfg-alias-DHT the incoherent outlier; heterogeneity across 3 bridges is architectural). But it must (a) name the uniffi/napi reversal explicitly in Slice 1, (b) stop treating allow_in_memory_custody as a clean nullifier gate, (c) give the inject-vs-feature rule mechanical teeth or admit it's review-only, (d) justify one DhtMode type across two opposite-direction surfaces.
