**(b) did:key gate = SYMPTOM-PATCH, not root fix.** `extract_public_key_from_did` (scp-did) is a PRODUCTION function on 5 signature/issuer-verification paths that carries a `did:key:{hex}` branch gated by `#[cfg(any(test, feature="testing"))]`. scp-did/testing is transitively unified by CUSTODY opt-ins: `allow_in_memory_custody → dep:scp-testing → scp-core/testing → scp-protocol/testing → scp-did/testing` (also scp-event-log/testing → scp-did/testing). Cargo feature unification turns did:key ON for the whole build. The commit re-gates ONLY resolvers.rs (BridgeDidResolver, UCAN issuer) with a local `#[cfg(not(any(test, feature="testing")))]` fail-closed prefix check against scp-ffi-common's OWN testing (which is NOT in the custody chain — verified: allow_in_memory_custody doesn't touch scp-ffi-common/testing, so the re-gate is effective there). BUT the same custody-flag build leaves did:key:{hex} LIVE at: scp-event-log tree.rs verify_event_signature (event actor sigs), scp-protocol bridge/claiming.rs verify_claim_signature + verify_attestation_signature, scp-protocol trust/attestation.rs IdentityDidPublicKeyResolver — all pass raw DID into the parser with NO method guard. (app_sandbox.rs is SAFE — routes did:key to its own base58/multicodec decoder, only sends did:dht: into scp-did.) The did:key-via-testing design PRE-DATES the branch (present in scp-primitives/identity.rs at 86519aa6f); the branch newly exposed resolvers.rs via delegation and restored it, but the sibling exposures are pre-existing and untouched. Maintainer's own invariant "did:key must never ride in on a custody flag" is categorical → violated at 3 sites after the fix. Also a DOA smell: ADR says T1c consolidation must "carry a matching, custody-independent gate," i.e. the local re-gate is a known-temporary stepping stone. ROOT FIX (flows from scp-did): remove did:key:{hex} from the production symbol (relocate the test convenience to a genuinely test-only helper, or a feature NOT pulled by the custody chain) — closes all 5 consumers uniformly, removes the need for any per-consumer re-gate. Test-ergonomics cost (fixtures must build did:dht z-base-32 directly) is the tradeoff.

**(c) Python UCAN error-string scanner = REFRAME-WORTHY (biggest finding).** trust.py `evaluate_trust` calls `ucan_validate` (the state-RECORDING gate) and reverse-engineers WHICH of 6 CapabilityValidation booleans failed from the prose error string via `_classify_ucan_error` + 6 prefix arrays + `_PASSED_BEFORE`. test_ucan_conformance.py scans Rust source (now incl. scp-did/lib.rs, added by this commit) for the error-string literals to keep the Python prefix list in sync. This IS the "structured info crosses FFI as prose strings, SDK reverse-engineers it" anti-pattern the project wants eliminated (PR #1867 first-principles audit root cause). The structured typed path ALREADY EXISTS and is exported: `PyScp::ucan_evaluate` (scp-ffi/src/ucan.rs:364) → `PyCapabilityValidation` (6 typed booleans, exact fields evaluate_trust reconstructs), documented as the "side-effect-free diagnostic counterpart" designed for exactly this. evaluate_trust should call `instance.ucan_evaluate(...)` and read `.tokens_valid/.signatures_valid/...` directly — deleting `_classify_ucan_error`, the 6 prefix arrays, `_PASSED_BEFORE`, AND the entire test_ucan_conformance.py scanner. Bonus: using ucan_validate for a diagnostic is a latent bug (records/consumes the nonce; ucan_evaluate is the read-only one). Per CLAUDE.md over-engineering guard (b): a gate re-checking in weaker source-text form a property another mechanism enforces soundly = negative value. Scanner + classifier PRE-DATE the branch (#556/#985 classifier; #989/#998 scanner), so keep-in-sync here is defensible interim maintenance — but this commit EXTENDS the doomed mechanism (new source file scanned, new brace-matching format!-extractor, new pinning test), which is sunk-cost investment. File the reframe; schedule classifier+scanner deletion in favor of ucan_evaluate.
