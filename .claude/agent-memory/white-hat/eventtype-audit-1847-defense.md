# EventType audit-leaf changes (issue #1847, branch fix/eventtype-audit-1847) — white-hat review 2026-07-16 (/tmp/scp-1847)

Scope: scp-event-log lib.rs (77-variant closed EventType) + payload.rs (positional-msgpack per-variant structs) + 3 runtime emit paths.

**KEY ARCH FACT: audit-leaf failure semantics are INCONSISTENT (the central finding).** In every path the ENFORCEMENT action is fail-closed and durable BEFORE the audit leaf; only the durable Merkle-leaf append's failure mode varies:
- `block_broadcast_subscriber` (broadcast_helpers.rs:619): block enforcement (epoch advance + block-list) fail-closed via `commit_class_s_keep` (KEEP combinator, persist-fail RETAINS block + returns Err). MemberBlocked leaf FAIL-CLOSED (`.await?` L664-674). KeyEpochAdvance leaf BEST-EFFORT (match+`tracing::warn`, no propagate L681-711).
- `revoke_ucans` (recovery.rs:965, ProductionRecoveryBackend): TokenRevoked leaf BEST-EFFORT (L1004-1019 warn, no propagate). **The prompt's premise that TokenRevoked is "fail-closed" is WRONG — it is best-effort.** Revocation distribution (RevocationList + notification dispatch) IS fail-closed (Err step=3).
- `execute_reconfigure_governance` (governance_helpers.rs:2983): GovernanceReconfigured leaf FAIL-CLOSED (`.await?` L3059 after Class-S restore commit). GovernanceDeadlockRecovery companion leaf BEST-EFFORT (`append_deadlock_recovery_event_best_effort` L2930).

So: MemberBlocked + GovernanceReconfigured = fail-closed; KeyEpochAdvance + TokenRevoked + GovernanceDeadlockRecovery = best-effort. No documented rationale for the split.

**Threat characterization:** best-effort audit leaves do NOT let an attacker evade ENFORCEMENT (block/revoke/reconfig already durable). They let a party who can induce storage failures suppress the durable non-repudiable AUDIT record while enforcement still happens = loss of provenance/legibility, not loss of security control. Lower severity but real (violates "provenance everywhere" tenet).

**Second-order durability nuance:** even "fail-closed" appends only guarantee the leaf enters the IN-MEMORY Merkle tree; MerkleEventLogProvider.append_event (providers/event_log.rs:686) does `persist_entry_best_effort` — durable write is itself best-effort. Crash between in-memory append and persist can drop even a fail-closed leaf; recovered only via Merkle-root-rebuild-from-persisted on restart. `no event log for context` = the only hard `?` failure.

**TEST COVERAGE:**
- Governance path (GovernanceReconfigured + GovernanceDeadlockRecovery): WELL COVERED — `crates/scp-runtime/tests/governance_integration.rs:~3000` drives real Supervisor `propose_governance_action`→ReconfigureGovernance, reads `manager.event_log_entries()` (real MerkleEventLogProvider), asserts both leaves present + payload fields decode + ordering (recovery.seq > reconfigured.seq). THIS IS THE MODEL.
- payload.rs: WELL COVERED unit round-trips (positional fixarray marker check, projection target/subject_did, malformed→None-no-panic).
- Block path (MemberBlocked + KeyEpochAdvance leaves): **GAP.** supervisor.rs tests (broadcast_block_persist_is_fail_closed…, broadcast_per_author_block_survives_crash…) assert block STATE durability only, NEVER read event_log_entries for the leaves. Protocol-layer `block_subscriber_rotates_key` (scp-testing broadcast.rs) tests epoch/block-list on pure BroadcastContext, no event log.
- Recovery path (TokenRevoked leaf): **GAP.** `production_backend_revoke_ucans_succeeds` (recovery.rs:2189) uses NO-OP `TestEventLog` (append_event→Ok, entries→None) + asserts only `result.is_ok()`. Best-effort append means even a FAILING log passes. Zero assertion the leaf fires.

**Q3 no-op provider:** Confirmed — recovery.rs/governance_helpers.rs `TestEventLog` + governance_integration.rs `MockEventLog` are no-op Ok. Appends "work silently"; correctness intact because best-effort or fail-closed-`?`-satisfied-by-Ok. This is exactly why block/recovery tests can't catch append removal — a no-op provider can't distinguish fired-vs-skipped. governance_integration.rs's real-provider approach is the correct defense.

**Q4 verifier detecting missing pair:** To flag MemberBlocked w/o KeyEpochAdvance, verifier must positionally/temporally pair (same actor_did, adjacent seq, new_epoch=old+1). **Weakness: KeyEpochAdvancedPayload carries ONLY old_epoch/new_epoch — no author_did, no blocked_did, no back-ref to the MemberBlocked leaf seq.** No cryptographic binding between the paired leaves. Since KeyEpochAdvance is best-effort, a missing one is ambiguous (benign append-fail vs tampering). Verifier can only heuristically pair.

**HARDENING (recommended):**
- P1 Make audit-leaf failure semantics consistent & deliberate; where a verifiable pairing invariant exists (MemberBlocked↔KeyEpochAdvance), either both fail-closed or treat as one atomic record. KeyEpochAdvance best-effort undercuts its own "always co-located in the Merkle log" comment (broadcast_helpers.rs:677).
- P1 Add emission tests w/ real/capturing provider for block path (MemberBlocked+KeyEpochAdvance) + recovery path (TokenRevoked), modeled on governance_integration.rs: assert presence + payload + adjacency.
- P2 Enrich KeyEpochAdvancedPayload with author_did (+ blocked_did / MemberBlocked seq ref) so verifier binds the pair unambiguously.
- P2 Emit a metric (mirror `crate::metrics::record_persistence_failure()`) on every best-effort audit-append failure so silent gaps are observable/alertable, not only WARN.
