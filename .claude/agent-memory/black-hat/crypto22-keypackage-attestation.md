# CRYPTO-22 KeyPackage attestation (spec-only, commit 20f7a036b, §9.7.1/§9.5.2/§25.22)

Binds ephemeral MLS leaf `signature_key` to DID via `#active`/`#agent`-signed attestation (0xFF03 LeafNode ext). Context-agnostic. Verified at Add/join + every Commit/Proposal. Fail-closed for did:dht:z*.

## Findings (could NOT forge/replay without leaf private key — that claim HOLDS)
- **HIGH BLACK-C22-1 (non-revocable context-agnostic attestation defeats PCS for new-group joins).** No attestation revocation mechanism exists (UCAN/sender-key have lists; attestation has none). §9.7.3 claims MLS-state compromise window "bounded by PCS Update interval" — FALSE for new-group vector. Attacker with compromised leaf sig private key (MLS-state compromise, exactly what PCS bounds) can mint a BRAND-NEW KeyPackage reusing the same (still-valid) attestation + compromised sig key, pair it with their OWN fresh X25519 init key (attestation binds only sig key, not init key), self-sign it, publish it → get victim added to NEW groups as victim's DID. Reads all group content (Welcome→own init key) + signs Commits/Proposals attributed to victim. PCS Update in group G does NOT heal group G'. Only expiry (leaf Lifetime.not_after) or #active rotation kills it — but §9.12 recovery prescribes #active rotation only for #active/#0 compromise, NOT leaf-key. Freshness check (line 624) has NO lower bound on issued_at age → old-but-unexpired attestation fully accepted.
- **HIGH/MED BLACK-C22-2 (unbounded attestation window).** attestation window == leaf Lifetime.not_after; NO bound on leaf Lifetime anywhere in specs (only illustrative 24h in vector 37). Directly sets the BLACK-C22-1 replay window.
- **MED BLACK-C22-3 (fail-closed MUST scoped to did:dht:z* only).** §9.6.2 makes did:web a supported production fallback. Line 626 MUST-reject scoped literally to "(did:dht:z*)"; testing carve-out is did:test/did:key only. did:web attestation handling is UNSPECIFIED → if impl keys enforcement on did:dht:z prefix, did:web leaves bypass attestation entirely (forge any did:web-claiming leaf). Should be positive: reject all non-carve-out DIDs.
- **MED BLACK-C22-4 (governance/handshake actions rest on software-only ephemeral leaf key).** Commits/Proposals only leaf-signed (leaf key in MLS state / platform storage, software), attributed via attestation. Application messages #active-signed (poss. HSM). Membership changes have WEAKER non-repudiation than chat. Plausible-deniability of governance actions via "leaf compromise."
- **LOW BLACK-C22-5 (resolution-failure handling).** Spec says reject if attestation "does not verify"; transient DHT resolution failure ≠ "does not verify" → accept-if-uncertain OR liveness DoS. Specify resolution timeout = reject.

## What resisted (honest)
- Cross-protocol sig reuse (item 5): SOUND. Distinct domain sep "SCP-KEYPACKAGE-ATTESTATION-V1:" + SHA-256 collision-resistance + all-fixed/length-prefixed fields. Can't reinterpret as UCAN/vote/inner-envelope/block/trust-Attestation.
- Transplant w/o leaf private key (item 2): claim HOLDS. Leaf self-sig must be under attestation-pinned sig key; no private key → invalid leaf → MLS rejects pre-attestation-check.
- #active/#agent confusion: check 4 (attestation.signing_key_id == credential.signing_key_id) + resolve-against-victim-DID-doc blocks it.
- Ephemeral-leaf design ITSELF is an improvement: isolates #active from per-group MLS state (old leaf==#active meant MLS-state compromise = #active compromise).

## Recommended fixes
- Bind leaf INIT/encryption key into attestation (one field) → neutralizes the read/confidentiality half of C22-1 (attacker can't re-pair compromised sig key w/ own init key).
- Add attestation revocation (per-context RevocationList analog keyed on leaf_signature_key) OR cap leaf Lifetime tightly (≤ PCS interval) AND add leaf-key/MLS-state-compromise recovery step prescribing #active rotation.
- Restate fail-closed scope positively (all DIDs except testing carve-out).

## SECOND PASS @49ace8b5 (hardened) — C22-1 read-half STILL OPEN (HIGH, BLACK-C22-6)
Fixes applied: bound leaf ENCRYPTION key (6th field), capped window to 84d, positive whitelist (did:web in scope), resolution-fail=reject, rotation-revocation, resolve #active/#agent CURRENT only. Whitelist/cap/rotation-bite/governance-containment all SOUND.
- **BLACK-C22-6 (HIGH): the fix bound the WRONG HPKE key.** Spec §9.5.2 conflates "init/encryption key" as ONE key (fields 451/456, verifier check 4 line 624, leaf-key lifecycle line 681). In RFC 9420 they are TWO distinct HPKE keys: `KeyPackage.init_key` (Welcome/GroupSecrets sealed to THIS) vs `LeafNode.encryption_key` (ratchet-tree path only). Code confirms: openmls `hpke_init_key()` ≠ `encryption_key`, RFC §10.1 REQUIRES init_key≠encryption_key. Attestation binds encryption_key; init_key UNBOUND + UNCHECKED. Attacker with ONLY stolen leaf SIGNING key crafts KeyPackage: victim's sig_key(pub+priv) + victim's enc_key(pub only, copied) + victim's genuine attestation(copied) + ATTACKER's own init_key → all 9 verifier checks pass (attestation covers sig+enc, both victim's) → Added to new group → Welcome sealed to attacker init_key → attacker HPKE-opens EncryptedGroupSecrets w/ own init priv → joiner_secret → derives epoch key schedule → READS as victim. enc_key priv NEVER needed for joiner_secret (only for future UpdatePath). Standard openmls StagedWelcome; bespoke attacker can manual-HPKE-open regardless. My OWN prior C22-1 said read vector = "Welcome→own init key" — fix bound encryption_key not init_key, missed it.
- FIX: attestation must bind KeyPackage `init_key` too (add field) + Add-time verifier check `attestation.init_key == KeyPackage.init_key`. init_key only present at Add-time (not in ratchet tree) — that IS where the read-join attack lands, so bind+check there.

## THIRD PASS @c7773cad (8-field fix) — read-as-victim CLOSED at spec level; ONE latent-HIGH impl trap
Fix binds all 8 fields (did, leaf_sig, leaf_enc, init_key, wrapping, signing_key_id, issued/expires). Check 6 (init_key==KeyPackage.init_key) at Add ONLY; checks 3/4/5/7-11 every leaf read. Resolution-fail=reject, no stale fallback. NOTE: attestation is SPEC-ONLY (no Rust impl yet — provider.rs +2826 is ephemeral-leaf refactor, not verifier). SCPR-frame stuff reverted (unrelated).
- **read-as-victim (signing-key-only) genuinely CLOSED** IF check 6 triggered structurally: attacker needs KeyPackage.init_key=own K → check6 needs attestation.init_key=K → can't mint attestation (no #active) → genuine copied attestation binds victim's I≠K → reject. Creator/Update attestations bind E_pub → Welcome sealed to E_pub → signing-key-only lacks E_priv → can't read. Add proposal EMBEDS full KeyPackage so ALL members (not just adder) run check 6 → group-wide enforce even vs malicious adder.
- **HEADLINE BLACK-C22-7 (MEDIUM, latent-HIGH): creator/Update carve-out is an implementation trap.** Spec prose describes carve-out by FIELD VALUE ("for those leaves this field equals leaf_encryption_key, and check 6 does not apply"). Creator(site1)/Update(site3) attestations are GENUINE #active-signed objects with init_key==leaf_encryption_key, and they ride PUBLICLY in the ratchet-tree LeafNode ext (harvestable by any co-member). IF an implementer keys the check-6 skip on `attestation.init_key==attestation.leaf_encryption_key` (the natural reading), THEN a signing-key-only attacker (C22-6 model) who harvests a victim creator/Update attestation crafts an Add: leaf_sig=victim's, leaf_enc=E_pub, KeyPackage.init_key=ATTACKER's K (≠E_pub → passes RFC§10.1) → check 6 skipped (init==enc in attestation) → Welcome sealed to K → reads as victim. Reopens C22-6. FIX: spec MUST mandate check 6 triggered STRUCTURALLY (run on every Add regardless of field values), MUST forbid the init==enc field-comparison shortcut, AND name an explicit verifier check "reject any Add whose KeyPackage has init_key==encryption_key (RFC 9420 §10.1)" rather than silently depending on openmls.
- **MED BLACK-C22-8: current-key resolver-cache TTL has NO hard numeric cap.** "kept short" is a SHOULD, in tension with §9.10.7's 24h/7d privacy caching (short TTL = more resolutions = more traffic-analysis exposure). A compliant impl could accept attestations signed by a RETIRED #active/#agent for up to the general cache TTL post-rotation → weakens "rotation is the fast lever." Pin a hard MUST upper bound (minutes) distinct from the 24h/7d privacy cache. Unlike MAX_KEYPACKAGE_ATTESTATION_LIFETIME (hard 84d const), this window is unbounded-by-spec.
- **LOW BLACK-C22-9: check-numbering drift.** §9.18.7 MAX_KEYPACKAGE_ATTESTATION_LIFETIME note cites "check 8" (cap) and "check 7" (window-pin) but the final §9.7.1 list has cap=check 10, window-pin=check 9. Stale numbering → implementer confusion.
- Full-state-theft residual (attacker has HPKE privates): join OTHER groups as victim bounded by 84d cap + rotation — HONEST, acknowledged, no new break. consumed_init_key_store (production_backend.rs) is per-verifier-node not global → doesn't close cross-group reuse against fresh members. External-commit vector within residual (no Welcome to read; likely disabled).
- COULD NOT break the 8-field model at spec level. The init_key binding is the correct fix and it holds under structural triggering.

- **NEW MED BLACK-C22-10 (steady-state resolution-failure censorship, aggravated by check 2).** Checks 1-2 apply on EVERY leaf read (Commit/Proposal), mandating ≤5-min-fresh resolution of every member's DID. Check 2's 300s cache (vs 24h) raises re-resolution frequency ~288x. "Resolution failure is a reject" DoS discussion only reasons about the JOIN case ("retry/queue the join") — but a fail-closed reject of an ALREADY-ADMITTED member's Commit due to transient resolution outage forks the epoch (committer advances, others reject) / effectively censors. An attacker who degrades a target's DID resolution (DHT eclipse, did:web DoS) gets the target's Commits/Proposals rejected group-wide across ALL their groups. Core reject-on-fail preexisted (check 1); check 2 sharpens frequency + the DoS framing under-addresses steady-state. Spec should extend the availability discussion beyond join.
- **NEW LOW BLACK-C22-11 (check-8 load-bearing overstatement).** Prose (line 639, 630) frames check 8 as closing the read-as-victim "degenerate path together with check 7". Precisely: the READ is denied by check 5 (encryption_key binding forces the sealing key to victim's E_v, which signing-key-only attacker can't decrypt). Without check 8 the creator-attestation Add would be ADMITTED but sealed to E_v → unauthorized-add nuisance, NOT a read. Check 8 is correctly required by RFC 9420 §10.1 (malformed-KP / HPKE key-reuse) + good defense-in-depth; only the "closes the read vector" credit is imprecise. Does NOT weaken security.
- **Boundary (not a fix-scope break): the ≤5-min revocation guarantee presupposes rollback-resistant DID resolution.** A DHT/did:web rollback serving an OLD but validly-signed (lower-seq) document as a "fresh resolution" would return a pre-rotation #active that check 2 can't catch (check 2 bounds CACHE age, not the resolved record's own recency). Inherited from the resolution layer (did:dht seq monotonicity is the mitigation), out of the attestation verifier's scope, but the 5-min claim rests on it.
- **Completeness note:** §25 has only the POSITIVE vector 37; no negative conformance vectors for check 7 (init mismatch), check 8 (init==enc), or check 2 (stale resolution). Given "enforce mechanically" tenet, negative vectors would strengthen — not a break.
