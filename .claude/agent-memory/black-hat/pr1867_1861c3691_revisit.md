## Only finding (LOW, fail-closed-biased, NOT privilege-gain)
evaluateTrust extracts attacker-controlled att[0].with and passes it as capUri to
ucanValidate. If att[0].with contains a control char or HTML-special char (`<>&"'`),
BOTH NAPI and WASM pre-flight `validate_capability_uri` reject with VALID-* → TS
validateOneCapUri re-throws → evaluateTrust THROWS instead of returning all-false.
Contrast: capUri===null (no att / non-string with) correctly fail-closes to all-false
(trust.ts:547-551). Inconsistent malformed-token treatment: one shape → all-false,
another → exception. NOT exploitable to forge `true` (throw aborts, never mints trust).
Legit URIs (tool:invoke:* / tool_invoke:*) never contain forbidden chars → legit flows
unaffected. Identical NAPI+WASM (no native/WASM divergence). HARDENING: in
validateOneCapUri, also fold VALID-* (boundary-rejected malformed cap URI) into all-false
for consistency with the null path, OR pre-validate capUri shape before calling the bridge.
