# Standing-Pair §5.15.8 (docs-only review, commit 38b99639a, branch spec/standing-pair-not-a-saga-v2)

Classification settled: standing-pair = single-context async creation, NOT a saga. Attacked the hardened security claims.

## BLACK-SP-01 (HIGH) — known_did / discovery_context bypass the not-self-created rule
The §5.15.8 step-4(b) hardening applies the "not-self-created, distinct" qualifier to clear the stranger bar, but then says B MAY auto-join if A satisfies an AutoAcceptPolicy TrustRequirement "via a qualifying non-self-created, distinct shared context — e.g. `shared_context`, `known_did`, or `discovery_context`." This is wrong: `known_did(list)` and `discovery_context` (§5.12.2) are NOT shared-context predicates. `known_did` = "DID is in an explicit allowlist"; `discovery_context` = "DID is registered in a context with discovery tools I trust." Neither requires a *shared* context, so the "non-self-created, distinct shared context" qualifier is structurally inapplicable to them — the sentence conflates three disjoint predicates. An attacker who gets onto a discovery context B trusts (register an agent via agent_register in a discovery context — §9.3 admission only, no relationship with B) satisfies `discovery_context` and auto-clears the stranger bar with zero shared context and zero self-created-context detection. The not-self-created control only guards the shared_context path; the other two TrustRequirement arms are an unguarded bypass.
Fix: state the qualifier per-arm. For shared_context: not-self-created+distinct. For discovery_context: the discovery context itself must be not-self-created (else attacker spins up his own discovery context, registers, self-clears). known_did is human-curated so exempt, but say so explicitly.

## BLACK-SP-02 (MEDIUM) — "distinct context" is undefined; N-party self-created context evades
Qualifier says shared context counts only if "not self-created and is a distinct context." "Distinct" is glossed only as "a bilateral pair created in the same first-contact flow MUST NOT count." That phrasing pins the exclusion to the *same-flow bilateral pair*. An attacker creates a 3+-member context (himself + victim + a throwaway sybil) OUT of band ahead of time — not in the first-contact flow, not bilateral. It is "distinct" (a different context from the standing pair) and the prose exclusion ("same first-contact flow," "two-party") doesn't catch it. But it is still self-created by the attacker, so §9.3's actual rule (not-self-created) WOULD reject it — meaning the §5.15.8 prose under-specifies relative to the §9.3 invariant it claims to import. The load-bearing word is "self-created," not "distinct"; "distinct" adds nothing and invites the reading that a different self-created context qualifies. Fix: drop reliance on "distinct"; make "not self-created — i.e. neither party to the pair is a creator/admin of the qualifying context" the operative test, matching §9.3.

## BLACK-SP-03 (LOW/INFO) — enforcement-layer disclosure is honest but the non-overridable claim is unenforceable at protocol layer
The "honest disclosure" correctly says the stranger-deny is an SDK consent-gate MUST, protocol sees a normal join. It then asserts a conformant SDK MUST NOT let AutoAcceptPolicy override stranger-deny. Both halves are individually true but jointly they are a pure honor-system: a non-conformant SDK that DOES auto-join a stranger produces an on-wire-identical join (the disclosure admits the protocol can't see the difference). So "non-overridable" has exactly the strength of the §5.12.2 tool/paid hard rules — which is to say, none against a malicious peer's own SDK. This is disclosed and is acceptable (consent is the joiner's own decision; a joiner who wants to auto-join strangers only harms itself), but the text's emphatic MUST NOT could read as a protocol guarantee. The disclosure IS complete on this point — it explicitly says "does not imply protocol-layer enforcement."

## BLACK-SP-04 — collision-resolution destroy: credential-confirm gate HOLDS
did_hi destroys its self-created group only after confirming the incoming Welcome's creator credential resolves to did_lo (verifiable from creator leaf ScpCredential after Welcome processing), and the predicate+confirm+destroy are atomic. This closes the targeted-DoS (attacker addressing a Welcome under the pair's derived_context_id to tear down did_hi's legitimate group): a Welcome whose creator≠did_lo MUST NOT trigger destroy. RESISTS:
- Spoof did_lo Welcome: creator credential is bound into the MLS leaf and verified post-Welcome-processing; attacker can't forge a leaf credential resolving to did_lo without did_lo's signing key.
- Replay a genuine did_lo Welcome: a real did_lo-authored Welcome IS did_lo's canonical group — destroying did_hi's self-created group and joining did_lo's is the CORRECT resolution outcome, not an attack (exactly one group survives = did_lo's). Replay just re-drives the same convergent end state; idempotent.
- Credential confusion: confirm requires the creator leaf credential to resolve to did_lo specifically (lower DID), not merely "some valid credential."
- TOCTOU confirm→destroy: spec mandates atomic evaluation of {self-created predicate, credential confirm, destroy}.
One residual to verify at impl time: "atomically" is a spec MUST; the per-context actor mutex must hold across confirm+destroy with a generation/identity check so a concurrent context-recreate can't slip a different group under the same id between confirm and destroy (standing contexts use deterministic ids — the confused-deputy-via-recreation pattern applies). Flag for code review, not a spec defect.

## BLACK-SP-05 — symmetric model wedge: no strand
did_lo ignores did_hi's Welcome and keeps its own group; did_hi destroys its own and joins did_lo's. did_lo "never observed did_hi's group" so the destroy equivocates against no peer. Checked for: (a) double-bind (both destroy) — impossible, only did_hi destroys, did_lo only ignores; (b) both-strand (neither converges) — did_lo's group is canonical and did_hi joins it, single survivor; (c) third-party wedge — a third party can't author a Welcome whose creator resolves to did_lo (BLACK-SP-04), and a Welcome from a non-pair DID isn't under the pair's derived_context_id with a did_lo creator. Symmetric initiation + did_lo tiebreak is sound. The initiator-side never-joined steady state (single-member replica + reaper) is internally consistent.

## BLACK-SP-06 (LOW) — reaper deliverability-window is the right control; one residual ambiguity
Reaper (step 4(d)) GCs a single-member replica only once BOTH idle-bound elapsed AND the emitted Welcome is no longer deliverable/expired — preventing reaping a group an offline B could still join. Sound. Residual: "no longer deliverable / has expired" depends on the relay's blob TTL for the Welcome (InvitationBundle TTL = 7 days default per §5.12.3.3). If A's relay set and B's relay set differ and a Welcome lingers on a relay A can't observe, A's "deliverability window" estimate may under-count, reaping a group B then joins from a stale Welcome on the other relay → B holds a 2-leaf replica of a context A reaped. A's next standing_context(peer) auto-revives via transparent re-drive (ADR-049 §10) under the deterministic id, so it self-heals, but for the interim B can SEND-gate-permitting reach a context A no longer has. This is the known Phase-2E joiner-send gap intersecting the reaper; bounded and self-healing, but the "no longer deliverable" predicate should be defined as max over ALL relays in the context's relay set, not A's local view.

## BLACK-SP-07 — published-KeyPackage oracle: disclosed correctly, chain-control acknowledged
A fetches B's published KeyPackage at step 2 BEFORE the consent gate, relay-observable. Spec discloses this precisely: async consent removes the *synchronous reply* oracle only, NOT the published-KeyPackage-existence bit. The text correctly notes that bit is a *targeting* primitive only when chained with a stranger-bar bypass — which is exactly why BLACK-SP-01 (the known_did/discovery_context bypass) matters: it re-opens the chain the not-self-created qualifier was meant to blunt. The oracle disclosure is honest and complete; its residual value is gated on closing SP-01.

## BLACK-SP-08 (MEDIUM) — fresh-DID flood: §9.3 consent-gate-evaluation enforcement is asserted, not authored
Per-DID 60s cooldown (1s floor) bounds single-DID Welcome churn. Spec correctly states the per-DID cooldown does NOT bound a fresh-DID fleet (many DIDs, one Welcome each) and defers that to "§9.3 earned-capacity applied at the consent-gate-evaluation layer." Problem: §9.3's earned-capacity table (initial_context_membership_limit=10, message rates, etc.) bounds the *new identity's own* capacity — context creation/membership/message/tool rates. It does NOT define an inbound-contact-attempt budget that a RECIPIENT applies to incoming strangers. §9.3 enforcement is "SDK tracks the identity's creation timestamp, participation record count, inactivity" — that is self-capacity, evaluated about the actor, not a per-recipient inbound flood control. So "§9.3 earned-capacity applied at the consent-gate-evaluation layer" is a forward reference to an enforcement point §9.3 does not currently specify: there is no clause saying B evaluates A's tier/participation-record count and rejects inbound contact from tier-0 fresh DIDs before consent. The spec explicitly says "This spec adds only the forward cross-reference; it does not author a new standalone limiter here (that bound lives in §9.3 and its enforcement layer)" — but §9.3's enforcement layer as written does not contain a recipient-side inbound-contact admission check keyed on the initiator's earned capacity. Net: the fresh-DID-fleet bound is asserted to exist elsewhere but is not actually specified anywhere. A fleet of N fresh admissible DIDs each sends B one standing-pair Welcome, each passes the per-DID cooldown (different DID), and nothing in §9.3-as-written stops B's consent gate from evaluating all N (each requiring the human out-of-band approval the default-deny mandates — so it's a notification/approval-prompt flood, not an auto-join). Bounded to a prompt-spam DoS, not an auto-join, because default-deny holds. Fix: either author the recipient-side inbound earned-capacity admission check in §9.3 (B rejects inbound contact from initiators below tier T before the consent prompt) or stop claiming §9.3 bounds the fleet and acknowledge the residual is a prompt-spam DoS gated only by minting-cost.

## Injectivity / MLS isolation — colon-join HOLDS under stated assumption
derived_context_id = "standing-"||hex(SHA-256("standing:"||did_lo||":"||did_hi)). Colon-join non-injective in the abstract but safe because admitted DID methods have self-delimiting, colon-free, fixed-alphabet method-specific ids (did:dht z-base-32; did:web %3A-encoded). Spec is honest: this rides a human method-admission-review gate (the length-prefixed group_id backstop was removed, so colon-join is now the sole structural isolation anchor), and recommends length-prefix framing (len32||did||len32||did) as RECOMMENDED hardening to retire the human gate — deferred as a coordinated spec+code change. MLS defense-in-depth (GroupId, key schedule, credentials) means a derived_context_id collision alone grants no plaintext. The disclosure that this is weaker-than-unconditional and the recommended-follow-up framing is honest. No finding beyond: adopting length-prefix framing should not stay deferred indefinitely since it's the only thing between an admitted-method bug and a silent isolation collision.
