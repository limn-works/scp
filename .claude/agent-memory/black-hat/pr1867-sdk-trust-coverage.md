# PR #1867 fix/sdk-coverage-fail-closed-and-parity (HEAD 8ddce4ab0) — black-hat

Verdict: APPROVED for changed SDK surfaces. No exploitable enforcement bypass.

## What resists attack (confirmed sound)
- **Revocation evasion impossible**: validate_ucan is sequential; revocation=step10 BEFORE expiry=step11. A revoked token ALWAYS stops at step 10 with fixed literal `UcanError::TokenRevoked` Display "token revoked: {0}" (mod.rs:168). Attacker controls only `{0}` suffix, never the literal prefix → can't emit a later-stage message. `_REVOCATION_PREFIXES=("token revoked:",)` only; removed "revocation unauthorized:"/"revocation failed:" now classify "unknown"→all-false (fail-CLOSED, safe dir).
- **Misclassification-to-fail-open unreachable**: `_PASSED_BEFORE` is monotonic (later stage = more true fields). Over-reporting needs an EARLY failure classified as LATE stage. All UcanError Display prefixes are fixed Rust literals; attacker controls only `{actual}`/`{0}`/URI suffix. Only cross-stage-ambiguous variant is MalformedToken (steps 1/2/6), disambiguated by specific sub-prefixes matched BEFORE generic "malformed token:". Serde parse errors ("unknown field", "missing field") never start with "DID not found"/"verification method"/"unparseable capability". So classification faithfully reflects failing stage.
- **Format drift is fail-closed**: classifier depends on exact "] permission error: " marker + fixed prefixes. Any bridge message reformat → "unknown" → all-false. Degrades diagnostic fidelity, NEVER fail-open.
- **Exhaustive UcanError→PERM_3001**: ucan_errors.rs `ucan_error_code` has NO `_ =>` wildcard; every variant (incl TokenRevoked/RevocationUnauthorized/RevocationFailed) → PERM_3001. TS PERM-3001-only allowlist misses nothing.
- **mapBridgeError position-0**: regex `/\[([A-Z]+-[A-Z]+-\d+)\]/` (linear, no ReDoS) takes FIRST match = real code at pos 0. Attacker-embedded code in DID/URI comes later → not matched. trust.ts/py use ANCHORED `^\[SCP-PERM-3001\]`/startswith → mid-string injection → propagate (throw)=fail-closed. ERROR_CODE_OVERRIDES checked pre-prefix but only on pos-0 code.
- **att[0] extraction**: parses UNVERIFIED payload but any exception→None→all-false. cap_uri from token's own att[0]; core binds to context_id + `scp:ctx:{ctxid}/` scope → no cross-context smuggle.
- **Coverage gate fail-closed**: floor guard total_ops==0→exit1; missing SDK key→err; true+no-symbol+no-exemption→unmatched_true err; all-exempted guard requires ≥1 statically-verified SDK per op (can't exempt ALL); non-bool/non-null cell→err. Structurally sound.

### BLACK-053 (ADR-053, MEDIUM/design — original R25 finding, now closed above)
ADR-053 §Decision claims the two-substrate model (§9.7.4.1 §3: pre-rotation key MUST NOT be accessible through the SAME custody provider/auth flow) is "enforced by the type system (separate provider), not by documentation." OVERCLAIM. A separate FFI callback TYPE (`PreRotationCustodyProvider` vs `KeyCustodyProvider`) enforces only "distinct callback object" — NOT distinct substrate or auth flow. A lazy/malicious SDK author can back BOTH providers with the SAME Keychain/Keystore item + SAME biometric/access-group → re-introduces exactly the §3 coupling. Rust cannot verify substrate separation for opaque hardware providers. The proposed conformance test ("pre-rotation key NOT recoverable from operational provider") is the REAL (partial) enforcement and fundamentally can't prove two hardware Keychain items don't share an access group. Recommend: downgrade claim to "structurally encouraged; substrate/auth separation is a foreign-impl obligation, verified by conformance test where observable." Also: migration reveal (consume→import_ed25519_signing_key) necessarily transits the 32-byte seed through shared bridge process memory (Zeroizing helps but a memory dump during migration captures pre-rotation seed = now-operational key). ADR threat model should state substrate isolation holds AT REST, not during migration transit.

### OBS-1 (att[0]-only ceiling gap — documented limitation, misuse hazard, NOT a bypass)
validate.rs:591 `verify_ceiling_compliance(std::slice::from_ref(required_capability), ...)` checks ceiling ONLY over the single required_capability (=att[0].with), NOT over `granted_caps` (all att). So a token with att[0]=benign-in-ceiling + att[1]=out-of-ceiling-Category-B (parseable, non-CategoryA) VALIDATES when SDK passes att[0].with → Layer 1 reports withinCeiling:true + all-true. Contradicts natural reading of "withinCeiling" (sounds token-wide). NOT an enforcement bypass: (a) per-action gate passes the SPECIFIC exercised cap as required_capability → att[1] caught at step 8 when used; (b) Category A enforced over ALL granted_caps (line 582) so DID-doc/pre-rotation/migration/key-mgmt can't smuggle. Impact = diagnostic over-reports; a consumer misusing withinCeiling as a "token grants nothing beyond ceiling" authz signal is misled. Extensively documented ("Layer 1 does NOT answer 'does this token authorize action X'"). Honest design.

### OBS-2 (Py/TS parity divergence — practically inert)
A UCAN failure arriving with a code != PERM-3001: Python catches by exception TYPE (bridge.UcanError) → classifies (or "unknown"→all-false verdict); TS (PERM-3001-only regex allowlist) → THROWS. Both fail-closed, divergent shape. Unreachable on matched bridges given exhaustive PERM_3001 mapping. File-an-issue at most.
