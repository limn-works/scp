description: VelocityRollbackToken can't be persisted/reconstructed — durable economy reversal across an actor restore must reverse velocity by (did,timestamp), not by token
metadata:
  type: project
---

`scp_protocol::economy::antispam::VelocityRollbackToken(u64)` is NOT serde and has NO public constructor from a raw `u64` (only `into_inner()` out). By its own doc it is "local-only identity marker that has no meaning once the process restarts": `SenderVelocityTracker::snapshot_entries()` persists ONLY timestamps; `from_snapshot()` re-synthesizes fresh seqs for restored entries, so a persisted token can never match a rehydrated tracker entry.

Consequence for ADR-049 Class-S durable economy reversal (e.g. §6.2.4 caller saga reservation): budget (`reverse_spend`, keyed did+amount) and hard-rate-limit (`refund`, keyed did) reverse fine across a same-node restore, but VELOCITY cannot be reversed by token post-crash. Production velocity window is 3600s (see `context/state.rs` GovernanceState init), so the Prepare-A velocity entry will NOT reliably age out before crash-recovery runs — you can't hand-wave it.

**Why:** discovered while fixing the §6.2.4 PreparingB-crash caller over-charge/escrow-leak HIGH finding. A durable `CallerReservationRecord` in the Class-S snapshot must carry serde-safe data only.

**How to apply:** to make velocity durably + precisely reversible from a serialized record, add a timestamp-based single-entry removal to `SenderVelocityTracker` (e.g. `rollback_one_at(did, timestamp_secs) -> bool` removing ONE `(ts,_)` entry) and store `recorded_at_secs` in the record — do NOT try to serialize/reconstruct the token. The serializable escrow handle is `economy::adapter::PaymentAuthorization` (IS serde), reachable as `prepared.envelope.authorization`; `PreparedAction`/`ActionEnvelope` are NOT serde, so persist the `Option<PaymentAuthorization>`, not the whole PreparedAction. See [[finding-runtime-eventlog-not-rfc6962]] for the broader actor-economy context.

**RESOLVED in §6.2.4 wave-6a** (`rollback_one_at` shipped; `CallerReservationRecord` in saga_prepared_state.rs; `xctx_caller_reservations` on PerContextState). The HIGH finding was: a PreparingB-window crash drives `Abort{reservation:None}` to the caller actor, whose abort no-op'd → durable over-charge + escrow leak. Design chosen = **carrier-authoritative; durable record is the crash-only fallback**: live `Abort{Some}`/`commit_a` reverse via the in-memory ToolEconomyReservation carrier then CONSUME the record (remove, no re-reverse); only `Abort{None}` reverses FROM the record (generation-checked). Mutually exclusive by construction (carrier present ⟺ `Some`) → never double-reversed. Rejected the "record is single source of truth" alt because the carrier's velocity token is precise in-process while the record can only do timestamp-removal. NeedsRepair never re-drives `Abort{None}`, so the record is never auto-reversed for it (escrow stays held). Currently-reachable caller deductions are velocity + hard-rate-limit only (outbound leg carries no spending UCAN, so budget/escrow are forward-looking — a positive cost rejects at Prepare-A with SCP-ECON-12060). Class-S gate marker added: `xctx_caller_reservations.insert(` (additive). NOTE the gate's `MUTATORS` is the single source of truth — only ever ADD markers.
