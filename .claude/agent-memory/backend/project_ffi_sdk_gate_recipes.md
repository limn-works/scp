Reusable facts for FFI/SDK work in scp (learned building ADR-049 2J / FFI-02 review fix-pass, commit 5e1faacdd on feat/adr049-2j-ffi-slice).

**Bridges reject non-SingleAdmin governance at `context_create`.** The pyo3 bridge (`build_core_context_params` / dict parse in `crates/scp-ffi/src/context.rs`) accepts ONLY `governance: "single_admin"` and errors on anything else ("invalid governance ...: expected 'single_admin'"). napi/uniffi are similar string-only. **Consequence:** a voting/Threshold/Majority context CANNOT be stood up through any SDK, so any runtime code path gated on non-SingleAdmin governance (e.g. `invite_member`'s governed-context `Err`) is UNREACHABLE from the SDK layer — test it at the runtime layer only (`spawn_from_welcome_tests`, which builds params structs directly). Do NOT write SDK tests that try to create a voting context; they fail at create, not at the code under test.
**Why:** avoids wasting a review cycle writing an SDK test that can never exercise the intended path.

**Single-instance self-join is impossible (first-writer-wins).** In an SDK invite→join round-trip, if creator and invitee share ONE `SCP`/BridgeInstance, `context_join_from_welcome` rejects with "a context actor is already registered for '<id>' (first-writer-wins)" — the creator's actor already owns that context id. A full 2-party JOIN needs two separate instances/nodes (and cross-instance DID-doc resolution, which pyo3/napi publish but uniffi does NOT — see [[uniffi-identity-create-no-publish]]). So SDK invite tests assert the returned `bundle` is a well-formed `SealedInvitation` (proving direct join-usability at the type level); the actual 2-party join is proven at the runtime layer with distinct `alice_sup`/`bob_sup`.

**`ffi_conformance` scans pyo3 `#[getter] fn` NAMES as exports.** `scp-testing::ffi_conformance::every_exported_ffi_fn_is_registered_or_allowlisted` treats every pyo3 `#[pymethods]` getter fn (e.g. a new `bundle` getter) as a "leaked export" that must be either a registered parity op OR listed in `scripts/ffi-export-allowlist.json` with `kind: "getter"` + reason. `ffi_export_allowlist_has_no_stale_entries` fails if you REMOVE a getter but leave its allowlist entry. So adding a pyo3 getter → add allowlist entry (expanding coverage, legitimate); removing a getter → remove its stale entry (required by the no-stale test — legitimate maintenance, NOT an enforcement bypass). `scripts/ffi-export-allowlist.json` is NOT in the parallel-coder-owned set (that's `check-sdk-coverage.py`), so it is editable. napi `#[napi(object)]` fields and uniffi enum-variant fields are NOT scanned (not functions).

**Per-SDK rebuild recipes (macOS arm64) for verifying an FFI type/signature change end-to-end:**
- **napi `.node` addon:** `cargo build -p scp-ffi-napi --release --features scp-ffi-napi/allow_in_memory_custody`, then `cp target/release/libscp_ffi_napi.dylib bindings/typescript/node_modules/@limn-works/scp-ts-napi-darwin-arm64/index.node`. TS mock tests pass without this; the real-NAPI tests (and their `raw.bundle`-shape mapping) need the fresh addon. napi camelCases field names; `Vec<u8>` surfaces as `Buffer`/`Array<number>`.
- **Swift:** `bindings/swift/build-xcframework.sh --dev` regenerates `Sources/SCP/Internal/ScpBindings.swift` (committed) AND rebuilds `ScpFFI.xcframework` (gitignored). A STALE xcframework (old FFI checksum) makes generated bindings `fatalError` at init (checksum guard), so you MUST rebuild both — regen alone is insufficient for `swift test`. `--dev` uses `--features allow_in_memory_custody,testing`, target `aarch64-apple-darwin`. Verify the regen diff: converters + the per-method `uniffi_*_checksum_*` constant update coherently.
- **Kotlin:** the uniffi bindings (`scp-kt/src/main/kotlin/works/limn/scp/internal/uniffi/scp/scp.kt`) are GITIGNORED and auto-regenerated by the gradle build from the current Rust cdylib — no manual regen/commit. `./gradlew :scp-kt:detekt` and `:scp-kt:test` pick up the new shape automatically.

**Widened API:** `Supervisor::despawn_actor` is now `pub` (was `pub(in crate::context)`) so the FFI bridges can use it as the compensating teardown for a stranded post-commit Welcome-join (silent local actor drop — no MLS leave ceremony, no `MemberLeft` event). See [[project-invite-member-actor-routing]].
