Two fixes on branch fix/1866-direct-execute-trust (commits 16bbc3d41 perf, 3e3e92b14 fix), pushed.

**FIX A (perf):** `IdentityBackedDidResolver::resolve_sync` (crates/scp-ffi/common/src/resolvers.rs) was building a fresh current-thread tokio runtime PER CALL. Replaced the `handle` field with a lazily-built `OnceLock<Runtime>` (`resolution_rt`, small multi_thread, 2 workers). `resolve_sync` drives futures via `handle().block_on` from a freshly-spawned `std::thread::scope` thread (never inside a runtime) → deadlock-free from the in-`RUNTIME.block_on` caller posture (no nested block_on, no dependence on shared bridge runtime workers). `new(resolver, _handle)` keeps the handle arg for call-site stability (7 construction sites) but ignores it.

**FIX B (correctness):** rotate_key / add_agent_key / rotate_agent_key / remove_agent_key / migrate (crates/scp-ffi/src/identity.rs) built THROWAWAY `InMemoryDhtClient::new()` and published the updated doc only there — resolver kept serving stale pre-rotation doc (retired #active stayed live). Fix: new helper `rotation_publish_client(bi)` returns the shared `resolver_dht_client` (or fresh fallback when no resolver); build the rotation `DidDht` against it; call `DidDht::initialize_sequence(did)` FIRST so the re-publish carries strictly-higher BEP44 seq (InMemoryDhtClient::publish overwrites iff seq>existing, else no-op). `publish_to_resolver_dht_for`'s hardcoded seq=1 is correct because it is now ONLY the create path (first publish); rotations route through the DidDht monotonic seq machinery, not that fn. Migrate extracted to `run_migrate_publish<C>` helper (clippy too_many_lines).

**THE NON-OBVIOUS TRAP — DidCache TTL:** publishing to the shared DHT client is NOT enough. `DualLayerResolver::resolve` checks its `DidCache` FIRST (multi-day TTL: 24h active / 7d inactive). After create, the first resolution caches seq=1; after rotation the DHT has seq=2 but the cache still serves seq=1 → post-rotation verify FAILS with stale key. My first test run caught this (SCP-IDENT-1035 signature invalid). Fix: retain the resolver's `Arc<DidCache>` on the bridge instance via a NEW `resolver_cache` slot on shared `CoreFields` (crates/scp-ffi/common/src/bridge_instance.rs, mirrors the `dht_client` slot) + `set/get` accessors; PyO3 `ensure_did_resolver_initialized_on` stores `Arc::clone(&cache)` via `set_resolver_cache`; after each successful mutation call `invalidate_resolver_cache(bi,did,rt)` (sync, `runtime.rs`) or `resolver_cache(bi)` + `cache.remove(did).await` (migrate, async ctx, removes BOTH old+new did). NAPI/UniFFI have the SAME latent bug but task was PyO3-scoped; the shared CoreFields slot is harmless to them (unused until they wire it).

**Test (proves FIX B):** bindings/python/tests/test_scpid.py::TestScpIdVerify::test_verify_uses_rotated_active_key_not_stale — create→sign→verify (baseline), identity_rotate_key, then fresh challenge signed with NEW #active must verify via scpid_verify (resolves through shared resolver). Fails pre-fix, passes post-fix.
