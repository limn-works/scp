`Supervisor::invite_member` (scp-runtime supervisor.rs) was reworked to route the member-add through the context actor's governance gate instead of calling `deps.crypto.add_member` directly (commit 648d4d2fa on `feat/adr049-2j-ffi-slice`).

**Two latent root bugs discovered in the governance AddMember path (both pre-existed, fixed here):**
- `execute_add_member` (governance_helpers.rs) never broadcast its MLS Commit — it only buffered it into the broadcast-suppressed `WelcomeGenerated` event. `execute_remove_member`/`execute_reset_member` DO broadcast. So any add into a multi-member context silently desynced existing members. Fixed by adding `try_broadcast_commit_or_enqueue` + a new `CommitOperation::AddMember` variant.
- `execute_add_member` calls `deps.crypto.add_member(ctx, did, None)`. Production `MlsCryptoProvider::add_member` (provider.rs) **errors** on `None` — it only returns a default under `cfg(test)`/`testing`. So `GovernanceAction::AddMember` never did a REAL MLS add in production.

**CORRECTION (commit 76f5d8316, review-fix pass on 648d4d2fa — supersedes the staging-map + testing-gated-propose design below):**
- The provider `staged_key_packages` DashMap + `stage_key_package`/`unstage_key_package` were SCAR TISSUE and are DELETED. The invitee KeyPackage now rides the **in-process actor command envelope**: `ProposeGovernanceActionPayload.key_package: Option<Vec<u8>>` (NOT the signed/logged `GovernanceAction` wire type), threaded `propose_inner → execute_governance_action → dispatch_governance_action → dispatch_context_governance_action → execute_add_member(key_package: Option<&[u8]>) → add_member(Some(kp))`. `execute_add_member` also calls `validate_key_package(did, kp)` to bind the KP credential DID to the target DID before the add. Generic-governance AddMember arm, `execute_reset_member`, vote-approval, and direct-execute all pass `None` (preserves their pre-existing #2029 behavior).
- CRITICAL that 648d4d2fa shipped: `invite_member` called the **`#[cfg(any(test, feature="testing"))]`-gated** `propose_governance_action` → prod (`cargo check -p scp-runtime`, no features) failed E0599. Fixed by routing through un-gated `propose_governance_action_checked` (also does the in-lock `GovernancePropose` capability check) via a new private `Supervisor::propose_governance_action_checked_carrying_key_package` (public 4-arg method delegates with `None`; only invite supplies `Some(kp)` — zero blast radius on FFI/test callers).
- FIX 3: voting contexts (`Threshold`/`Majority`/`Unanimity`) are gated out BEFORE proposing → `RequiresGovernanceApproval { proposal_id: None }` (field is now `Option<ProposalId>`, always None; governed invites = deferred #2027). No dangling DOA proposal.
- FIX 4: post-add steps (sign/serialize/HPKE-seal/fatal-delivery) run in an inline `async {..}.await` fallible region; on any Err → compensating `RemoveMember` through the same governance gate (broadcasts its own Commit), then surface original Err. Non-fatal `TransportFailed` delivery still tolerated (caller delivers enc/ct). Compensation failure logged loudly (member may linger).

**Design decision — collapse two signing inputs to one (deviates from the literal task ask, which said keep the `sign` closure):** `Supervisor::propose_governance_action` mandates a raw `&ed25519_dalek::SigningKey` (the governance engine signs the proposal vote; there is no closure variant without a large engine refactor). So `invite_member` must take a raw key regardless. Using that SAME key for the bundle signature (dropping the old closure) is structurally safer: a two-input design could sign the proposal under admin A while sealing a bundle claiming creator B, caught only after the joiner burns its single-use KeyPackage. `SingleAdminEngine::propose` rejects non-admin proposers (`NotAdmin`) and verifies the vote sig against the proposer's resolved #active key, so key↔identity divergence is caught up-front.

**Why:** directive was "structurally prevent issues; no scar tissue." Auth-by-construction comes free from the governance gate (SingleAdmin auto-executes; voting returns a pending proposal → `InviteMemberOutcome::RequiresGovernanceApproval`, a first-class outcome not an error).

**How to apply:** When exposing `invite_member` over FFI, the bridge supplies the raw signing key (as the governance/propose exports already do) and maps the two-variant `InviteMemberOutcome` enum (`Sealed{enc,ciphertext,delivered}` | `RequiresGovernanceApproval{proposal_id}`). The voting-context path creates a pending proposal but does NOT execute the deferred add later (KeyPackage-at-vote-execution is unbuilt — out of scope). `GovernanceActionResult::MemberAdded` is now a struct variant `{welcome_bytes, commit_bytes}` (RedactedBytes); napi's governance match uses a wildcard so it was unaffected, pyo3/uniffi string arms updated to `MemberAdded { .. }`.
