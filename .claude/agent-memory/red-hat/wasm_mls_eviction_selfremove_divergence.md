# WASM governance MLS-eviction fix (commit b98c5b1a9, task #227) — PRIOR-ROUND findings (RED-MLS1 since FIXED)

Diff: WASM `dispatch_remove_member` now does real MLS eviction (governance_remove_from_group → remove_member_by_did → leaf_index_for_did) + drop sender key + rotate + append durable MemberLeft leaf + return commit hex. Missing-leaf = no-op empty commit (matches native #1294).

## RED-MLS1 (HIGH, PROVEN) — self-removal stealth fork
**Root cause:** WASM `leaf_index_for_did` (group.rs:191) scans ALL members incl. own leaf and has NO self short-circuit. Native `provider.rs::remove_member` (provider.rs:1041) short-circuits `member_did==self.local_did → Ok(empty)` BEFORE scanning, AND skips `own_index` in the scan (1060-1062). WasmCryptoState/WasmMlsGroup have NO local_did field at all.
- OpenMLS `remove_members` on own leaf → `RemoveMemberFailed("The Commit tried to remove self from the group. This is not possible.")` (proven via throwaway probe in group.rs + manager.rs).
- dispatch maps it to `ScpWasmError::Crypto{CRYPTO_4011}` → fail-closed-keep → member KEPT, NO MemberLeft leaf, wrapper rolls back executed_proposals + appends NO GovernanceActionExecuted leaf.
- Native same proposal: Ok → strips membership + appends MemberLeft THEN GovernanceActionExecuted (governance_helpers.rs:1231 execute_remove_member + finalize).
- **RESULT:** identical approved RemoveMember proposal → native client: member gone + 2 leaves; WASM client: member present + 0 leaves. Divergent membership set AND divergent event-log tree::root for the SAME governance history → false-positive §9.9.3 equivocation OR (worse) a real undetected fork on a mixed-client context. No upstream self-target guard in execute_governance_action (3078). Native explicitly permits self-removal (lifecycle_helpers.rs:190).
- **Fix:** add the native self short-circuit to WASM crypto layer (needs a local_did on WasmCryptoState) OR special-case target==executor in dispatch_remove_member (skip MLS, proceed to strip + leaf), matching native's empty-RemoveMemberOutput-on-self.

## RED-MLS2 (MEDIUM) — WASM add-member never adds an MLS leaf
`dispatch_add_member` (manager.rs:3407) ONLY inserts into ctx.members (governance map). NO crypto.add_member / key package / Welcome. So the only real MLS leaf on a WASM-created context is leaf 0 (creator). Every governance RemoveMember of a WASM-governance-added member hits the missing-leaf no-op path → empty commit → "eviction" does ZERO crypto. Defensible only because such members never had real MLS leaves via WASM's own add path (they get keys, if at all, via the pre-existing OOB sender-key gap). But it means the new "real eviction" only ever fires for members added via join_from_welcome (real MLS joiners). Native vs WASM still produce same leaf STRUCTURE here (both no-op empty commit), so NOT a root divergence — flagged for the security illusion.

## RED-MLS3 (MEDIUM) — commit-distribution desync (no internal transport)
WASM returns commit hex to JS; NO auto-broadcast, NO retry, NO pending-commit queue, NO fault marker. Native `try_broadcast_commit_or_enqueue` (governance_helpers.rs:5028) sends via transport + retries w/ backoff + caps queue + emits CommitBroadcastFailed/Pending. Documented in scp.ts/context.rs doc-comments ("caller MUST relay"). A malicious/lazy WASM committer can strip a member from governance + append MemberLeft leaf locally while NEVER broadcasting the eviction commit → remaining members keep old epoch, removed member's key schedule stays valid for traffic on the old epoch. The durable log says "removed" but the MLS group never advanced. Attacker-useful: appear to evict for audit while keeping the target cryptographically live.

## RED-MLS4 (LOW, pre-existing, chained) — rotated sender key never redistributed
`governance_rotate_sender_key` (state.rs) rotates local_sender_key, but WASM `encrypt_message` emits only double-ciphertext, never attaches the key; `decrypt_message` reads sender_key_store (OOB). So rotation denies the sender layer to nobody new and grants the new key to no remaining member on the WASM bridge for encrypted contexts. Diff's own comments admit this. Eviction security rests SOLELY on the MLS epoch advance (RED-MLS3's commit) — which RED-MLS3 shows can be silently skipped. Chain: RED-MLS3 (no commit broadcast) + RED-MLS4 (no sender-key redistribution) = if the committer withholds the commit, the evicted member retains BOTH layers.

## What holds up

- Convergent timestamp (proposal.created_at not now()) + executor actor_did + empty MemberLeft payload + MemberLeft-before-Executed ordering = byte-parity w/ native (well-tested).
- evicted_member_cannot_decrypt_after_removal_and_rotation proves eviction works WHEN commit IS distributed.
- per-DID cleanup (suspended_capabilities, read_exclusion_list) closes a re-admit phantom-state foothold.
