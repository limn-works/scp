**LOW #1 (systemic, PRE-EXISTING pattern — shared with same-context InvocationHandle + Python reference, NOT introduced here): cancellation-during-lazy-open can orphan / double-reserve a money-moving saga.** Lazy open reserves escrow at the Commit-transition. The open runs in an uncancellable background context (Swift unstructured `Task{}`, Python `asyncio.to_thread`, TS memoized promise). If the consuming task is cancelled while awaiting the open, the background open still completes server-side (saga minted, escrow reserved), but the actor/handle's sagaId field is never set (catch path clears openTask instead). A retry on the SAME handle → second open → DOUBLE escrow reservation; a discarded handle → orphaned reserved saga. Root cause = "lazy-open-reserves-escrow + uncancellable background open + memoize-on-return." Consistent across all SDKs incl. Python reference; flag because it is money-moving.

**LOW #2 (systemic, PRE-EXISTING): single-consumer guard is a footgun-detector, not a hard concurrency guarantee.** `#draining`/`draining`/AtomicBoolean is held only ACROSS the poll await, released between chunks. Two truly-concurrent drivers (two `for await` / `collect` / aggregate-racing-iterate) usually collide inside pollNext (guard fires, second throws), but can in principle alternate in the brief draining=false window between poll-return and emit/consume, splitting the chunk sequence. Docs slightly overpromise ("a second CONCURRENT collector raises"). True of the Python reference too (Python `_draining` reset in __anext__ finally). Not new.
