### Known Bug Patterns (Apr 2026 — Phase 4 Façade Deletion PR 4 review)

- **PyO3 init_context_manager has no bi parameter (CRITICAL):** crates/scp-ffi/src/runtime.rs:864 `init_context_manager(local_did)` always attaches to DEFAULT_BRIDGE_INSTANCE. Called from PyScp::context_join (ctx.rs:1887) and PyScp::context_import (ctx.rs:2417). Then `context_manager(bi)` is called — which looks up bi's manager. For non-default bi, bi's manager is never set and returns "ContextManager not yet attached". `init_context_manager_for_test` has the same issue. NAPI (init_context_manager(bi, did)) and UniFFI (self.init_context_manager_with_did) got this right; PyO3 was missed. Pattern: asymmetry across bridges during migration — missed call-site in one bridge.
- **NAPI get_transport_manager ignores bi (HIGH):** crates/scp-ffi/napi/src/transport.rs:207 `get_transport_manager()` has no bi parameter, always reads DEFAULT_BRIDGE_INSTANCE. Called from context_subscribe_on(bi=non-default) at context.rs:1127. Subscription task is spawned into bi's JoinSet but uses DEFAULT's transport — cross-instance relay pollution. Pattern: new `_on` wrappers correctly threaded bi for most helpers but this one-off helper was overlooked.
- **PyO3 known_contexts_for_member ignores bi (HIGH):** crates/scp-ffi/src/runtime.rs:1658 and `all_known_contexts` at 1648 take no bi, read DEFAULT. PyScp::load_contexts in mcp.rs:1881 mixes per-instance `context_ids_for_member(bi, ...)` with process-global `known_contexts_for_member(did)` — SCP B sees DEFAULT's known-contexts, not B's. Pattern: split personality in method — some lookups threaded to bi, others still global.
- **PyO3 fullstack_* methods don't call pyscp_check_handle (LOW):** crates/scp-ffi/src/testing.rs:439-523. `fullstack_reset_network`, `fullstack_create_context`, `fullstack_add_member`, `fullstack_join_from_welcome`, `fullstack_sync_sender_keys`, `fullstack_remove_member` take &PyFullStackNode but no check. PyFullStackNode has no instance_id field — type isn't handle-affine. Testing scaffold, latent but low-impact.
- **RECURRING PATTERN (PHASE 4):** Migration converted most helpers to take `bi` first argument, but singleton-style helpers without state (init_context_manager, get_transport_manager, known_contexts_for_member) were overlooked. When auditing such a migration, grep for every `fn .*\(\)` in the bridge's runtime.rs/transport.rs and verify every caller in methods on Scp routes to it with a bi argument. Bulk-rename completeness audit applies — same failure mode as PR #347 hpke_sealed_key and PR #311 BridgeDidResolver.
