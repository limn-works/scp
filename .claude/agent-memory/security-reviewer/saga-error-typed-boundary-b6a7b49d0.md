## Security verdict per lens (ALL CLEAR)
1. message-field info leak: 13050/13062 messages echo only caller-SUPPLIED values (caller_did, caller_hex, target_hex, tool_registration_id from the request). Gate-1 proves caller IS member of caller_hex; gate-2 reports only "YOUR context <-> the target YOU named for the tool YOU named has no interface" — caller's own relationship, NOT a foreign-context existence oracle. Text byte-identical to pre-diff PermissionDenied messages minus the now-structural `SCP-SAGA-13050:` prefix. NeedsRepair message = mark_resolved/commit failure detail (no capability/secret); saga_id is unguessable UUIDv4 handle, not a capability. No escrow amounts, no membership of unrelated DIDs.
2. Busy{contended_context}: `contended` = `context_set.iter().find(|id| reserved.contains)` and `saga_participant_context_set(CrossContextToolInvocation)` = `{caller_ctx, target_ctx}` ONLY — both hex ids the caller put in the request. Cannot name a third context the caller doesn't already know. NOT an oracle.
3. retry_after_ms: Some(ms)=sliding-window cooldown, None=token-bucket. Yes the type is technically distinguishable, but the limiter TYPE (which resource: join/send/tool_invoke vs per-interface) is already known to the caller from the action it invoked; None-vs-Some leaks nothing beyond the resource the caller chose. None NEVER coerced to Some(0) (explicit test `lift_run_saga_error_propagates_token_bucket_none_backoff`). Non-issue.
4. double-charge fix SOUND. commit_with_retry==Ok ⇒ both Commit-B & Commit-A settled ⇒ prepared_a already None ⇒ run_saga escrow-tail hold-for-repair is a no-op (correct). mark_resolved-fail ⇒ reached_needs_repair=true ⇒ lifts NeedsRepair (halts blind retry, no second execute/charge). Genuinely-aborted (executor Err at commit_b_first_execute 13057, pre-Commit-A) keeps reached_needs_repair=false ⇒ escrow-tail voids+consumes prepared_a ⇒ caller refunded (NO fund-lock). The Err-arm of run_saga_fsm sets reached_needs_repair BEFORE the fallible NeedsRepair journal append (so a journal-durability failure can't downgrade a diverged saga to a clean refunding Abort). All 3 directions tested.
5. saga_code_from_message forgery: IMPOSSIBLE. Every genuine saga error message places `SCP-SAGA-<digits>:` at byte 0, BEFORE any interpolated caller/target data ({caller_did}/{tool_registration_id}/{e} executor error/etc). `find` returns FIRST occurrence ⇒ real code always wins even if a malicious tool's Err(String) embeds a literal `SCP-SAGA-99999`. Membership/interface rejects (13050/13062) bypass the parser entirely (returned as typed Aborted with explicit `code`). Prefix-less aborts (TransportTimeout/journal InvalidState) fall back to GENERIC 13067 — deliberately NOT 13050 (the specific caller-not-member code), tested.
