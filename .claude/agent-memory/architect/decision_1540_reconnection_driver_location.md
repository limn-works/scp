#1540 Step-4 reconnection driver — architectural location DECIDED = **option (b): drive `ReconnectionCoordinator`/`SyncPhaseDriver` at the FFI/SDK relay-client layer (a `context_reconnect` bridge fn)**, exactly where `context_subscribe` already lives.

**Why:** The actor's `ContextTransportProvider` (`context/builder.rs:31`) is SEND-ONLY (`is_connected`/`publish_context`/`delete_published`/`send_message`/`send_to_routing_id`/`publish_key_package`) — NO message retrieval. Buffered-message retrieval (`subscribe`/`query` with `since`) lives ONLY in `scp-transport` `NativeRelayAdapter` (`native/adapter.rs:525/549`) reached via `TransportManager`, which is held in the FFI bridge instance, never inside the actor. Upstream artifacts mandate the SDK layer drives reconnection: spec §23.3 "the SDK executes the following ordered six-phase protocol", §23.5 "the SDK verifies event log consistency"; ADR-029 (phase-6.md:1311) "the SDK executes…"; `ReconnectionCoordinator::plan` doc (hours_offline.rs:920) "the transport layer is injected at the SDK level, not in scp-core"; `EpochState.needs_reconnect` doc (state.rs:1091) "The SDK MUST check this flag when message processing begins…and initiate the reconnection protocol if set." The `context_subscribe_on` proof (napi context.rs:1224-1585) already shows the canonical pattern: a bridge task holds BOTH `transport_mgr` (subscribe/query) AND `supervisor` (actor handle) and feeds relay results into the actor via `supervisor.dispatch_command(ctx, MessagingCommand::DeliverIncoming{..})`, reading actor state via `dispatch_query`.

**How to apply:** Reconnection driver = a new bridge surface that owns the `SyncPhaseDriver`/`SnapshotTransport`/`ResetTransport` impls (all 3 tier engines are GENERIC over a transport trait, by design, so they can be implemented at the relay-client layer). The driver pulls from `TransportManager` (retrieval) and reaches actor-owned state (epoch, MLS commit-processing, checkpoint build/compare, event-log, queue drain) via NEW actor command/query variants on `Supervisor::dispatch_command`/`dispatch_query` — never by widening `ContextTransportProvider`.

**Rejected:**
- (a) Add `retrieve_buffered(ctx,since)` to `ContextTransportProvider` + all impls — DOA. Contradicts the deliberate send-only actor-transport design and ADR-049 §Decision 12 (`&mut PerContextState` is the only in-actor read path; transport is `OnceLock<Arc<dyn>>` send-only). Pushes a retrieval/streaming concern INTO the actor mailbox where it does not belong; relay reconnection/backfill is a connection-lifecycle concern owned by `TransportManager` (the FFI layer). Would be a permanent widening to serve one caller.
- (c) Driver takes `&mut PerContextState` + injected retrieval dep — DOA. `&mut PerContextState` only exists INSIDE the actor task (ADR-049 §Decision 12), which has no retrieval dep; you cannot inject a relay client into the actor task without reintroducing (a). A driver running there would be 8/9 phases non-functional.

ADR-029 §2 AC currently specs `ReconnectionCoordinator { context_manager: Arc<ContextManager>, transport_manager: Arc<TransportManager>, ... }` (phase-6.md:1575) — STALE post-ADR-049 (`ContextManager` deleted, replaced by actor `Supervisor` behind a mailbox). Artifact-flow fix REQUIRED FIRST: write an ADR-029 addendum (or ADR-049 cross-ref) documenting the post-actor reconnection-driver location = FFI/SDK layer composing `TransportManager` (retrieval) + `Supervisor` commands/queries (actor state). Code already diverged (coordinator holds `context_ids` + `SyncPhaseDriver`, no manager). Do NOT let code lead the artifact.

Zero external callers of `ReconnectionCoordinator`/`SyncPhaseDriver`/`on_reconnect`/`RelayBackedDeltaSyncEngine` today (grep clean outside sync/*) — entire subsystem built-but-unwired; Step-4 is the wiring.
