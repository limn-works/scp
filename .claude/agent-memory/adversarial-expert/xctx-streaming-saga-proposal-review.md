## Load-bearing code facts (verified)
- Saga Commit contract is an EXPLICIT INVARIANT: "Commit must eventually succeed" (actor plan L1127, L1134). Commit deliberately does NOT re-validate; only failure mode = infra (timeout/actor-death) → 3× retry (500ms/1s/2s) → NeedsRepair. Path: `context/supervisor/supervisor.rs` `commit_with_retry`:7323, `dispatch_xctx_commit`:7426, `commit_b_first_execute`:7557, FSM NeedsRepair lift ~7095.
- Current unary executor-error behavior: executor is `FnOnce`, `ctx.executor.take()` on 1st run; on `Err` the `.map_err(?)` returns BEFORE `ctx.executor_output` is stashed → retry re-enters, `take()` now None → SCP-SAGA-13056 InvalidState → retries exhaust → **NeedsRepair**. So a tool that ERRORS today → NeedsRepair (holds escrow, divergence markers), NOT a committed error receipt.
- Branch bridge `run_cross_context_bridge` (`context/manager/outlets.rs`:6123) NEVER returns Err — always resolves `event_tx` with completion carrying `status=Success|Error`, manifest over `forwarded` (incl. synthesized terminal Error chunk). `build_completion`:6049 uses `compute_chunk_manifest_root(...).unwrap_or([0u8;32])` — fallible root silently collapses to ALL-ZERO on JCS failure.
- Receipt (`scp-protocol/.../cross_context_saga.rs`): CARRIES full `output_jcs: Vec<u8>` (serde_bounded_bytes 512 KiB), preimage field #6 = `Fixed32(SHA-256(output_jcs))`. Receipt is self-verifying BY CARRYING the whole output. `output_hash()` infallible.
- KAT `receipt_preimage_is_byte_exact`:487 hardcodes `SHA-256({"result":42})`; `receipt_tamper_each_covered_field_fails_verify`:528 has an `output_jcs` tamper case; `receipt_output_hash_recomputed_from_carried_bytes`:596 recomputes from carried bytes. - Shipped SDK surface `PySagaResult` (`scp-ffi/src/tools.rs`:164): sync block-until-committed, returns `output: Option<Vec<u8>>` — ONE buffered blob. §6.2.0.5 contract = `mpsc::Receiver<OutletStreamChunk>` async stream. Irreconcilable without full call-shape redesign ×4 SDKs.
- `ChunkPayload::Data { value: serde_json::Value }` (stream.rs:368) — UNBOUNDED per chunk. NO per-chunk byte cap in bridge. `MAX_CHUNK_PAYLOAD_SIZE` (262140) is the MLS envelope chunk cap (`envelope/chunk.rs`), a DIFFERENT module — proposal's T1 bound "max_billable × MAX_CHUNK_PAYLOAD_SIZE ≈ 8 MiB" cites the wrong constant; real per-chunk size is unbounded. Billable-chunk COUNT ceiling = min(credit_window=32, max_calls); count bounded even w/o max_calls, but byte-size is not.

- T2 credit: bridge only mpsc(32) backpressure; signed `OutletStreamCredit`/`CreditTracker` live in same-context dispatch pump, not bridge. §6.2.0.5 "end-to-end credit" is spec'd-not-implemented across the hop.

## The central hole (Attack #1)
Proposal says bridge "synthesizes terminal error chunk so Commit still succeeds with an errored stream captured." That is a SEMANTIC INVERSION of the saga contract, silently chosen: it makes an error-terminated stream a COMMITTED terminal (signs receipt over error manifest, appends ToolInvoked, Commit-A settles/CHARGES caller, writes provenance edge). Today an executor error → NeedsRepair (reverses). Proposal never states which way it goes, never acknowledges "outlet ERRORS mid-stream" becomes indistinguishable from "saga FAILED", never reconciles with the explicit "Commit must eventually succeed" invariant. A streaming executor introduces a NEW first-class Commit-phase failure mode the FSM was DESIGNED to exclude.

## Verdict rationale
Inventory/composition-table (§1,§2) is accurate and useful. But §0 "drop-in preimage shape", §3.4 self-verifying-AND-32-bytes (contradiction), §6 T1 wrong constant, §8 "one-line asks" all understate. T4 mislabeled as decide-later when it's a security-tenet blocker. Needs: (1) explicit Commit-error semantics decision, (2) resolve receipt self-verification vs size (carry chunks = not 32 bytes; carry manifest only = not self-verifying), (3) correct T1 bound + real per-chunk cap, (4) T4 reclassified BLOCKING, (5) SDK stream call-shape redesign acknowledged as XL not a bullet.
