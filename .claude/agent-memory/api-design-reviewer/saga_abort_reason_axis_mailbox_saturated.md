Issue #121 (branch fix/121-mailbox-saturated-saga-terminal; base/merge-base with main = 5a67b771d). Reviewed APPROVED on the API/taxonomy axis across multiple passes/tips. DESIGN EVOLVED between tips: at tip fb4c2584c `MailboxSaturated` was field-carrying `{retry_after_ms: Option<u64>}` AND the 4 SDK docstrings were NOT updated; by tip afc795ef2 BOTH were fixed — variant is now FIELDLESS `MailboxSaturated`, and all 4 SDK docstrings now describe the retryable-transient-vs-permanent-by-code distinction. The two prior findings below (field-indistinguishability nuance + docstring gap) reflect the OLD tip; current-tip status noted inline.

The §6.2.4 cross-context-tool-invocation saga error model has a **two-layer taxonomy**:

- **Core (scp-runtime `supervisor.rs` ~L405):** `SagaError` has 3 terminals — `Aborted { reason, code, message }`, `NeedsRepair { saga_id }`, `Busy { contended_context }`. The `Aborted` terminal carries a sub-reason enum `SagaAbortReason` = `RateLimited { retry_after_ms: Option<u64> }` (retryable) | `MailboxSaturated` (FIELDLESS at current tip afc795ef2; retryable, NEW) | `Rejected` (permanent). Retryable-vs-permanent abort axis. Fieldless-vs-Option asymmetry vs RateLimited is HONEST: RateLimited has a computable drain instant, MailboxSaturated has none, so a hint would be fabricated (same logic as RateLimited carrying None for the token-bucket hard limit). Lift `lift_run_saga_error` (~L5701) maps `ContextError::ActorBusy(_)` → `MailboxSaturated{None}` + code 13068 BEFORE the generic `saga_code.unwrap_or(13067)`; sound because `needs_repair` guard above guarantees any ActorBusy here is Prepare-phase (commit-phase ActorBusy short-circuits to NeedsRepair). Hardcoding 13068 (ignoring saga_code) is correct — a mailbox send failure is not a saga_reject! path, so saga_code is always None there.
- **FFI (`crates/scp-ffi/common/src/saga_errors.rs` `decompose_saga_error` ~L112):** folds the abort reasons into ONE `SagaErrorKind::Aborted { retry_after_ms }` via or-pattern `RateLimited | MailboxSaturated => retry_after_ms; Rejected => None`. The shared `retry_after_ms` field name is load-bearing for the single-arm fold. SDK distinguishes reasons ONLY by `SCP-SAGA-{code}` string + message, NOT structurally.

**Why MailboxSaturated on the Aborted axis (not Busy, not a new terminal):** Busy.contended_context is the per-context-set overlap gate (ADR-049 §3a) — inapplicable to mailbox saturation, would force a fabricated field (type-level dishonesty). A new top-level terminal is semantically wrong (it IS a Prepare-phase clean abort, neither side committed) AND would churn every bridge map_saga_error + SagaErrorKind + every SDK wrapper. Adding a SagaAbortReason variant is the natural extension; same field shape + None-never-Some(0) rule as RateLimited. All correct.

**THE ONE DEBATABLE POINT (sharpened this pass — the retryability-signal gap):** MailboxSaturated's whole purpose is "retryable, distinct from permanent Rejected." But the producer ALWAYS emits `retry_after_ms: None`, and permanent `Rejected` ALSO folds to `None`. So at the SDK boundary both surface as `SagaAbortedError(retry_after_ms=None)` — FIELD-INDISTINGUISHABLE. The ONLY retryable discriminator is the code string 13068 vs 13067/13050. The SDK exposes NO typed `retryable: bool` / no reason discriminant. **Misuse enabled:** an agent-authored consumer following the SDK docstrings' own documented heuristic ("retry if retry_after_ms present, None = no precise back-off") will NOT retry MailboxSaturated, defeating the variant's entire reason for existing — unless it special-cases the 13068 code string. Consistent with the pre-existing RateLimited{None}/Rejected collapse (not a regression), but this change lands squarely on the gap. Two fix directions if pursued: (a) emit a conservative NONZERO retry_after_ms for MailboxSaturated so the field heuristic works (diverges from RateLimited{None} rationale), or (b) add a uniform `reason`/`retryable` discriminant on SagaAborted across all bridges. Neither is blocking.

**SDK docstring completeness gap — RESOLVED at tip afc795ef2:** earlier tip left the 4 SDK docstrings stale; current tip updates all of them (Python errors.py SagaAbortedError + scp.py, TS errors.ts + scp.ts, Swift Tools.swift, Kotlin Scp.kt) to "PERMANENT rejection OR RETRYABLE transient (rate limit / participant-mailbox saturation), distinguished by the SCP-SAGA-* code." Uniform across all 4. Minor residual: docstrings say "distinguished by the code" without enumerating WHICH codes are retryable — acceptable (registry sdk-common.md is source of truth; enumerating in-docstring would be brittle).

**NEW observation this pass (naming honesty, MODERATE, no-DOA permanence):** `MailboxSaturated` abstracts `ContextError::ActorBusy`, which has 3 producers in scp-runtime context/actor/handle.rs ~L130: (1) "mailbox full for SEND_TIMEOUT" (backpressure, actor ALIVE), (2) "actor inbox is closed — actor has terminated" (actor DEAD), (3) "dropped reply channel". The NAME advertises (1)/backpressure, but the variant doc-comment LEADS with (2)/termination and the e2e test exercises (2) (drops the receiver); the doc even concedes the truly-saturated full-but-open case usually races the phase timeout into a generic 13067 abort. So the name foregrounds the least-reliable sub-case. Misuse: an LLM reading "MailboxSaturated, retryable" infers "actor draining, short backoff, same target recovers" when reality is "actor terminated, retry = fresh handle / respawn." A name covering all 3 (ParticipantUnavailable / MailboxUnavailable) would be honest. Non-blocking.

**No SagaBusy collision (verified this pass):** the overlap gate's `ContextError::ActorBusy(...SagaBusy...)` is consumed by `try_reserve_context_set` → `SagaError::Busy` via `.map_err` (supervisor.rs ~L5632) BEFORE `run_saga`, so it never reaches the new `ActorBusy(_) => MailboxSaturated` arm in `lift_run_saga_error`. The "needs_repair==false ⇒ Prepare-phase only" invariant holds.

**Type-system wins:** `SagaAbortReason` exhaustively matched in decompose_saga_error — cannot add a reason without the FFI fold failing to compile. Codes 13050-13099 = supervisor partition; 13068 next sequential, registry row added, no collision; numeric-formatted (`format!("SCP-SAGA-{code}")`) not named constants, so no missing-constant gap. check-error-codes.sh covers the band.

**SDK surface: zero wrapper CODE changes needed.** All 3 native bridges (PyO3 src/tools.rs ~L965, NAPI napi/src/tools.rs ~L685, UniFFI uniffi/src/bridge.rs ~L5425) route through decompose_saga_error + 3-arm SagaErrorKind → existing typed SagaAborted{code,retry_after_ms,msg}. New code 13068 flows through transparently. WASM N/A (no Supervisor, ADR-034). Payoff of the centralized decompose design. (But see docstring gap above — "no code change" ≠ "no doc change".)
