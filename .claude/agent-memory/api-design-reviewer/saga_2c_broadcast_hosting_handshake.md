API-design review of branch `feat/2c-saga-dispatch` (worktree saga-2c), commits `b001f49a6` (hosting_handshake.rs) + `a784ca50d` (restore_on_startup). Verdict (revised after chronicler #1883 corroboration): NEEDS REVISION — 2 blocking (see bottom), several non-blocking.

**Why:** This is the reference-quality realization of the "Agent-first API design" tenet (CLAUDE.md line 42) + the cross_context_saga.rs `*Fields` precedent. Reviewer pre-flagged 3 concerns; assessed all as acceptable-by-design.

**How to apply (for future 2C/2D saga-type reviews):**
- `sign(key, Fields{...})` / `verify(&self, &VerifyingKey)` is the established protocol pattern (cross_context_saga.rs + hosting_handshake.rs). `verify` takes an EXTERNALLY-RESOLVED key — a type-level guarantee a caller can't verify against a self-supplied key embedded in the message. This is correct and consistent; don't flag it.
- The `clamp` (total/infallible, range fields) vs `validate` (rejects expires_at_ms==0) split: `sign()` always calls `validate()` internally, so a born-expired grant cannot be SIGNED. A `clamp`-but-don't-sign caller producing expires_at_ms==0 is a theoretical footgun but the only consumer of an unsigned config is `sign`, which gates it. Non-blocking; recommend `clamp` doc cross-link to `validate`.
- `verify()` deliberately does NOT call `validate()` (signature-validity ≠ policy-validity is the right separation). The Prepare-B handler (later 2C runtime step) must independently re-run validate + lifetime-ceiling clamp. This is a documented downstream contract, not an enforceable property of the leaf type. Acceptable; recommend a `# Verification scope` doc note on both `verify()` methods.

**Doc-accuracy bug found (real, non-blocking):** FFI bridge doc-comments (PyO3 context.rs, napi context.rs, uniffi bridge.rs) say `ContextManager::restore_on_startup` / `ContextManager::restore_all_contexts`, but the method lives ONLY on `Supervisor` (supervisor.rs:7873/7837). `context_manager_or_error()` in uniffi/runtime.rs:723 returns `Arc<Supervisor>` despite its name — pre-existing naming muddle this commit perpetuates. Doc claims a guarantee on a type that has no such method.

**restore_on_startup:** good "make-illegal-states-unrepresentable" move — folds replay+restore behind one method so a bridge can't call one without the other or out of order, pinned by 2 pipeline_wiring structural assertions. BUT `Supervisor::restore_all_contexts` + `replay_unresolved_sagas` stay fully `pub`, so the encapsulation is by-convention + CI-gate, not by-visibility. Only legit bare caller is WASM (no journal, ADR-034). Recommend (non-blocking) narrowing the two sub-sweeps to `pub(crate)` if no external caller needs them, making bypass a compile error rather than a gate violation — stronger per the "compiler over CI gate" lesson.

**UPGRADE after chronicler doc-accuracy review (#1883) — verdict moved to NEEDS REVISION (2 blocking):**
- BLOCKING (contract honesty): `restore_on_startup` doc (supervisor.rs:7843-7860) + bridge_instance.rs:1688-1690 document a "later sweep" that re-drives a non-resident-caller reversal left non-terminal at PreparingB — but NO post-restore sweep is wired. Verified: only production caller of `replay_unresolved_sagas` is `restore_on_startup` (single pre-restore call, :7875); `recover_preparing_b_entry` reachable only from there (:5504/:5507). A crashed xctx caller whose context wasn't resident during the single replay strands its refund until next restart, which re-strands (same ordering). The public method's doc claims a completion handoff the system doesn't provide. Spec §17.16.4 (:961-969) + §6.2.4 (:294) ASSUME a post-restore sweep "after the caller is restored" — so this is spec↔code contradiction (fix flows down from §17.16.4 per artifact-flow). Also: doc says "the order §17.16.4 proof REQUIRES" but §17.16.4 states no ordering — over-claim.
- BLOCKING (provenance): error codes SCP-SAGA-13003/13004/13005 (hosting_handshake.rs:72/76/84) sit in `cross_context_saga.rs`'s sub-block (13000-13009 per sdk-common.md:60; only 13000-13002 registered). Broadcast-hosting is RESERVED 13100-13999 (sdk-common.md:62). Doc-comment cites sdk-common.md as justification while that file refutes the numbers. check-error-codes.sh only range-checks the band, won't catch sub-block. Fix: renumber into 13100+, register rows in sdk-common.md.
- STALE: supervisor.rs:5569 "ordering ... not enforced in-tree" — 2D now enforces it; reword.
- MINOR: signing_preimage docs (:313,:492) say `RawBytes16(nonce)` but CanonicalField has only `RawBytes` (no RawBytes16 variant); mirrors spec pseudocode notation but names a non-existent code symbol.
- LESSON: my first pass APPROVED on type-contract grounds and missed that restore_on_startup's own doc promises an unwired completion mechanism. The signing/clamp/validate/verify TYPE contracts ARE accurate (chronicler confirmed) — the defect is in the runtime-wiring doc + the cross-artifact error-code registry, which a pure type-surface read doesn't reach. For saga STARTUP/recovery methods, trace the documented "later sweep / deferred completion" claim to an actual caller before trusting it.
