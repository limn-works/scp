## Context / how this was scoped

The 2026-07-15 session (D4) settled the transport *seam*: an injected `JsSocket` port, WebSocket-first. It deliberately did **not** settle what the browser puts on that seam. Two design questions were left open, and both are DOA-grade (a wrong answer is a permanent privacy or interop regression):

1. **The routing model.** Does the browser fan app-data out to per-member pseudonym addresses with a zeroed outer `routing_id` (as native does), or does an MVP take the shortcut of publishing app-data to the single shared `context_routing_id` and reading it back off one channel?
2. **The join wire.** Does native↔browser join reuse the shared §5.12.3 `InvitationBundle` (HPKE-sealed), or does the browser bootstrap over a simpler plaintext `JoinBundle`, deferring real native-context join?

Both questions are the same question the `scp-mls` extraction and D5 already answered for the MLS machine and the relay wire types: **share the real primitive, do not fork a browser-local shortcut.** Reopening it for the pseudonym layer would reintroduce exactly the byte-parity tax ADR-055/057 exist to kill — and, worse than the MLS case, a routing-layer shortcut is not just a maintenance tax but a *reduced-unlinkability* change that would need its own ADR carve-out. The resolution (T-1/T-2) is to apply the discipline uniformly: the browser transports the REAL §9.10.4 model and the REAL invitation bundle, and the pure §9.10.4 logic is extracted so native and browser share one copy.

A third question — the shape of the transport code itself — resolved to T-3: the only genuinely per-target code is **sync orchestration** over the shared primitives (fan-out, announce, inbound pump), which is new code but not a crypto/wire fork, exactly as `scp-client` is already new orchestration over the shared `scp-mls` machine.

## Decisions

**T-1 — Real §9.10.4 per-context-pseudonym routing; extract the pure logic; no shared-channel shortcut.** The browser routes app-data **byte-for-byte as native does**: outer-envelope cleartext `routing_id` zeroed (`[0u8; 32]`), one sealed blob fanned out to N per-member pseudonym transport addresses. The browser MUST NOT publish app-data to `context_routing_id` (native reserves it; publishing there **adds** a direct relay-readable per-context correlator — on top of the pre-existing known-limitation residual that the same MLS ciphertext is fanned to every pseudonym address, so a relay can already blob-match, `messaging_helpers.rs` ~line 1092 — and breaks native interop; per-member fan-out is **reduced, not full**, unlinkability, and the shared-RID correlator would erode even that). To share-don't-fork §9.10.4, the **pure** logic is EXTRACTED from native-only `messaging_helpers.rs` into a new wasm-safe **`scp-protocol::context::pseudonym`** submodule; native and browser consume one copy.

- **Extraction inventory (what MOVES to `scp-protocol::context::pseudonym`):** `is_reserved_pseudonym`, `is_pseudonym_announcement_payload`, `pseudonym_collides_with_other_did`, the `PseudonymAnnouncement` wire struct + `PSEUDONYM_ANNOUNCEMENT_TAG` constant, and a **new pure** `classify_pseudonym_announcement` decision core carved out of the current stateful `ingest_pseudonym_announcement`. (`context_routing_id` / `broadcast_routing_id`, which `is_reserved_pseudonym` calls, already live in wasm-safe `scp_protocol::context`.)
- **What STAYS native-async:** the stateful ingest wrapper — the peer-registry `insert`, the `PseudonymAnnounced` event emit, the rejection metric + `tracing::warn!`, and the per-site follow-up (sequence-tracker advance, reorder-buffer drain, velocity, event-log append). These touch the `&mut` runtime state (`ClassCMut` / `view.routing_mut().peer_registry_mut()`) and cannot leave `scp-runtime`. The native wrapper calls the shared `classify_*` core, then performs the effects.
- **Decision topology (so the native wrapper is byte-AND-trace-identical to today).** The pure core returns a `PseudonymAnnouncementDecision` enum that carries **per-branch data** rather than a bare `&'static str`, so the native wrapper reproduces its existing metric/warn/insert/emit sequence with no drift:
  - `Accept { did: DID, pseudonym: [u8; 32] }` — passed every check; the wrapper does the registry insert + `PseudonymAnnounced` emit.
  - `NotAnnouncement` — untagged/ordinary app data; deliver as a normal message.
  - `Reject { .. }` per failing check, **carrying the branch's data** — critically the **sender-mismatch** reject carries `claimed_did` (the announced `member_did`) so the wrapper can log the exact `claimed_did = %…` warn field it emits today; the reserved-value, broadcast-context, and cross-DID-collision rejects carry their stable reason. The wrapper maps each `Reject` to the same metric + warn + caller-return it emits now.
- **Registry parameter — `classify(registry: Option<&HashMap<DID, [u8; 32]>>)` where `None` == broadcast.** The pure core takes an **immutable** view of the peer registry for the collision check; `None` encodes the broadcast-context case (native's `peer_registry_mut()` returning `None`), which the core rejects as a spec-level violation. Passing `Option<&…>` (not `&mut`) keeps the classifier pure — the mutation (`insert`) stays in the native wrapper.
- **Dedicated submodule, not a leaf crate.** The logic lands as `scp-protocol/src/context/pseudonym.rs`, a submodule of the existing wasm-safe `scp-protocol` — no new crate. It uses `scp_did::DID` for the registry key/DID types (already a `scp-protocol` dependency).
- **Derivation ALGORITHM shared; a browser derivation SEAM is a named prerequisite (not yet built) — distinct from this extraction.** The §9.10.4.A derivation algorithm (`scp-platform/src/pseudonym.rs`) is behind `KeyCustody::derive_pseudonym` and reached by **native** today; the browser does **not** reach it (verified: no `derivePseudonym` on `JsKeyCustody`, no `scp-platform` dep in `scp-client-wasm`, zero pseudonym refs in the browser stack). Because the browser MUST derive its own per-context pseudonym to (a) announce it via `PseudonymAnnouncement` and (b) be addressed in peers' fan-out, adding a **browser pseudonym-derivation seam** is a **structural prerequisite of the T-1/T-3 transport slice** — a peer of D5 (wire types) and D6 (`panic=unwind`), NOT a "later custody nicety." Do NOT conflate two separate obligations: **existence** (can the browser derive a pseudonym at all? — the prerequisite here) versus **byte-parity** (does the browser's derived pseudonym byte-match native's? — validated by the §25.19 KAT once the seam exists). **Mechanism is an OPEN design point, coupled to #1980** (the browser key-custody model, currently punted), and is deliberately NOT decided in this session: with the key currently in wasm memory the browser could derive in Rust via the shared §9.10.4.A algorithm (which would require factoring `derive_pseudonym` into a wasm-safe crate, e.g. `scp-crypto`); alternatively a JS-side `JsKeyCustody.derivePseudonym` seam would re-derive off-wasm (risking a §9.10.4.A re-implementation — a fork to be validated by the §25.19 KAT). Named here as an open prerequisite to be scoped/decided when the transport slice is planned; this session picks no mechanism. This is separate from the pure-logic extraction (which moves classification/wire, not derivation). **Resolved 2026-07-16: Option A** — derive in Rust over the wasm-held key via the shared `scp-crypto::pseudonym` factoring (the §9.10.4.A derivation was moved out of `scp-platform` into wasm-safe `scp-crypto`), so native and browser run ONE implementation; see the ADR-057 [Amendment (2026-07-16 — Option A)](../adrs/ADR-057-in-browser-client-over-shared-mls.md). The browser CALL SITE (the `derivePseudonym` seam) is still the transport slice.
- **Cross-target byte-parity KAT (added by the extraction slice).** A native-vs-wasm32 known-answer test pins that `classify_pseudonym_announcement` and the `PseudonymAnnouncement` wire encoding produce byte-identical verdicts/bytes on both targets, with goldens anchored in spec §25.19. Same rationale as the ADR-057 Prereq-5 cross-target KAT: "byte-identical by construction" is an invariant only if tested (wasm32 is 32-bit; `HashMap` iteration order can differ).

  *Rationale:* Applies the `scp-mls` / D5 anti-parity-tax discipline to the pseudonym layer — one copy of §9.10.4, native and browser reject identical inputs by construction. The extraction is behavior-preserving on native (the wrapper's observable metric/warn/insert/emit trace is unchanged), so it is a safe prequel to the transport code.

  *Rejected alternatives:*
  - **Shared-channel pseudonym MVP** (publish app-data to `context_routing_id`, read back one channel). Rejected: it is not merely a maintenance shortcut but a **further-reduced-unlinkability** change — it hands the relay an *additional* direct per-context correlator on top of the already-known blob-matching residual (fan-out is reduced, not full, unlinkability to begin with), further eroding what §9.10.4 preserves — so it would require an ADR carve-out sanctioning weaker privacy, against the privacy-paramount and no-DOA tenets. It also breaks native interop (a native member reserves `context_routing_id` and never reads app-data off it).
  - **Fork §9.10.4 into a browser-local copy.** Rejected: this is the exact byte-parity tax ADR-055/057 kill; two copies of the reserved-value / collision / tag logic would drift, and drift here is a routing/privacy bug.
  - **A new leaf crate for the pseudonym logic** (e.g. `scp-pseudonym`). Rejected: over-factoring. The logic is protocol-domain and depends only on types already in `scp-protocol` (`scp_did::DID`, `context_routing_id`); a submodule is the right grain (the naming-principle test from the 2026-06-30 amendment — a crate must own a *refusal criterion* — is not met by a one-module pseudonym crate).
  - **Extract the stateful ingest wholesale** (move the registry insert + event emit too). Rejected: those touch `&mut` runtime state (`ClassCMut`, the event sender) that cannot compile to wasm and must not leave `scp-runtime`; only the pure decision core is liftable. The `Decision`-enum split is what lets the native effects stay put while the verdict is shared.

**T-1 Option A — as-built key-source ruling (2026-07-17; human-ruled, coupled to #1980).** When the transport slice wired the Option-A call site, the **only** Ed25519 private key the browser holds in wasm is the **per-context MLS `SignatureKeyPair`** (minted inside `scp-mls` at `create_group` / `generate_key_package`) — there is **no DID identity key in wasm** in this slice. The human **explicitly ruled** to **ACCEPT** keying the browser's per-context pseudonym on the **MLS key** (via `ScpMlsGroup::derive_pseudonym`, which feeds the MLS signing key's 32-byte seed to the shared `scp_crypto::pseudonym::derive_pseudonym_keypair`), even though this **BREAKS same-human native↔browser pseudonym parity pre-#1980** — a parity that this session (and the Option-A resolution recorded in T-1 above) had previously **ASSUMED held**. The acceptance rests on the **device-local-pseudonym model** §9.10.4 already uses: each member **announces its own** per-context routing id and peers **record** it from the authenticated announcement (`classify_pseudonym_announcement`), so no member ever *recomputes* a peer's pseudonym and cross-device / cross-target byte-parity is **not a routing requirement**. Only the shared derivation *algorithm* is byte-identical native vs. browser (KAT-pinned, §25.19); the *key it is keyed on* differs, so same-human pseudonyms differ until #1980 makes the identity key reachable in wasm — at which point the derivation moves onto the identity key and same-human parity is restored. Recorded down as a human ruling (PS-10 / Option A had assumed byte-parity; this corrects that assumption); see the ADR-057 "Amendment (2026-07-16 — Option A)" **A1 as-built** note.

**T-2 — Native↔browser join over the already-shared §5.12.3 invitation bundle; done in the transport slice, not deferred.** The browser join bootstrap uses the shared `hpke_seal_invitation` / `hpke_open_invitation` / `InvitationBundle` / `derive_invitation_routing_id` in `scp-protocol` — the same crate/primitives `scp-client` already consumes for `hpke_seal_sender_key` (ADR-057 T4, #1976) — **not** a plaintext `JoinBundle`. Full native↔browser join interop lands **in the transport slice**. No extraction is needed: the primitives are already shared and wasm-reachable.

  *Rationale:* The invitation bundle is the real §5.12.3 join wire; native members seal Welcomes/bundles with it. A browser that spoke a different join wire could not join a native context — a half-client. Reusing the already-shared, already-wasm-reachable primitives is free (the extraction cost T-1 pays does not recur here).

  *Rejected alternatives:*
  - **Plaintext `JoinBundle` MVP.** Rejected: it is an unencrypted forked join wire that no native member speaks, shipping a browser that can only join browser-created contexts — a half-client. It also drops the HPKE seal §5.12.3 mandates, a confidentiality regression on the join path.
  - **Defer native-context join to a later slice.** Rejected per the no-deferral tenet: nothing external blocks it (the primitives exist and are wasm-reachable), so "later" is a self-imposed scope cut that ships a knowingly-incomplete client.

  *As-built re-slice (2026-07-17; human-ruled, coupled to #1980):* The shipped transport slice is the **#1980-independent half only**. The invitation **join** path and the invitation **HPKE-open** custody are **DEFERRED pending #1980** — opening an `InvitationBundle` requires a Diffie-Hellman against the invitee's on-device custody key (`hpke_open_invitation_with_external_dh` / `JsKeyCustody.dhAgree`), a seam that is **unwired** in the browser pre-#1980 (the browser holds no custody key to DH-agree with). The T-2 premise above — "nothing external blocks it (the primitives exist and are wasm-reachable)" — is therefore **FALSIFIED as-built**: the seal/open *primitives* are wasm-reachable, but HPKE-**open** needs a browser custody key that **does not exist pre-#1980**, a genuine external block. The no-deferral rejection stands for everything the #1980-independent half reaches; the join / HPKE-open half defers on a *real* external constraint (#1980 browser custody), not a self-imposed scope cut. Recorded down as a human ruling; see the ADR-057 T-2 "re-slice as-built" note.

**T-3 — Injected `JsSocket` port; the only per-target code is sync orchestration.** Transport is an injected `JsSocket` extern (outbound `send(frame: Vec<u8>)` sink), NOT a `web_sys::WebSocket` call — keeping `scp-client-wasm` portable-non-native and the wasm fence clean (composes with the 2026-07-15 D4/Component-3 note). Inbound frames are JS-pumped into a **synchronous** `handleRelayFrame` method, because the driver is a sync `&mut self` machine that cannot hold an `onMessage` callback. WebSocket is the baseline (§10.15.3); WebTransport is a follow-on behind the same port. The browser's sync **fan-out / announce / inbound-pump orchestration** is genuinely new code, but it is orchestration **over shared primitives** — the ADR-057 sync-driver-over-shared-machine pattern, identical in kind to how `scp-client` already re-orchestrates send/receive over the shared `scp-mls` machine — **not** a crypto/wire fork. **No dev/test transport stand-in on the production path:** an in-memory loopback socket is `#[cfg(test)]` only and never exported (no-dev/test-stand-in-in-production tenet).

  *Rationale:* Injecting the socket (vs. binding `web_sys::WebSocket`) is what keeps the wasm tier honestly mechanism-named and portable to Deno/Bun/Workers/edge (2026-07-15 D1/D4). The sync inbound pump is forced by the driver's shape, not chosen: a sync `&mut self` machine cannot own an async `onMessage` closure, so JS pumps frames into `handleRelayFrame`. The new orchestration is not a parity liability because the bytes it produces (envelope, fan-out RIDs, announcement wire) all come from the shared T-1 primitives and shared `scp-protocol`/`scp-mls`.

  *Rejected alternatives:*
  - **Direct `web_sys::WebSocket` binding inside the Rust crate.** Rejected: pulls `web-sys` transport features into `scp-client-wasm`, breaks portability-non-native, and dirties the wasm fence — the same rejection the 2026-07-15 D4 recorded, restated here for the routing code that now rides the port.
  - **An `onMessage` async callback the driver holds.** Rejected: the driver is a sync `&mut self` machine; it cannot register or await a callback. The sync `handleRelayFrame` pump is the only shape consistent with the driver.
  - **A dev/test loopback socket reachable in production.** Rejected per the no-dev/test-stand-in-in-production tenet: the loopback is `#[cfg(test)]`-only and never exported; production with no injected socket fails closed, it does not fall back to a stand-in.

## Execution notes

- **Sequencing:** (1) the §9.10.4 pseudonym-logic **extraction** slice — create `scp-protocol::context::pseudonym`, carve `classify_pseudonym_announcement` + the `PseudonymAnnouncementDecision` enum out of native `ingest_pseudonym_announcement`, native adopts the shared copy (behavior-preserving; the wrapper's metric/warn/insert/emit trace unchanged), add the cross-target byte-parity KAT; (2) **NAMED PREREQUISITE — the browser pseudonym-derivation seam** — give the browser a way to derive its own per-context pseudonym at all (mechanism open, #1980-coupled; see T-1), without which it cannot announce a pseudonym or be addressed in fan-out; a peer of the D5/D6 prerequisites, to be scoped when the transport slice is planned; (3) the **`JsSocket` transport** slice — sync fan-out/announce/inbound-pump orchestration + shared §5.12.3 invitation join + real §9.10.4 zeroed-`routing_id` fan-out; (4) the `@limn-works/scp-ts-wasm` package (planning-session-09 step 4); (5) Slice-4 — re-add the TS browser examples (#1951). This composes with, and precedes the transport-code half of, planning-session-09's Execution-notes sequencing (whose step 3 named the transport slice).
- **Fence:** everything stays inside the ADR-057 mechanical scope fence (`scp-client`/`scp-client-wasm` MUST NOT reach `scp-runtime`/`scp-identity`/tokio). The extraction's destination is the already-wasm-safe `scp-protocol`, so it does not widen the fence; the stateful ingest stays native by construction.
- **Prerequisites carried from planning-session-09:** D6 (`panic=unwind` + effective `catch_unwind`, #1444) remains a hard prerequisite for feeding an untrusted relay's frames into the driver safely; D5 (relay wire-types move) remains the prequel that puts `ClientMessage`/`RelayMessage` in a wasm-safe home for the same transport slice.
- **Existence vs. byte-parity — two distinct obligations, do not conflate:** the browser pseudonym-derivation *seam* (can the browser derive a per-context pseudonym at all?) is a **structural prerequisite of the transport slice** (Sequencing step 2 above), with an open #1980-coupled mechanism. Its byte-*parity* with native (§9.10.4.A, does the derived pseudonym byte-match?) is validated by the §25.19 KAT and is a **custody-model** obligation that presupposes the seam exists — parity is meaningless until the browser can derive at all. Neither is part of the pure-logic extraction (Sequencing step 1), which moves classification/wire, not derivation.
