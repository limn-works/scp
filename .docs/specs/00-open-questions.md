# Open Questions

## Design Decisions Pending

- **~~Context capability ceiling mutability.~~** ✅ **Resolved.** Ceiling policy declared at context creation (`immutable` or `governed`). Policy itself is immutable. Default for all well-known templates is `immutable`. See §5.3.
- **~~Context governance primitives.~~** ✅ **Resolved.** ADR-008 specifies context lifecycle state machine with single-admin governance. ADR-009 specifies role assignment and capability ceiling enforcement. ADR-031 specifies multi-admin governance models. Fully implemented: `GovernanceEngine` trait with `SingleAdminEngine`, `ThresholdEngine` (M-of-N threshold), `MajorityVoteEngine`, and `UnanimityEngine` models; `GovernanceModelConfig` enum with `SingleAdmin`, `Threshold`, `Majority`, and `Unanimity` variants (SCP-129 through SCP-133, all done). Proposal interaction with MLS epochs handled by SCP-133 (done).
- **~~Direct agent-to-agent negotiation primitive.~~** ✅ **Resolved (rejected).** Considered and rejected. The protocol does not and will not include a mechanism for agents to contact agents they share no context with. Cross-context interaction uses tool interfaces (§6.2) for asymmetric service calls, multi-parent child contexts (§5.13) for symmetric collaboration, and standing bilateral contexts (§5.12.6) for persistent direct communication. All three require existing context membership or human facilitation. This is intentional: context isolation is the security boundary, and any mechanism that lets agents bypass it reintroduces the attack surface isolation was designed to eliminate. See planning-session-06.md §2 for the full analysis.
- **~~Context-to-context tool interface mechanics.~~** ✅ **Resolved.** §6.2 specifies bidirectional consent, schema constraints, rate limits, chain depth limits. §6.2.1 specifies stateful sessions with optional TTL and per-caller cap. §6.2.2 specifies discovery via DID document capabilities and discovery contexts with standard tool schemas.
- **Sybil resistance enforcement.** **Still open — needs design work.** §9.3 describes the three-layer architecture (device attestation, earned capacity, context thresholds) and §4.8 notes "Mechanism TBD" for earned capacity. The architectural intention is sound but lacks concrete enforcement. **What IS specified:** (1) Device attestation concept — one physical device = one DID creation via Apple App Attest / Google Play Integrity (§9.3). `DeviceAttestation` trait exists in `scp-platform::traits`. (2) Context-level thresholds — contexts set their own admission requirements for behavioral history, endorsements, attestations (§9.3, §7.3.5). (3) Economic deterrent — cost escalation via `SenderVelocity` (§19.7) makes high-velocity Sybil behavior expensive. **What is NOT specified (blocking):** (1) Device attestation integration — how `DeviceAttestation` is invoked during DID creation, what happens on platforms without hardware attestation (desktop Linux), and how the attestation proof is stored/verified. (2) Earned capacity algorithm — what signals increase capacity (participation duration? context count? endorsements?), what the starting limits are, and the growth curve. Must not be gamifiable. (3) Cross-DID blocking — how `block_list.contains(&request.requester_did)` is extended to block the human behind multiple DIDs, requiring either device attestation linkage or earned-capacity correlation. **Concrete gap (BLACK-006, [#22](https://github.com/limn-works/scp/issues/22)):** Sybil identity bypasses per-DID block list. Primary mitigation: device attestation makes Sybil creation expensive; earned capacity makes Sybil accounts limited. Neither is concretely specified. Found in [PR #4 Pass 4](https://github.com/limn-works/scp/pull/4#issuecomment-3955926987), verified in [threat verification](https://github.com/limn-works/scp/pull/4#issuecomment-3956679058). **Classification: P0 — security-critical. Not blocking Phase 1 SDK implementation (device attestation and earned capacity are Phase 2+ concerns per `.docs/architecture.md`) but must be resolved before any deployment handling untrusted identities.**
- **Agent capability metadata standard.** ✅ **Partially resolved.** §4.4 specifies the two-tier structure: self-attested capabilities (claimed by agent's human operator, unverified) and challenge-verified capabilities (tested via §7.3.4 challenge-response, recorded with verifier identity and timestamp). Contexts can require specific capability levels for admission as mechanical checks. §7.4.1 defines the `agent_capability` attestation type within the common attestation envelope format. **Remaining gap:** The specific fields of the capability metadata profile (what capabilities are expressible, the vocabulary/ontology) are not enumerated. §7.3.4 lists examples ("prompt injection resistance, schema validation, rate limit compliance, content formatting") but no formal registry or schema exists. **Classification: P3 — needed before multi-vendor agent interoperability but not blocking SDK implementation.** The SDK can ship with an extensible capability metadata structure and define the initial vocabulary iteratively.
- **~~Content provenance system.~~** ✅ **Resolved.** DataProvenance format specified in §7.7.1. Provenance attached automatically by protocol on context boundary crossings. Provenance evaluation rules in §7.7.2. Absence-as-signal principle established. Cross-context tool calls and structured messages carry provenance.
- **~~Rate limiting defaults.~~** ✅ **Resolved.** Context creation limits, context participation limits per human. Behavioral rate limiting surfaces identified. Economic rate limiting fully specified in §19.7 — cost escalation via `SenderVelocity` metric provides complementary spam prevention alongside behavioral rate limits (§9.2.1). Default values are context-template-specific (not protocol-level), which is the correct design — contexts are sovereign. Audit 2026-03-01: promoted from partial to resolved.
- **~~Identity attestation discovery.~~** ✅ **Resolved.** Attestations are discoverable through discovery contexts (§6.2.2B) and DID document capability entries (§7.4.1). Platform-specific contexts and bridges surface attestation data alongside their own data, eliminating the need for separate discovery infrastructure.
- **~~Identity attestation verification methods.~~** ✅ **Resolved.** §3.5 and §7.4.2 specify platform-specific verification flows: OAuth, DNS records, signed posts. Verification is decentralized — each attestation type carries its own verification method.
- **~~Shadow identity role defaults.~~** ✅ **Resolved.** Observer role by default with restricted capabilities (§12.3). Context governance can override defaults for specific bridges.
- **Bridge connector interface specification.** **Still open — needs design work.** §12.4 describes four operating modes (relay, puppet, API, cooperative) and §12.9 describes the incentive structure for cooperative mode. §12.2 specifies bridge properties (operator DID, platform, mode, provenance marking) and §12.3-12.5 specify shadow identities, trust hierarchy, and provenance chains. **What IS specified:** The semantic model (what a bridge does), the trust properties (provenance chain, operator accountability), and the incentive argument (cooperative mode gives platforms control over a process that happens anyway). **What is NOT specified:** The actual interface definition — the "handful of structured endpoints" mentioned in §12.9. This includes: (1) message ingestion endpoint (SCP context -> external platform), (2) message emission endpoint (external platform -> SCP context), (3) identity attestation endpoint (platform vouches for user identity), (4) presence/status endpoints, (5) error/retry semantics. **Classification: P3 — bridges are Phase 4+ per `.docs/architecture.md`. The semantic model in §12 is sufficient for spec completeness; the interface definition is an implementation detail.**
- **Bridge credential custody.** **Still open — needs design work.** §12.4 describes puppet mode (bridge authenticates as the SCP user on the external platform using delegated credentials) and notes self-hosted bridges mitigate the trust concern. §12.7 specifies bridges are self-hostable. **What IS specified:** The trust model (user trusts bridge operator with credentials, self-hosting eliminates third-party trust), the revocability (context governance can remove bridges at any time per §12.2), and the transparency (bridge presence and operator identity visible to all members). **What is NOT specified:** (1) Credential delegation mechanism — OAuth tokens (most platforms), API keys, session cookies? Platform-specific. (2) Credential storage — encrypted at rest? Separate from bridge operator's own keys? (3) Credential revocation — revoking bridge access should revoke delegated platform credentials, but the mechanism depends on the platform's auth model. (4) Zero-knowledge options — can the bridge authenticate to the platform without the operator seeing the credentials? Possible with OAuth token forwarding, not with raw credentials. **Classification: P4 — bridges are Phase 4+. The credential model is necessarily platform-specific and cannot be fully specified at the protocol level. The protocol's contribution is the trust framework (operator accountability, self-hosting option, revocability).**
- **~~Shadow identity claiming mechanics.~~** ✅ **Resolved.** §12.3 specifies claiming flow: claimant presents identity attestation matching shadow's platform handle, shadow is retired, historical actions retroactively attributed to claimant DID. API specified in .docs/sketch.md (`Bridge.claimShadow`).
- **~~Capability declaration format.~~** ✅ **Resolved.** §8.4 specifies the capability declaration contract: declarative (apps say what they need), validated against ceiling + role, machine-readable and self-documenting, versionable. §8.5 establishes that SCP tool schemas use MCP-compatible JSON Schema — "SCP tool definitions should be a superset of MCP tool definitions, adding SCP-specific metadata (context scope, capability requirements, provenance) while keeping the core schema MCP-compatible." This answers the format question: **JSON Schema (MCP-compatible)**, with SCP-specific extensions. The declaration lists required capabilities as resource URIs (`scp:ctx:{context_id}/{capability}`) matching the UCAN attenuation format (ADR-016 criterion 1). LLMs generating apps parse the same JSON Schema format they already understand from MCP.
- **~~Context state portability format.~~** ✅ **Partially resolved.** §17.5 specifies MessagePack (`rmp-serde`) as the serialization format with version envelopes (`StoredValue<T>`) for forward compatibility. §17.3 defines the key convention for all protocol state. The full portability format (export/import between apps) remains unspecified — what's resolved is the internal serialization and storage architecture.
- **Minimum viable agent specification.** ✅ **Partially resolved.** §4.4-4.5 specify that agents range from "full autonomy to direct manual control" and the protocol does not define what agents are internally. §8.5 specifies that any MCP-compatible model participates in SCP without modification — "the model doesn't need to know about DIDs, capability tokens, encryption, or context governance. It sees tools." **What IS resolved:** The minimum viable agent is an MCP server/client that translates between the model and the SCP SDK. The SDK handles all protocol mechanics (identity, encryption, capability tokens, envelope construction). The agent is a translation layer. **What is NOT specified (remaining gap):** A concrete reference implementation — the actual code/library for the "transparent pipe" agent that forwards human input as SCP messages and presents SCP messages to the human. **Classification: P2 — the reference implementation is an SDK deliverable, not a spec concern. The spec correctly defines the agent's role (§4.5) and the integration surface (§8.5 MCP compatibility). The reference implementation follows naturally from the Python SDK (ADR-014) and MCP adapter (ADR-015).**
- **~~Relay protocol specification.~~** ✅ **Resolved.** ADR-004 specifies the SCP native relay protocol: PUBLISH/SUBSCRIBE/UNSUBSCRIBE operations over WebSocket, blob TTL enforcement, recipient_hint for directed delivery. Minimal outer envelope format specified in §9.10.2.
- **~~Cooperative mode trust tiers.~~** ✅ **Resolved.** §12.5 specifies a four-tier trust hierarchy with two independent axes (identity confidence x transport confidence). The tiers explicitly define the trust differential: (1) Native SCP identity + native action = strongest. (2) Native SCP identity + bridged action = strong (identity verified via DID, transport via bridge infrastructure). (3) Claimed shadow + historical bridged = moderate (retroactive DID link, pre-claim content). (4) Shadow identity + bridged action = weakest (no DID claim, trust depends entirely on bridge operator). §12.9 specifies the incentive: "bridged-cooperative is more trusted than bridged-relay because the platform has vouched for the attribution." Cooperative mode gives the platform a "seat" — influence over how its users are perceived in SCP. Non-cooperation means relay/puppet mode scraping with weaker provenance. The trust differential IS the incentive — platforms that implement cooperative mode get their users perceived at tier 2 instead of tier 4.
- **~~Primary transport binding.~~** ✅ **Resolved.** SCP native relay protocol is the canonical transport. Transport is fully abstracted — 17 adapter options listed, no structural dependency on any single transport. Transport security requirements specified in §9.13 (TLS 1.3 required). Relay threat model formalized in §9.9.
- **~~Transport abstraction interface.~~** ✅ **Resolved.** ADR-005 specifies the `TransportAdapter` trait: connect, send, subscribe, query, disconnect. Async interface, error types defined. SCP native relay is the canonical implementation.
- **~~Context key management.~~** ✅ **Resolved.** MLS (RFC 9420) selected. One MLS group per context. MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519 ciphersuite. Full specification in §9.7 (group key management), §9.5 (cryptographic primitives), §9.8 (message security). MLS tree-based key management provides O(log N) member exclusion. Blocking uses a separate sender-side key layer (§9.16) that operates independently of MLS epoch advancement.
- **~~Metadata privacy.~~** ✅ **Fully resolved.** Comprehensive metadata privacy architecture specified in §9.10: minimal outer envelope (§9.10.2), fixed bucket padding (§9.10.3), per-context pseudonyms (§9.10.4), persistent connections + TLS (§9.10.5), cover traffic configurable default-on (§9.10.6), DID resolution privacy (§9.10.7), relay query privacy via pseudonyms + partitioning (§9.10.8). Push notification opacity mandated in §10.7. Sender-side key layer for blocking specified in §9.16 with HPKE-wrapped per-recipient key distribution.
- **~~Verifiable event log format.~~** ✅ **Resolved.** ADR-011 specifies the event log: append-only Merkle tree per context, SHA-256 hash chain, entry structure (event type, sender DID, sequence number, timestamp, payload hash), inclusion proofs, consistency checkpoints. Efficient enough for device-as-node participation.
- **Behavioral record schema.** **Still open — needs design work.** §7.3.2 defines the 7 derivable fact categories (context participation with duration, tool invocations by type/frequency, governance actions against identity, governance actions by identity, role progression history, attestation history with accuracy, context creation history). Each fact is verifiable against the relevant context's Merkle root. **What IS specified:** The fact categories, the derivation source (context event logs), and the verification mechanism (Merkle proofs). Behavioral records are computed by any agent from accessible context logs — not stored centrally. **What is NOT specified:** (1) Serialization format for exchange between agents (MessagePack per §17.5 is the obvious choice for consistency). (2) Compact presentation format for inline inclusion in attestations or admission checks. (3) Merkle proof format for individual behavioral claims. (4) Privacy boundaries — which behavioral facts from which contexts an agent is willing to share, and how to present aggregate facts without revealing specific context memberships. **Classification: P2 — needed before behavioral validation (Layer 2) can function at scale, but Phase 1 can operate with Layer 1 (protocol enforcement) and Layer 4 (trust evaluation) only.**
- **Challenge suite standards.** **Still open — needs design work.** §7.3.4 specifies the mechanism (repeatable, standardized, distinguishable challenge-response) and lists example capabilities (prompt injection resistance, schema validation, rate limit compliance, content formatting). **What IS specified:** Challenge suites are standardized, repeatable, and results are recorded with verifier identity and timestamp. Custom challenges are possible for context-specific capabilities. Agent metadata distinguishes self-attested from challenge-verified capabilities. **What is NOT specified:** (1) Concrete test cases for any standard challenge suite. (2) Challenge suite registry — who defines, maintains, and versions the standard suites. (3) Fairness validation for custom challenges — how to ensure a challenge tests the claimed capability and not something unrelated. (4) Anti-gaming — preventing agents from hardcoding challenge answers rather than demonstrating genuine capability. **Classification: P3 — challenge-response is a Layer 2 enhancement. Phase 1 operates on Layer 1 (protocol enforcement) + Layer 4 (trust). Challenge suites can be defined iteratively as the network identifies which capabilities matter most.**
- **Consequence mechanism defaults.** ✅ **Partially resolved.** §7.3.7 specifies the mechanism fully: automated rules declared at context creation, protocol-enforced (not governance-discretion), verifiable by any agent. §19.7 adds economic consequences via `SenderVelocity` cost escalation, providing a complementary tier. **What IS resolved:** The mechanism, the declaration point (context creation), the enforcement model (mechanical), the visibility (context metadata before opt-in), and the composability with economic consequences. Context templates (§5.12) provide well-known configurations with appropriate consequence structures for common use cases. **What is NOT specified (acceptable):** Specific threshold values and escalation curves. **Resolution: this is intentionally left to contexts.** The protocol provides the mechanism; contexts define the parameters. The spec already states consequence rules are "declared at context creation" and "visible in context metadata before opt-in" — this is the comparability format. Agents evaluate the declared consequence structure as part of their join decision. Defining protocol-level defaults would be prescriptive — different context types (casual chat vs. financial collaboration) need radically different thresholds. The well-known templates (§5.12) serve as de facto recommended defaults for their respective use cases.
- **Endorsement accuracy tracking.** **Still open — needs design work.** §7.4.2 states endorsement accuracy history pushes endorsements from Layer 4 toward Layer 2, and §7.3.2 lists "endorsement accuracy" as a derivable behavioral record fact. **What IS specified:** The concept (endorsers build accuracy track records), the data source (behavioral records derived from event logs), and the directional effect (accurate endorsers gain credibility). **What is NOT specified:** (1) Definition of "bad endorsement" — candidate signals include: endorsed identity ejected from a context (strong), governance action taken against endorsed identity (moderate), endorsement revoked by issuer (weak — may indicate changed circumstances, not bad judgment). (2) Accuracy scoring formula — ratio of "endorsed identities that subsequently had governance actions" to total endorsements? Time-weighted? Context-weighted? (3) Feedback delay — an endorsement made today may not show accuracy signals for months. How is the accuracy score updated retroactively? (4) Gaming resistance — endorsing only safe, established identities maximizes accuracy trivially. Should the scoring reward endorsing newer identities that turn out well? **Classification: P3 — endorsement accuracy is a Layer 2 refinement that improves trust evaluation quality but is not required for protocol function.**
- **~~Attestation storage and discovery.~~** ✅ **Partially resolved.** Forward discovery (DID → attestations) via discovery contexts (§6.2.2B) and DID document capability entries (§7.4.1). Reverse-lookup (external handle → DID) via `attestation_lookup` tool in discovery contexts (§22.5). Storage location question (DID documents vs relays vs dedicated layer) remains open for attestation data itself.
- **Threshold independence verification.** **Still open — needs design work.** §7.3.5 specifies the mechanism (N-of-M independent attestors) and the independence signals (shared context memberships, mutual endorsement relationships, correlation patterns). **What IS specified:** Independence is verifiable — the protocol CAN check whether attestors share context memberships or have mutual endorsement relationships. Threshold counts and independence requirements are mechanical. **What is NOT specified:** (1) Independence metric — is it binary (any shared context = not independent) or graduated (3+ shared contexts = correlated)? (2) Correlation threshold — how many shared memberships or mutual endorsements disqualify independence? (3) Transitive correlation — if A and B share no contexts but both share contexts with C, are A and B independent? (4) Implementation: does the evaluating agent compute independence locally from accessible Merkle logs, or is there a protocol-level independence oracle? **Classification: P3 — threshold attestations function with basic independence checks (any shared context = correlated). Sophisticated independence metrics can be refined iteratively.**
- **~~Identity private state size constraints.~~** ✅ **Resolved.** Less constrained than context state. Single-owner case allows growth. Relays MAY enforce per-DID storage quotas. See §3.7.
- **~~Identity private state relay obligations.~~** ✅ **Resolved.** Same storage class and retention as context events. No differentiated commitment. See §3.7.
- **~~Identity key rotation and private state re-encryption.~~** ✅ **Resolved.** §9.12 specifies the 6-step ordered compromise recovery protocol including private state re-encryption. §9.7.4 covers key rotation triggers. Single-owner case is straightforward — no group redistribution needed. See §3.7.
- **~~Identity private state discovery pointer.~~** ✅ **Resolved.** Explicit service endpoint of type `IdentityPrivateState` in DID document. See §3.7.

## Context Lifecycle and Governance

- **~~Memory scope enforcement boundary.~~** ✅ **Resolved.** The boundary is now precisely specified across three sections. §5.11 ("Enforcement honesty") explicitly states: "The protocol enforces memory scope through cryptographic key destruction — specifically, MLS group state destruction (tree secrets, all epoch key schedules, application key material). This is verifiable and absolute for protocol-level data. [...] However, the protocol cannot enforce memory scope above the protocol boundary. An agent's underlying model may retain information from an ephemeral interaction in its own memory." §9.15 specifies the three trust levels for key destruction verification: hardware-attested (Secure Enclave/Keystore), software-only (`memset(0)`), no attestation (member offline). The `KeyDestructionAttestation` struct is fully defined. §7.7 provides the provenance defense: data an agent reproduces from memory without protocol-level origin carries no provenance — "the absence of provenance is itself a signal." **The enforcement boundary is:** protocol-level data (MLS keys, ciphertext) = enforceable via destruction; agent-local memory = not enforceable, mitigated by provenance-absence signals. This is explicitly documented for implementers in §5.11's "Enforcement honesty" paragraph.
- **~~Context promotion mechanics.~~** ✅ **Resolved.** Promotion policy declared at context creation (`no_promotion` or `promotable`). Policy itself is immutable. Default for ephemeral templates is `no_promotion`. See §5.10.
- **Summary generation mechanics.** ✅ **Partially resolved.** §5.11 specifies the lifecycle hooks but defers content responsibility: "The summary format is defined by the context (via tools or governance), not by the protocol — the protocol provides the lifecycle hooks (pre-close summary generation, verification window, key destruction) but does not prescribe summary content." **What IS specified:** (1) Summary is produced before key destruction. (2) Both parties verify the summary against the event log before keys are destroyed. (3) The summary persists with full provenance after key destruction. (4) Full content is destroyed (keys destroyed as with ephemeral). **What is NOT specified (remaining gap):** (1) Verification window duration — how long members have to verify/dispute before keys are destroyed. (2) Dispute resolution — what happens if a member rejects the summary (does key destruction proceed? is the context downgraded to full scope?). (3) Default summary tool — while the spec correctly defers summary content to context governance, a reference implementation of a summary tool would be useful for templates. **Classification: P3 — summary scope is the least common of the three memory scopes. Ephemeral and full are sufficient for Phase 1.**

## Crypto and Security

- **~~Offline member MLS re-sync.~~** ✅ **Resolved.** ADR-029 (`.docs/adrs/phase-6.md`) specifies the full three-tier offline strategy: Tier 1 (hours — relay buffering + MLS catch-up), Tier 2 (days — state snapshot + delta sync), Tier 3 (weeks — forced re-join with group state reset). Trigger conditions, initiation protocol, and context lifecycle during reset are fully specified. Implemented in `crates/scp-core/src/sync/` (SCP-121 through SCP-124).
- **Commit delivery assurance under adversarial relays.** ✅ **Partially resolved.** The recovery mechanism is specified; "delivery confirmation" semantics need tightening. **Recovery mechanism (specified):** §9.9.4 specifies that members who are behind on epochs (receive epoch N+1 message while on epoch N) MUST request the missing Commit from other members or other relays. §9.9.2 specifies multi-relay cross-check (publish to at least 2, recommended 3 relays) with a 30-second inconsistency timeout, after which the non-delivering relay is marked potentially adversarial. §9.9.3 specifies the Relay Consistency Protocol (signed checkpoints every 50 events or 10 minutes) for detecting equivocation — epoch divergence between members indicates a missed Commit. §9.9.2 also specifies 60-second heartbeats for suppression detection. **Remaining gap:** "delivery confirmation" in §9.9.4 should be clarified as relay-level ACK (the relay confirms it received and stored the blob), not recipient-level ACK (which would leak metadata). The split-brain recovery path (epoch-behind detection + request from peers/alternate relays) is the actual assurance mechanism. **Action:** Update §9.9.4 to define "delivery confirmation" as relay-level storage ACK and explicitly cross-reference the recovery path (epoch-behind detection in §9.9.3, peer-to-peer Commit request, alternate relay fallback).
- **Pseudonym rotation and traffic analysis resistance.** **Still open — P2 defense-in-depth.** Pseudonym derivation in `envelope/pseudonym.rs` is `HMAC-SHA256(identity_key_material, context_id || "scp-pseudonym")` — deterministic, never rotated. Confirmed by code review: `derive_pseudonym()` takes only `identity_key_handle` and `context_id`, no epoch or nonce. Same inputs always produce same output. **What IS specified (mitigations in place):** (1) Per-context pseudonyms prevent cross-context linkage (§9.10.4). (2) Cover traffic masks activity patterns at 1/30s constant rate (§9.10.6). (3) Fixed bucket padding normalizes message sizes (§9.10.3). (4) Persistent connections prevent connection-timing correlation (§9.10.5). (5) Relay set partitioning limits activity visible to any single relay (§9.10.8). **What is NOT specified (the gap):** (1) Pseudonym rotation — within a single context, the same `routing_id` is used for the entire membership lifetime, making long-term pseudonym-level traffic analysis possible. A rotation mechanism (periodic re-derivation with epoch or nonce, plus a transition protocol to avoid message loss) is not designed. (2) Delivery batching/delay at the relay to break timing correlation. (3) Cross-relay fanout decorrelation (jitter, different padding per relay). **Why P2 not P0:** The existing mitigations (cover traffic, padding, pseudonym unlinkability across contexts, relay partitioning) provide substantial traffic analysis resistance. The residual risk is long-term pattern analysis against a static pseudonym within a single context by a colluding relay — a targeted attack requiring significant resources. **(BLACK-001, [#17](https://github.com/limn-works/scp/issues/17)).** Found in [PR #4 Pass 4](https://github.com/limn-works/scp/pull/4#issuecomment-3955926987), verified in [threat verification](https://github.com/limn-works/scp/pull/4#issuecomment-3956679058).
- **~~Cover traffic parameters.~~** ✅ **Resolved.** §9.10.6 fully specifies all parameters: (1) rate: one padded message per relay connection per 30 seconds; (2) scope: per relay connection, not per context — prevents relay from correlating traffic rate changes with context activity; (3) format: single-byte flag inside encrypted payload distinguishes real from dummy; recipients decrypt, check flag, discard dummies; (4) bandwidth: ~15MB/day for 5 relay connections at 1KB padding; (5) configurability: enabled by default, configurable per-client via SDK configuration; disabling degrades traffic analysis resistance but has no functional impact; (6) push-wake connections: no cover traffic (connection is transient). The relay-side distinguishability concern is addressed by design: the single-byte flag is inside the encrypted payload, so relays cannot distinguish real from dummy messages. The only residual risk is statistical timing analysis against the constant rate (acknowledged in §9.10.10).
- **Compromise recovery orchestration.** ✅ **Partially resolved.** §9.12 specifies 6 steps with implicit ordering (numbered 1-6). **Ordering is already specified:** Steps are sequential — key rotation (1) must precede MLS Updates (2) because Updates use the new key; MLS Updates (2) must precede UCAN revocation/reissuance (3) because new UCANs are signed by the new key; KeyPackage rotation (4) follows to prevent new group additions using old key material; contact notification (5) and re-encryption (6) are cleanup. **Partial failure handling (clarified):** Each step is independent per-context for steps 2-4. MLS Update failing in one context does not block other contexts — the SDK retries failed contexts. A context where MLS Update cannot succeed (e.g., member has been offline too long, needs Tier 3 re-join per ADR-029) is flagged for manual re-join. **Remaining gap:** The spec should explicitly state that steps 2-4 are per-context and failures are isolated. The ordering (1 before 2, 2 before 3, 3 before 4, 4-6 independent) should be stated explicitly rather than implied by numbering. **Action:** Add a brief ordering and failure isolation paragraph to §9.12.
- **~~UCAN revocation mechanism.~~** ✅ **Resolved.** Fully specified across ADR-016 acceptance criteria 5 and 7, and implemented in `crates/scp-core/src/crypto/ucan/revoke.rs`. **List format:** Per-context `RevocationList` — a `HashMap<String, RevocationState>` mapping token CIDs to one of three states: `Active` (default, not stored), `RevocationPending` (fail-closed — capability denied while MLS distribution is in flight), `Revoked` (fully committed). Append-only with `merge()` for MLS-distributed synchronization. **Check frequency:** Every action — step 10 of the 11-step `validate_ucan` pipeline (ADR-016 criterion 2) checks the revocation list. No periodic polling; revocation is checked inline on every capability exercise. **Behavior on failure:** Fail-closed. `RevocationPending` state denies capability exercise even before MLS confirmation. If MLS distribution of the revocation fails, the local revocation is rolled back (transactional) so there is no split-brain between the revoker and other members. Network errors during revocation distribution result in rollback to `Active` — the revoker must retry. Revocations are distributed as MLS application messages; `TokenRevoked` events are appended to the context's event log. See `RevocationDistributor` and `RevocationEventLogger` traits in `revoke.rs`.

## Tools and Verification

- **Tool integrity verification execution.** ✅ **Partially resolved.** §7.3.3 specifies the verification model comprehensively: (1) **Who runs tests:** "Any agent can verify a tool's integrity at any time" — verification is decentralized, not delegated to a single authority. (2) **Test vectors:** Defined at tool registration — "known input-output pairs that define correct behavior." (3) **Pass/fail:** "Test vectors verify behavioral conformance and schema compliance, not exact string matching. A tool that returns a correct answer in a valid schema passes, even if the phrasing differs." (4) **Threshold confidence:** "Multiple agents verifying independently creates threshold confidence. If 10 agents all get expected outputs, the tool is almost certainly behaving correctly." (5) **Continuous:** "This is continuous validation, not a one-time trust decision." (6) **Mutation detection:** Tool changes are recorded in the Merkle log; agents can set their own policies (refuse changed tools, accept from trusted operators, require N verifications). **Remaining gap:** Execution environment isolation — tests are run by agents calling the tool, but the spec does not specify sandboxing or environment requirements for test execution. This is acceptable because tool verification is behavioral (does it produce expected outputs?) not environmental (did it run in a controlled sandbox?). **Classification: resolved for spec purposes. Execution environment details are SDK implementation concerns.**
