# Open Questions

## Design Decisions Pending

- **~~Context capability ceiling mutability.~~** ✅ **Resolved.** Ceiling policy declared at context creation (`immutable` or `governed`). Policy itself is immutable. Default for all well-known templates is `immutable`. See §5.3.
- **~~Context governance primitives.~~** ✅ **Resolved.** ADR-008 specifies context lifecycle state machine with single-admin governance. ADR-009 specifies role assignment and capability ceiling enforcement. ADR-031 specifies multi-admin governance models. Fully implemented: `GovernanceModel` trait with `SingleAdmin`, `MultiSig` (M-of-N threshold), `MajorityVote`, and `Unanimity` models (SCP-129 through SCP-133, all done). Proposal interaction with MLS epochs handled by SCP-133 (done).
- **~~Direct agent-to-agent negotiation primitive.~~** ✅ **Resolved (rejected).** Considered and rejected. The protocol does not and will not include a mechanism for agents to contact agents they share no context with. Cross-context interaction uses tool interfaces (§6.2) for asymmetric service calls, multi-parent child contexts (§5.13) for symmetric collaboration, and standing bilateral contexts (§5.12.6) for persistent direct communication. All three require existing context membership or human facilitation. This is intentional: context isolation is the security boundary, and any mechanism that lets agents bypass it reintroduces the attack surface isolation was designed to eliminate. See planning-session-06.md §2 for the full analysis.
- **~~Context-to-context tool interface mechanics.~~** ✅ **Resolved.** §6.2 specifies bidirectional consent, schema constraints, rate limits, chain depth limits. §6.2.1 specifies stateful sessions with optional TTL and per-caller cap. §6.2.2 specifies discovery via DID document capabilities and discovery contexts with standard tool schemas.
- **Sybil resistance enforcement.** §9.3 describes three layers (device attestation, earned capacity, context thresholds) but provides no concrete algorithms, thresholds, or enforcement mechanisms for any of them. Currently architectural intention only. Key sub-question: how do new identities earn more agent slots / context participation capacity? What signals are used? Must not be gamifiable. **Concrete gap (BLACK-006, [#22](https://github.com/limn-works/scp/issues/22)):** `handle_sender_key_request` in `crypto/sender_keys/key_protocol.rs` uses per-DID blocking (`block_list.contains(&request.requester_did)`). A Sybil identity (new DID, same actor) bypasses the block list and receives the sender key. The protocol tenet "every agent traces to a human DID" is not mechanically enforced. Primary mitigation direction: 1 account per device via device attestation makes Sybil creation expensive. Identity-level blocking (blocking the human behind multiple DIDs) requires either device attestation linkage or earned-capacity signals — neither is specified. Found in [PR #4 Pass 4](https://github.com/limn-works/scp/pull/4#issuecomment-3955926987), verified in [threat verification](https://github.com/limn-works/scp/pull/4#issuecomment-3956679058). **Audit assessment (2026-03-01):** This is an inherent limitation of decentralized identity systems without KYC. §9.3 correctly identifies it as a deterrent, not an enforcement guarantee. The three-layer approach (device attestation via App Attest/Play Integrity — SCP-095/SCP-111 done; earned capacity — unspecified; context thresholds — unspecified) is architecturally sound. **Blocking info needed:** (1) earned capacity signal definition — what metrics determine capacity? (2) default threshold values for new identity restrictions (3) attestation-linkage protocol for device-level Sybil detection. **Classification: P1 — defense-in-depth, not blocking for launch. Device attestation provides the primary Sybil deterrent.**
- **Agent capability metadata standard.** What's surfaced, how it's structured, how it's verified. **Audit assessment (2026-03-01):** §8 (Products and Apps) specifies that apps expose capabilities via tool registrations in their contexts. Agent capabilities are implicitly surfaced through context membership and tool availability. A formal machine-readable agent capability manifest is not specified. **Proposed approach:** agent capabilities expressed as the set of tools they can invoke and contexts they participate in — already implicit in the protocol. A dedicated manifest format adds complexity without clear benefit given that tool schemas (JSON Schema in `ToolRegistration`) already describe capabilities. **Classification: P3, defer — existing tool schema mechanism may be sufficient.**
- **~~Content provenance system.~~** ✅ **Resolved.** DataProvenance format specified in §7.7.1. Provenance attached automatically by protocol on context boundary crossings. Provenance evaluation rules in §7.7.2. Absence-as-signal principle established. Cross-context tool calls and structured messages carry provenance.
- **~~Rate limiting defaults.~~** ✅ **Resolved.** Context creation limits, context participation limits per human. Behavioral rate limiting surfaces identified. Economic rate limiting fully specified in §19.7 — cost escalation via `SenderVelocity` metric provides complementary spam prevention alongside behavioral rate limits (§9.2.1). Default values are context-template-specific (not protocol-level), which is the correct design — contexts are sovereign. Audit 2026-03-01: promoted from partial to resolved.
- **~~Identity attestation discovery.~~** ✅ **Resolved.** Attestations are discoverable through discovery contexts (§6.2.2B) and DID document capability entries (§7.4.1). Platform-specific contexts and bridges surface attestation data alongside their own data, eliminating the need for separate discovery infrastructure.
- **~~Identity attestation verification methods.~~** ✅ **Resolved.** §3.5 and §7.4.2 specify platform-specific verification flows: OAuth, DNS records, signed posts. Verification is decentralized — each attestation type carries its own verification method.
- **~~Shadow identity role defaults.~~** ✅ **Resolved.** Observer role by default with restricted capabilities (§12.3). Context governance can override defaults for specific bridges.
- **Bridge connector interface specification.** The cooperative mode interface — what a platform implements to participate — needs to be minimal and well-specified. This is the "pitch" to platforms. **Audit assessment (2026-03-01):** §12 specifies the four bridge modes (Relay, Puppet, API, Cooperative) and the `BridgeConnector` type is implemented in `scp-core/bridge/`. However, the cooperative mode API surface (what a platform MUST implement) is not specified as a standalone interface document. **Blocking info needed:** define a minimal REST/WebSocket API that platforms implement for cooperative mode (message relay, identity verification, content attestation). **Classification: P2, deferred until platform partnerships require it.**
- **Bridge credential custody.** In puppet mode, how are user credentials for external platforms delegated to bridges? Needs to be secure, revocable, and ideally zero-knowledge to the bridge operator. **Audit assessment (2026-03-01):** This is a platform-specific concern. Each platform's authentication mechanism differs (OAuth tokens, API keys, session cookies). **Proposed approach:** UCAN delegation chain — human mints a UCAN granting the bridge operator a scoped capability to act on their behalf on the platform. Credential material stored in the bridge operator's key custody, revocable via standard UCAN revocation. Zero-knowledge to the bridge operator requires platform-side support (e.g., OAuth scoped tokens). **Classification: P3, platform-specific — design when implementing first puppet-mode bridge.**
- **~~Shadow identity claiming mechanics.~~** ✅ **Resolved.** §12.3 specifies claiming flow: claimant presents identity attestation matching shadow's platform handle, shadow is retired, historical actions retroactively attributed to claimant DID. API specified in .docs/sketch.md (`Bridge.claimShadow`).
- **Capability declaration format.** What does the machine-readable app capability manifest look like? JSON schema, protocol buffers, something else? Must be parseable by LLMs generating apps. **Audit assessment (2026-03-01):** Capabilities are already expressed as URI strings (`scp:ctx:{context_id}/{capability}`) in UCAN attestations. Tool registrations use JSON Schema for input/output validation. Context templates declare capability ceilings as string sets. **Proposed resolution:** JSON Schema for tool capabilities (already in use) + capability URI format for UCAN attestations (already in use) = sufficient for LLM-generated apps. A formal manifest aggregating both is straightforward but not blocking. **Classification: P3, defer — existing mechanisms cover the core need.**
- **~~Context state portability format.~~** ✅ **Partially resolved.** §17.5 specifies MessagePack (`rmp-serde`) as the serialization format with version envelopes (`StoredValue<T>`) for forward compatibility. §17.3 defines the key convention for all protocol state. The full portability format (export/import between apps) remains unspecified — what's resolved is the internal serialization and storage architecture.
- **Minimum viable agent specification.** What does the simplest possible agent look like? The "transparent pipe" agent that just forwards human input needs a reference implementation that's trivially embeddable. **Audit assessment (2026-03-01):** The SDK-first approach means the minimum viable agent is an SDK consumer that creates an identity, joins a context, and sends/receives messages. The Python SDK already provides this in ~10 lines of code. A formal "transparent pipe" reference implementation is a documentation/example concern, not a protocol design question. **Classification: P3, documentation — create an example in each SDK.**
- **~~Relay protocol specification.~~** ✅ **Resolved.** ADR-004 specifies the SCP native relay protocol: PUBLISH/SUBSCRIBE/UNSUBSCRIBE operations over WebSocket, blob TTL enforcement, recipient_hint for directed delivery. Minimal outer envelope format specified in §9.10.2.
- **Cooperative mode trust tiers.** How much does cooperative mode actually improve trust provenance for bridged content? Need to define the specific trust differential that incentivizes platforms. **Audit assessment (2026-03-01):** §12 specifies `BridgeProvenance` with `ProvenanceQuality` tiers (`NoProvenance < EphemeralKnownParties < SummaryVerified < PersistentVerifiable`). Cooperative mode yields `PersistentVerifiable` (highest) while puppet mode yields `EphemeralKnownParties` at best. The trust differential is already quantified through the provenance quality enum. **Proposed resolution:** document the provenance quality mapping per bridge mode in §12 and reference it in bridge connector marketing materials. **Classification: P3, documentation enhancement.**
- **~~Primary transport binding.~~** ✅ **Resolved.** SCP native relay protocol is the canonical transport. Transport is fully abstracted — 17 adapter options listed, no structural dependency on any single transport. Transport security requirements specified in §9.13 (TLS 1.3 required). Relay threat model formalized in §9.9.
- **~~Transport abstraction interface.~~** ✅ **Resolved.** ADR-005 specifies the `TransportAdapter` trait: connect, send, subscribe, query, disconnect. Async interface, error types defined. SCP native relay is the canonical implementation.
- **~~Context key management.~~** ✅ **Resolved.** MLS (RFC 9420) selected. One MLS group per context. MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519 ciphersuite. Full specification in §9.7 (group key management), §9.5 (cryptographic primitives), §9.8 (message security). MLS tree-based key management provides O(log N) member exclusion. Blocking uses a separate sender-side key layer (§9.16) that operates independently of MLS epoch advancement.
- **~~Metadata privacy.~~** ✅ **Fully resolved.** Comprehensive metadata privacy architecture specified in §9.10: minimal outer envelope (§9.10.2), fixed bucket padding (§9.10.3), per-context pseudonyms (§9.10.4), persistent connections + TLS (§9.10.5), cover traffic configurable default-on (§9.10.6), DID resolution privacy (§9.10.7), relay query privacy via pseudonyms + partitioning (§9.10.8). Push notification opacity mandated in §10.7. Sender-side key layer for blocking specified in §9.16 with HPKE-wrapped per-recipient key distribution.
- **~~Verifiable event log format.~~** ✅ **Resolved.** ADR-011 specifies the event log: append-only Merkle tree per context, SHA-256 hash chain, entry structure (event type, sender DID, sequence number, timestamp, payload hash), inclusion proofs, consistency checkpoints. Efficient enough for device-as-node participation.
- **Behavioral record schema.** §7.3.2 defines what facts are derivable from event logs, but the record format is unspecified. How are behavioral records serialized, exchanged between agents, and verified against source logs? Must be compact enough for inline presentation and rich enough for meaningful evaluation. **Audit assessment (2026-03-01):** The `BehavioralRecord` type in `scp-core/trust/behavioral.rs` defines the internal representation: `total_messages`, `governance_proposals`, `governance_votes`, `tool_invocations`, `contexts_joined`, `contexts_left`, `violations`, `computed_at`. This is the working implementation. **Proposed resolution:** formalize as the wire format using MessagePack serialization (matching §17.5). Exchange via discovery contexts as a standard tool response. Verification: present Merkle inclusion proofs for the source events alongside the derived record. **Classification: P2, needs story — wire format and verification protocol.**
- **Challenge suite standards.** §7.3.4 introduces challenge-response verification for agent capabilities but doesn't define the challenge suites themselves. What tests constitute "prompt injection resistance"? Who defines and maintains challenge suites? How are custom challenges validated as fair? Need a registry or discovery mechanism. **Audit assessment (2026-03-01):** The `ChallengeProtocol` in `scp-core/trust/challenge.rs` implements the framework: challenge issuance, response verification, timeout. Challenge types are currently opaque (`ChallengeType` enum with `Custom(String)`). **Proposed approach:** community-maintained challenge registry published as a discovery context with standard tool schemas. Challenges are versioned tool invocations with expected outputs. Fairness validated by publishing challenge + expected output hash; verifier computes output independently. **Classification: P3, post-launch — framework exists, specific suites are ecosystem content.**
- **Consequence mechanism defaults.** §7.3.7 defines automated consequence rules but leaves threshold values and escalation curves to individual contexts. Should the protocol define recommended defaults? Minimum consequence severity for certain violations? How do contexts communicate their consequence structure in a comparable format? **Audit assessment (2026-03-01):** The `ConsequenceRule` type in `scp-core/trust/consequence.rs` implements the framework with configurable thresholds. Context templates already define governance defaults. **Proposed resolution:** include recommended defaults in well-known context templates (e.g., `general-discussion` template: 3 warnings before mute, auto-eject on 5 violations). Consequence structures are already visible in context parameters (§5.2 legibility principle). No protocol-level minimum severity needed — contexts are sovereign. **Classification: P3, template defaults — straightforward to add.**
- **Endorsement accuracy tracking.** §7.4.2 mentions that endorsement accuracy history pushes endorsements from Layer 4 toward Layer 2. How is accuracy measured? What constitutes a "bad endorsement" — the endorsed identity being ejected from a context? A governance action? This feedback loop needs design. **Audit assessment (2026-03-01):** Not yet implemented. The trust engine (`scp-core/trust/`) has attestation verification but no endorsement accuracy feedback loop. **Proposed approach:** track endorsed identity's behavioral record changes after endorsement. A "bad endorsement" is an endorsed identity that subsequently receives governance actions (role downgrade, ejection, violation recording) within N contexts within T time. Accuracy score = (endorsements where endorsed identity maintained good standing) / (total endorsements). **Classification: P2, needs story — feedback loop between behavioral records and attestation weight.**
- **~~Attestation storage and discovery.~~** ✅ **Partially resolved.** Forward discovery (DID → attestations) via discovery contexts (§6.2.2B) and DID document capability entries (§7.4.1). Reverse-lookup (external handle → DID) via `attestation_lookup` tool in discovery contexts (§22.5). Storage location question (DID documents vs relays vs dedicated layer) remains open for attestation data itself.
- **Threshold independence verification.** §7.3.5 says the protocol can check attestor independence via shared memberships and mutual endorsements. The specific independence metric and correlation thresholds need definition. **Audit assessment (2026-03-01):** Not yet implemented. The trust aggregation module (`scp-core/trust/aggregate.rs`) counts attestations but does not compute independence scores. **Proposed approach:** independence score = 1 - (shared_context_count / total_context_count) between attestor pairs. Two attestors sharing >50% of contexts are considered correlated. Require >=2 independent attestors (correlation < 0.5) for Layer 2 trust. **Classification: P2, needs story — correlation computation and threshold enforcement.**
- **~~Identity private state size constraints.~~** ✅ **Resolved.** Less constrained than context state. Single-owner case allows growth. Relays MAY enforce per-DID storage quotas. See §3.7.
- **~~Identity private state relay obligations.~~** ✅ **Resolved.** Same storage class and retention as context events. No differentiated commitment. See §3.7.
- **~~Identity key rotation and private state re-encryption.~~** ✅ **Resolved.** §9.12 specifies the 6-step ordered compromise recovery protocol including private state re-encryption. §9.7.4 covers key rotation triggers. Single-owner case is straightforward — no group redistribution needed. See §3.7.
- **~~Identity private state discovery pointer.~~** ✅ **Resolved.** Explicit service endpoint of type `IdentityPrivateState` in DID document. See §3.7.

## Context Lifecycle and Governance

- **Memory scope enforcement boundary.** Ephemeral key destruction is protocol-enforceable. Local agent memory is not. The spec acknowledges this (§5.11), but the boundary between "protocol can enforce" and "protocol can only signal" needs precise documentation for implementers. (§9.15 specifies the three trust levels for key destruction verification — hardware-attested, software-only, no attestation — which partially addresses this, but the agent-side memory boundary remains unspecified.) **Audit assessment (2026-03-01):** §9.15 and the key destruction implementation in `scp-core/context/key_destruction.rs` (SCP-067, done) handle the protocol-enforceable boundary. The agent-side memory boundary is fundamentally non-enforceable by the protocol — this is a documented limitation, not a design gap. **Proposed resolution:** add a section to §5.11 explicitly documenting the enforcement boundary: "The protocol guarantees key destruction (verified via device attestation when available). The protocol CANNOT guarantee that agent-side application memory (RAG databases, conversation logs, learned preferences) is destroyed. Context parameters SHOULD declare which memory scopes the context requires, and agents SHOULD honor them, but compliance is trust-based above the key destruction layer." **Classification: P2, documentation — clarify the enforcement boundary.**
- **~~Context promotion mechanics.~~** ✅ **Resolved.** Promotion policy declared at context creation (`no_promotion` or `promotable`). Policy itself is immutable. Default for ephemeral templates is `no_promotion`. See §5.10.
- **Summary generation mechanics.** For summary memory scope (§5.11): how is the summary produced? Who generates it — the context's tools, the participants collaboratively, or the protocol? What happens if participants disagree on the summary? What's the verification window before keys are destroyed? **Audit assessment (2026-03-01):** Not yet implemented. `scp-core/context/close.rs` (SCP-069, done) handles close orchestration with summary verification but the summary generation mechanism is not specified. **Proposed approach:** (1) Summary generated by the closing party's agent using context history. (2) Summary published as a governance proposal; other members approve/reject via the context's governance model. (3) Verification window = context TTL extension (configurable, default 24 hours). (4) On approval, summary is signed by all approving members and stored; keys are destroyed. On rejection or timeout, close is aborted or summary is revised. **Classification: P2, needs story and spec section addition.**

## Crypto and Security

- **~~Offline member MLS re-sync.~~** ✅ **Resolved.** ADR-029 (`.docs/adrs/phase-6.md`) specifies the full three-tier offline strategy: Tier 1 (hours — relay buffering + MLS catch-up), Tier 2 (days — state snapshot + delta sync), Tier 3 (weeks — forced re-join with group state reset). Trigger conditions, initiation protocol, and context lifecycle during reset are fully specified. Implemented in `crates/scp-core/src/sync/` (SCP-121 through SCP-124).
- **Commit delivery assurance under adversarial relays.** Relays can suppress MLS Commits. Spec says "publish to all relays with delivery confirmation" but: (1) "delivery confirmation" semantics are undefined (ACK from relay? from recipients?), (2) recovery mechanism for split-brain state (some members got the Commit, some didn't) is unspecified. **Proposed resolution (audit 2026-03-01):** §9.9.4 already specifies the mitigation: members behind on epochs request missing Commits from other members or relays. The Relay Consistency Protocol (§9.9.3) detects divergence via Merkle root comparison. Delivery confirmation should be relay ACK (not recipient ACK — recipients are offline). Recovery: epoch catch-up protocol (ADR-029 Tier 1) already handles missed Commits. **Remaining gap:** No specification of the "request missing Commit from other members" mechanism — needs a peer-to-peer Commit fetch protocol. **Blocking info needed:** define the CommitRequest/CommitResponse wire types and their routing (direct member-to-member via relay, or via a separate side-channel).
- **Pseudonym rotation and traffic analysis resistance.** Pseudonym derivation in `envelope/pseudonym.rs` is `HMAC-SHA256(identity_key_material, context_id || "scp-pseudonym")` — deterministic, never rotated. The relay sees `routing_id` and `recipient_hint` on every envelope. `deliver_to_subscribers` delivers blobs by `routing_id` with no delay or batching, making timing correlation trivial. Cross-relay fanout sends identical envelopes simultaneously. **(BLACK-001, [#17](https://github.com/limn-works/scp/issues/17)).** Requires: (1) pseudonym rotation mechanism — periodic re-derivation with epoch or nonce so the same identity presents different `routing_id` values over time, with a transition protocol so messages during rotation aren't lost; (2) delivery batching/delay to break timing correlation at the relay; (3) cross-relay fanout decorrelation (jitter, different envelope padding per relay). §9.10.4 specifies per-context pseudonyms but assumes they're static. §9.10.6 specifies cover traffic but doesn't address pseudonym linkability. Classification: P2 defense-in-depth. Found in [PR #4 Pass 4](https://github.com/limn-works/scp/pull/4#issuecomment-3955926987), verified in [threat verification](https://github.com/limn-works/scp/pull/4#issuecomment-3956679058). **Audit assessment (2026-03-01):** Cover traffic (SCP-225, pending) partially addresses timing correlation. **Proposed approach for pseudonym rotation:** derive `routing_id = HMAC-SHA256(key_material, context_id || epoch_counter || "scp-pseudonym")` where `epoch_counter` increments on MLS epoch changes. During rotation, subscribe to both old and new pseudonyms for a grace period (matching the sender key 30s grace period pattern). Relay sees subscription churn but cannot link old/new pseudonyms without the key material. **Blocking info needed:** (1) grace period duration, (2) relay SUBSCRIBE/UNSUBSCRIBE atomicity, (3) cross-relay fanout jitter parameters. **Classification: P2 defense-in-depth.**
- **Cover traffic parameters.** Constant-rate cover traffic is mandatory on persistent connections (Decision 8). Suggested rate: 1 message per 30 seconds. Not finalized. Dummy message format specified (single-byte flag inside encrypted payload) but relay-side distinguishability analysis is incomplete. **Proposed resolution (audit 2026-03-01):** SCP-225 (pending) covers cover traffic generation and heartbeat messages. Proposed defaults: 1 cover message per 30 seconds (matching spec suggestion), fixed-bucket padded to same size as real messages. Relay-side indistinguishability guaranteed by outer envelope uniformity (§9.10.2 — relay sees only `routing_id + encrypted_blob`; cover traffic and real messages are identical at this layer). **Classification: P2, covered by SCP-225.**
- **Compromise recovery orchestration.** §9.12 lists 6 recovery steps but does not specify ordering constraints, atomicity guarantees, or partial failure handling (e.g., if MLS Update fails in one context but succeeds in others). **Proposed resolution (audit 2026-03-01):** The 6 steps have implicit ordering (key rotation must precede MLS Update; UCAN revocation must precede new UCAN issuance). Propose: (1) steps are strictly ordered (no parallelism); (2) partial failure is tolerated — each context's MLS Update is independent, and failure in one context does not block others; (3) failed contexts are retried with exponential backoff; (4) a `CompromiseRecoveryState` type tracks per-context progress. **Blocking info needed:** none — this is a straightforward engineering story. **Classification: P1, needs story.**
- **~~UCAN revocation mechanism.~~** ✅ **Resolved.** ADR-016 (`.docs/adrs/phase-3.md`) fully specifies: (1) **List format:** per-context `RevocationList` — `HashMap<String, RevocationState>` mapping token CIDs to `Active`/`RevocationPending`/`Revoked` states. (2) **Check frequency:** every UCAN validation checks the revocation list (step 10 of the 11-step pipeline). (3) **Behavior on failure:** fail-closed — both `RevocationPending` and `Revoked` states deny capability exercise; MLS distribution failure triggers local rollback (transactional). Revocations distributed as MLS application messages; all members merge incoming lists (set union, append-only). Implemented in `crates/scp-core/src/crypto/ucan/revoke.rs`. SCP-055 (done).

## Tools and Verification

- **Tool integrity verification execution.** §5.4 requires "deterministic testing" of tools but does not specify: who runs tests, execution environment, what constitutes pass/fail, how many agents must verify. **Audit assessment (2026-03-01):** The `ToolRegistry` in `scp-core/context/tools/registry.rs` stores test vectors per tool. Test vector verification infrastructure exists but the execution policy is unspecified. **Proposed approach:** (1) Test vectors are JSON input/output pairs stored in tool registration metadata. (2) Any context member MAY run test vectors on tool registration; results are recorded in the event log. (3) Pass = output matches expected output (JSON deep equality). Fail = output differs or tool errors. (4) The registering member MUST run test vectors before registration (self-verification). (5) Other members MAY re-verify (opportunistic, not mandatory). **Classification: P2, needs spec clarification in §5.4.**
