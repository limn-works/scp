# Open Questions

## Design Decisions Pending

- **~~Context capability ceiling mutability.~~** ✅ **Resolved.** Ceiling policy declared at context creation (`immutable` or `governed`). Policy itself is immutable. Default for all well-known templates is `immutable`. See §5.3.
- **~~Context governance primitives.~~** ✅ **Resolved.** ADR-008 specifies context lifecycle state machine with single-admin governance. ADR-009 specifies role assignment and capability ceiling enforcement. ADR-031 specifies multi-admin governance models. Fully implemented: `GovernanceEngine` trait with `SingleAdminEngine`, `ThresholdEngine` (M-of-N threshold), `MajorityVoteEngine`, and `UnanimityEngine` models; `GovernanceModelConfig` enum with `SingleAdmin`, `Threshold`, `Majority`, and `Unanimity` variants (SCP-129 through SCP-133, all done). Proposal interaction with MLS epochs handled by SCP-133 (done).
- **~~Direct agent-to-agent negotiation primitive.~~** ✅ **Resolved (rejected).** Considered and rejected. The protocol does not and will not include a mechanism for agents to contact agents they share no context with. Cross-context interaction uses tool interfaces (§6.2) for asymmetric service calls, multi-parent child contexts (§5.13) for symmetric collaboration, and standing bilateral contexts (§5.12.6) for persistent direct communication. All three require existing context membership or human facilitation. This is intentional: context isolation is the security boundary, and any mechanism that lets agents bypass it reintroduces the attack surface isolation was designed to eliminate. See planning-session-06.md §2 for the full analysis.
- **~~Context-to-context tool interface mechanics.~~** ✅ **Resolved.** §6.2 specifies bidirectional consent, schema constraints, rate limits, chain depth limits. §6.2.1 specifies stateful sessions with optional TTL and per-caller cap. §6.2.2 specifies discovery via DID document capabilities and discovery contexts with standard tool schemas.
- **~~Sybil resistance enforcement.~~** ✅ **Resolved.** The protocol provides the mechanism; scoring is not protocol-level. **Protocol responsibilities (P0 — wire before launch):** (1) DID creation calls `DeviceAttestation::attest()` when the platform supports it (optional, platform-gated). (2) Attestation proof is stored in the DID document as a service entry. (3) `DeviceAttestation` is exposed through FFI so SDK consumers can attest and verify. (4) Contexts MAY require device attestation for admission via `ContextParams` admission requirements. **What the protocol does NOT prescribe (by design):** Scoring algorithms, earned capacity formulas, weighting, or cross-DID correlation. The protocol carries attestation proofs as verifiable data — participants interpret that data however they choose. Same pattern as participation records: protocol provides facts, not interpretations. Earned capacity scoring is a product-layer concern (potential Limn offering), not a protocol-level specification. This preserves the tenet: "Protocol requires no operator." **Implementation:** `DeviceAttestation` trait in `scp-platform::traits` (attest/verify), Android adapter in `scp-platform::android`, context admission requirements in `ContextParams`. Cross-DID blocking is a natural consequence: same device attestation = same physical device = linkable if the verifier chooses. See BLACK-006, [#22](https://github.com/limn-works/scp/issues/22). **Sub-gap tracking:** [#399](https://github.com/limn-works/scp/issues/399) (proof-of-personhood), [#400](https://github.com/limn-works/scp/issues/400) (identity creation rate limiting), [#401](https://github.com/limn-works/scp/issues/401) (reputation decay).
- **~~Agent capability metadata standard.~~** ✅ **Resolved.** ADR-041 specifies the full URI namespace and protocol registry. Three authorities: `scp:capability:{kebab-case}/v{N}` (protocol-defined, reserved, SDK-enforced), `did:{method}:{id}:capability:{kebab-case}/v{N}` (DID-scoped custom), `scp:system:{kebab-case}` (protocol feature flags). Initial protocol registry: 28 challenge capabilities across 10 categories + 5 system capabilities. Anti-spoofing: SDKs reject unknown `scp:capability:*` URIs; DID-scoped capabilities derive authority from the definer's identity; `ChallengeVerification` records distinguish self-attested from challenge-verified. §4.4 specifies the two-tier structure (self-attested vs challenge-verified). §7.3.4 specifies the URI format and registry reference. §7.4.1 defines the `agent_capability` attestation type.
- **~~Content provenance system.~~** ✅ **Resolved.** DataProvenance format specified in §7.7.1. Provenance attached automatically by protocol on context boundary crossings. Provenance evaluation rules in §7.7.2. Absence-as-signal principle established. Cross-context tool calls and structured messages carry provenance. Dedicated spec section: §24 (provenance system architecture, types, attachment model, quality evaluation, chain depth enforcement).
- **~~Rate limiting defaults.~~** ✅ **Resolved.** Context creation limits, context participation limits per human. Participation rate limiting surfaces identified. Economic rate limiting fully specified in §19.7 — cost escalation via `SenderVelocity` metric provides complementary spam prevention alongside participation rate limits (§9.2). Default values are context-template-specific (not protocol-level), which is the correct design — contexts are sovereign. Audit 2026-03-01: promoted from partial to resolved.
- **~~Identity attestation discovery.~~** ✅ **Resolved.** Attestations are discoverable through discovery contexts (§6.2.2B) and DID document capability entries (§7.4.1). Platform-specific contexts and bridges surface attestation data alongside their own data, eliminating the need for separate discovery infrastructure.
- **~~Agent verification method (`#agent` VM).~~** ✅ **Resolved.** ADR-039 specifies the shared-DID human-agent identity model: human and agent share one DID with three verification methods — `#0` (Identity Key), `#active` (Human Signing Key), `#agent` (Agent Signing Key, optional). Both `#active` and `#agent` are valid operational signing keys for Category B actions (messages, tool calls, governance proposals). Category A actions (DID document modifications, KeyPackage signing) require `#0` only. Self-delegation UCANs use `iss == aud` with `fct.scp_key_scope: "#agent"` to scope capabilities to the agent key. Agent key rotation uses a simpler model than pre-rotation (software key, not hardware-bound). Accountability is structural: agent actions trace to the human's DID because they share it.
- **~~Identity attestation verification methods.~~** ✅ **Resolved.** §3.5 and §7.4.2 specify platform-specific verification flows: OAuth, DNS records, signed posts. Verification is decentralized — each attestation type carries its own verification method.
- **~~Shadow identity role defaults.~~** ✅ **Resolved.** Observer role by default with restricted capabilities (§12.3). Context governance can override defaults for specific bridges.
- **~~Bridge connector interface specification.~~** ✅ **Resolved.** §12.10 specifies the Cooperative Mode HTTP Binding — a six-endpoint REST API that cooperating platforms implement. Endpoints: shadow creation (`POST /v1/scp/bridge/shadow`), message emission (`POST /v1/scp/bridge/message`), identity attestation (`POST /v1/scp/bridge/attest`), bridge status (`GET /v1/scp/bridge/status`), shadow deletion (`DELETE /v1/scp/bridge/shadow/{shadow_id}`), and platform webhook receiver (`POST /v1/scp/bridge/webhook`). Authentication via DID-signed bearer tokens. JSON over HTTPS with TLS 1.3. Versioned under `/v1/` prefix. Error format, rate limiting, idempotency semantics, and webhook delivery guarantees all specified. Maps directly to existing `scp-core/bridge/` operations. See §12.10.
- **~~Bridge credential custody.~~** ✅ **Resolved (out of protocol scope).** Credential custody is intentionally platform-specific and cannot be specified at the protocol level. The protocol provides the trust framework: operator accountability via DID (§12.2), self-hosting option eliminating third-party credential delegation (§12.7), revocability via context governance (§12.2), and transparency of bridge presence and operator identity to all context members. Credential mechanics (OAuth tokens, API keys, session cookies) vary by platform and authentication model. The cooperative mode HTTP binding (§12.10) eliminates credential delegation entirely — the platform authenticates the bridge operator via DID-signed tokens, and the bridge authenticates to the platform via the platform's own authentication system. No SCP-level credential custody specification is needed or appropriate.
- **~~Shadow identity claiming mechanics.~~** ✅ **Resolved.** §12.3 specifies claiming flow: claimant presents identity attestation matching shadow's platform handle, shadow is retired, historical actions retroactively attributed to claimant DID. API specified in .docs/sketch.md (`Bridge.claimShadow`).
- **~~Capability declaration format.~~** ✅ **Resolved.** §8.4 specifies the capability declaration contract: declarative (apps say what they need), validated against ceiling + role, machine-readable and self-documenting, versionable. §8.5 establishes that SCP tool schemas use MCP-compatible JSON Schema — "SCP tool definitions should be a superset of MCP tool definitions, adding SCP-specific metadata (context scope, capability requirements, provenance) while keeping the core schema MCP-compatible." This answers the format question: **JSON Schema (MCP-compatible)**, with SCP-specific extensions. The declaration lists required capabilities as resource URIs (`scp:ctx:{context_id}/{capability}`) matching the UCAN attenuation format (ADR-016 criterion 1). LLMs generating apps parse the same JSON Schema format they already understand from MCP.
- **~~Context state portability format.~~** ✅ **Resolved.** Export format: `ContextExport` = `ContextSnapshot` (membership, roles, governance, TTL, broadcast) + full event log + opaque `mls_state: Vec<u8>` (filled when MLS integration lands, #333). Serialized as MessagePack with `StoredValue<T>` version envelopes (§17.5). Import verifies Merkle root matches event log. See [#363](https://github.com/limn-works/scp/issues/363) for implementation.
- **~~Minimum viable agent specification.~~** ✅ **Resolved.** The minimum viable agent is an MCP server/client that translates between the model and the SCP SDK. The SDK handles all protocol mechanics. §4.4-4.5 define the agent's role, §8.5 defines the integration surface (MCP compatibility). Reference implementation is an SDK deliverable tracked at [#364](https://github.com/limn-works/scp/issues/364).
- **~~Relay protocol specification.~~** ✅ **Resolved.** ADR-004 specifies the SCP native relay protocol: PUBLISH/SUBSCRIBE/UNSUBSCRIBE operations over WebSocket, blob TTL enforcement, recipient_hint for directed delivery. Minimal outer envelope format specified in §9.10.2.
- **~~Cooperative mode trust tiers.~~** ✅ **Resolved.** §12.5 specifies a four-tier trust hierarchy with two independent axes (identity confidence x transport confidence). The tiers explicitly define the trust differential: (1) Native SCP identity + native action = strongest. (2) Native SCP identity + bridged action = strong (identity verified via DID, transport via bridge infrastructure). (3) Claimed shadow + historical bridged = moderate (retroactive DID link, pre-claim content). (4) Shadow identity + bridged action = weakest (no DID claim, trust depends entirely on bridge operator). §12.9 specifies the incentive: "bridged-cooperative is more trusted than bridged-relay because the platform has vouched for the attribution." Cooperative mode gives the platform a "seat" — influence over how its users are perceived in SCP. Non-cooperation means relay/puppet mode scraping with weaker provenance. The trust differential IS the incentive — platforms that implement cooperative mode get their users perceived at tier 2 instead of tier 4.
- **~~Primary transport binding.~~** ✅ **Resolved.** SCP native relay protocol is the canonical transport. Transport is fully abstracted — 17 adapter options listed, no structural dependency on any single transport. Transport security requirements specified in §9.13 (TLS 1.3 required). Relay threat model formalized in §9.9.
- **~~Transport abstraction interface.~~** ✅ **Resolved.** ADR-005 specifies the `TransportAdapter` trait: send, subscribe, unsubscribe, query, delete. Async interface, error types defined. SCP native relay is the canonical implementation.
- **~~Context key management.~~** ✅ **Resolved.** MLS (RFC 9420) selected. One MLS group per context. MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519 ciphersuite. Full specification in §9.7 (group key management), §9.5 (cryptographic primitives), §9.8 (message security). MLS tree-based key management provides O(log N) member exclusion. Blocking uses a separate sender-side key layer (§9.16) that operates independently of MLS epoch advancement.
- **~~Metadata privacy.~~** ✅ **Fully resolved.** Comprehensive metadata privacy architecture specified in §9.10: minimal outer envelope (§9.10.2), fixed bucket padding (§9.10.3), per-context pseudonyms (§9.10.4), persistent connections + TLS (§9.10.5), cover traffic configurable default-on (§9.10.6), DID resolution privacy (§9.10.7), relay query privacy via pseudonyms + partitioning (§9.10.8). Push notification opacity mandated in §10.7. Sender-side key layer for blocking specified in §9.16 with HPKE-wrapped per-recipient key distribution.
- **~~Verifiable event log format.~~** ✅ **Resolved.** ADR-011 specifies the event log: append-only Merkle tree per context, SHA-256 hash chain, entry structure (event type, sender DID, sequence number, timestamp, payload hash), inclusion proofs, consistency checkpoints. Efficient enough for device-as-node participation.
- **~~Participation record schema.~~** ✅ **Resolved.** The schema is implemented: `ParticipationRecord` struct with 12 fields (`subject_did`, `context_id`, `participation_count`, `participation_duration_seconds`, `tool_invocations`, `governance_actions_by`, `governance_actions_against`, `role_history`, `attestation_history`, `context_creation_count`, `computed_at`, `event_log_root`) in `crates/scp-core/src/trust/participation.rs`. `compute_participation_record()` is pure computation from event log slices — no side effects, no storage. Serialization uses `serde::Serialize`/`Deserialize` (MessagePack per §17.5 for wire format, JSON for debugging). Merkle root captured at computation time enables verification. **Governance-enforceable admission requirements** use the same pattern as capability requirements (§7.3.4.4): `RequireParticipation` in `ContextParams` admission requirements specifies fact category, threshold, freshness, and minimum independent contexts. **Participation admission model:** context-hosted signed participation statements (`ParticipationProfile`). Core invariant: agents CANNOT write, modify, or delete their own statements — contexts produce and host them on source context relays. Each `ParticipationProfile` is a full participation profile containing all 7 fact categories (participation duration, governance actions against/by, tool invocations, context creation, role progression, attestations), one statement per member per context, mutated in place when facts change. Agents opt in by allowing contexts to publish statements about them. Agent's DID document lists a `ParticipationStatements` service endpoint for discovery. Admitting contexts fetch statements from the service endpoint, verify Ed25519 signatures from distinct context-specific signers, and evaluate against admission requirements. Statements omit `context_id` — the admitting context cannot identify source contexts. See §7.3.2.1.
- **~~Challenge suite standards.~~** ✅ **Resolved.** ADR-041 specifies the URI namespace, protocol registry, and initial vocabulary. §7.3.4 updated with URI format specification and registry reference. **Registry structure:** 28 protocol-defined challenge capabilities (`scp:capability:*/v1`) across 10 categories (safety, schema compliance, behavioral compliance, operational, spending, reasoning, code, recall, bias, factual). DID-scoped custom capabilities (`did:{method}:{id}:capability:*/v{N}`) enable ecosystem extension without protocol changes. **Versioning:** `/v{N}` suffix enables breaking changes to challenge suites without invalidating existing verifications. **Anti-gaming and fairness:** remain implementation concerns for individual challenge suite definitions — the protocol provides the namespace, verification, and anti-spoofing infrastructure. Concrete test vectors for each standard suite are implementation deliverables, not spec concerns. **What remains unspecified (acceptable):** Concrete test cases for each standard suite; anti-gaming measures for individual suites. These are necessarily iterative — suites evolve with the ecosystem.
- **~~Consequence mechanism defaults.~~** ✅ **Resolved.** Intentionally left to contexts. The protocol provides the mechanism (§7.3.7: automated rules declared at context creation, protocol-enforced, verifiable). §19.7 adds economic consequences via `SenderVelocity`. Specific thresholds and escalation curves are context-defined — different context types need radically different values. Well-known templates (§5.12) serve as de facto defaults for their use cases.
- **~~Endorsement accuracy tracking.~~** ✅ **Resolved.** Endorsement accuracy is a derivable computation from existing protocol data — cross-reference `AttestationType::Endorsement` attestations with the endorsed agent's `ParticipationProfile` (specifically `governance_actions_against`). No new protocol machinery needed. The protocol provides attestations (subjective claims) and participation profiles (objective facts). Correlation is computable by any agent. Scoring is client policy.
- **~~Attestation storage and discovery.~~** ✅ **Resolved.** Multi-layer storage by design: `TrustProtocolRepository` trait for local cache with TTL-based refresh (`trust/aggregate.rs`), DID documents for discovery pointers (capability entries §7.4.1), relays for published attestation blobs. Forward discovery via discovery contexts (§6.2.2B) and DID doc entries. Reverse-lookup via `attestation_lookup` tool (§22.5). Production `TrustProtocolRepository` implementation tracked under #329.
- **~~Threshold independence verification.~~** ✅ **Resolved.** All four sub-questions answered by existing implementation in `trust/attestation.rs`. (1) **Graduated**, not binary — independence is a 0.0–1.0 score, not a boolean. (2) **Configurable** — `ThresholdRequirement` carries `shared_context_penalty` (default 0.1, capped at `shared_context_penalty_cap` default 0.5), `mutual_endorsement_penalty` (default 0.2), and `independence_threshold` (context-configurable minimum). Contexts tune penalty weights for their trust requirements. (3) **Transitive correlation deferred** — direct correlation (shared memberships, mutual endorsements) catches the meaningful cases. Transitive checking is O(N²) and doesn't catch sophisticated attackers who avoid shared intermediaries. The real defense against coordinated attestation fraud is device attestation + participation profiles, not graph analysis. (4) **Local computation** — the evaluating agent computes independence from its own view of attestor data. No oracle.
- **~~Identity private state size constraints.~~** ✅ **Resolved.** Less constrained than context state. Single-owner case allows growth. Relays MAY enforce per-DID storage quotas. See §3.7.
- **~~Identity private state relay obligations.~~** ✅ **Resolved.** Same storage class and retention as context events. No differentiated commitment. See §3.7.
- **~~Identity key rotation and private state re-encryption.~~** ✅ **Resolved.** §9.12 specifies the 6-step ordered compromise recovery protocol including private state re-encryption. §9.7.4 covers key rotation triggers. Single-owner case is straightforward — no group redistribution needed. See §3.7.
- **~~Identity private state discovery pointer.~~** ✅ **Resolved.** Explicit service endpoint of type `IdentityPrivateState` in DID document. See §3.7.

## Context Lifecycle and Governance

- **~~Memory scope enforcement boundary.~~** ✅ **Resolved.** The boundary is now precisely specified across three sections. §5.11 ("Enforcement honesty") explicitly states: "The protocol enforces memory scope through cryptographic key destruction — specifically, MLS group state destruction (tree secrets, all epoch key schedules, application key material). This is verifiable and absolute for protocol-level data. [...] However, the protocol cannot enforce memory scope above the protocol boundary. An agent's underlying model may retain information from an ephemeral interaction in its own memory." §9.15 specifies the three trust levels for key destruction verification: hardware-attested (Secure Enclave/Keystore), software-only (`memset(0)`), no attestation (member offline). The `KeyDestructionAttestation` struct is fully defined. §7.7 provides the provenance defense: data an agent reproduces from memory without protocol-level origin carries no provenance — "the absence of provenance is itself a signal." **The enforcement boundary is:** protocol-level data (MLS keys, ciphertext) = enforceable via destruction; agent-local memory = not enforceable, mitigated by provenance-absence signals. This is explicitly documented for implementers in §5.11's "Enforcement honesty" paragraph.
- **~~Context promotion mechanics.~~** ✅ **Resolved.** Promotion policy declared at context creation (`no_promotion` or `promotable`). Policy itself is immutable. Default for ephemeral templates is `no_promotion`. See §5.10.
- **~~Summary generation mechanics.~~** ✅ **Resolved.** Protocol provides lifecycle hooks: `SummaryVerificationWindow` (default 300s, configurable), verification/dispute actions, key destruction after window closes. (1) **Verification window duration:** `DEFAULT_VERIFICATION_WINDOW_SECS = 300`, configurable per context. (2) **Dispute resolution:** context governance decides — SingleAdmin: admin decides; Threshold/Majority/Unanimity: vote on acceptance. Configurable policy for incomplete verification (proceed vs extend). (3) **Summary content:** defined by context governance/tools, not protocol. Default summary tool is an SDK deliverable. Implementation tracked at [#365](https://github.com/limn-works/scp/issues/365).

## Crypto and Security

- **~~Offline member MLS re-sync.~~** ✅ **Resolved.** ADR-029 (`.docs/adrs/phase-6.md`) specifies the full three-tier offline strategy: Tier 1 (hours — relay buffering + MLS catch-up), Tier 2 (days — state snapshot + delta sync), Tier 3 (weeks — forced re-join with group state reset). Trigger conditions, initiation protocol, and context lifecycle during reset are fully specified. Implemented in `crates/scp-core/src/sync/` (SCP-121 through SCP-124). Dedicated spec section: §23 (sync architecture, tier definitions, reconnection protocol, conflict resolution, MLS group rebuild).
- **~~Commit delivery assurance under adversarial relays.~~** ✅ **Resolved.** §9.9.4 now explicitly defines "delivery confirmation" as relay-level storage ACK (the relay confirms it received and stored the blob), not recipient-level ACK (which would leak metadata). The actual assurance mechanism is the recovery path: epoch-behind detection triggers Commit requests from peers or alternate relays. **Full specification:** §9.9.2 specifies multi-relay cross-check (publish to at least 2, recommended 3 relays) with a 30-second inconsistency timeout. §9.9.3 specifies the Relay Consistency Protocol (signed checkpoints every 50 events or 10 minutes) for detecting equivocation. §9.9.2 also specifies 60-second heartbeats for suppression detection.
- **~~Pseudonym rotation and traffic analysis resistance.~~** ✅ **Resolved.** **(BLACK-001, [#17](https://github.com/limn-works/scp/issues/17)).** Three protocol-level mitigations: (1) Pseudonym rotation via `derive_rotatable_pseudonym` with dual-subscription grace period (§9.10.4.1). (2) Relay delivery jitter (§9.10.10). (3) Residual risks documented (§9.10.11). Cross-relay fanout decorrelation is a client-side SDK concern — per-relay jitter in multi-relay publish path. Implementation tracked at [#366](https://github.com/limn-works/scp/issues/366).
- **~~Cover traffic parameters.~~** ✅ **Resolved.** §9.10.6 fully specifies all parameters: (1) rate: one padded message per relay connection per 30 seconds; (2) scope: per relay connection, not per context — prevents relay from correlating traffic rate changes with context activity; (3) format: single-byte flag inside encrypted payload distinguishes real from dummy; recipients decrypt, check flag, discard dummies; (4) bandwidth: ~15MB/day for 5 relay connections at 1KB padding; (5) configurability: enabled by default, configurable per-client via SDK configuration; disabling degrades traffic analysis resistance but has no functional impact; (6) push-wake connections: no cover traffic (connection is transient). The relay-side distinguishability concern is addressed by design: the single-byte flag is inside the encrypted payload, so relays cannot distinguish real from dummy messages. The only residual risk is statistical timing analysis against the constant rate (acknowledged in §9.10.11).
- **~~Compromise recovery orchestration.~~** ✅ **Resolved.** §9.12 specifies 6 ordered steps with an explicit "Step ordering and failure isolation" paragraph. Ordering: key rotation (1) before MLS Updates (2) before UCAN revocation (3) before KeyPackage rotation (4); steps 5-6 are cleanup, order-independent. Steps 2-4 are per-context with independent retry; failure in one context does not block others. Contexts where MLS Update cannot succeed are flagged for manual re-join (Tier 3 per ADR-029).
- **~~UCAN revocation mechanism.~~** ✅ **Resolved.** Fully specified across ADR-016 acceptance criteria 5 and 7, and implemented in `crates/scp-core/src/crypto/ucan/revoke.rs`. **List format:** Per-context `RevocationList` — a `HashMap<String, RevocationState>` mapping token CIDs to one of three states: `Active` (default, not stored), `RevocationPending` (fail-closed — capability denied while MLS distribution is in flight), `Revoked` (fully committed). Append-only with `merge()` for MLS-distributed synchronization. **Check frequency:** Every action — step 10 of the 11-step `validate_ucan` pipeline (ADR-016 criterion 2) checks the revocation list. No periodic polling; revocation is checked inline on every capability exercise. **Behavior on failure:** Fail-closed. `RevocationPending` state denies capability exercise even before MLS confirmation. If MLS distribution of the revocation fails, the local revocation is rolled back (transactional) so there is no split-brain between the revoker and other members. Network errors during revocation distribution result in rollback to `Active` — the revoker must retry. Revocations are distributed as MLS application messages; `TokenRevoked` events are appended to the context's event log. See `RevocationDistributor` and `RevocationEventLogger` traits in `revoke.rs`.

## Tools and Verification

- **~~Tool integrity verification execution.~~** ✅ **Resolved.** §7.3.3 specifies the full verification model: decentralized (any agent verifies), test vectors at registration, schema+semantic pass/fail (not exact match), threshold confidence via independent verification, continuous validation, mutation detection via Merkle log. Execution environment isolation is not a protocol concern — verification is behavioral (expected outputs), not environmental (sandbox). SDK implementation tracked at [#367](https://github.com/limn-works/scp/issues/367).
