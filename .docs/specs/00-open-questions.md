# Open Questions

## Design Decisions Pending

- **~~Context capability ceiling mutability.~~** ✅ **Resolved.** Ceiling policy declared at context creation (`immutable` or `governed`). Policy itself is immutable. Default for all well-known templates is `immutable`. See §5.3.
- **~~Context governance primitives.~~** ✅ **Resolved.** ADR-008 specifies context lifecycle state machine with single-admin governance. ADR-009 specifies role assignment and capability ceiling enforcement. ADR-031 specifies multi-admin governance models. Fully implemented: `GovernanceEngine` trait with `SingleAdminEngine`, `ThresholdEngine` (M-of-N threshold), `MajorityVoteEngine`, and `UnanimityEngine` models; `GovernanceModelConfig` enum with `SingleAdmin`, `Threshold`, `Majority`, and `Unanimity` variants (SCP-129 through SCP-133, all done). Proposal interaction with MLS epochs handled by SCP-133 (done).
- **~~Direct agent-to-agent negotiation primitive.~~** ✅ **Resolved (rejected).** Considered and rejected. The protocol does not and will not include a mechanism for agents to contact agents they share no context with. Cross-context interaction uses outlet interfaces (§6.2) for asymmetric service calls, multi-parent child contexts (§5.13) for symmetric collaboration, and standing bilateral contexts (§5.12.6) for persistent direct communication. All three require existing context membership or human facilitation. This is intentional: context isolation is the security boundary, and any mechanism that lets agents bypass it reintroduces the attack surface isolation was designed to eliminate. See planning-session-06.md §2 for the full analysis.
- **~~Context-to-context outlet interface mechanics.~~** ✅ **Resolved.** §6.2 specifies bidirectional consent, schema constraints, rate limits, chain depth limits. §6.2.1 specifies stateful sessions with optional TTL and per-caller cap. §6.2.2 specifies discovery via service-record capability URIs and contexts equipped with standard outlet schemas.
- **~~Sybil resistance enforcement.~~** ✅ **Resolved.** The protocol provides the mechanism; scoring is not protocol-level. **Protocol responsibilities (P0 — wire before launch):** (1) The owner's SDK calls `DeviceAttestation::attest()` once for each context whose policy weights device attestation, when the platform supports it (optional, platform-gated). Identity creation attests nothing, because the binding digest `D` of `09-security-model.md` §9.3.1 covers a context id and that context's challenge (amended 2026-09-27). (2) The identity publishes the attestation as an `ScpDeviceAttestation` entry of its service record, which `#active` signs, and every reader verifies the entry offline under `09-security-model.md` §9.3.1 (amended 2026-09-27; this item previously called the proof its own signed object). No reader exists in the shipped code: story SCP-316, still pending, specifies the reader, and no code verifies a device attestation yet. (3) `DeviceAttestation` is exposed through FFI so SDK consumers can attest and verify. (4) Contexts MAY require device attestation for admission via `ContextParams` admission requirements. **What the protocol does NOT prescribe (by design):** Scoring algorithms, earned capacity formulas, weighting, or cross-DID correlation. The protocol carries attestation proofs as verifiable data — participants interpret that data however they choose. Same pattern as participation records: protocol provides facts, not interpretations. Earned capacity scoring is a product-layer concern (potential Limn offering), not a protocol-level specification. This preserves the tenet: "Protocol requires no operator." **Implementation:** the platform adapters in `scp-platform` mint the attestation, the reader is a pure function in `scp-protocol` (`09-security-model.md` §9.3.1, story SCP-316), the producer that publishes, renews and deletes entries is in `scp-runtime` (story SCP-317), and context admission requirements live in `ContextParams`. A device attestation proves neither a distinct device nor the same device: under `09-security-model.md` §9.3.1 a `Verified` outcome states that a genuine app on a device the platform recognizes produced the entry for this identifier and context, and it states nothing about which physical device, so two identifiers' entries show neither that one device nor that two devices produced them (amended 2026-09-27; this item previously claimed they did). See BLACK-006, [#22](https://github.com/limn-works/scp/issues/22). **Sub-gap tracking:** [#399](https://github.com/limn-works/scp/issues/399) (proof-of-personhood), [#400](https://github.com/limn-works/scp/issues/400) (identity creation rate limiting), [#401](https://github.com/limn-works/scp/issues/401) (reputation decay).
- **~~Agent capability metadata standard.~~** ✅ **Resolved.** ADR-041 specifies the full URI namespace and the protocol capability list. Three authorities: `scp:capability:{kebab-case}/v{N}` (protocol-defined, reserved, SDK-enforced), `{identifier}:capability:{kebab-case}/v{N}` (identifier-scoped custom, `03-identity.md` §3.1 text form), `scp:system:{kebab-case}` (protocol feature flags). Protocol capability list: 28 challenge capabilities across 10 categories + 4 system capabilities. Anti-spoofing: SDKs reject unknown `scp:capability:*` URIs; identifier-scoped capabilities derive authority from the definer's identity; `ChallengeVerification` records distinguish self-attested from challenge-verified. §4.4 specifies the two-tier structure (self-attested vs challenge-verified). §7.3.4 specifies the URI format and the protocol capability list. §7.4.1 defines the `agent_capability` attestation type.
- **~~Content provenance system.~~** ✅ **Resolved.** DataProvenance format specified in §7.7.1. Provenance attached automatically by protocol on context boundary crossings. Provenance evaluation rules in §7.7.2. Absence-as-signal principle established. Cross-context outlet calls and structured messages carry provenance. Dedicated spec section: §24 (provenance system architecture, types, attachment model, quality evaluation, chain depth enforcement).
- **~~Rate limiting defaults.~~** ✅ **Resolved.** Context creation limits, context participation limits per human. Participation rate limiting surfaces identified. Economic rate limiting fully specified in §19.7 — cost escalation via `SenderVelocity` metric provides complementary spam prevention alongside participation rate limits (§9.2). Default values are context-template-specific (not protocol-level), which is the correct design — contexts are sovereign. Audit 2026-03-01: promoted from partial to resolved.
- **~~Identity attestation discovery.~~** ✅ **Resolved.** Attestations are discoverable through contexts with discovery outlets (§6.2.2B [no such section]) and through the attestation-revocations pointer of the subject's service record (`03-identity.md` §3.10.13, §7.4.1). Platform-specific contexts surface attestation data alongside their own data, eliminating the need for separate discovery infrastructure.
- **Agent verification method.** **Reopened 2026-09-10.** The shared-DID model ADR-039 decided — one identity carrying a root key, a human signing key and an agent signing key — is overturned by ADR-063, the inception-derived key-event-log identity substrate, which supersedes ADR-039; ADR-064, cooperative delegation, is the record that writes the replacing model. An agent is now a separate identity whose establishment events the human's key-event log anchors. **What is open: how a controller produces that anchor, how a verifier fetches the delegator's chain and finds the seal, and how a verifier ranks a delegated chain.** Until that model is written, `09-security-model.md` §9.7.4.2 R3 makes `Invalid` every identifier whose inception names a nonzero `delegator`, and discards every later event that names one, so no delegated agent identity resolves.
- **~~Identity attestation verification methods.~~** ✅ **Resolved.** §3.5 and §7.4.2 specify platform-specific verification flows: OAuth, DNS records, signed posts. Verification is decentralized — each attestation type carries its own verification method.
- **~~Capability declaration format.~~** ✅ **Resolved.** §8.4 specifies the capability declaration contract: declarative (apps say what they need), validated against ceiling + role, machine-readable and self-documenting, versionable. §8.5 establishes that SCP outlet schemas use MCP-compatible JSON Schema — "SCP outlet definitions should be a superset of MCP tool definitions, adding SCP-specific metadata (context scope, capability requirements, provenance) while keeping the core schema MCP-compatible." This answers the format question: **JSON Schema (MCP-compatible)**, with SCP-specific extensions. The declaration lists required capabilities as resource URIs (`scp:ctx:{context_id}/{capability}`) matching the UCAN attenuation format (ADR-016 criterion 1). LLMs generating apps parse the same JSON Schema format they already understand from MCP.
- **~~Context state portability format.~~** ✅ **Resolved.** Export format: `ContextExport` = the signed `ContextSnapshot` (membership, roles, governance, TTL, broadcast) + full event log. Live MLS crypto state lives in the signed `mls_crypto_state` field on the persistence/restore path; the portable export path currently leaves it empty — whether portable export should include MLS crypto state is an open design decision (security tradeoff) tracked in [#1768](https://github.com/limn-works/scp/issues/1768). Serialized as MessagePack with `StoredValue<T>` version envelopes (§17.5). The whole snapshot is P-256-signed by the creator (§23.16.8, ADR-050); all importer-restored state — including MLS crypto state — lives inside that signed preimage, never in an unsigned envelope blob. Import verifies the signature and that the recomputed Merkle root matches the signed snapshot root. See [#363](https://github.com/limn-works/scp/issues/363) for implementation.
- **~~Minimum viable agent specification.~~** ✅ **Resolved.** The minimum viable agent is an MCP server/client that translates between the model and the SCP SDK. The SDK handles all protocol mechanics. §4.4-4.5 define the agent's role, §8.5 defines the integration surface (MCP compatibility). Reference implementation is an SDK deliverable tracked at [#364](https://github.com/limn-works/scp/issues/364).
- **~~Relay protocol specification.~~** ✅ **Resolved.** ADR-004 specifies the SCP native relay protocol: PUBLISH/SUBSCRIBE/UNSUBSCRIBE operations over WebSocket, blob TTL enforcement, recipient_hint for directed delivery. Minimal outer envelope format specified in §9.10.2.
- **~~Primary transport binding.~~** ✅ **Resolved.** SCP native relay protocol is the canonical transport. Transport is fully abstracted — 17 adapter options listed, no structural dependency on any single transport. Transport security requirements specified in §9.13 (TLS 1.3 required). Relay threat model formalized in §9.9.
- **~~Transport abstraction interface.~~** ✅ **Resolved.** ADR-005 specifies the `TransportAdapter` trait: send, subscribe, unsubscribe, query, delete. Async interface, error types defined. SCP native relay is the canonical implementation.
- **~~Context key management.~~** ✅ **Resolved.** MLS (RFC 9420) selected. One MLS group per context. MLS_128_DHKEMP256_AES128GCM_SHA256_P256 ciphersuite. Full specification in §9.7 (group key management), §9.5 (cryptographic primitives), §9.8 (message security). MLS tree-based key management provides O(log N) member exclusion. Blocking uses a separate sender-side key layer (§9.16) that operates independently of MLS epoch advancement.
- **~~Metadata privacy.~~** ✅ **Fully resolved.** Comprehensive metadata privacy architecture specified in §9.10: minimal outer envelope (§9.10.2), fixed bucket padding (§9.10.3), per-context pseudonyms (§9.10.4), persistent connections + TLS (§9.10.5), cover traffic configurable default-on (§9.10.6), DID resolution privacy (§9.10.7), relay query privacy via pseudonyms + partitioning (§9.10.8). Push notification opacity mandated in §10.7. Sender-side key layer for blocking specified in §9.16 with HPKE-wrapped per-recipient key distribution.
- **~~Verifiable event log format.~~** ✅ **Resolved.** ADR-011 specifies the event log: append-only Merkle tree per context, SHA-256 hash chain, entry structure (event type, sender DID, sequence number, timestamp, payload hash), inclusion proofs, consistency checkpoints. Efficient enough for device-as-node participation.
- **~~Participation record schema.~~** ✅ **Resolved.** The schema is implemented: `ParticipationRecord` struct with 12 fields (`subject_did`, `context_id`, `participation_count`, `participation_duration_seconds`, `outlet_invocations`, `governance_actions_by`, `governance_actions_against`, `role_history`, `attestation_history`, `context_creation_count`, `computed_at`, `event_log_root`) in `crates/scp-protocol/src/trust/participation.rs` (re-exported via `scp-core`). `compute_participation_record()` is pure computation — no side effects, no storage. The six leaf-derived facts (participation duration, governance actions against/by, outlet invocations, context creation, role progression) come from event-log slices; `attestation_history`/`attestation_count` is the one exception — it is a **credential-layer fact (§7.4)**, NOT event-log-derived. There is no `AttestationPublished`/`AttestationRevoked` event type; attestations are credential-layer artifacts threaded in by the caller (the accessible, currently-valid endorsements the verifying agent can reach), so `attestation_count` is verifier-relative and NOT covered by `event_log_root` (see the ADR-011 amendment exclusion taxonomy and §7.3.2). Serialization uses `serde::Serialize`/`Deserialize` (MessagePack per §17.5 for wire format, JSON for debugging). Merkle root captured at computation time enables verification of the leaf-derived facts (but not `attestation_count`). **Governance-enforceable admission requirements** use the same pattern as capability requirements (§7.3.4.4): `RequireParticipation` in `ContextParams` admission requirements specifies fact category, threshold, freshness, and minimum independent contexts. **Participation admission model:** context-hosted signed participation statements (`ParticipationProfile`). Core invariant: agents CANNOT write, modify, or delete their own statements — contexts produce and host them on source context relays. Each `ParticipationProfile` is a full participation profile containing all 7 fact categories (participation duration, governance actions against/by, outlet invocations, context creation, role progression, and attestation history — the last being the credential-layer fact of §7.4, not an event-log-derived count), one statement per member per context, mutated in place when facts change. Agents opt in by allowing contexts to publish statements about them. The agent's service record carries the `ParticipationStatements` pointer (`03-identity.md` §3.10.13). Admitting contexts fetch statements from it, verify P-256 signatures from distinct context-specific signers, and evaluate against admission requirements. Statements omit `context_id` — the admitting context cannot identify source contexts. See §7.3.2.1.
- **~~Challenge suite standards.~~** ✅ **Resolved.** ADR-041 specifies the URI namespace, the protocol capability list, and initial vocabulary. §7.3.4 states the URI format and the protocol capability list. **Capability list:** 28 protocol-defined challenge capabilities (`scp:capability:*/v1`) across 10 categories (safety, schema compliance, behavioral compliance, operational, spending, reasoning, code, recall, bias, factual). Identifier-scoped custom capabilities (`{identifier}:capability:*/v{N}`) enable ecosystem extension without protocol changes. **Versioning:** `/v{N}` suffix enables breaking changes to a capability's standard without invalidating existing verifications. Each protocol URI defines a standard (minimum case count, threshold, scoring); the challenger writes the cases. **Anti-gaming and fairness:** belong to the cases each challenger writes — the protocol provides the namespace, the standards, verification, and anti-spoofing infrastructure. **What remains unspecified (acceptable):** anti-gaming measures in the cases a challenger writes. These are necessarily iterative — challengers revise their cases as attacks evolve.
- **~~Consequence mechanism defaults.~~** ✅ **Resolved.** Intentionally left to contexts. The protocol provides the mechanism (§7.3.7: automated rules declared at context creation, protocol-enforced, verifiable). §19.7 adds economic consequences via `SenderVelocity`. Specific thresholds and escalation curves are context-defined — different context types need radically different values. Well-known templates (§5.12) serve as de facto defaults for their use cases.
- **~~Endorsement accuracy tracking.~~** ✅ **Resolved.** Endorsement accuracy is a derivable computation from existing protocol data — cross-reference `AttestationType::Endorsement` attestations with the endorsed agent's `ParticipationProfile` (specifically `governance_actions_against`). No new protocol machinery needed. The protocol provides attestations (subjective claims) and participation profiles (objective facts). Correlation is computable by any agent. Scoring is client policy.
- **~~Attestation storage and discovery.~~** ✅ **Resolved.** Multi-layer storage by design: `TrustProtocolRepository` trait for local cache with TTL-based refresh (`trust/aggregate.rs`), the subject's service record for the discovery pointer (`03-identity.md` §3.10.13), relays for published attestation blobs. Forward discovery via contexts with discovery outlets (§6.2.2B [no such section]) and that pointer. Reverse-lookup via `attestation_lookup` outlet (§22.5). Production `TrustProtocolRepository` implementation tracked under #329.
- **~~Threshold independence verification.~~** ✅ **Resolved.** All four sub-questions answered by existing implementation in `trust/attestation.rs`. (1) **Graduated**, not binary — independence is a 0.0–1.0 score, not a boolean. (2) **Configurable** — `ThresholdRequirement` carries `shared_context_penalty` (default 0.1, capped at `shared_context_penalty_cap` default 0.5), `mutual_endorsement_penalty` (default 0.2), and `independence_threshold` (context-configurable minimum). Contexts tune penalty weights for their trust requirements. (3) **Transitive correlation deferred** — direct correlation (shared memberships, mutual endorsements) catches the meaningful cases. Transitive checking is O(N²) and doesn't catch sophisticated attackers who avoid shared intermediaries. The real defense against coordinated attestation fraud is device attestation + participation profiles, not graph analysis. (4) **Local computation** — the evaluating agent computes independence from its own view of attestor data. No oracle.
- **~~Identity private state size constraints.~~** ✅ **Resolved.** Less constrained than context state. Single-owner case allows growth. Relays MAY enforce per-DID storage quotas. See §3.7.
- **~~Identity private state relay obligations.~~** ✅ **Resolved.** Same storage class and retention as context events. No differentiated commitment. See §3.7.
- **~~Identity key rotation and private state re-encryption.~~** ✅ **Resolved.** §9.12 specifies the 6-step ordered compromise recovery protocol including private state re-encryption. §9.7.4 covers key rotation triggers. Single-owner case is straightforward — no group redistribution needed. See §3.7.
- **~~Identity private state discovery pointer.~~** ✅ **Resolved.** An explicit `IdentityPrivateState` entry of the identity's service record (`03-identity.md` §3.10.13). See §3.7.
- **How a context's relay list names a tier 3 relay.** **Open, 2026-10-18.** Alec chose the option in which "a relay entry becomes `{url, bridge_target}`", and `18-addressability-and-deployment.md` §18.2.1 applies that ruling to the `SCPRelay` entries of a service record. The relay lists a context carries do not take that form: `InvitationBundle.relay_urls` (`05-contexts.md` §5.12.3.1) is a `Vec<String>` of URLs, and a member stores each one by its canonical URL. A tier 3 relay's URL is its bridge relay's URL, so a URL in that list names the bridge relay, never a node behind it, and a member that learns a context's relays from the list cannot learn the `bridgeTarget` it needs to open a bridge session, to compute the tier 3 push routing ID of `09-security-model.md` §9.18.2, or to register for push with the node that hosts the context (`10-infrastructure-and-self-hosting.md` §10.7.1 **Tier 3 relays**). Whether a context's relay list carries `{url, bridge_target}` entries, and which structures change if it does, is undecided. Until it is decided, a client registers for push with a tier 3 relay only when it holds that relay's `SCPRelay` entry from a service record.
- **~~A response path from a bridged node to the peer.~~** ✅ **Resolved 2026-10-20.** Alec first chose the option "Bridge reply path", which read: "Add a reply channel to the bridge protocol, so the node can answer a fetch through the bridge. This fixes fetching for every kind of data, not only KeyPackages, and would also let the node accept or reject push registrations. Cost: a protocol change to §10.12.4, framing and routing for replies, and more work for the bridge relay." Later that day he replaced that design with the option "Tunnel sessions", which read: "Replace the reply windows, forward_id, BRIDGE_REPLY and BRIDGE_CLOSE with per-peer virtual connections. The bridge enforces only per-session caps (sessions per peer, sessions per node, bytes per second). Cost: rewrite [the pull request's] reply-path text in spec 10 §10.12.4, the ADR-004 frame rows, and the SCP-339 and SCP-340 criteria. The bridge holds one session per peer, as a relay holds a connection today, and the node multiplexes many sessions over its one bridge connection." (The bracketed words replace a pull request number.) The question it answered said: "The bridge opens one virtual connection per peer and forwards every frame both ways until either side closes it. The node runs its ordinary relay protocol over that connection, so SUBSCRIBE with live deliveries, ACK and paging all work unchanged." `10-infrastructure-and-self-hosting.md` §10.12.4 **Sessions** defines the session frames `BRIDGE_SESSION_OPEN`, `BRIDGE_DATA`, `BRIDGE_SESSION_CREDIT` and `BRIDGE_SESSION_CLOSE`, session identifiers, credit-based backpressure, the caps keyed by source prefix, and what each side does when a connection drops, and ADR-004 lists the frames and the codes `4033` BRIDGE_SESSION_UNKNOWN and `4035` BRIDGE_FLOW_VIOLATION. §10.7.1 **Tier 3 envelope** states the node's answer to a push registration on a session: `OK`, `4060` or `5000`.
- **~~Live SUBSCRIBE deliveries through a bridge.~~** ✅ **Resolved 2026-10-20** by the option "Tunnel sessions" recorded in the entry above. A session carries every frame both ways until either end closes it, and the node serves it as one of its own listener connections, so a `SUBSCRIBE` on a session delivers its backfill and every blob the node stores later, and `ACK` works unchanged (`10-infrastructure-and-self-hosting.md` §10.12.4 **Sessions**). The session caps and credit of §10.12.4 **Caps** and **Backpressure** bound what a session costs the bridge.
- **~~Where a peer fetches a KeyPackage of an identity whose relays are all tier 3 entries.~~** ✅ **Resolved 2026-10-20** by the choice recorded in the entry "A response path from a bridged node to the peer" above. A client opens a session through the bridge relay to the node behind a tier 3 entry and sends a `QUERY` for the identity's KeyPackages on it, paging with ordinary `QUERY` frames (`10-infrastructure-and-self-hosting.md` §10.7.1 **KeyPackages at the node**, §10.12.4 **Sessions**). A peer that adds such an identity to a group reaches its KeyPackages through the same `QUERY`.
- **~~Whether a wrapping-key compromise rotation invalidates older KeyPackage attestations.~~** ✅ **Resolved 2026-10-20.** A rotation of the stable wrapping key on suspected compromise (`09-security-model.md` §9.16, the second trigger) leaves `#active` in place, so a KeyPackage attestation naming the old wrapping key keeps verifying until its `expires_at`, up to 84 days and 1 hour after its `issued_at`. A tier 3 push registrant that has never seen the new key can be handed only the old one by a party on its path to the node, and seal to it, which `09-security-model.md` §9.10.4 **Superseded wrapping key** states; the node refuses a saved old-key KeyPackage that any other party publishes again at the identity's KeyPackage routing ID (`10-infrastructure-and-self-hosting.md` §10.7.1 **A republished old key**). Three answers existed: accept the residual, bounded by the attestation lifetime; require that rotation to rotate `#active` as well, which invalidates every older attestation within five minutes and re-issues every UCAN and leaf credential the identity holds; or add a signed record naming a superseded wrapping key, which every reader of a wrapping key checks. Alec confirmed this resolution: "keri adds the stable wrapping key to the key state as its own role. Rotating the wrapping key then drops the old one as Superseded, or as Compromised{from: N} after a suspected compromise. A reader sealing to a wrapping key checks its condition the way it checks any other key, so a republished old KeyPackage no longer works." A later ruling makes that role one entry per device, carried in the device-authorization event: each device holds its own wrapping keypair, whose private half never leaves that device's custody, and the keri workstream adds the role in keri P7 (#2874). `09-security-model.md` §9.10.4 **Superseded wrapping key** states what remains once the role exists. The 2026-10-21 ruling in the entry "Which device's wrapping key a tier 3 client seals to" below removes the registrant's KeyPackage read, so no party on its path can hand it a KeyPackage at all, and §9.10.4 states the residual that remains in the registrant's own view of the key state.
- **~~Which device's wrapping key a tier 3 client seals to.~~** ✅ **Resolved 2026-10-21.** Alec wrote "Ok on keys" in answer to the recommendation of answer (1), which stated that the node's signed tier 3 relay entry names the node device's wrapping-key entry by its key identifier in the identity's key state, and that the client checks that this entry is `Current` before sealing. `18-addressability-and-deployment.md` §18.2.1 **`wrappingKey`** carries that field, `03-identity.md` §3.10.13 signs it, and `10-infrastructure-and-self-hosting.md` §10.7.1 **Recipient key** states the client's check. The identifier is the 33 bytes the key state carries as the entry's `key`, because a key entry carries no other identifier (`09-security-model.md` §9.7.4.2 definitions). The keri workstream owns the key state, and agreed that answer (1) needs nothing new from keri; it objected to answer (2). The field's encoding and its reader rules are the architect agent's design, the rule that a reader accepts the field only when it equals the `key` of a wrapping-key entry the resolved `KeyState` lists `Current` is keri's, and keri P7 (#2874) re-signs the service record after a wrapping-key rotation, and `25-test-vectors.md` Vector 48 pins the bytes. The client reads no KeyPackage to learn `pkR`, so the full KeyPackage read and its bound are gone from §10.7.1, and the node's KeyPackage admission stays for the peers that add the identity to a group (§10.7.1 **KeyPackages at the node**). The question as it stood: The wrapping key is a per-device key-state entry, carried in the device-authorization event (keri P7 (#2874)), and the node's relay opens a tier 3 envelope through the custody of the device whose SCP instance runs the node (`10-infrastructure-and-self-hosting.md` §10.7.1 **Recipient key**), so it opens only an envelope sealed to that device's wrapping key. The identity's KeyPackage routing ID holds KeyPackages from every device of the identity, each naming its own device's wrapping key, and neither a KeyPackage, its attestation, nor the tier 3 entry tells the client which device runs the node. Three answers exist. (1) The tier 3 entry, which the identity signs in its service record, names the node's device, and the client reads that device's `Current` wrapping-key entry from the key state. This adds a field to the signed `SCPRelay` entry (`03-identity.md` §3.10.13, `18-addressability-and-deployment.md` §18.2.1), and the client then needs no KeyPackage read to learn `pkR`. (2) The key state's device entry marks the device that runs a node. This changes keri's key-state data model, and an identity with two devices that each run a node still needs the tier 3 entry to choose between them. (3) The client seals one envelope to each device's `Current` wrapping key. This multiplies every registration by the number of devices and shows the bridge relay that number. Recommendation: (1), because the service record already binds the tier 3 entry to its node.

## Context Lifecycle and Governance

- **The `Majority` deadline arm under Commit-carried votes.** **Open, 2026-10-17.** ADR-031 §4c approves a `Majority` proposal at its deadline when approvals exceed rejections and participation meets `min_participation`. ADR-066 has every receiver decide from the executing Commit's contents alone, and an executor can leave out a rejection the receiver cannot know exists, so the Commit cannot prove that arm. `07-trust-validation-and-capabilities.md` §7.3.1.1 executes a `Majority` proposal only when approvals exceed half of the eligible voters until this is settled. The choices are to drop the arm, or to keep it with the Commit carrying rejections too and the receiver trusting the executor to carry every rejection it holds.
- **~~When a governed ceiling change takes effect under Commit-carried governance.~~** ✅ **Resolved, 2026-10-18.** Alec picked the option "At execution", which read: "The new ceiling takes effect in the Commit that executes the ModifyCeiling. Members can leave at any time while the proposal is open for voting, before it executes. Every member can check this, and no timer is needed. Cost: the promise changes from 'you get 72 hours after approval' to 'you can leave while the vote is open'. A Majority vote can collect its approvals quickly, so the time to leave can be short." `05-contexts.md` §5.3.2 now puts the new ceiling in effect from the Commit that executes the `ModifyCeiling`, with no notification period, and §5.13.3 rule 11 changes `ceiling_hash` in that Commit (ADR-066 decision 18). On 2026-10-19 Alec picked the option "Two Commits" for the window under `SingleAdmin`, which read: "A ModifyCeiling proposal must be recorded in an earlier Commit's governance block before a later Commit can execute it. Receivers reject an execution whose proposal they have not seen in an earlier epoch, so every member is guaranteed at least one epoch to see the proposal and leave, under every governance model. Cost: each ceiling change takes two Commits, and the window is one epoch, which can still be short." §5.3.2 now records the proposal in an earlier Commit's `GovernanceProposalRecorded` leaf, which ADR-066 decision 21 renamed from `CeilingModificationPending`, and every receiver rejects an unrecorded execution (ADR-066 decision 20).
- **Unverifiable deadlock justification.** **Open, 2026-10-17.** ADR-031 §10's fallback quorum is a majority of the active voters, and the `DeadlockJustification` the proposer writes names who is inactive. A receiver of the executing Commit cannot check that list, so an executor that lists every voter but two as unavailable needs only two approvals to reduce a `Threshold` context's threshold. ADR-066 counts the fallback as `07-trust-validation-and-capabilities.md` §7.3.1.1 states and inherits this weakness; ADR-031 does not say how to bound it.
- **Growth of the executed-proposal set.** **Open, 2026-10-17.** `05-contexts.md` §5.9 invariant 2 keeps every executed proposal ID forever, and ADR-066 puts the set in every checkpoint snapshot, so the set and the snapshot grow with every governance action a context executes. A proposal's `anchor_seq` could bound it: if a receiver rejected a proposal anchored more than a fixed number of leaves before the executing Commit, a member could drop every ID anchored before that point. No spec states such a bound or its size.
- **A protocol cap on a vote's `expires_epoch`.** **Open, 2026-10-17.** A voter chooses `expires_epoch` (`05-contexts.md` §5.9.1), and no rule bounds it, so a voter can sign an approval that never expires and can then end it only by replacing its leaf key (`07-trust-validation-and-capabilities.md` §7.3.1.1). Whether a receiver should reject a vote whose `expires_epoch` lies more than a fixed number of epochs past the Commit, and what that number is, is not decided.
- **Revisiting the per-Commit approval cap.** **Open, 2026-10-17.** Alec ruled: "Let's go with 96 cap and no split for now, threshold for more. we can revisit later." Asked to choose between 96 and 65, he picked "96, 32 KB block": a cap of 96 in a fixed 32 KiB block, with the 8 KB action limit kept. ADR-066 applies it as `MAX_GOVERNANCE_APPROVALS` 96 (`07-trust-validation-and-capabilities.md` §7.3.1.1). Whether the cap is raised later is his to decide. The alternatives ADR-066 records are splitting an action across Commits, size buckets up to 256 KiB, and BLS aggregate signatures, which the 2026-09-10 move of every key to P-256 rules out. The cap also leaves the ADR-031 §10 deadlock fallback unable to execute in a `Threshold` context with more than 191 eligible voters.
- **~~Checkpoint snapshot fields that no Commit orders.~~** ✅ **Resolved, 2026-10-20.** Alec ruled on all three. `ucan_revocations`: he picked the option "Commit leaf", which read: "A Commit carries a TokenRevoked leaf authorized by the token's issuer or the context creator, so every member and joiner refuses a revoked token from the same epoch on. Cost: one epoch and one Commit per revocation." (ADR-066 decision 28). `blocks`: he picked the option that read: "The snapshot loses `blocks`, and cosigners agree. Enforcement doesn't change. Bans still ride Commits. Spec 09 step 7's MemberBlocked record stays an application message, so a joiner never learns of an earlier in-context block." (decision 30). `outlets`: he ruled: "If we can't differentiate then do it by role. But it would be nice to differentiate by some context config so that certain outlet additions, likely by capability or read access, get sent to vote"; every outlet change is now a Commit carrying an outlet leaf, which a holder of `outlet:register` sends unless the context's outlet registration policy routes it to a vote (`05-contexts.md` §5.4, decision 31). Every remaining snapshot field derives from commit-ordered leaves. The question read: Every signer of an encrypted context's checkpoint computes the ADR-030 snapshot from its own state and cosigns only when its digest equals the creator's (ADR-066 decision 24), so every field must be a value every member holds identically at one leaf count. Three fields are not. `outlets` changes by a governance `RegisterOutlet` or `RemoveOutlet`, which a Commit executes, and also by a direct registration under the `outlet:register` capability (`05-contexts.md` §5.3.1, ADR-010), which appends an `OutletRegistered` event that no Commit derives. `blocks` changes by a block, whose notification is an MLS application message and whose `MemberBlocked` record `09-security-model.md` §9.16.3 step 7 appends to the context log, while §3.7.1 of the identity spec makes the blocker's identity private state the authoritative record. `ucan_revocations` changes by a revocation that travels as an MLS application message and appends a `TokenRevoked` event (ADR-016 criterion 5). ADR-011 admits to the canonical log only records every member appends identically and in one order, and ADR-066 decision 14 lets a Commit carry only the leaves it derives, so none of these three records has a path into the log, and a snapshot that holds them can miss its quorum. Each needs a ruling on how it reaches every member in one order, or on leaving the snapshot.
- **Fork-merge carry cap.** **Open, 2026-10-24.** ADR-067 ("Mechanisms", obligation 2) caps the pending items one Commit carries at `MERGE_CARRY_ITEMS` and then places the member's own action, so the action always fits, and admission refuses a fork record whose `end_count` − F exceeds K(e_F) · `MERGE_CARRY_ITEMS`. No ruling or plan gives the value. Body item 5 shares the 32,764-byte governance block body with the action and its approvals (`07-trust-validation-and-capabilities.md` §7.3.1.1), so the value must leave room for the largest action. A larger value repairs a fork in fewer Commits and admits a longer losing branch; a smaller one leaves more room per Commit for the action.
- **Log growth while a checkpoint cannot reach its quorum.** **Open, 2026-10-17.** ADR-066 lets a joiner adopt a checkpoint only under its full ADR-031 §9 quorum, and members prune nothing after the latest checkpoint that has one. In a `Unanimity` context one voter that never cosigns therefore stops all pruning, and the log grows without bound for as long as that voter stays. No spec bounds the growth. ADR-066 decision 27 removed the second half of this question on 2026-10-20: a joiner accepts the latest checkpoint by its inclusion under the committed log head and counts no quorum, so a change of voters no longer stops a joiner.
- **~~Who consents to a TTL extension or a promotion under Commit-carried votes.~~** ✅ **Resolved, 2026-10-18.** Alec picked the option "Every member", which read: "Keep the spec's rule. Members joined expecting the context to expire, so none of them can have it extended or made permanent without their approval. The cost: every context with a TTL is limited to 96 members, including members who have no vote." `ExtendTtl` and `PromoteContext` need a signed approval from every current member, carried in the Commit that executes them, in every governance model, `Threshold` included, and a member without `GovernanceVote` approves them too (`07-trust-validation-and-capabilities.md` §7.3.1.1). Every context with a TTL has at most 96 members (`05-contexts.md` §5.9 invariant 4). The carried approvals replace the `TTLExtensionConsent` message and its 24-hour deadline (`05-contexts.md` §5.10.1). ADR-066 decision 15 records the ruling.
- **Governed changes that take effect when a clock period ends.** **Open, 2026-10-18.** Each receiver would decide when such a change is in effect by reading its own clock, which ADR-066 decision 10 forbids, so two members could disagree on the state at the same Commit. **Resolved for economic policy, 2026-10-18:** `19-economic-governance.md` §19.3 gave an economic policy change a minimum 24-hour notification period, which a context could lengthen through `economic_policy_notification_period_secs`. Alec picked the option "At execution", which read: "The new economic policy takes effect in the Commit that executes it. Members can leave while the proposal is open for voting. This matches the ceiling ruling, every member can check it, and no timer is needed. Cost: the per-context economic_policy_notification_period_secs setting goes away, and a fast Majority vote leaves members little time to leave." §19.3 now puts the new policy in effect from the executing Commit (ADR-066 decision 19), as decision 18 did for governed ceiling changes. On 2026-10-19 Alec picked the option "Two Commits" for the economic policy change too, which read: "Apply the ceiling mechanism to SetEconomicPolicy: the proposal is recorded in an earlier Commit, and receivers reject an execution without that record. Every member gets at least one epoch under every governance model. Cost: each economic-policy change takes two Commits, and the recording state, pruning rule and snapshot field are extended to a second action." §19.3 now records a `SetEconomicPolicy` in an earlier Commit's `GovernanceProposalRecorded` leaf, and every receiver rejects an unrecorded execution (ADR-066 decision 21). The ruling also covers §19.4's pricing-formula grace period, because §19.3 puts the formula in the policy: `pub pricing_formula: Option<PricingFormula>,    // for dynamic pricing (§19.4)`. **Still open:** `05-contexts.md` §5.11A.4 and §5.11A.5 close the source context of an approved migration, and emit `ContextTombstoned`, when its `grace_period_end` passes (7 days by default); and `05-contexts.md` §5.11 lets key destruction proceed 300 seconds after a summary is published when no member disputes it, and 24 hours after an unresolved dispute. Open: whether each of these takes effect at an executing Commit, or how a receiver decides the moment without a clock.
- **~~`KeyEpochAdvance` records.~~** ✅ **Resolved, 2026-10-21.** `05-contexts.md` §5.14.10 and ADR-011's event types named a `KeyEpochAdvance { sender_did, epoch }` log event in both context modes, but no Commit derived it. Alec refused applying the blocks ruling to every rotation: "Ban and block are not the same, so why are you implying they must/do share all the same machinery? I feel like epochs must be a commit event, that's the point right?" He then ruled "Yes to ban rotate commit" (ADR-066 decision 36) and "Yes to block app msg but it needs to become effective asap so blockees lose read access immediately upon being blocked and I don't want confusing epoch delivery fragmentation" (ADR-066 decision 37). Sender keys and broadcast keys rotate only on a block and on the governance Commits of `09-security-model.md` §9.16.10 (§9.16.5), so the two rulings cover every rotation, and no rotation is a log record of its own. A rotation that a ban (`RevokeAccess` with `Read` or `Both`) or a `RotateContentKeys` causes is bound to that decision's Commit, whose `GovernanceActionExecuted` leaf records it. A rotation that a block causes is the `SenderKeyEpochAdvance` application message, or in a broadcast context the `BroadcastEpochAdvance`, outside the commit-ordered log and the checkpoint snapshot. The `KeyEpochAdvance` event type is removed and its tag 18 retired; SCP-349 removes it from the code and from the `25-test-vectors.md` "`EventType` tags" row together.
- **~~Memory scope enforcement boundary.~~** ✅ **Resolved.** The sections below state the boundary. §5.11 ("Enforcement honesty") explicitly states: "The protocol enforces memory scope through cryptographic key destruction — specifically, MLS group state destruction (tree secrets, all epoch key schedules, application key material). This is verifiable and absolute for protocol-level data. [...] However, the protocol cannot enforce memory scope above the protocol boundary. An agent's underlying model may retain information from an ephemeral interaction in its own memory." §9.15 specifies the three trust levels for key destruction verification: hardware-attested (Secure Enclave/Keystore), software-only (`memset(0)`), no attestation (member offline). The `KeyDestructionAttestation` struct is fully defined. §7.7 provides the provenance defense: data an agent reproduces from memory without protocol-level origin carries no provenance — "the absence of provenance is itself a signal." **The enforcement boundary is:** protocol-level data (MLS keys, ciphertext) = enforceable via destruction; agent-local memory = not enforceable, mitigated by provenance-absence signals. This is explicitly documented for implementers in §5.11's "Enforcement honesty" paragraph.
- **~~Context promotion mechanics.~~** ✅ **Resolved.** Promotion policy declared at context creation (`no_promotion` or `promotable`). Policy itself is immutable. Default for ephemeral templates is `no_promotion`. See §5.10.
- **~~Summary generation mechanics.~~** ✅ **Resolved.** Protocol provides lifecycle hooks: `SummaryVerificationWindow` (default 300s, configurable), verification/dispute actions, key destruction after window closes. (1) **Verification window duration:** `DEFAULT_VERIFICATION_WINDOW_SECS = 300`, configurable per context. (2) **Dispute resolution:** context governance decides — SingleAdmin: admin decides; Threshold/Majority/Unanimity: vote on acceptance. Configurable policy for incomplete verification (proceed vs extend). (3) **Summary content:** defined by context governance/outlets, not protocol. Default summary outlet is an SDK deliverable. Implementation tracked at [#365](https://github.com/limn-works/scp/issues/365).

## Crypto and Security

- **~~Offline member MLS re-sync.~~** ✅ **Resolved.** ADR-029 (`.docs/adrs/phase-6.md`) specifies the full three-tier offline strategy: Tier 1 (hours — relay buffering + MLS catch-up), Tier 2 (days — state snapshot + delta sync), Tier 3 (weeks — forced re-join with group state reset). Trigger conditions, initiation protocol, and context lifecycle during reset are fully specified. Implemented in `crates/scp-core/src/sync/` (SCP-121 through SCP-124). Dedicated spec section: §23 (sync architecture, tier definitions, reconnection protocol, conflict resolution, MLS group rebuild).
- **~~Commit delivery assurance under adversarial relays.~~** ✅ **Resolved.** §9.9.4 now explicitly defines "delivery confirmation" as relay-level storage ACK (the relay confirms it received and stored the blob), not recipient-level ACK (which would leak metadata). The actual assurance mechanism is the recovery path: epoch-behind detection triggers Commit requests from peers or alternate relays. **Full specification:** §9.9.2 specifies multi-relay cross-check (publish to at least 2, recommended 3 relays) with a 30-second inconsistency timeout. §9.9.3 specifies the Relay Consistency Protocol (signed checkpoints every 50 events or 10 minutes) for detecting equivocation. §9.9.2 also specifies 60-second heartbeats for suppression detection.
- **~~Pseudonym rotation and traffic analysis resistance.~~** ✅ **Resolved.** **(BLACK-001, [#17](https://github.com/limn-works/scp/issues/17)).** Three protocol-level mitigations: (1) Pseudonym rotation via `derive_rotatable_pseudonym` with dual-subscription grace period (§9.10.4.1). (2) Relay delivery jitter (§9.10.10). (3) Residual risks documented (§9.10.11). Cross-relay fanout decorrelation is a client-side SDK concern — per-relay jitter in multi-relay publish path. Implementation tracked at [#366](https://github.com/limn-works/scp/issues/366).
- **~~Cover traffic parameters.~~** ✅ **Resolved.** §9.10.6 fully specifies all parameters: (1) rate: one padded message per relay connection per 30 seconds; (2) scope: per relay connection, not per context — prevents relay from correlating traffic rate changes with context activity; (3) format: single-byte flag inside encrypted payload distinguishes real from dummy; recipients decrypt, check flag, discard dummies; (4) bandwidth: ~15MB/day for 5 relay connections at 1KB padding; (5) configurability: enabled by default, configurable per-client via SDK configuration; disabling degrades traffic analysis resistance but has no functional impact; (6) push-wake connections: no cover traffic (connection is transient). The relay-side distinguishability concern is addressed by design: the single-byte flag is inside the encrypted payload, so relays cannot distinguish real from dummy messages. The only residual risk is statistical timing analysis against the constant rate (acknowledged in §9.10.11).
- **~~Compromise recovery orchestration.~~** ✅ **Resolved.** §9.12 specifies 6 ordered steps with an explicit "Step ordering and failure isolation" paragraph. Ordering: key rotation (1) before MLS Updates (2) before UCAN revocation (3) before KeyPackage rotation (4); steps 5-6 are cleanup, order-independent. Steps 2-4 are per-context with independent retry; failure in one context does not block others. Contexts where MLS Update cannot succeed are flagged for manual re-join (Tier 3 per ADR-029).
- **~~UCAN revocation mechanism.~~** ✅ **Resolved.** **Amended 2026-10-20 (ADR-066 decision 28):** in a context with an MLS group, a Commit carrying a `TokenRevoked` leaf revokes a token, the `ucan_revocations` governance state replaces the merged list, and the `RevocationPending` rollback below is retired; the text below describes the mechanism before the amendment and still governs a Broadcast context. Fully specified across ADR-016 acceptance criteria 5 and 7, and implemented in `crates/scp-core/src/crypto/ucan/revoke.rs`. **List format:** Per-context `RevocationList` — a `HashMap<String, RevocationState>` mapping token CIDs to one of three states: `Active` (default, not stored), `RevocationPending` (fail-closed — capability denied while MLS distribution is in flight), `Revoked` (fully committed). Append-only with `merge()` for MLS-distributed synchronization. **Check frequency:** Two-tier design (see §7.2). Tier 1: revocation is checked as step 10 of the 11-step `validate_ucan` pipeline at token presentation boundaries (role assignment, cross-context outlet invocation, broadcast admission). Tier 2: intra-context operations check a derived capability cache (`ContextRoleState::member_capabilities`) that is updated atomically on role change; revocations take effect at the next Tier 1 boundary or role reassignment. **Behavior on failure:** Fail-closed. `RevocationPending` state denies capability exercise even before MLS confirmation. If MLS distribution of the revocation fails, the local revocation is rolled back (transactional) so there is no split-brain between the revoker and other members. Network errors during revocation distribution result in rollback to `Active` — the revoker must retry. Revocations are distributed as MLS application messages; `TokenRevoked` events are appended to the context's event log. See `RevocationDistributor` and `RevocationEventLogger` traits in `revoke.rs`.

## Identity and Custody

- **The default root custody's dependency on the `ctx.network` relying-party identifier.** **Open, 2026-09-10.** `09-security-model.md` §9.7.4.1 item 4 makes the SDK's default root custody a discoverable WebAuthn credential under the relying-party identifier the SDK ships, `ctx.network` by default. WebAuthn admits an assertion only from an origin whose effective domain is that identifier or a registrable-domain suffix of it, and a native application reaches the credential through an association file that domain serves. **Two things are undecided at Alec's instruction**, and each keeps the default its own entry below states until he rules. He called the second "too detailed too early" on 2026-09-10; the portability ruling of the same day defers the first: what the protocol does about a lapsed or hostile `ctx.network`, and whether the origin under that identifier can obtain root signatures over events it composed, since a passkey prompt shows the domain and never the challenge. **What already exists and is not the answer to either:** the root is a threshold set, so an identity may register a second root credential under another relying-party identifier or on a FIDO2 token (§9.7.4.1 item 4, §9.7.4.2 definitions). This entry records both questions as open and recommends nothing.
- **StrongBox opt-in on Android.** **Open, 2026-09-28.** ADR-027, the Android platform adapter, in `.docs/adrs/phase-6.md`, makes the TEE-backed Keystore the only option and states "There is no user-visible opt-in to StrongBox", because StrongBox signing runs 10-100x slower than TEE signing. `17-persistence-and-storage.md` makes StrongBox opt-in in two places: the Android row of the platform-encryption table in §17.5 says "StrongBox opt-in only (dramatically slow)" for the SQLCipher key, and the Android row of the key custody table in §17.8 says "StrongBox is available, dramatically slower, and opt-in". Both rulings cannot hold. SCP-110, the Android Keystore key custody story, follows ADR-027 until a human decides which artifact changes. This entry records the conflict and recommends nothing.
- **Whether a `RootRecovery` snapshot may keep a root member `Current`.** **Open, 2026-10-20; narrowed 2026-10-21.** `09-security-model.md` §9.7.4.2 R8 says a `RootRecovery` "replaces the entire key state in one event" and "also carries the fresh root set and the operational keys it installs", and its key list carries "every key `Current` at that position" and one entry per dropped key. **A kept `#active` key is settled.** §9.12's root-compromise row says the recovery carries every operational key by role, "the controller's own key re-listed otherwise", so a `RootRecovery` that re-lists an uncompromised operational key is valid (Alec, 2026-10-21). **A kept root member stays open.** R3 requires a `RootRecovery`'s field 9 to equal the `Current` `RootMember` entries of its snapshot, so a kept root member would sit in field 9, which installs K′. §9.7.4.2 states: "A public key is installed by at most one event on a chain and holds one role there, and listing an already-installed key in a later snapshot is not an installation." The sentences admit three readings, and no sentence says which holds:
  1. Field 9 installs every key it lists, so a kept root member would be installed twice, and the rule forbids keeping one.
  2. Field 9 installs every key it lists while the second clause says listing a kept key is not an installation, so the two sentences contradict each other.
  3. Listing an already-installed key in field 9 is not an installation, so a kept root member is permitted. Under this reading a key kept from the compromised root may sign as a member of K′, and so satisfy the K′ group of a `RootRecovery{Lost}`.

  Vectors 54 and 55 of `25-test-vectors.md` §25.29 keep no key. The snapshot-order rule of §9.7.4.2's definitions orders kept, installed and dropped entries and is silent on the case. Until Alec rules, the verifier discards a `RootRecovery` whose snapshot keeps a root member `Current` at step 8 with its own defect, `ContentDefect::KeptRootMember`, which names this entry and no other rule. This entry records the question and recommends nothing.
- **Members can resolve different keys for one KeyPackage attestation.** **Open, 2026-10-20.** A `0xFF03` attestation names the role `#active`, not a key, and each member resolves that role against its own view of the signer's key state when the leaf enters or is replaced in its tree. Every member that admits the leaf holds the one key the attestation's signature verifies under. The gap is in two places. A member that processes the Commit bringing the leaf after the signer rotated `#active`, or with a fresher cache of the signer's key state, rejects the leaf and so a Commit the others accept, and the group forks. A Welcome joiner, an importer, or a restorer never ran that check for a leaf already in the tree, so it holds no resolved key for that leaf's attestation. ADR-066 decision 27(d) closed the key-event-log split only up to this gap (`09-security-model.md` §9.7.1, "Known gap: members can resolve different keys for one attestation"). The keri workstream owns the attestation body and preimage, and SCP-315 owns the fix.
