# 4. Agents

## 4.1 Core Principle

Humans and their bound agents are the only actors in the system. Every action on the protocol — every message, every outlet invocation, every state change — is traceable to a human(s) as an action they took or their attributed agent took. There are no anonymous actors or unaccountable software participants.

## 4.2 Binding

Every agent is bound to its human through the DID document itself — the agent's signing key is a verification method (`#agent`) on the human's DID. Binding is structural, not an external proof: the DID document is the single source of truth for which key is the human's (`#active`) and which is the agent's (`#agent`). The binding is verifiable by any participant who resolves the DID.

- **Personal agents:** Bound to a single human. The common case. The human's DID document contains at most one `#agent` verification method.
- **Institutional agents:** Bound to multiple humans through shared governance (multi-sig, elected operators, organizational hierarchy). Structurally identical to personal agents; the difference is in who holds the keys and how revocation/control works. Institutions get one agent per context, the same as individuals — one seat per institution per table.

**Institutional agent key governance.** Institutional agents share one `#agent` verification method on the institution's DID document, with operational control distributed among authorized humans. Key governance follows these rules:

1. **Key generation.** The institution's `#agent` key is generated by the designated key administrator (a human with `#0` or `#active` access on the institution's DID). The key MAY be generated in an HSM accessible to the institutional infrastructure.
2. **Key rotation authority.** Only holders of the institution's Identity Key (`#0`) can rotate the `#agent` key. Rotation follows the same protocol as personal agent key rotation (ADR-039) — publish a new DID document with a replacement `#agent` verification method, revoke old scoped UCANs, issue MLS Updates in all active contexts.
3. **Multi-operator access.** When multiple humans operate an institutional agent, the private key material for `#agent` is distributed via threshold key sharing (t-of-n Shamir secret sharing, GF(2^8)) or stored in a shared HSM with access controls. The protocol does not mandate a specific multi-operator key management scheme — it requires only that the `#agent` key is singular in the DID document (one `#agent` VM per DID, per ADR-039).
4. **Revocation cascade.** When an authorized operator is removed from the institution, the institution MUST rotate the `#agent` key. All scoped UCANs delegated to the old key are revoked and reissued. This is the standard key rotation path — no institution-specific revocation mechanism exists.
5. **Audit trail.** Institutional agent actions are signed by the `#agent` key and are indistinguishable from personal agent actions at the protocol level. The institutional governance structure (who authorized what) is an organizational concern above the protocol boundary. The protocol guarantees only that every action traces to the institution's DID.

## 4.3 One Agent Per Person Per Context

At the protocol level, each human has exactly one agent per context. This is structurally enforced: a DID document contains exactly one `#agent` verification method. Verifiers reject DID documents with multiple `#agent` VMs. The agent can be arbitrarily capable internally — parallel execution, complex orchestration, sophisticated reasoning. The constraint is on presence: one seat per person per table.

Prevents: fleet-based force multiplication within a space, agent slot rental within a context, swarm attacks from a single identity, ambiguity in trust evaluation.

## 4.4 Bring Your Own Agent

The protocol defines how agents communicate and what capabilities they can exercise. It does not define what agents are internally. Users bring their own: models, configurations, logic, local infrastructure. A user running a frontier model and a user running a basic assistant both have one seat. The asymmetry in capability is acknowledged, not policed.

The protocol surfaces **agent capability metadata** — a standardized profile of what an agent can do — so other participants can evaluate it. Not the model name or implementation details, but a functional profile. Capability metadata distinguishes between:

- **Self-attested capabilities.** Claimed by the agent's human operator but not independently verified. Any agent can make these claims. Trust in the claim depends on trust in the claimant.
- **Challenge-verified capabilities.** Tested via the protocol's challenge-response mechanism (§7.3.4). A verifier issued a standard challenge suite; the agent passed. The metadata records what was verified, when, and by whom. Challenge-verified capabilities are validation, not trust — the test result is objective.

Contexts can require specific capability levels for admission. "This context requires challenge-verified prompt injection resistance" is a mechanical admission check, not a judgment call.

### 4.4.1 Agent Capability Metadata Schema

The capability metadata profile published in a DID document's `SCPCapabilities` service endpoint (§6.2.2A, §18.2.2) uses the following structured format:

```json
{
  "id": "#scp-capabilities",
  "type": "SCPCapabilities",
  "serviceEndpoint": {
    "scp_version": "1.0",
    "self_attested": [
      "scp:capability:schema-validation/v1",
      "scp:capability:multilingual/v1"
    ],
    "challenge_verified": [
      {
        "capability": "scp:capability:prompt-injection-resistance/v1",
        "verifier_did": "did:dht:z6MkVerifier...",
        "verified_at": 1700000000,
        "expires_at": 1702592000,
        "verification_id": "cv-abc123"
      }
    ],
    "custom": [
      {
        "capability": "did:dht:z6MkDefiner...:capability:cooking-expertise/v1",
        "level": "challenge_verified",
        "verifier_did": "did:dht:z6MkChef...",
        "verified_at": 1700000000
      }
    ]
  }
}
```

**Field definitions:**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `scp_version` | string | Yes | Protocol version for this metadata format. `"1.0"`. |
| `self_attested` | array of URI strings | No | Capability URIs (§7.3.4.1) that the agent claims but has not been challenge-verified for. |
| `challenge_verified` | array of objects | No | Capabilities with `ChallengeVerification` records. |
| `challenge_verified[].capability` | URI string | Yes | The capability URI that was verified. |
| `challenge_verified[].verifier_did` | DID | Yes | DID of the verifier who issued the challenge. |
| `challenge_verified[].verified_at` | u64 | Yes | Unix timestamp (seconds) of the verification. |
| `challenge_verified[].expires_at` | u64 | No | Expiry timestamp. If absent, the verification does not expire but may become stale per renewal intervals (§7.3.6). |
| `challenge_verified[].verification_id` | string | Yes | Unique identifier for the `ChallengeVerification` record (§7.3.4). |
| `custom` | array of objects | No | DID-scoped custom capabilities (§7.3.4.1). |

Capability URIs in `self_attested` MUST conform to the capability URI namespace rules (§7.3.4.1). Protocol-scoped URIs (`scp:capability:*`) MUST be present in the signed protocol registry. DID-scoped URIs follow the `did:{method}:{id}:capability:{name}/v{n}` format. Freeform strings (e.g., bare keywords like `"translation"`) are NOT valid — all capabilities use structured URIs.

## 4.5 The Human-Agent Pair

The fundamental unit of participation in SCP is not the agent alone — it is the human-agent pair. The human is the root of identity, trust, and accountability. The agent is how the human is present at the protocol level. Neither is complete without the other: an agent without a human binding is unaccountable; a human without an agent has no protocol-level presence.

This pairing is what the protocol provides. At the protocol level, the agent acts. At the trust level, the human is accountable. Other participants evaluate both: "Do I trust this person?" and "Do I trust what their agent can do?" These are separate questions with a single answer — the trust function (§7.1) evaluates identity and capability together.

The human and agent share a single DID but their actions carry distinct provenance. Messages signed with `#active` are human-direct; messages signed with `#agent` are agent-autonomous. This distinction is structural — verifiers can determine provenance from the signing key alone, without out-of-band metadata. The human can always act directly through `#active`, and the agent acts through `#agent`. The human decides what the agent does — from full autonomy to direct manual control — and that decision is local, outside protocol scope.

What this means for the ecosystem:

- **One actor model.** Every protocol action has the same structure: an agent acts, bound to a human, within a context. No bifurcation between "agent actions" and "human actions." This keeps the protocol simple and trust evaluation uniform.
- **Agent capability is a spectrum.** A passthrough agent that forwards human keystrokes is valid. A fully autonomous agent that acts on its own judgment is valid. The protocol treats both identically — the difference is in the human's local configuration, not in the protocol's evaluation.
- **The minimum viable agent is trivial.** A user doesn't need to "set up an agent" any more than they need to "set up TCP." The simplest agent can be generated, embedded in an app, or provided as a default. The protocol requires the pairing to exist, not that it be sophisticated.

## 4.6 Agents Are Consumers, Not Enforcers

Human-bound agents are **protocol consumers** — the same identity as their human, distinguished only by verification method (`#agent` vs `#active`), but consumers nonetheless. They use apps. They use context outlets. They interact with contexts through the protocol. They have zero responsibility for enforcing protocol rules.

The protocol enforces itself — through cryptography (encryption-as-access-control, key tree exclusion for blocks, capability token validation) and through the SDK that builders use to construct conformant apps. Agents do not enforce blocking, role permissions, capability ceilings, or any other protocol rule. The protocol and its cryptographic guarantees handle enforcement. Apps built on the SDK inherit those guarantees. Agents and humans consume those apps.

This distinction matters because SCP is designed for a world of generated, ephemeral clients. Any enforcement that depends on agent or client behavior is not enforcement — it's a suggestion that non-conformant software can ignore. Protocol guarantees must be cryptographic or structural, never behavioral.

A separate class of agents exists outside this context: **builder agents** — the LLMs and AI systems that generate apps and services on top of SCP using the SDK. These are developers, not protocol participants. They are responsible for constructing software; human-bound agents are responsible for nothing beyond using it.

## 4.7 Context-Bound at Protocol Level

An agent in Context A has no protocol-level awareness of or connection to the same human's agent in Context B. At the protocol level, they are separate instances. They share no state through the network.

The human coordinates locally. On the user's machine, agents share state freely, coordinate, plan across contexts. The protocol only governs what touches the network. Each agent only operates within its own context.

This eliminates: cross-context infection via agent memory, runaway agent coordination at the protocol level, the need for bridging rate limits, metastatic growth patterns through agent connections.

**Category C — per-context restrictions on agents.** A context restricts what an agent may do inside it through four mechanisms, each declared in the context's parameters or its role assignments and each changed by the context's own governance (§5.9). `agent_keys_allowed` set to `false` bars every `#agent`-signed artifact from the context. An agent-restricted role narrows the capability set a member exercises through `#agent` below the set that member's own role grants. `agent_rate_limit` caps how many `#agent`-signed actions a member takes in a rolling window. `agent_cosign_required` names the capabilities whose exercise through `#agent` also needs an `#active` signature over the same payload. ADR-039 introduces no new primitive for any of the four — each one is a context parameter or a role the protocol already defines. §4.9.3 states each mechanism and where its state lives; §4.9.4 states what a verifier does when a context's restriction and the DID owner's own Category B configuration disagree.

**No direct agent-to-agent primitive.** The protocol does not and will not include a mechanism for agents to contact agents they share no context with. This was considered in depth (see planning-session-03.md for the full analysis, planning-session-06.md §2 for the rejection rationale) and rejected. The core reasoning: context isolation is the security boundary, and any mechanism that lets agents bypass it — even a "governed" one with rate limits and trust evaluation — reintroduces the attack surface isolation was designed to eliminate. Cross-context interaction uses outlet interfaces (§6.2) for asymmetric service calls, multi-parent child contexts (§5.13) for symmetric collaboration, and standing bilateral contexts (§5.12.6) for persistent direct communication. All three require existing context membership or human facilitation. Agents that need new relationships require their humans to arrange them.

## 4.8 Agent Fleet

A human can be in many contexts, each with one agent configured for that context. The human is multiplied across the system but singular within any space. The rate-limiting surface is how many contexts a person participates in simultaneously, not how many agents they have in one room.

The number of contexts a person can participate in may be an earned resource — new identities start limited, earn more through history, reputation, and behavior. The Sybil resistance mechanism is resolved: the protocol provides device attestation proofs (`DeviceAttestation` trait) and contexts may require attestation for admission via `ContextParams`; scoring algorithms and earned capacity formulas are product-layer concerns, not protocol-level. See the resolved Sybil resistance entry in `.docs/specs/00-open-questions.md`.

## 4.9 Agent Permission Model

A bound agent signs with `#agent`, its human signs with `#active`, and the DID's identity key is `#0` (§9.7.4, ADR-039). This section states which of those three keys authorizes which action, who writes that rule, and what a verifier checks. Three mechanisms answer three different questions, and a reader must not collapse them into one list:

- **Category A** fixes the answer in the protocol. No participant configures it.
- **Category B** lets the human who owns the DID bound their own agent's authority, through the UCAN fact `fct.scp_agent_permissions` (§4.9.2).
- **Category C** lets a context restrict what an agent may do inside that context, through the governance the context already runs (§5.9, §4.7).

Category A and Category B partition the protocol's actions: every action falls in exactly one of the two, and which one it falls in decides *who writes the signing-key rule for it* — the protocol, or the human. Category C partitions nothing. It is a second axis. A context adds restrictions on top of whatever Categories A and B already permit, and §4.9.4 states what a verifier does when the two axes disagree. An action that is not Category A is therefore Category B, and that fact says nothing about whether any given context permits it.

### 4.9.1 Category A — protocol-immutable

Category A is the set of actions that must be human-only for the accountability model to hold: an agent that could perform one of them could either bootstrap its own authority or rewrite its own constraints (ADR-039, Permission Model). Two criteria decide membership, and each names the key the action is reserved to.

**Criterion — reserved to `#0`.** An action is reserved to `#0` when performing it writes to the DID document: the record whose BEP44 signature a resolver verifies against the public key encoded in the DID string itself (§3.10.4, §9.6.1). Every field of that document is in scope, with no per-field carve-out, because publication is atomic — a writer cannot change one field without re-signing the whole document, and `#0` is the only key whose signature a resolver accepts on it (§9.7.4). The set is closed by construction: it is exactly the DID document's own field set (§18.2.2A), so a field added to the document joins the set without anyone extending an enumeration.

**Criterion — reserved to `#active`.** An action is reserved to `#active` when it creates authority that no existing delegation confers. Root UCAN issuance is that action: a root UCAN carries an empty `prf`, so its authority derives from the issuer's own key rather than from a parent token. An agent that could issue a root UCAN could grant itself every capability inside a context's ceiling, which is why the protocol fixes this rule rather than leaving it to the human's Category B configuration. Sub-delegation — minting a narrower UCAN from a delegation the agent already holds — is Category B, because a sub-delegation creates no authority its parent did not already confer.

**Indicators, not the criterion.** The table below lists the UCAN capability resource tokens a verifier uses to recognize a Category A capability inside a token's attestation set. Seven of the eight name DID-document writes, so they are evidence that an action writes the DID document; they are not the test for whether it does. The test is the criterion above, and a resource token absent from this table is still Category A when it writes the DID document. The eighth entry, `identity`, satisfies neither criterion: it names no DID-document field and creates no authority. It is in the set because `crates/scp-protocol/src/trust/custody_violation.rs` has carried it since before ADR-039 stated these criteria, and removing it would admit `#agent` on a resource no one has decided an agent may sign. Which criterion admits it, or whether it leaves the set, is the same open question `.docs/specs/00-open-questions.md` records for its key reservation.

| Resource token | What it writes in the DID document | Reserved to |
|---|---|---|
| `did_document` | the document as a whole | `#0` |
| `verification_method` | the `verificationMethod` array (§18.2.2A) | `#0` |
| `key_management` | the key entries of the `verificationMethod` array | `#0` |
| `pre_rotation` | the pre-rotation commitment (§9.7.4.1) | `#0` |
| `service` | the `service` array (§18.2.2A) | undecided — see below |
| `relay_config` | the `SCPRelay` entries of the `service` array (§18.2.1) | `#0` |
| `did_migration` | the `alsoKnownAs` forwarding entry the old document carries after an Identity Key migration (§9.7.4) | `#0` |
| `identity` | no DID-document field — see below | undecided |

Two rows read `undecided`, each for its own reason, and on both a verifier rejects `#agent` and admits `#active`.

`identity` is a Category A resource whose key reservation ADR-039 does not state: no ADR-039 bullet names a resource token spelled `identity`, and the token names no field of the DID document. An agent MUST NOT sign it, which is why it stays in the table. Which human key may sign it is an open question recorded in `.docs/specs/00-open-questions.md`. Reserving it to `#0` on the strength of its name would decide that question from downstream.

`service` is a DID-document field name and a legal custom context capability at the same time, and the resource token alone does not say which one a given capability URI means. §5.3.1.1 admits a custom ceiling entry `{resource}:{action}` whose segments match `[a-z0-9-]+` and which names no built-in, so a context may declare `service:read` and mean its own service registry by it. `service` is the only one of the seven DID-document resource tokens that grammar admits; the other six carry an underscore, which a custom entry may not. Reserving `service` to `#0` would reject a capability a context legitimately declared, so a verifier admits `#active` on it and `.docs/specs/00-open-questions.md` records which namespace owns the token. Admitting it grants nothing on the DID document: rule 2 below states that authority for a DID-document write comes from the `#0` signature on the published document, never from a capability token.

**What a verifier does.** Enforcement runs at every point where a signed artifact declares the verification method that produced its signature. UCAN validation is that point today, at step 6b of the eleven-step chain validation (§7.2.1). The inner envelope carries a `signing_key_id` and `SenderKeyEpochAdvance` carries a `signer_key_ref` (§9.5.2), and each reaches rule 1 through `enforce_inner_envelope_category_a` and `enforce_sender_key_category_a`; neither of those two functions applies rule 2, and no protocol flow carries a DID-document write inside either structure today, so no production path calls either one. At each point the verifier applies two rules in order:

1. When the signing key is `#agent` and the artifact carries a Category A capability, reject the artifact and record a `ScpCustodyViolationAttestation` (ADR-039, enforcement stack layer 4; §27.1 lists the record as attestation family F7). This is a custody violation: the agent key crossed a boundary the protocol fixes, and the record is permanent. No production path writes the record today, on the UCAN point or on either envelope point — §27.4.7 of the attestations spec derives that absence and records it as open question OQ-26. This rule states what a verifier does; a verifier that rejects and writes nothing satisfies its first half only.
2. When the artifact carries a capability reserved to `#0`, reject the artifact whatever key signed it. `#0` never signs a UCAN — the UCAN `kid` header admits `#active` and `#agent` and nothing else (ADR-039, Key Roles; `SigningKeyId` in `crates/scp-did/src/lib.rs`) — so a UCAN over a `#0`-reserved resource conveys authority no verifier can accept, and its presence is a malformed grant rather than a custody violation. Rule 1 runs first, so an `#agent` signature on a `#0`-reserved resource is still reported as a custody violation.

Rule 2 rejects a token signed by `#active`, and that is not a custody violation: the human used a key that cannot carry the authority, which the protocol reports as an error and does not record against the DID's reputation. Authority for a DID-document write comes from the `#0` signature on the published document (§9.6.1, §9.7.4), never from a capability token.

Rule 2 reads the resource segment of a capability URI and ignores its action segment, so it rejects `did_document:read` on the same grounds it rejects `did_document:update`, although the criterion above names a DID-document *write*. Rejecting the read spelling rejects nothing a context can grant: each of the six `#0`-reserved tokens carries an underscore, §5.3.1.1 forbids an underscore in a custom ceiling entry, and none of the six is a built-in capability, so no context ceiling admits one of them at any action and step 8 rejects such a token whatever rule 2 does. `service` is the one Category A resource token the custom grammar admits, and it is the one the `#0` reservation omits.

### 4.9.2 Category B — user-configurable

Every action that is not Category A is Category B. The human who owns the DID states which of them their agent key may exercise, in the UCAN fact `fct.scp_agent_permissions` (ADR-039, Permission Model).

**What the fact does that a narrower `att` set cannot.** A capability URI is bound to one context (`scp:ctx:{context_id}/{resource}:{action}`, §7.2.3), while the agent key is global — one `#agent` verification method per DID, not one per context (ADR-039, Key Roles). A human who narrows `att` states a bound for one context and must restate it in every context they ever join. The fact states the bound once, for the key, and a verifier applies it in every context. The fact also supplies a property `att` cannot: its absence denies rather than permits (see the default below), so a token that grants an agent key more than the human enumerated is rejected by a conformant verifier even when a non-conformant SDK minted it.

**Shape.** The fact is a JSON object under the key `scp_agent_permissions` in a UCAN's `fct` map:

```json
{
  "scp_agent_permissions": {
    "v": 1,
    "allow": ["messages:read", "messages:write", "outlet_call:*"]
  }
}
```

| Field | Type | Required | Meaning |
|---|---|---|---|
| `v` | integer | Yes | Fact format version. `1` today. A verifier rejects a version it does not implement rather than ignoring the fact. |
| `allow` | array of strings | Yes | The capabilities the agent key may exercise. Each entry is the `{resource}:{action}` tail of a UCAN capability URI (§7.2.3), carrying no `scp:ctx:{context_id}/` prefix because the bound applies to every context. The asterisk is permitted only as the whole action segment (`outlet_call:*`), never in the resource position and never as a substring — the rule §5.3.1.1 states for a ceiling entry's action segment. |

`allow` is a whitelist and the fact carries no deny list. Everything the human does not enumerate is denied, so the fact's meaning does not depend on the order in which a verifier reads two lists, and a capability family added to the protocol later is denied to every existing agent until its human enumerates it.

**Default when the fact is absent.** A verifier that finds no `scp_agent_permissions` on the chain applies the protocol default `allow` set: `["messages:read", "messages:write"]`. ADR-039 states the default as "messaging allowed, most other actions denied by default", and §5.3.1 spells the two messaging capabilities `messages:read` and `messages:write`. The default is a floor, not a placeholder — a human raises it by publishing the fact, and no code path widens it.

**Who may carry it.** Only a token whose `kid` is `#active` may carry `scp_agent_permissions`. A verifier that finds the fact on a token whose `kid` is `#agent` rejects that token, because an agent that could write its own bound has no bound. The rule keys off `kid`, the RFC 7515 header naming the verification method that produced the signature, so it does not depend on `fct.scp_key_scope` (§7.2.3).

**How a validator reads it.** When a presented token's `kid` is `#agent`, the verifier resolves the permission set and then applies it:

1. Walk the token's `prf` chain from the leaf toward the root and take the `scp_agent_permissions` of the first token that carries the fact, whose `kid` is `#active`, and whose `iss` equals the presented token's `iss`. The `iss` condition is what makes the bound the DID owner's own: the human and the agent share one DID (ADR-039), so the human's `#active` key writes the bound on a self-delegation (`iss == aud`, §7.2.3), and a delegator from any other DID cannot write a bound on someone else's agent. When no token on the chain satisfies all three conditions, use the protocol default above.
2. Check every capability in the presented token's `att` set — not only the invoked capability — against that permission set. A capability matches when its resource and action equal an entry, or when its resource equals an entry's resource and that entry's action is the asterisk. One unmatched attestation rejects the whole token, the same all-attestation rule the capability ceiling applies at step 8 of §7.2.1.

A token whose `kid` is `#active` skips both steps: the fact bounds the agent key, not the human's own key.

**The permission set never stands alone.** An agent key's effective authority in a context is the intersection of four bounds: the capabilities its token grants (`att`), the context's capability ceiling (§5.3), the context's Category C restrictions (§4.9.3), and the permission set. A verifier checks each bound on its own and no one of them widens another. Amount limits are not part of this fact: the permission set decides whether the agent may spend at all, and the `SpendingCapability` a token carries over the `scp:spending:{context_id}` resource decides how much (§19.5).

### 4.9.3 Category C — context-configurable

A context restricts what an agent may do inside it. ADR-039 introduces no new protocol primitive for this: each restriction is a context parameter or a role, declared at creation and changed through the context's own governance model (§5.9). A prospective member reads all four before joining, by two different routes: the three `ContextParams` fields are structural metadata, which §5.7 lists and makes visible before joining, and an agent-restricted role is part of the role definitions and role assignments the context publishes (§5.5).

**`agent_keys_allowed`.** A boolean on `ContextParams`, default `true`. When `false`, the context admits no artifact signed by `#agent`: a UCAN whose `kid` is `#agent`, an inner envelope whose `signing_key_id` is `Agent`, and an MLS credential whose `signing_key_id` is `Agent` are each rejected (§9.5.2, §9.7.1). Members still participate through `#active`. A governance proposal changes it.

**Agent-restricted roles.** A role assignment names the role a member holds (§5.5). Under the shared-DID model the human and the agent present the same DID, so an assignment may name a second role that applies when the signer is `#agent`. When the assignment names one, a capability check on an `#agent`-signed action reads that role's capability set; otherwise it reads the member's own role. The agent role's capability set MUST be a subset of the member's own role's set, so an agent never exceeds its human in the same context, and — as for every role definition — within the context's ceiling (§5.5.1, §7.2.1). The context's governance assigns and changes it, exactly as it assigns any role.

**`agent_rate_limit`.** An optional cap on how many actions signed by `#agent` a single member may take within a rolling window, on `ContextParams`, default absent. It bounds the agent persona only: an action signed by `#active` does not count against it. The cap denies an action once the window is full, which is what distinguishes it from the cost escalation of §19.7 — that mechanism reprices a high-velocity sender and never denies the send. A governance proposal sets and changes it.

**`agent_cosign_required`.** The list of capabilities that a member exercising them through `#agent` must additionally have signed with `#active`, on `ContextParams`, default empty. The list names capabilities rather than carrying a single boolean, because a context that required a human signature on every agent action would leave the agent nothing to do autonomously; a context names the consequential actions instead — for example `governance:vote` and `member:remove` (§5.3.1). When the invoked capability is on the list, the verifier requires a second signature over the same signed payload, produced by the `#active` verification method of the same DID, and rejects the action when that signature is absent or does not verify. A governance proposal sets and changes it.

### 4.9.4 What a verifier does when Category B and Category C disagree

Category B and Category C answer different questions, so neither overrides the other:

- Category B answers whether the DID's owner permits their agent key to take this action anywhere.
- Category C answers whether this context admits that action from an agent key at all.

A verifier admits an `#agent`-signed action only when both answers permit it. When Category B permits an action and the context's Category C parameters forbid it, the verifier rejects: context isolation is the security boundary (§4.7), and every member consented to the context's parameters before joining (§5.7), so a human's configuration of their own agent cannot reach past it. When a context's parameters permit an action and the owner's Category B permission set omits it, the verifier also rejects: the owner's bound on their own agent is theirs to set, and a context cannot widen it — a context that could would let an agent acquire authority its human never granted.

The effective authority of an agent key in a context is therefore the intersection of four bounds — Category B's permission set, the context's Category C parameters, the capabilities the token grants, and the context's capability ceiling — and no one of them widens another.

Category A sits outside both axes. No Category B permission set and no Category C parameter can permit `#agent` on a Category A action, and no context can waive the `#0` reservation on a DID-document write. Configuration reaches only the actions the protocol leaves configurable.
