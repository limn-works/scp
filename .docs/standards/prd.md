# PRD Standards

Standards for PRD stories in `.docs/prds/`. Every story — whether generated by `/loom:prd`, created manually, or added during an audit — must conform to these rules. CI enforces structural and provenance checks; agents enforce semantic accuracy during creation and review.

## Required Fields

Every story object must include all of these fields. No exceptions.

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | `PREFIX-NNN` format, zero-padded 3 digits |
| `title` | string | Short imperative title |
| `gate` | string | Gate ID — must reference an existing gate in the same PRD |
| `priority` | string | `P0` (blocking/foundational), `P1` (core functionality), `P2` (polish/optimization) |
| `severity` | string | `critical`, `major`, `minor`, or `moderate` |
| `status` | string | `pending`, `in-progress`, or `done` |
| `files` | array | Files this story creates or modifies |
| `description` | string | What and why — enough context for autonomous implementation |
| `acceptanceCriteria` | array | Concrete, machine-verifiable assertions (see below) |
| `actionItems` | array | Specific implementation steps |
| `blockedBy` | array | Story IDs this story cannot start without (may be empty). May reference stories in other PRDs for cross-PRD dependencies. |
| `sources` | array | Backlinks to source artifacts (see below) |
| `details` | object | Arbitrary metadata — use `{}` when empty |

## Optional Fields

Include when relevant. Absence implies the default.

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `tools` | array | `[]` | Capability categories: `browser`, `mobile`, `design` |
| `blockedByIssues` | array | `[]` | GitHub issue numbers that must be closed before this story can start |

## Gate Registration

Every story's `gate` value must reference a gate in the PRD's `gates` array, and that gate's `stories` array must include the story's `id`. A story that exists in `stories[]` but is not listed in any gate's `stories` array is orphaned — CI rejects this.

## Sources (Provenance)

Every story must trace back to at least one source artifact. The decision-making flow is unidirectional:

```
planning sessions / sketches → specs → ADRs → PRD stories
```

Stories must reference the **most specific** artifact in this chain:

- If an ADR defines the implementation approach, reference the ADR section.
- If a spec section defines the requirement, reference the spec section.
- If both apply (spec says *what*, ADR says *how*), reference both.

### Source format

```json
"sources": [
  { "file": ".docs/adrs/phase-4.md", "section": "## ADR-017: Trust Engine" },
  { "file": ".docs/specs/07-trust-validation-and-capabilities.md", "section": "### 7.3.6 Time-Locked Attestation Renewal" }
]
```

Every source `file` must exist in the repository. Every source `section` must exist as a heading in that file. CI verifies both.

### When no external source exists

If a story was inferred from codebase context (e.g., a bug found during audit), use `[]` for sources and explain the origin in `description`. This is valid but exceptional — most stories should trace to specs or ADRs.

## Acceptance Criteria

Every acceptance criterion must be **machine-verifiable**: a test can be written for it, or a grep/build/lint command can check it. Criteria that fail this test:

| Bad | Why | Good |
|-----|-----|------|
| "it works correctly" | Untestable | "POST /api/x returns 200 with a JWT" |
| "all functions are wired" | Vague quantity | "outlet_register, outlet_invoke, outlet_verify call scp-core pipeline" |
| "async/await works" | No observable | "at least one async roundtrip test per module compiles and executes" |
| "handles edge cases" | Which ones? | "rejects expired attestations (returns RenewalError::Expired)" |

### 1:1 mapping from source requirements

Every structured requirement in the source spec/ADR must have a corresponding acceptance criterion. Do not merge multiple requirements into one criterion. Do not drop conditional language ("unless", "except when", "only if") — these become explicit test cases.

## Dependencies (`blockedBy`)

### Directionality

Dependencies must be **forward-only**: a story depends on work that must exist before it can start. Common errors:

- **Backwards dependency**: Story A "depends on" Story B, but B actually consumes A's output. The dependency is reversed.
- **Transitive over-specification**: Story A depends on B which depends on C. Story A lists both B and C. Only list B — C is transitively covered.
- **Scope confusion**: Story A wires tools/UCAN/event_log in a bridge. Story B wires KeyCustody. A lists B as a dependency, but only identity operations in A actually need KeyCustody — not the tools/UCAN/event_log work. Either split A or remove the false dependency.

### Validation

Every ID in `blockedBy` must reference an existing story — either in the same PRD or in another PRD file (for cross-PRD dependencies). CI rejects dangling references. CI also warns on stories that are `blockedBy` a `done` story — a completed dependency should not block pending work.

Cross-PRD references enable orchestrator scheduling: a story is assignable when all `blockedBy` stories are `"done"` and all `blockedByIssues` (GitHub issue numbers) are closed.

## Story Scope

Each story must be completable by a single agent in one iteration (~15-30 minutes). If a spec section has more than ~7 subsections or the implementation spans more than ~3 files with distinct concerns, split into multiple stories with a blocking sequence.

## Status Consistency

- `pending`: no implementation exists
- `in-progress`: partial implementation
- `done`: all acceptance criteria met, code merged, tests passing

A story marked `done` must have zero stubs against its acceptance criteria (see `sdk-common.md` §Stub Policy). CI cross-references stub comments (`// Stub — see SCP-NNN`) against story status.

## Description Quality

Descriptions must give an implementer enough context to work autonomously. Include:

- What the story accomplishes and why
- Relevant spec section references (e.g., "per §7.3.6")
- Relationship to other stories (e.g., "data model from SCP-062, orchestration is this story")
- Scope boundaries (e.g., "identity wiring is SCP-214, not this story")

Use the source's own language — do not paraphrase unless the original is ambiguous.

## Files List

- List all files the story will create or modify.
- Include module declaration files (`mod.rs`, `__init__.py`, `mod.ts`) if new modules are added.
- Files that don't exist yet are expected for implementation stories.

## CI Enforcement

The `prd-validate` CI job checks all `.docs/prds/*.json` files on every PR that touches them. It enforces:

1. **Schema**: all required fields present on every story
2. **Gate registration**: every story listed in its gate's `stories` array
3. **Source existence**: every `sources[].file` exists in the repo
4. **Source section existence**: every `sources[].section` exists as a heading in the referenced file
5. **Dependency validity**: every `blockedBy` ID references an existing story
6. **No orphaned stories**: every story's gate exists
7. **Status consistency**: no `pending` story blocked by only `done` stories (likely stale)
8. **ID uniqueness**: no duplicate story IDs
