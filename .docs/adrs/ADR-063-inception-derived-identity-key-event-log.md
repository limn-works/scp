## Context

Every SCP participant needs a decentralized identifier that no central operator controls, that supports key rotation, and that a relying party can verify without trusting the party that served it. ADR-003, DID Creation (did:dht), settled this need by adopting did:dht as SCP's primary and only planned DID method: the identifier was the z-base-32 encoding of the identity's root public key, the SDK published each DID document to the BitTorrent Mainline DHT as a BEP44 signed mutable item, and a resolver read the highest-sequence record back and re-verified its self-certifying binding.

ADR-003's did:dht-only mandate rested on one settled decision that misread its own source. That decision widened a preference Alec stated on 2026-08-11 about the Mainline bootstrap record's *encoding* — "ok we should be just doing did:dht as it should be. no need to do anything custom" — into a mandate governing SCP's entire identity *method*, dropped the controlling clause "no need to do anything custom," changed a preference into a settled fact, and stamped Alec's name on it. Alec repudiated that widened decision on 2026-08-30: "that was in the context of mainline bootstrapping. ultimately it is a falsification of intent." This ADR rebuilds the identity architecture from Alec's actual intent, recorded in the identity-substrate execution plan (`/Users/alec/.claude/plans/identity-substrate-plan.md`), §1.

Alec's intent names a different substrate: a self-certifying identifier derived from an inception event, governed by an append-only key-event log, in SCP's own encoding. The KEL model and the did:dht model differ at the root. did:dht resolves identity by reading one mutable record and taking the highest sequence number; the KEL resolves identity by replaying an append-only log of key events from its inception event forward. did:dht's identifier binds permanently to the initial public key and cannot rotate at the root, which forced ADR-003 to change the DID string on recovery; the KEL's identifier binds to the inception event, so root recovery appends a rotation event and never renames the identifier.

## Decision

SCP's identity is an **inception-derived self-certifying identifier over an append-only key-event log (KEL)**, encoded in SCP's own format. The identifier is a digest — SHA-256, matching the hash the security-model spec uses throughout its canonical constructions — over a canonical, domain-separated, length-prefixed serialization of the inception event, in the construction style the security-model spec already fixes (`09-security-model.md` §9.5.1 canonical construction and the §9.12 preimage style: a domain separator, then each field in a fixed order, a 4-byte big-endian length prefix on every variable-length field, fixed widths for keys and timestamps, and the §9.5.1 absent-value sentinel for an absent optional field — with the caveat that the sentinel is a bare 32-byte constant, so the Track U4 byte layout gives a presence discriminator to any optional field whose value an adversary can choose, because an adversary-chosen field set equal to the sentinel constant would otherwise collide with the absent encoding). The substrate spec fixes the exact field order and byte layout under Track U4. The inception event does **not** carry the identifier as one of its serialized fields — the identifier is derived from the event and then names the log — so no self-addressing fixpoint arises and no placeholder value is needed during derivation. The inception event fixes the root key `#0`, the first pre-rotation commitment, and the identity's initial witness set and cosigning policy (Layer B of the key-status-resolution section). Every later key event — rotation, retirement, recovery — appends to the log and carries its own signature. Each event preimage carries an event-type discriminator byte, the anti-type-flipping device the security-model spec's inner envelope already uses (the `message_type` byte of `09-security-model.md` §9.5.2), and every KEL domain separator is a fresh, version-suffixed string **registered** in the security-model spec's domain-separator registry (`09-security-model.md` §9.18.2) with its construction class stated — registration in the one table, not distinctness maintained by inspection, is what keeps separators collision-free as the table grows. The registration duty covers every signed artifact this ADR defines, not only key events: the witness cosignature (Layer B of the key-status-resolution section) is a §9.5.1 canonical construction under its own registered separator, because a witness is a relay whose key also signs other relay structures, and a signature without its own separator invites cross-protocol confusion between those structures. The gate bundle and the equivocation fault proof carry no separator of their own, because neither is a signed structure: each is a container over already-signed material — the bundle holds a head, a chain of key events, and the cosignatures a party gathered, and the fault proof holds two cosignatures over divergent heads — and a verifier checks either one by replaying the signatures the container carries, each of which verifies under the separator its own structure registered. Track U4 fixes the exact byte layouts and registers the separators.

Self-certification is an **offline** check: a relying party verifies the identifier-to-inception-event binding from the inception-event bytes alone, with no network call, because the identifier is that event's digest. Resolving an identity's **current** key status is a **separate, network-dependent** operation — a log resolution over the relay network subject to the freshness, completeness, and non-equivocation model in the next section — and is not offline.

This substrate takes KERI's inception-derived append-only-log **shape** and adopts none of KERI's code or wire formats: no CESR encoding, no out-of-band-introduction (OOBI) discovery, and no dedicated witness or watcher pool infrastructure. SCP keeps the witness and watcher *function* — freshness, corroboration, and non-equivocation — but provides it with its own two-layer mechanism over its own relay network (the next section), not with KERI's pools. SCP does not adopt did:dc, the abandoned bespoke digest-chain DID method. The log is SCP's own append-only key-event log in SCP's own encoding.

The following elements of ADR-003 no longer govern SCP:

- **did:dht is not SCP's method.** did:dht is not SCP's identity method. The mutable-highest-sequence-record resolution model is replaced by log replay.
- **Mainline DHT is removed.** SCP runs no did:dht-conformant Mainline bootstrap layer. The SCP relay network carries identity: a resolver reads an identity's key-event log over the relay network and replays it. The relay stays untrusted — it may validate a public, self-certifying key-event frame it stores for availability, but a relying party re-verifies every event independently, so correctness never depends on a relay.
- **The DID string is an optional, deferred facade.** SCP does not depend on a DID string. A `did:scp` method facade over the KEL is deferred on Alec's 2026-08-30 ruling — "punt, be ready, don't foreclose": the `IdentityBackend` seam (the identity-substrate execution plan, Track S6) keeps the facade interface-ready, the facade itself stays unbuilt and unspecified, and SCP builds it when a concrete external-verifier demand (an EUDI, eIDAS, or W3C Verifiable Credentials consumer) appears.
**The curve, and what a key event names about each key (Alec, 2026-09-10).** Every key this substrate defines is an **ECDSA key on NIST P-256** — each root-set member, each pre-rotation key, and each operational key — and a signature over a key event is an ECDSA signature under SEC1 point encoding, 64 raw bytes of `r` concatenated with `s`. A software signer draws its nonce deterministically under RFC 6979, and every verifier rejects a signature whose `s` exceeds half the group order, so one message and one key yield one signature and a relay cannot re-encode a signature into a second accepted form. **The inception event names each key's algorithm**, in KERI's and CESR's style, so an identity created where no P-256 custody exists is still legible to every verifier rather than unrepresentable. **A root signature MAY be a WebAuthn assertion**: the signed bytes are `authenticatorData || SHA-256(clientDataJSON)` with the event's §9.5.1 preimage digest carried as the WebAuthn challenge, and a verifier accepts that form beside the raw ECDSA form. That signature carries `SHA-256(rpId)` inside `authenticatorData`, which is public in the log; the rpId binds the passkey and never the identity, because a relying party verifies the identifier and the key state and reads no rpId in either.

**Root custody defaults to a passkey (Alec, 2026-09-10).** The SDK's default custody for a root-set member is a passkey under a universal relying-party identifier, `ctx.network` by default, and the pre-rotation key is a second passkey created ahead of time. Alec's reason, from the identity-substrate decision log: the residuals this design carried were self-custody cases, and the intended default custody is "a passkey in your apple passwords or similar", under which the lost-root case becomes platform-account loss, which SCP does not own. `09-security-model.md` §9.7.4.1 states the custody methods, the profiles each one conforms on, and the residual that survives on the profile with no passkey API. **Portability across several vendors' applications is deliberately not decided** (Alec, 2026-09-10: "do we have to decide on portability right now? want to avoid sidequests"), and nothing in this substrate forecloses any of the paths the decision log records; custody and operations carry that decision, not the KEL.

## Resolving current key status over an untrusted relay

An append-only log served by an untrusted relay raises a completeness problem that per-event signatures do not solve: a relay can withhold the tail of the log and serve a valid earlier prefix, so a resolver replays a stale-but-signed history in which a rotated-away or `Compromised{from:N}` key still reads as current. Each event's signature proves that event's authenticity; no event's signature proves that the resolver has received every later event. SCP addresses this in two layers, and adopts none of KERI's CESR encoding, OOBI discovery, or dedicated witness and watcher pool infrastructure.

The log is hash-chained: each key event names the digest of its predecessor, so a resolver that receives a set of events verifies by construction that it holds a contiguous prefix and detects any reordering, substitution, or gap within what it received. Hash-chaining secures the integrity of received events; it does not, on its own, prove that a resolver received the latest event, and it does not detect two divergent logs. The two layers below add those two properties.

### Layer A — freshness and anti-rollback, at parity with did:dht

The current key-state is the replay of the key-event log; freshness is anchored on the **highest-sequence key event**, not on a separate signed statement about the log (the current `#active` may have been set several events before the newest one, which could be a status assertion — the highest sequence fixes recency, and the replay fixes the state). Each key event carries a monotonic sequence number and is signed once by its authorizing key at the moment it occurs (the matrix below); a relay re-serves that already-signed event and never re-signs it, so `#0` stays cold and no key signs on a resolution schedule — an identity signs a key event only when it actually rotates, retires, updates its witness set, refreshes its pre-rotation commitment, or recovers. A resolver establishes the current key-state by two rules the security-model spec already states for did:dht, re-homed onto the key-event log, and the serving tier backs the second rule with an append-only invariant:

- **The highest head of the winning chain, across independent relays.** A resolver queries several independent relays. Heads of one chain differ only in how far each relay has caught up, so among those the resolver takes the longest — the highest sequence — re-homing §3.10.7 (the highest valid sequence is authoritative) onto the log. Heads of *divergent* chains are not comparable by sequence at all: the resolver first settles which chain wins by the precedence comparison of the root-recovery section, and only then takes the highest head of that chain. Sequence orders a chain against its own prefixes; rank orders one chain against another. Highest-valid selection applies at both nesting levels — within one relay's response, when a relay serves several stored records, and then across relays — because a first-valid selection is a shipped defect this repository has already corrected once: ADR-062, capability injection, records the merged relay querier selecting first-valid and directs its completion to highest-valid. A single relay that withholds the tail is defeated when another relay serves the newer event — which presupposes the newer event reached an independent relay, so the controller submits each key event to its relays and witness set, and a resolver that has just seen a newer head re-publishes it to a relay serving a stale one (resolver-driven relay healing — the resolver, having seen both heads, is the actor of record, since a relay has no incentive to heal a competitor's stale replica). Healing re-serves an already-signed event and never re-signs, so it warms no key. "Several independent relays" carries the same unsolved independence problem as the witness set of Layer B: a resolver whose queried relays are one operator's fleet gets no withholding resistance, so relay-population independence is part of the replication requirement Track U4 must state, not assume.
- **Reject a lower sequence on the accepted chain, and settle a divergent chain by precedence rather than by sequence.** The reject-lower rule governs a candidate head that lies on the chain the resolver already accepted: for an identity it has seen before, a resolver rejects a head of that chain at a sequence strictly lower than the highest it previously observed, re-homing §9.6.1 (the reject-lower rule, which the source states over strictly-lower sequences) and the §9.7.1 rollback-resistance assumption off the removed BEP44 record onto the log. At an equal sequence on that chain, an identical head confirms the stored baseline. A candidate head that does **not** lie on the accepted chain is a divergent chain, and its sequence number decides nothing: each fork's author assigned its own sequence numbers, so comparing them measures how far each author extended its own fork rather than which fork is authoritative, and an attacker who appends filler events to a fork would win every such comparison. The resolver therefore settles every divergence by the precedence comparison of the root-recovery section — it computes the shared prefix, ranks each divergent suffix by whether that suffix reveals the shared prefix's standing commitment and by whether the revealing event also carries the signature of the root standing at that event's predecessor, and adopts the winning chain **in its entirety**, whether that chain's head sequence stands above or below the head it previously held. A divergent chain that loses the comparison never updates the baseline. A divergence whose two suffixes tie at the same rank makes the identity contested (the root-recovery section): the resolver adopts neither side, retains both heads as equivocation evidence, and feeds the equivocation flag (the lock-free resolver state in the implementation-constraints section). Adopting a lower-sequence winner is the one non-monotone transition the baseline admits, and the precedence comparison over two chains is what decides it — a scalar watermark cannot, which is why the implementation-constraints section states that watermark as a floor over candidates on the accepted chain and never as the arbiter between chains.
- **The serving tier is append-only for key events.** The reject-lower rule protects a resolver that has observed the identity before; a serving relay's cold restart re-opens a delete-the-head-then-replay-an-older-signed-record rollback that client-side monotonicity cannot close at first contact, so the serving tier generalizes the storage-derived, fail-closed delete gate the identity spec fixed for exactly this attack on the single BEP44 record (`03-identity.md` §3.10.8 rule (d)). The generalization is wider than the source rule because the store is wider: the BEP44 gate protected one self-certifying blob whose protected status a relay re-derives from the blob's own bytes with one hash and one signature check, while a KEL is many events and a non-inception event is chain-certified — its authorizing key is fixed by the prior chain, not by its own bytes — and deleting an interior event severs the chain on that relay exactly as deleting the head does. The serving-tier invariant is therefore: a KEL-serving relay's store is append-only for the key events of any log whose inception event it holds — the relay refuses a client delete of any such event, derives the refusal by replaying the stored chain (a cost linear in the log length per delete request, so the gate is rate-limited), and fails closed on a storage read error.

This is **parity in mechanism with did:dht's actual guarantee**, with effective strength scaling with the independent-relay population rather than equalling Mainline's out of the gate: did:dht mitigated withholding the same way — take the highest sequence across the nodes queried, and heal a stale replica from a fresher one — and never prevented it either. Under Layer A, withholding is *mitigated* (an honest relay defeats it), not *prevented* (a resolver whose every queried relay withholds the tail is held on the stale head). The mechanism is at parity; the strength is only as large as the independent-relay population — did:dht drew that breadth from Mainline's node count, and here the A+B system draws it from the community relay-and-witness set, a property Track U4 must state as a replication requirement, not assume. The relay's availability and anti-suppression role is defense-in-depth; a resolver trusts no single relay, consistent with the untrusted-relay tenet. The sequence mechanism is therefore availability and reconciliation, not a freshness guarantee: a sequence number cannot reveal that a newer event is being withheld, so a relying party that wants a bound on an accepted head's staleness reads a Layer B cosigned head, whose witness timestamp supplies one — the division every at-scale transparency system draws between replica reconciliation and witnessed freshness. That Layer B guarantee is conditional: a witness timestamp bounds the staleness of the newest head *that witness received*, so the guarantee holds only while the controller's new key events reach the recognized witness set within the witnessing interval. The guarantee defends a relying party against a stale-serving relay; it does not defend against an adversary who withholds the controller's new events from the witnesses themselves, because honest witnesses starved of an event re-cosign the older head as fresh — starvation and a quiet log present the same evidence. The controller's witness-submission duty and the propagation assumption behind this condition are the liveness assumptions the detection bullet routes to Track U4. Layer A does not detect **equivocation** — a controller, or an attacker holding `#0`, who signs two divergent but individually-valid logs from one inception. did:dht did not detect this either. Layer B adds it.

### Layer B — the watch-and-report witness layer

Layer B is a witness and watcher layer that keeps KERI's witness-and-watcher function and its role split — witnesses answer to the identity's controller, watchers answer to the verifying party — in SCP's own encoding: no CESR, no OOBI, no dedicated pools. It reuses the relay machinery SCP already runs: **witnesses are relays.** The witness attestation is a **cosigned log head**, the head-granularity form every transparency system that shipped equivocation protection at scale converged on — Certificate Transparency's multi-log policy, WhatsApp's and Apple's audited key-transparency maps, the Go checksum database, and Sigsum's cosigned tree heads, whose witness protocol this design follows — while per-event witness receipts remain KERI's mechanism alone, deployed at no comparable scale (the external patterns dossier named in the provenance chain grounds the comparison, and the alternatives section records the rejection).

**A witness watches and reports, and it decides nothing.** On top of its store-and-serve role, a witness cosigns an identity's log head once per witnessing interval, and before it signs it runs **one check**: does the chain it is asked to cosign carry, at that exact sequence, the exact event digest of the head this same witness last cosigned for this identity. Where the chain carries it, the witness signs. Where the chain does not, the witness refuses and emits a **conflict statement** naming the head it holds and the head it was offered. The witness runs no other test on the two chains and reaches no verdict about them. `09-security-model.md` §9.7.4.3 states the cosigned head's fields, its signature preimage, its address, the check, the conflict statement, and the witness's durable per-subject state; this ADR states the model and restates none of that text.

- **A cosignature is evidence, and no verdict, key-state derivation, rank, or gate depends on one (Alec, 2026-09-10).** A relying party derives an identity's key state by replaying the chain it adopted under Layer A, and it settles a fork by the root rule of the root-recovery section below. It reads a cosignature for three things and no fourth: a bound on how stale the head it holds may be, evidence at first contact that operators it recognizes were serving this chain at a stated time, and evidence that a party offered two divergent chains for one subject. Where an identity designates no witnesses, a relying party reads none of those three for it and every other rule behaves exactly as it does with the layer present. The amendment record below states the ruling that put the layer here and the reason Alec gave for it.
- **The witness never adjudicates, and the reason is that it holds nothing to adjudicate with.** At a witness, a genuine recovery and a theft of a spent pre-rotation key are the same object: in each, one party reveals the standing commitment of the two chains' shared prefix on a suffix that diverges below the head the witness last cosigned. A witness holds a per-subject record of about 112 bytes — the subject's identifier, the sequence and event digest of the head it last cosigned, the digest of that cosigned head, and the timestamp it stamped — and no chain, while separating those two cases requires both chains back to their common ancestor. **A relying party can answer "I cannot decide" by returning a contested verdict; a witness's answer is a signature, and a signature ends the matter.** Adjudication between two chains that one set of key material signed therefore belongs at the relying party, and never at a witness.
- **A recovered identity reaches witnesses by naming a fresh set in its recovery event.** The outgoing witnesses hold a last-cosigned head the recovered suffix does not carry, so the one check makes them refuse it, and they go on refusing it. The recovery event names fresh witnesses, which hold no last-cosigned head for this subject; each verifies the chain from the inception event — self-certifying, because the identifier is that event's digest — seeds its baseline, and cosigns. **A party holding a spent pre-rotation key takes that same path**, because the path reads nothing that party cannot produce. Both suffixes then carry cosignatures from disjoint sets, and neither set's signatures decide anything: the relying party compares the two suffixes under the root rule below, exactly as it would with no cosignature in hand.
- **A witness that cosigns two divergent heads is proven faulty by those two signatures**, which is the layer's fault proof and the reason each cosigned head names its predecessor. That proof is about the operator, never about the subject: it tells a reader that a named operator departed from the one check, and it decides no fork.
- **The witness set names itself in the identity's signed record, and it carries a witnessing interval.** An identity's establishment events name the **witness set** — the relays this identity asks to cosign its head, which every relying party reads to learn where to fetch cosigned heads from — and the **witnessing interval**, the cadence at which each named witness re-cosigns the head and the input to the staleness bound a relying party applies. The field pattern is the same "designated in your own signed record" pattern as the `SCPRelay` transport set. The fields exist from the first version of the inception-event schema for a narrow, stated reason: an identity's inception event is immutable — its digest is the identifier — so a field absent from the first schema can never appear in an existing identity's *initial* record, and the initial witness set is exactly the field a first-contact resolver reads. A later `#0`-signed establishment event replaces both fields (the signing-authority matrix below). For a normal user the app and SDK supply the set from a shipped default, and the user never chooses a relay.
- **Which operators a relying party recognizes is that party's own policy, and it defaults to the SDK-shipped community relay list.** `18-addressability-and-deployment.md` §18.5.1 defines that list — a per-release artifact, identical across bindings, each entry declaring the operator identity that runs the relay — and it is the source of the recognized set. **Independence is not enforceable, and the spec says so in those terms (Alec, 2026-09-07).** Nothing in the protocol proves two operators are different parties, because an inception-derived identifier is a self-signed digest. What is mechanical is a local set-membership test against that shipped list, together with proof of control of the declared operator identity, which a cosignature supplies by construction because only that operator's `#active` key produces one. A badly curated list, or several entries secretly under one operator, is a supply-chain risk no protocol check covers — the class a compromised browser root store belongs to — and `09-security-model.md` §9.7.4.3 states that plainly. **Anti-self-witnessing is a curation obligation the list's curator carries and not a property this protocol delivers**, because an operator identity is a different identifier from the identity that operator witnesses, so a controller whose operator identity the list carries sits in every default recognized set.

**Timestamps and convergence.** A cosigned head's timestamp is the witness's authenticated value and every consumer adopts it verbatim; the only party that judges it against a clock is a relying party applying a staleness bound to evidence it holds — a per-party judgement by construction, because a party whose clock runs ahead treats more cosignatures as stale and therefore reads less evidence, never more. No cosignature and no witness timestamp enters the context event log or any other structure honest context members compare, so no receiver-side clock verdict can fork honest members — the convergence discipline the security model's equivocation test requires (`09-security-model.md` §9.9.3), which ADR-057, the in-browser client, re-established in its T3 slice by removing a receiver-side timestamp-plausibility window after the repository shipped that mistake once.

**Open item — first-contact discovery.** How a relying party first learns an identifier — the mapping from a human-readable handle or a referral to an inception-derived identifier — is the first-contact bootstrapping problem the security-model spec already frames (`09-security-model.md` §9.6.4: shared-context membership, registry discovery, or referral). Those paths supply the *identifier*; resolving its *current key-state* is then the Layer A path above. A discovery registry (`22-human-readable-addressing.md`) returns a handle-to-identifier binding and does not itself carry key-state. First contact is where Layer A is weakest, and the ADR states it rather than hiding it: a resolver with no previously-observed sequence has no reject-lower baseline, so its recency evidence is Layer A's highest head of the precedence-winning chain across independent relays, plus any cosigned head whose witness it recognizes — that witness's timestamp gives a first-contact resolver a bounded-staleness signal did:dht never offered, and the reject-lower gap itself remains until a first observation seeds the baseline. SCP drops KERI's OOBI mechanism, not the first-contact function. The substrate spec settles the exact KEL discovery surface (Track S2 resolution, Track U4 spec amendment) before any Track S implementation lands; this ADR records it as an open item, not a resolved mechanism.

## Which authority signs which key event

The compromise model follows directly from which authority signs which kind of event. SCP fixes that assignment here.

| Event or signed artifact | Signing authority |
|---|---|
| Inception event (fixes `#0`, the pre-rotation commitment, and the initial witness set; the identifier is derived from the event, not carried in it) | `#0` (root), at inception |
| Operational-key rotation (replace an operational signing key, currently `#active` or `#agent`) | `#0` (root) |
| Witness-set and cosigning-policy update (names the current witness set and the witnessing interval; changes no key) | `#0` (root) |
| Key-status assertion (`Superseded`, `Retired`, `Compromised{from:N}`; a later `#0`-signed assertion over the same key supersedes an earlier one, so a false alarm is withdrawn by a new event, never by deletion) | `#0` (root) |
| Pre-rotation commitment refresh (reveals the standing commitment's preimage, keeps `#0`, and fixes the next commitment — the `09-security-model.md` §9.7.4.1 item 6 refresh) | the pre-rotation private key (over its revealed public half) **and** the incumbent `#0`, together (see root recovery below) |
| `#0` recovery (reveals the standing commitment's preimage, installs the revealed key as the new root, and fixes the next pre-rotation commitment) | the pre-rotation private key, by a signature over the recovery event whose revealed public half's SHA-256 equals the standing commitment, together with the incumbent `#0` where the controller still holds it — which is what puts the recovery at tier A of the precedence order (see root recovery below) |
| Content signature (broadcast authorship) | an operational signing key (currently `#active` / `#agent`), never `#0` |
| KeyPackage attestation (`09-security-model.md` §9.5.2) | an operational signing key (currently `#active` / `#agent`), never `#0` |
| Service record (mutable owner-signed metadata: relay endpoints, capability and broadcast advertisements, attestation pointers) | the operational key a `#0`-signed key event designates for the service-record role, never `#0` (the Consequences section states the record's lifecycle) |
| Cosigned log head (Layer B): the triple of identifier, sequence, and head digest, plus the witness's own timestamp | a witness relay — evidence, not identity authority |

The matrix is the compromise model, and one closure rule makes it a model rather than a list: **the pre-rotation commitment moves only in an event that reveals the standing commitment's preimage** — inception fixes the first commitment, and the two reveal-authorized event kinds in the matrix (the commitment refresh and the `#0` recovery) are the only events that fix a later one, so no `#0`-signed event can re-point the commitment, and the standing commitment is unique on every fork: it is the commitment fixed by the last reveal-authorized event on the chain prefix the forks share. Because `#0`, not an operational key, signs every rotation and every status assertion, an attacker who compromises only an operational signing key (currently `#active`/`#agent`, or the designated service key) cannot rotate a key, cannot assert a key's status, and cannot withdraw an assertion; it cannot equivocate the log head either, because a fork is a pair of divergent `#0`-signed heads and this attacker does not hold `#0`. That attacker can sign content and mint KeyPackage attestations under a compromised `#active`/`#agent` key, or redirect the service record under a compromised service key, only until `#0` signs a rotation event that retires the compromised key, at which point the security-model spec's current-key-only rule (`09-security-model.md` §9.7.1 check 1) revokes it. Operational-key compromise is therefore self-contained and recovered by an ordinary `#0`-signed rotation, exactly as the compromise-recovery protocol already specifies (`09-security-model.md` §9.12 steps 1–4). Compromise of `#0` is the case the root-recovery section below handles: an attacker holding the compromised `#0` can sign a fork but cannot reveal the pre-rotation preimage, so the legitimate owner's reveal-authorized recovery supersedes the attacker's chain deterministically and offline (the root-recovery section states the precedence rule), with no dependency on Layer B witnesses; a Layer B watcher's surfacing of a `#0` fork is an additional asynchronous signal, not the mechanism that resolves the recovery. Compromise of the **pre-rotation key alone** is the converse case: the thief can sign a reveal-authorized takeover, and the controller — who still holds the intact `#0` and the same pre-rotation key — signs a commitment refresh that reveals the same standing commitment and carries the standing root's signature. **An intact `#0` contains that outcome**, because the refresh stands at tier A and the thief's bare reveal at tier B, so the controller's chain wins the precedence comparison of the root-recovery section outright. The refresh also fixes a commitment the thief cannot reveal, which stops the takeover from being attempted a second time on the controller's suffix. A thief with *exclusive* possession of the pre-rotation key — the controller's copy destroyed, not copied — leaves the controller unable to sign any reveal-authorized event, so the thief's reveal-authorized chain stands and exclusive pre-rotation-key theft is root takeover; the independent-custody dependency of the root-recovery section is load-bearing for exactly this case. Compromise of **both** the `#0` key and the pre-rotation key is unrecoverable: the attacker can then produce every event class the matrix defines, and no rule in this ADR distinguishes it from the controller — the independent-custody dependency of the root-recovery section exists to keep the two compromises from being one event. This matrix scopes key events in the log; the security-model spec's `KeyDestructionAttestation` (§9.15) is a per-context artifact that `#0` or `#active` signs — §9.15 forbids `#agent` — outside this matrix.

## Root recovery and the stable identifier

`#0` recovery installs the revealed pre-committed key as the new `#0` **root** authority. The recovery event reveals the pre-rotation public key, whose SHA-256 equals the standing pre-rotation commitment, and is signed by that key's private half (`09-security-model.md` §9.12 Identity-Key compromise names the reveal-against-commitment step; ADR-003 §4b verified the reveal alone and had the *old* `#0` sign the migration, so the signature-by-the-revealed-key requirement is this ADR's addition to that precedent, not §4b's shape). Authorization is the signature, not the reveal alone: a revealed public key is public the instant it appears, so a matching value by itself is replayable, and the signature by the corresponding private key is what authorizes. Recovery therefore does not depend on the secrecy of the compromised `#0` key — it depends on control of the independently-held pre-rotation private key.

**Every reveal-authorized event fixes the next pre-rotation commitment in the same event.** The recovery event reveals the old preimage, installs the revealed key as the new `#0`, and commits to a fresh pre-rotation key generated in the independent custody substrate before the reveal; the commitment refresh (the signing-authority matrix) reveals and re-commits the same way while keeping `#0`. A valid chain therefore always carries a standing commitment — inception fixes the first, and every event that consumes one fixes the next — so recoverability never exhausts, and a chain whose latest reveal-authorized event fixes no successor commitment is invalid: a verifier rejects it with a typed error rather than treating the identity as recoverable. Fixing the next commitment restarts the retention contract below for the new preimage and private key.

**Precedence between conflicting root-authority chains is deterministic, offline-checkable, and evaluated at chain granularity.** When two chains diverge from a shared prefix, a verifier ranks each divergent suffix by reading two properties of it — whether the suffix carries an event revealing the standing commitment of the shared prefix, and whether that revealing event also carries a signature by the root standing at its own predecessor — and it prefers, in order: a suffix whose revealing event carries that root signature (rank 1, tier A); a suffix whose revealing event carries no such signature (rank 2, tier B); a suffix that reveals nothing (rank 3). **The root rule, in one sentence: a reveal that the standing root co-signed outranks a reveal that it did not, and any reveal outranks no reveal.**

**Amendment, 2026-09-10 — the two-tier order is restored, and the two-rank order that replaced it on 2026-09-07 is withdrawn.** The 2026-09-07 amendment collapsed the two tiers into one rank, so that a root co-signature on a revealing event stopped counting toward precedence at all. That amendment carried out an instruction the orchestrator issued, and Alec had already ruled the other way on the same day: **"Root wins sounds like a good solution."** His reason, verbatim: **"If an attacker has the root, it's GG. What would you gain by trying to optimize against that case?"** The argument the collapsed order rested on — that ranking by co-signature hands a thief holding both the root and a copied pre-rotation key the win over a controller who lost its root and holds the genuine pre-rotation key — describes an adversary who already holds the root, and Alec ruled that the comparison buys nothing against that adversary while it costs the far commoner case: a controller whose root is intact and trusted, facing a holder of a copied pre-rotation key, wins under the two-tier order and only ties under the collapsed one. The two-tier order above therefore governs, and every sentence of this ADR that stated the collapsed order is superseded.

**Tier reads the root's standing at the revealing event's predecessor, and that is what makes tier a property the shared prefix fixed rather than one the claimant chose.** Read at the event itself, the standing root of a `RootRecovery` is the fresh set K′ that the event installs, so any claimant would satisfy the tier test with its own key and the test would decide nothing. Read at the predecessor, the standing root is the root of the shared prefix, because the only two event kinds that install a root are the inception event and a `RootRecovery`, a `RootRecovery` is itself reveal-authorized, and no reveal-authorized event sits below the suffix's *first* revealing event. A claimant therefore cannot install a root of its own and then satisfy tier A against it.

The verifier reads each suffix in full for the reveal rather than the divergence event alone, because a reveal that sits above the first event after the shared prefix fixes the suffix's rank exactly as one at that first event does. A revealing suffix's reveal verifies against the standing commitment of the shared prefix, which the closure rule of the signing-authority matrix makes unique — no `#0`-signed event can move it — so the comparison needs no witness, no clock, and no network: it reads the two suffixes and the shared prefix. The winning chain supersedes the losing chain **in its entirety**, including losing-side events at sequences below the winning suffix's revealing event, because precedence selects a chain, never individual events — a per-event sequence comparison would leave attacker events below the recovery's sequence standing, and no hybrid of two forks is a valid log.

**What each tie proves, and which ties are terminal.** Two suffixes at equal rank resolve no winner: the identity is contested, a gating relying party fails closed on it, and a watcher records the pair as evidence. A tie at rank 1 proves that two parties each held the pre-rotation keys **and** a threshold of the shared prefix's root, which is the both-keys-compromised case the signing-authority matrix names unrecoverable. A tie at rank 2 proves that two parties each held the pre-rotation keys while neither could produce the shared prefix's root signature. **Ranks 1 and 2 are both terminal by key material**, because each side's reveal consumed the commitment the comparison read, so no later key event on either suffix changes the comparison. A tie at rank 3 is **pending**: neither suffix has revealed, so a later reveal on one suffix decides the divergence, and a later reveal on both escalates the tie to rank 1 or rank 2 and to terminal.

**What the order delivers, case by case.** A `#0` thief that cannot reveal is rank 3 and loses to the controller's recovery at either tier. **A party holding a copied pre-rotation key against a controller whose root is intact and trusted loses**, because the controller's commitment refresh carries the standing root's signature at tier A while the copy holder can produce only a bare reveal at tier B — the case the collapsed order left contested and the case Alec's ruling was about. **A party holding a copied pre-rotation key against a controller whose root is lost ties it**, because neither side can produce the shared prefix's root signature and both stand at rank 2. **An attacker holding both the root and a copy of the pre-rotation key ties the controller at rank 1**, which is Alec's "GG" case stated as a rank. A `#0`-compromise fork is therefore resolved with no dependency on Layer B witnesses; a witness's conflict statement about the fork is evidence a party may read and never the mechanism that resolves it.

Each reveal-authorized event increments the chain's **reveal generation** — the count of reveal-authorized events from inception, named for what it counts, since a commitment refresh increments it while leaving the root key in place. The reveal generation records how far a chain has advanced through the commitment sequence, so a resolver's stored state shows whether the chain it holds arrived by a verified recovery (the lock-free resolver state in the implementation-constraints section); it is **not** the precedence comparison, and no ordering over the pair of reveal generation and sequence reproduces one. A controller's commitment refresh and a copy holder's recovery consume the same standing commitment and reach the same reveal generation while standing at different ranks, so a resolver ordering on the pair of reveal generation and sequence would take a longer fork over the tier comparison that decides the pair. Rotating an operational (currently `#active`/`#agent`) signing key is a **separate** key event signed by `#0` (the matrix above); the two events are distinct, and `#0` recovery is stated only here.

**Reveal-on-recovery depends on independent pre-rotation custody.** Revealing the pre-committed key is sound against a compromised current key **only if** the pre-rotation key resides in a custody substrate whose compromise is independent of operational-custody compromise — the recovery-authority principal-distinctness rule (`09-security-model.md` §9.7.4.1 item 3a). If the pre-rotation key were reachable from operational custody, an attacker who compromised `#0` through operational custody could also reveal the pre-rotation key and complete the recovery as the identity's owner, so the reveal would protect nothing against that adversary. The realization of that independent custody is the pre-rotation recovery custody design proposed in RFC #2130 (pre-rotation recovery custody) and the substrate-isolation rule of ADR-054, pre-rotation key custody substrate isolation (`.docs/adrs/ADR-054-pre-rotation-custody-substrate-isolation.md`); this ADR names the dependency and does not realize it. Retention is part of this dependency's contract: the pre-rotation public key's preimage and its private key are retained from the moment the commitment is fixed until a recovery event reveals and uses them, on every reachable code path — the commitment-lifetime rule two shipped defects taught (`.docs/lessons/hash-commitment-preimage-lifetime.md` and `.docs/lessons/pre-rotation-key-must-be-stored-at-creation.md`) — and because the recovery ceremony has fallible steps after the irreversible reveal, its implementation returns a typed recovery handle on a post-reveal failure rather than a bare error that strands the caller (`.docs/lessons/migration-publish-recovery-handle.md`). A lost pre-rotation private key or preimage forecloses both reveal-authorized event kinds — the controller can sign no refresh and no recovery ever again, and the identity keeps operating under its intact `#0` with no root-recovery path. No `#0`-only escape from that state exists, because an event that let `#0` alone fix a new commitment would be exactly the commitment-move authority the closure rule of the signing-authority matrix denies an attacker; the retention contract above is the mechanism that prevents the loss.

**The identifier is stable, so migration disappears.** ADR-003 modeled recovery as `migrate_identity`, which revealed the pre-rotation key, derived a *new* DID string from it, wrote an `alsoKnownAs` link into the old document, published both documents, and forced every per-context reference to migrate through a `DidRotationEvent`. Under the KEL the inception-derived identifier is stable for the identity's whole life: `#0` recovery appends one key event that installs the revealed key as the new root, and the identifier — derived from the inception event, which recovery does not rewrite — does not change. No new identifier is derived, no `alsoKnownAs` forwarding record is published, and no per-context reference migrates. Migration as a rename of the identifier does not exist in this substrate; recovery is one more key event in the log. Because the identifier does not change across recovery, the identifier itself no longer signals that the root moved, so a relying party re-verifies key continuity (`09-security-model.md` §9.11) on a `#0` recovery event — that re-verification is the signal the stable identifier no longer carries.

## Clauses of ADR-003 this decision retires

Each clause below is retired by this decision. The clause text stays in ADR-003's retained body as the historical record; this ADR states that it no longer governs SCP.

1. **The did:dht-only mandate.** ADR-003's Context named did:dht "the primary and only planned DID method" and named did:web "a contingency fallback." Neither governs: did:dht is not selected, and did:web is cut (clause 7 below).
2. **The DID-method trait whose purpose was a did:web swap.** ADR-003's Decision abstracted the DID method behind a trait "so the contingency did:web fallback could be swapped in without changing any calling code." The substrate is the inception-derived KEL; the trait survives only as the `IdentityBackend` seam (the identity-substrate execution plan, Track S3), whose purpose is backend evolution inside the KEL, not a did:web swap.
3. **The pkarr dependency and the DNS-record encoding.** ADR-003's Implementation depended on the `pkarr` crate and on roughly 300 lines of DID-document-to-DNS-resource-record encoding. SCP uses neither pkarr, BEP44, the Mainline crate, the z-base-32 DID string, nor any DNS-record encoding. The identifier derives from the inception event in SCP's own encoding.
4. **Mainline publish and republish.** ADR-003 published each DID document to the Mainline DHT as a BEP44 signed mutable item and ran a background task that republished every two hours with exponential backoff, emitted a `DhtPublishDegraded` warning after six consecutive failures, and marked stale resolutions past a republish window. Identity is the key-event log on the relay network, resolved by log replay. SCP runs no Mainline-DHT expiry-republish loop and no Mainline expiry handling; what survives is the substrate-agnostic propagation the highest-sequence-wins rule depends on — a relay or resolver heals a stale replica from a fresher one (Layer A). The distinction is between periodic *signing* (removed: no key signs on a schedule) and periodic *propagation* of the already-signed head (kept, as relay healing).
5. **The `did:dht:z` self-certification bindings.** ADR-003's migration verification enforced three invariants that bound a z-base-32 `did:dht:z` string to a public key — the self-cert binding of the old document to the old DID, the self-cert binding of the old DID, and the self-cert binding of the new DID. All three are retired: SCP's self-certifying binding is the binding of the identifier to its inception event under SCP's encoding, not a z-base-32 encoding of a public key.
6. **The retired-key retention bound of two.** ADR-003 retained at most the two most recent retired active keys and the two most recent retired agent keys, pruning older ones on rotation to hold the DID document within DHT size constraints. The DHT size constraint that motivated the pruning bound is gone; the append-only KEL retains the full key-event history by construction, so no retention bound applies.
7. **The did:web contingency and its acceptance criterion.** ADR-003's Context and its acceptance criterion 6 named a `DidWeb` implementation as a contingency the DID-method trait could swap in. did:web is cut outright; no did:web code is authorized. The trait survives only as `IdentityBackend` (clause 2).

## Surviving rulings this decision re-homes onto the KEL

Two rulings that ADR-003 stated over the did:dht document survive. This ADR re-homes each onto the KEL key-status model rather than dropping it.

- **A content signature verifies against a retired key, with a compromise carve-out; an attestation verifies against the current key only.** ADR-003 retained a rotated-away active key as a historical verification method so a signature over content it once signed stayed verifiable after rotation, while the security-model spec requires a KeyPackage attestation to verify against the identity's *current* `#active` or `#agent` verification method only and to reject any retired key, so that rotation revokes the attesting key group-wide (`09-security-model.md` §9.7.1 check 1). This asymmetry survives over the KEL, with the compromise carve-out made explicit: a relying party verifying a content signature accepts a key the log later retired as `Superseded` or `Retired`, but **rejects** a key retired `Compromised{from:N}` for content the compromise boundary places at or after the compromise, because a compromised key otherwise lets an attacker forge backdated content. The ordering the carve-out compares against is neither a self-asserted timestamp an attacker could backdate nor one global sequence: an application message is not itself a key event and, under the causal-DAG content model (`09-security-model.md` §9.8), carries causal head-references — a partial order within its context — not a position in a single total commit order. The carve-out therefore evaluates content against a per-context **compromise anchor** — the point in that context where the compromised key's retirement took effect — and the verdict direction is fail-closed: the verifier rejects content that is causally at or after the anchor, **and rejects content whose order against the anchor is indeterminate** (causally concurrent content, which an attacker can manufacture at any later wall-clock time by referencing only pre-anchor heads); it accepts only content that is causally before the anchor. That anchor **must be a value that converges across honest members** of the context (for example, the context frontier at which the `#0`-signed retirement propagated in as a convergent event), so that two honest verifiers derive the same boundary and agree on a given content signature; the every-field-convergent rule of the security model's equivocation test (`09-security-model.md` §9.9.3) binds every field a soundness test consults. The boundary N is `#0`'s asserted first-compromised sequence in the key-event log; how N maps onto a convergent per-context compromise anchor, and the exact causal-reachability rule, is an open model question Track U4 settles, not merely a byte layout. When a later `#0`-signed status assertion withdraws a `Compromised{from:N}` assertion as a false alarm (the status row of the signing-authority matrix), the withdrawal also retires the compromise anchor derived from it, and verifiers re-derive the key's status from the now-latest assertion. Content committed after the actual compromise but before the anchor is the residual an asserted boundary cannot recover, so the carve-out is a deliberate, root-signed judgment, not a guarantee. A relying party verifying an attestation consults the current key status only and rejects any retired key.
- **The root verification method `#0` is a distinct root authority.** SCP keeps `#0` as a root authority in the key-event log, distinct from the rotating operational signing key, and `#0` asserts each key's status. A distinct root authority asserting status decouples status-assertion from the operational key: a status assertion is signed by `#0`, so it survives compromise of the operational `#active`/`#agent` key without that key's cooperation, and it can name a reason — `Superseded`, `Retired`, or `Compromised{from:N}`, where N is the sequence from which compromise is asserted — that an assertion signed by the retiring key itself could not make once that key is the thing being disavowed. Root-asserted status is strictly more expressive than retiring-key-asserted status for this reason. (Whether KERI's rotation model can or cannot express equivalent reason codes is UNVERIFIED against KERI primary sources and is not relied on here; the decision rests on the decoupling argument, not on a KERI comparison.) The identity specs realize the named status vocabulary across the spec corpus under the identity-substrate execution plan's Track U4; this ADR states the model and its reason codes and edits no spec.

## Implementation constraints this decision fixes

The dedicated architecture review (time-of-check-to-time-of-use, locking, and cross-tier placement) and the two research dossiers named in the provenance chain fixed the following constraints at the ADR level, because each one forecloses a defect class this repository has already paid for. Track S realizes them; Track U4 states the spec-level ones.

- **One hash implementation.** The KEL leaf hash, the event-type tag, and the inception derivation each have exactly one implementation in one module. A second copy that drifts breaks verification silently — proofs return false and no error is raised — the failure the hash-deduplication lesson records (`.docs/lessons/hash-pair-deduplication.md`).
- **RFC 9162 proof machinery, adopted verbatim.** Where the substrate needs inclusion or consistency proofs beyond the hash chain's own predecessor links — a relay's multi-identity overlay, compact bundle proofs — it adopts the constructions of RFC 9162, Certificate Transparency version 2.0, and invents no Merkle profile. The runtime event log's recorded divergence from the older RFC 6962 profile is a Track U4 convergence item, not an obligation of this ADR.
- **Determinism across compilation targets.** No KEL preimage contains a `usize`, a float, or a value dependent on map-iteration order; integers are big-endian and fixed-width. A native-versus-wasm32 known-answer test pins byte identity, in the deterministic build-and-compare modality that Prerequisite 5 of ADR-057, the in-browser client, defines for constructions that draw no randomness.
- **An injected clock for every time-dependent decision.** A witness's cosigning interval and a relying party's freshness evaluation take an injected clock (the `scp-clock` port), never a direct system-time read, so every time-dependent decision is deterministic under test — the rule the nonce-tracker clock lesson states (`.docs/lessons/in-memory-nonce-tracker-system-clock.md`).
- **Lock-free, crash-surviving cross-identity resolver state.** The resolver's mutable state — the per-identity record of the accepted chain and the equivocation flag — is cross-context by nature, so it lives outside the actor-per-context ownership model of ADR-049, actor-per-context, and on the read path uses only the primitives that ADR's §12 admits: a `DashMap` keyed by identifier, each entry publishing through an `ArcSwap` one immutable descriptor of the accepted chain — its reveal generation, its head sequence, its head digest, and its equivocation status. A reader loads that descriptor once and decides against the one pinned value. The descriptor is an `ArcSwap` and **not** an `AtomicU64` advanced by `fetch_max`, because a maximum cannot express the outcome the precedence comparison reaches: adopting a chain that won on rank while carrying a lower head sequence than the chain it supersedes *decreases* the recorded sequence, and a monotone maximum discards exactly that adoption — the `#0`-compromise case of the signing-authority matrix, where the controller's winning recovery sits at a lower head sequence than the `#0` thief's padded fork. **The copied-pre-rotation-key case supplies a second such example under the two-tier order**: a controller whose root is intact wins at tier A with a commitment refresh that may sit far below the head of the copy holder's padded tier-B fork, so the resolver publishes a decrease there too. The watermark is therefore a floor over candidate heads **on the accepted chain**, where sequence is the right comparison and monotonicity holds; a divergent candidate goes to the precedence comparison instead (the reject-lower bullet of Layer A), and the resolver publishes the winner by swapping in its descriptor, whether that moves the recorded sequence up or down. The descriptor is durable in the crash-surviving class ADR-049 §9 defines for per-sender replay floors — state a restart erased would re-open the first-contact rollback window for every identity the resolver had ever observed — and it is restored **verbatim** from the resolver's own persisted snapshot, never by a maximum-merge and never adopted from another party's state: merging by maximum would clobber a recovery-lowered sequence for the same reason a maximum cannot publish one, and a node reloading its own snapshot restores it as written while only an untrusted import merges under a ceiling, the trusted-local restore rule the storage lesson states (`.docs/lessons/guard-restore-sink-on-incoming-not-live-store.md`). The floor holds only while neither counter wraps: the head sequence and the reveal generation are monotone counters, and Track U4 fixes each width so that no identity's log can exhaust one, because a wrapped counter reads as a regression and re-opens the rollback the floor closes. The equivocation flag carries the stricter Class-S discipline (the detection bullet). No read path acquires a `RwLock` or a `Mutex`.
- **A wasm-safe pure-sync leaf crate owns the KEL logic.** The KEL data model, canonical serialization, replay, and all pure verification — event signatures, chain links, cosignature checks, bundle verification — live in a wasm-safe leaf crate named for the capability it owns (extending `scp-did`, or a new `scp-kel`; Track S2 names it), with no tokio, IO, or thread edge and no `scp-dht` dependency. The rationale is Alec's ruling of 2026-08-31: servers never target wasm — wasm32 is the browser client's target only; wasm32-compilability is the mechanical purity fence proving the leaf has no tokio, IO, or thread edge, and every native tier links the same crate natively — one shared pure sync core, consumed two ways. Asynchronous fetch, publication, witness cosigning, and lifecycle stay in the tokio-coupled native identity crate (`scp-identity`), and cosigning runs only on relays. The fence is a dependency-direction invariant the wasm32 compile job enforces, not prose.

- **ADR-057, the in-browser client, has forced downstream work.** ADR-057 (Accepted) rests on did:dht resolution: its ≤ 5-minute attestation-freshness dependency assumes did:dht sequence monotonicity (`09-security-model.md` §9.6.1), and its browser resolution stack reaches the `did:dht:z` public-key parser (`scp_did::extract_public_key_from_did`) behind a production-DID-method whitelist that admits `did:dht:z*`. Under this ADR, the rollback-resistance foundation ADR-057 assumes moves onto the key-event log's highest-sequence-wins and reject-lower rules (Layer A of the key-status-resolution section above), and the `did:dht:z` parser and its production-method whitelist entry are superseded by KEL resolution. Track U4's ADR drift sweep reconciles ADR-057's own body — its `did:dht seq`-monotonicity and `did:dht:z`-parser prose, not only the spec anchors it cites — and Track S rebuilds the browser resolution path; this ADR does not edit ADR-057.
- **The pre-rotation custody realization re-homes onto the KEL recovery event.** ADR-054, pre-rotation key custody substrate isolation, records `Related: ADR-003 §4b`, which now points at a superseded ADR; its custody-isolation rule survives, and its reference re-homes onto this ADR's `#0` recovery event. RFC #2130, pre-rotation recovery custody, is the proposed realization of the independent pre-rotation custody the recovery path depends on (the root-recovery section); it re-homes from did:dht's migration document onto the KEL recovery event. This ADR names the re-homing and edits neither artifact.
- **The relay network gains an identity-availability role.** Because the SCP relay network carries identity, a resolver depends on the relay layer to serve an identity's key-event log rather than on the Mainline DHT. The relay stays untrusted: a validating relay may keep and serve a public, self-certifying key-event frame for anti-suppression, and every relying party replays, re-verifies, and corroborates the log independently (the key-status-resolution section).
- **The identity's non-key content moves off the identifier record.** The did:dht DID document bundled key material with mutable service metadata (relay endpoints, capability and broadcast-context advertisements, attestation and revocation pointers) and with attestations. Under the KEL a key event carries key material, the key's custody-tier declaration (the F4 custody split of the plan's §1a ledger — the tier is intrinsic to the key, so it rides the key event; the platform proof stays a separate attestation), rotation, and status; the mutable service metadata moves to a separate, owner-signed **service record**, and attestations become their own signed objects referenced by the identity. The service record's lifecycle is the two-record split the external patterns dossier's service-metadata section grounds: the KEL-designated service key signs it (the signing-authority matrix), it carries its own monotonic sequence resolved by the Layer A rules re-applied to that sequence — highest-valid across relays, reject-lower per resolver — and it is TTL-bounded with explicit staleness semantics Track U4 states. Plain sequence ordering is complete for the service record, and the precedence comparison the key-event log needs does not apply to it: the record has no reveal-authorized event class, so no legitimate update ever lowers its sequence, and two divergent service records at one sequence are the key holder equivocating rather than a recovery superseding a fork. The Layer B cosigned head covers the key-event log only: a witness cosignature asserts nothing about the service record, so the record's guarantee is the Layer A one and no more. Extending a cosignature to cover the service-record sequence would give a witness a second thing to check, which the watch-and-report ruling of 2026-09-10 forbids. The field-by-field homing is enumerated in the identity-substrate execution plan (`/Users/alec/.claude/plans/identity-substrate-plan.md`), §1a. Track U4 and Track J carry the spec work; this ADR settles only that non-key content leaves the identifier record, which key signs the record, and the record's lifecycle class.
- **Track routing this decision adds.** The Track U2 revision of ADR-039, cooperative delegation (the planned ADR-064), adopts the delegator-recovery property that KERI's delegated-identifier design demonstrates: the delegating identity supersedes a compromised delegate's delegation from its own log. Track S carries three implementation rules from the architecture review and the in-repo dossier: no backend enum arm or type parameter defaults to a local stand-in (the default-type-parameter defect that ADR-062, capability injection, records as its finding E1); witness-roster and gate-policy state is per-instance, never process-global (`.docs/lessons/process-global-policy-state-is-realm-local-rce.md`); and every `IdentityBackend` arm receives a durability-versus-nullifier classification row before it ships (§17.17 of the persistence spec). Track U4 binds to the two research dossiers named in the provenance chain as design inputs and inherits from them: converging the runtime event log on RFC 9162, the bundle wire format, the witness-set-acceptance policy, explicit staleness semantics on the service record, salted-digest selective disclosure for attestation presentation, and external links valid only when both directions verify. Track U4 also states the serving-tier resource bounds — the log-growth and per-request replay-cost limits on KEL-serving relays — because the single-slot store whose flood-inertness the identity spec's suppression analysis rested on (`03-identity.md` §3.10.8, slot-exclusivity) is now an unbounded multi-event store, and the bound that replaces slot-exclusivity has to be stated, not assumed.
- **No migration burden.** SCP is pre-release and no did:dht identity is deployed, so this decision carries no data migration.

## Alternatives considered

- **Keep did:dht as SCP's method — rejected.** The did:dht-only mandate rested on a widened, misattributed decision that Alec repudiated (the Context above). did:dht cannot rotate its root key, which forced the identifier-renaming migration this decision removes, and it depends on the Mainline DHT that this decision removes.
- **Adopt KERI's code — CESR, OOBIs, witness and watcher pools — rejected.** SCP takes KERI's inception-derived append-only-log shape because that shape gives rotation, pre-rotation, and self-certification. SCP does not adopt KERI's encoding or its discovery and pool infrastructure, which would couple SCP to CESR and to witness and watcher pools it does not run; SCP encodes the log in its own format, carries it on its own relay network, and provides the freshness-and-corroboration function with the log's own sequence rules (Layer A) and a witness-and-watcher layer over that same relay network rather than dedicated pools (Layer B of the key-status-resolution section).
- **Per-event first-seen witness receipts as the witness attestation — rejected; drafts through the fifth carried them, and this draft replaces them.** A per-event receipt proves a witness saw one event. It does not prove the witness holds the whole log, it gives a quiet log no freshness signal, and duplicity detection then rests on watchers exchanging everything they ever saw. A cosigned head subsumes all three: the one check the witness performs before cosigning covers every earlier event transitively, the witness timestamp gives freshness without warming any owner key, and two cosigned heads of which neither extends the other are a self-contained fault proof. Per-event receipts are KERI's mechanism and shipped at no scale comparable to the head-witnessing transparency systems; the first-seen rule survives as the watcher's comparison rule, not as the witness attestation (the external patterns dossier grounds the comparison).
- **Keep did:dc, the bespoke digest-chain method — rejected.** did:dc is abandoned and its repository is deleted. The inception-derived KEL replaces it.
- **Adopt KERI-pure rotate-everything key status — rejected.** SCP keeps `#0` as a distinct root authority so status is root-asserted and decoupled from the operational key, which lets a status assertion name a reason (`Superseded`, `Retired`, `Compromised{from:N}`) and survive operational-key compromise without that key's cooperation (the surviving-rulings section). Whether a KERI-pure model can express equivalent reason codes is UNVERIFIED against KERI primary sources; the rejection rests on the decoupling argument, not on that comparison. Alec confirmed keeping `#0` as root on 2026-08-30.
- **Build the `did:scp` DID-string facade now — deferred, not foreclosed.** No concrete external-verifier demand exists today, so building a DID-string facade would ship an interface with no consumer. The facade stays deferred on Alec's ruling — "punt, be ready, don't foreclose": interface-ready through the `IdentityBackend` seam, itself unbuilt and unspecified (the identity-substrate execution plan, Track S6), and not foreclosed by this decision.

## Amendment record

Each entry names a ruling that changed text this ADR already carried, the date Alec gave it, the text it replaced, and the reason he gave. The identity-substrate decision log (`/Users/alec/.claude/plans/identity-substrate-decision-log.md`) carries the verbatim quote record for every one.

1. **2026-09-07 — root wins, and the fork-precedence order is the two-tier order** (Alec: "Root wins sounds like a good solution"). It replaced the order this ADR carried into a 2026-09-07 amendment that collapsed the two tiers into one rank and stripped a root co-signature of any weight in the comparison. **That collapsing amendment was wrong on the record**: it executed an orchestrator instruction, and Alec's ruling on the same day already said the opposite. Alec's reason, verbatim: "If an attacker has the root, it's GG. What would you gain by trying to optimize against that case?" The collapsed order was defended by the case of a thief holding both the root and a copied pre-rotation key, and that case presupposes the adversary Alec's sentence describes, while the order it forced left a controller with an intact root merely tied against a copy holder. The root-recovery section states the restored order and the position at which tier is read.
2. **2026-09-10 — witnesses watch and report** (Alec: "watch and report as well"). It supersedes the 2026-09-07 ruling that made threshold witness cosignatures a condition of an event's acceptability. Alec's reason, from the decision log: the residual that ruling rested on — a lost root together with a leaked copy of a spent pre-rotation key — is removed for every default-profile user by the passkey custody ruling of the same day, because a passkey cannot be copied. Under the superseded ruling an unwitnessed event derived no key state, won no fork comparison, and entered no verdict; under this one a witness runs one check and signs or refuses, a cosignature is evidence a relying party may read, and no verdict, key-state derivation, rank, or gate depends on one. The relaxation runs the safe way: a design that required cosignatures could later relax to watch-and-report, while the reverse would be a flag day.
3. **2026-09-10 — every SCP key is an ECDSA key on P-256** (Alec: "ok p256 then"). On 2026-09-10 it superseded Ed25519, which this ADR and the security-model spec had carried since February 2026. **Ed25519, superseded on 2026-09-10, was never decided in the first place**: it arrived as the joint default of did:dht, of the MLS baseline ciphersuite, and of the one-algorithm rule of `09-security-model.md` §9.5, and no ADR, planning session, or issue argued it against an alternative. Of those three reasons, did:dht is dead, the MLS baseline is irrelevant to an identity key because an MLS leaf key is ephemeral, and the one-algorithm rule is a rule this project set and now points at P-256. The reason for P-256, which Alec accepted as a recommendation: it is the curve every secure enclave, every passkey provider, every FIDO2 token, every TPM, and every browser's WebCrypto speaks, so hardware custody becomes real on Apple platforms and in the browser. Costs accepted with the ruling: RFC 6979 nonces in software signers, low-`s` enforcement in verifiers, verification about twice as slow, 33-byte public keys, a defined seed-to-scalar step for pseudonym derivation, and regeneration of every known-answer test. SCP is pre-release, so no migration code follows.
4. **2026-09-10 — root custody defaults to a passkey, the inception event names each key's algorithm, and a root signature MAY be a WebAuthn assertion** (Alec: "a passkey in your apple passwords or similar"). It replaces the custody model under which every method had to hold a raw-Ed25519 signer, a requirement the same day's curve ruling of 2026-09-10 superseded along with Ed25519 itself, and which had excluded every passkey and every secure element by construction. Two protocol consequences follow and the Decision section states both: the algorithm field, so an identity created where no passkey API exists stays legible; and the WebAuthn assertion form, so a verifier parses `authenticatorData || SHA-256(clientDataJSON)` beside the raw ECDSA form. Alec also ruled the same day that self custody "is writing down a key, yes" and is "not a concern", which moves the copyable pre-rotation methods off the consumer profile; `09-security-model.md` §9.7.4.1 carries that.
