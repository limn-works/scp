## Context

Every SCP participant needs a decentralized identifier that no central operator controls, that supports key rotation, and that a relying party can verify without trusting the party that served it. ADR-003, DID Creation (did:dht), settled this need by adopting did:dht as SCP's primary and only planned DID method: the identifier was the z-base-32 encoding of an Ed25519 public key, the SDK published each DID document to the BitTorrent Mainline DHT as a BEP44 signed mutable item, and a resolver read the highest-sequence record back and re-verified its self-certifying binding.

ADR-003's did:dht-only mandate rested on one settled decision that misread its own source. That decision widened a preference Alec stated on 2026-08-11 about the Mainline bootstrap record's *encoding* — "we should be just doing did:dht as it should be. no need to do anything custom" — into a mandate governing SCP's entire identity *method*, dropped the controlling clause "no need to do anything custom," changed a preference into a settled fact, and stamped Alec's name on it. Alec repudiated that widened decision on 2026-08-30: "that was in the context of mainline bootstrapping. ultimately it is a falsification of intent." This ADR rebuilds the identity architecture from Alec's actual intent, recorded in the identity-substrate execution plan (`/Users/alec/.claude/plans/identity-substrate-plan.md`), §1.

Alec's intent names a different substrate: a self-certifying identifier derived from an inception event, governed by an append-only key-event log, in SCP's own encoding. The KEL model and the did:dht model differ at the root. did:dht resolves identity by reading one mutable record and taking the highest sequence number; the KEL resolves identity by replaying an append-only log of key events from its inception event forward. did:dht's identifier binds permanently to the initial public key and cannot rotate at the root, which forced ADR-003 to change the DID string on recovery; the KEL's identifier binds to the inception event, so root recovery appends a rotation event and never renames the identifier.

## Decision

SCP's identity is an **inception-derived self-certifying identifier over an append-only key-event log (KEL)**, encoded in SCP's own format. The identifier is a digest — SHA-256, matching the hash the security-model spec uses throughout its canonical constructions — over a canonical, domain-separated, length-prefixed serialization of the inception event, in the construction style the security-model spec already fixes (`09-security-model.md` §9.5.1 canonical construction and the §9.12 preimage style: a domain separator, then each field in a fixed order, a 4-byte big-endian length prefix on every variable-length field, and fixed widths for keys and timestamps). The substrate spec fixes the exact field order and byte layout under Track U4. The inception event does **not** carry the identifier as one of its serialized fields — the identifier is derived from the event and then names the log — so no self-addressing fixpoint arises and no placeholder value is needed during derivation. The inception event fixes the root key `#0`, the pre-rotation commitment, and the identity's initial witness set (Layer B of the key-status-resolution section). Every later key event — rotation, retirement, recovery — appends to the log and carries its own signature. Each event preimage carries an event-type discriminator byte, the anti-type-flipping device the security-model spec's inner envelope already uses (the `message_type` byte of `09-security-model.md` §9.5.2), and every KEL domain separator is a fresh, version-suffixed string **registered** in the security-model spec's domain-separator registry (`09-security-model.md` §9.18.2) with its construction class stated — registration in the one table, not distinctness maintained by inspection, is what keeps separators collision-free as the table grows. Track U4 fixes the exact byte layout and registers the separators.

Self-certification is an **offline** check: a relying party verifies the identifier-to-inception-event binding from the inception-event bytes alone, with no network call, because the identifier is that event's digest. Resolving an identity's **current** key status is a **separate, network-dependent** operation — a log resolution over the relay network subject to the freshness, completeness, and non-equivocation model in the next section — and is not offline.

This substrate takes KERI's inception-derived append-only-log **shape** and adopts none of KERI's code or wire formats: no CESR encoding, no out-of-band-introduction (OOBI) discovery, and no dedicated witness or watcher pool infrastructure. SCP keeps the witness and watcher *function* — freshness, corroboration, and non-equivocation — but provides it with its own two-layer mechanism over its own relay network (the next section), not with KERI's pools. SCP does not adopt did:dc, the abandoned bespoke digest-chain DID method. The log is SCP's own append-only key-event log in SCP's own encoding.

The following elements of ADR-003 no longer govern SCP:

- **did:dht is not SCP's method.** did:dht is not SCP's identity method. The mutable-highest-sequence-record resolution model is replaced by log replay.
- **Mainline DHT is removed.** SCP runs no did:dht-conformant Mainline bootstrap layer. The SCP relay network carries identity: a resolver reads an identity's key-event log over the relay network and replays it. The relay stays untrusted — it may validate a public, self-certifying key-event frame it stores for availability, but a relying party re-verifies every event independently, so correctness never depends on a relay.
- **The DID string is an optional, deferred facade.** SCP does not depend on a DID string. A `did:scp` method facade over the KEL is **not built, not designed, and not specified**; SCP does not foreclose it and builds it only when a concrete external-verifier demand (an EUDI, eIDAS, or W3C Verifiable Credentials consumer) appears.

## Resolving current key status over an untrusted relay

An append-only log served by an untrusted relay raises a completeness problem that per-event signatures do not solve: a relay can withhold the tail of the log and serve a valid earlier prefix, so a resolver replays a stale-but-signed history in which a rotated-away or `Compromised{from:N}` key still reads as current. Each event's signature proves that event's authenticity; no event's signature proves that the resolver has received every later event. SCP addresses this in two layers, and adopts none of KERI's CESR encoding, OOBI discovery, or dedicated witness and watcher pool infrastructure.

The log is hash-chained: each key event names the digest of its predecessor, so a resolver that receives a set of events verifies by construction that it holds a contiguous prefix and detects any reordering, substitution, or gap within what it received. Hash-chaining secures the integrity of received events; it does not, on its own, prove that a resolver received the latest event, and it does not detect two divergent logs. The two layers below add those two properties.

### Layer A — freshness and anti-rollback, at parity with did:dht

The current key-state is the replay of the key-event log; freshness is anchored on the **highest-sequence key event**, not on a separate signed statement about the log (the current `#active` may have been set several events before the newest one, which could be a status assertion — the highest sequence fixes recency, and the replay fixes the state). Each key event carries a monotonic sequence number and is signed once by its authorizing key at the moment it occurs (the matrix below); a relay re-serves that already-signed event and never re-signs it, so `#0` stays cold and no key signs on a resolution schedule — an identity signs a key event only when it actually rotates, retires, or recovers. A resolver establishes the current key-state by two rules the security-model spec already states for did:dht, re-homed onto the key-event log:

- **Highest-sequence-wins across independent relays.** A resolver queries several independent relays and accepts the highest sequence any of them serves, re-homing §3.10.7 (the highest valid sequence is authoritative) onto the log. Highest-valid selection applies at both nesting levels — within one relay's response, when a relay serves several stored records, and then across relays — because a first-valid selection is a shipped defect this repository has already corrected once: ADR-062, capability injection, records the merged relay querier selecting first-valid and directs its completion to highest-valid. A single relay that withholds the tail is defeated when another relay serves the newer event — which presupposes the newer event reached an independent relay, so the controller submits each key event to its relays and witness set, and a resolver that has just seen a newer head re-publishes it to a relay serving a stale one (resolver-driven relay healing — the resolver, having seen both heads, is the actor of record, since a relay has no incentive to heal a competitor's stale replica). Healing re-serves an already-signed event and never re-signs, so it warms no key. "Several independent relays" carries the same unsolved independence problem as the witness set of Layer B: a resolver whose queried relays are one operator's fleet gets no withholding resistance, so relay-population independence is part of the replication requirement Track U4 must state, not assume.
- **Reject a lower sequence than already observed.** For an identity it has seen before, a resolver rejects any key-state at a sequence not greater than the highest it previously observed, re-homing §9.6.1 (the reject-lower rule) and the §9.7.1 rollback-resistance assumption off the removed BEP44 record onto the log. The reject-lower rule protects a resolver that has observed the identity before; a serving relay's cold restart re-opens a delete-the-head-then-replay-an-older-signed-record rollback that client-side monotonicity cannot close at first contact, so the serving tier keeps the storage-derived, fail-closed delete gate the identity spec fixed for exactly this attack (`03-identity.md` §3.10.8), re-homed from the BEP44 record onto KEL-serving relays: a relay refuses a client delete of a stored binding-valid head, derives the refusal from storage rather than from a possibly-cold index, and fails closed on a storage read error.

This is **parity in mechanism with did:dht's actual guarantee**, with effective strength scaling with the independent-relay population rather than equalling Mainline's out of the gate: did:dht mitigated withholding the same way — take the highest sequence across the nodes queried, and heal a stale replica from a fresher one — and never prevented it either. Under Layer A, withholding is *mitigated* (an honest relay defeats it), not *prevented* (a resolver whose every queried relay withholds the tail is held on the stale head). The mechanism is at parity; the strength is only as large as the independent-relay population — did:dht drew that breadth from Mainline's node count, and here the A+B system draws it from the community relay-and-witness set, a property Track U4 must state as a replication requirement, not assume. The relay's availability and anti-suppression role is defense-in-depth; a resolver trusts no single relay, consistent with the untrusted-relay tenet. The sequence mechanism is therefore availability and reconciliation, not a freshness guarantee: a sequence number cannot reveal that a newer event is being withheld, so a relying party that requires a freshness *guarantee* obtains it from a Layer B cosigned head, whose witness timestamps bound the staleness of an accepted head — the division every at-scale transparency system draws between replica reconciliation and witnessed freshness. Layer A does not detect **equivocation** — a controller, or an attacker holding `#0`, who signs two divergent but individually-valid logs from one inception. did:dht did not detect this either. Layer B adds it.

### Layer B — non-equivocation and a freshness guarantee: the witness and watcher layer

Layer B is a witness and watcher layer that keeps KERI's witness-and-watcher function and its role split — witnesses answer to the identity's controller, watchers answer to the verifying party — in SCP's own encoding: no CESR, no OOBI, no dedicated pools. It reuses the relay machinery SCP already runs: **witnesses are relays.** The witness attestation is a **cosigned log head**, the head-granularity form every transparency system that shipped equivocation protection at scale converged on — Certificate Transparency's multi-log policy, WhatsApp's and Apple's audited key-transparency maps, the Go checksum database, and Sigsum's cosigned tree heads, whose witness protocol this design follows — while per-event witness receipts remain KERI's mechanism alone, deployed at no comparable scale (the external patterns dossier named in the provenance chain grounds the comparison, and the alternatives section records the rejection).

On top of its store-and-serve role, a witness **cosigns an identity's log head once per witnessing interval**. Before cosigning, the witness verifies that the head **extends the last head this same witness cosigned for this identity** — the hash chain from its last-cosigned head to the new head verifies, so the log is append-only past every head this witness ever cosigned, and a `#0`-signed fork fails the check, which makes the witness refuse it. The cosignature covers the immutable triple — identifier, sequence, head digest — **plus the witness's own timestamp**, so one cosignature asserts: as of this time, this head is the newest this witness holds, and it extends everything this witness previously cosigned for this identity. A quiet log stays fresh because the witness re-cosigns the same head with a new timestamp each interval; no owner key signs on any schedule, so `#0` stays cold, exactly as in Layer A. A witness whose cosignatures cover two heads of which neither extends the other is provably faulty by those two signatures alone. Cosigning runs on the relay, because a witness is a relay; verifying a cosignature is pure computation that any tier runs.

- **Detection is the base, and it never gates resolution.** Witnesses always cosign; a resolver establishes current key-state by Layer A alone and waits on no witness threshold, and the shipped SDK default runs no gate. A **watcher** — a relying party, or a party watching on its behalf — gathers cosigned heads across the witness set and applies the **first-seen rule**: it holds every later observation to the first head it saw at a given sequence. A pair of `#0`-signed heads of which neither extends the other proves the identity (the `#0`-holder) equivocated, and a witness whose cosignatures cover both sides of such a pair is itself provably faulty. Because detection is asynchronous and off the resolution path, an unavailable witness set costs an identity none of its resolvability: resolution degrades to Layer A (did:dht parity), the protocol keeps working if the witness operators disappear, and re-pointing a witness set is an ordinary `#0`-signed rotation that no vanished prior set has to ratify. Detection rests on two liveness assumptions Track U4 must state: at least one honest watcher polls the recognized witness set within a bounded detection window, and cosigned heads propagate to a common watcher with the same relay-healing property Layer A gives key-event heads. Detection makes an equivocation durable and attributable; it does not prevent a first-contact resolver from accepting one fork before a watcher surfaces the conflict. **A duplicity verdict is Class-S state:** when watcher evidence downgrades an identity's standing — the equivocation flag — the downgrade is durably persisted before any caller can observe it, and a persist failure fails the operation closed, the downward-transition discipline ADR-049, actor-per-context, fixes in its §9.
- **A relying party MAY gate, as its own policy.** For a high-stakes decision a relying party MAY require a **bundle**: the head, the chain of events from the party's last-verified position (or from the inception event at first contact) to that head, and cosignatures from k of the n witnesses the party recognizes, with every cosignature's timestamp inside the party's staleness bound. The party verifies the whole bundle **offline** — signature checks and chain replay, with no witness round-trip at decision time — because the resolver, a relay, or the counterparty gathers the bundle ahead of the decision and it travels with the request: the proof-bundle shape of Sigsum and the Go checksum database. The gate then **binds its decision to the immutable triple the cosignatures cover — identifier, sequence, head digest** — the bind-to-what-you-verified rule the security-model spec's current-key-only attestation check applies (`09-security-model.md` §9.7.1): the party acts on the exact head it verified, so no time-of-check-to-time-of-use window opens between verification and action, and a newer key event supersedes the decision's basis going forward rather than invalidating the act. Only that party's decision fails closed when no qualifying bundle exists; every other party still resolves the same identity on the detection base. A gating party that recognizes no controller-independent witness set for an identity (the independence rider below) **fails closed** for that decision — it does not silently degrade to Layer A, since degrading would void the gate it chose. **A refusal and a fault are different verdicts:** the gate absorbs exactly one condition into refusal — a verified absence of k qualifying cosignatures — and propagates everything else (an unreachable witness during gathering, a malformed bundle, a storage error) as a typed fault, never folding a fault into the refusal; absorption is a closed allowlist with propagate as the default, the direction the UCAN-validation lesson fixes (`.docs/lessons/ucan-validate-needs-real-capability-uri.md`). The party's staleness bound and threshold are explicit, legible parameters, per the legibility-before-opt-in tenet; their values and the bundle wire format are settled in the substrate spec under Track U4. This matches KERI, where witnesses attest and each validator picks its own acceptance policy.
- **The witness set names itself in the identity's signed record, and the guarantee is contingent on the watcher recognizing that set as independent of whoever holds `#0`.** An identity's inception and rotation events name a witness set, a threshold, and the cosigning-policy parameters (the witnessing interval and the staleness bound) — the same "designated in your own signed record" pattern as the `SCPRelay` transport set, which is why these fields are reserved in the establishment-event schema from the first version: the identifier is the digest of the inception event, so a later schema that added them would change the identifier for every existing identity. The inception event fixes the *initial* witness set; a rotation event updates the *current* one. For a normal user the app and SDK supply the set from a shipped default, and the user never chooses a relay. Because the controller names its own witnesses, **the non-equivocation guarantee is exactly as strong as the watcher's independence classifier and no stronger**: detection and any gate policy hold only against a witness set the watcher recognizes as independent of the entity that signs `#0` (under `#0` compromise that entity is the attacker, not the legitimate controller). Independence classification follows the trust spec's consumer-verified pattern (`07-trust-validation-and-capabilities.md` §7.3.5): the protocol supplies the facts — witness identifiers, serving endpoints, the resolved operator graph — and the watcher applies its own policy, with exactly one REQUIRED rule (distinct identities count once) and the rest as policy. The classifier is closed by construction: each witness resolves through the canonical identity resolver and the not-independent set derives from the resolved graph — the canonical-resolution pattern the context spec's capability-collision rule uses (`05-contexts.md` §5.3.1.1) — never a denylist of co-location heuristics. A raw count of cosignatures is a claim count that MUST NOT gate by itself, the rule the trust spec fixes for attestation counts (`07-trust-validation-and-capabilities.md` §7.4.1). The sound default is to recognize **only the SDK-shipped community set** as independent; everything else — including a self-hosting controller's own separately-operated relays, which "distinct from the transport set" alone does **not** rule out — yields no non-equivocation guarantee, so the watcher falls back to Layer A alone and takes no false assurance from cosignatures a colluding set produced. The second recognition path — a set a registry vouches for — is **not yet sound**: the addressing spec (`22-human-readable-addressing.md` §22.7) concedes cross-source independence cannot be cheaply established, so a gamed registry could vouch a controller's captive witnesses as independent; Track U4 must *establish* the registry-vouching classifier sound before admitting it, not assume it. Which witness sets a watcher accepts as independent is a resolver-side policy that rides with first-contact (below); Track U4 settles it.

**Timestamps and convergence.** A cosigned head's timestamp is the witness's authenticated value and every consumer adopts it verbatim; the only party that judges it against a clock is a gating relying party applying its own declared staleness bound inside its own local decision — a per-party verdict by construction, which is what the opt-in gate is. No cosignature and no witness timestamp enters the context event log or any other structure honest context members compare, so no receiver-side clock verdict can fork honest members — the convergence discipline the security model's equivocation test requires (`09-security-model.md` §9.9.3), which ADR-057, the in-browser client, re-established in its T3 slice by removing a receiver-side timestamp-plausibility window after the repository shipped that mistake once.

**Open item — first-contact discovery and witness-set acceptance.** How a relying party first learns an identifier — the mapping from a human-readable handle or a referral to an inception-derived identifier — is the first-contact bootstrapping problem the security-model spec already frames (`09-security-model.md` §9.6.4: shared-context membership, registry discovery, or referral). Those paths supply the *identifier*; resolving its *current key-state* is then the Layer A and Layer B path above. A discovery registry (`22-human-readable-addressing.md`) returns a handle-to-identifier binding and does not itself carry key-state. First contact is where Layer A is weakest, and the ADR states it rather than hiding it: a resolver with no previously-observed sequence has no reject-lower baseline, so its recency evidence is Layer A's highest-sequence-across-independent-relays plus any cosigned-head bundle whose witnesses it recognizes — the bundle's witness timestamps give a first-contact resolver a bounded-staleness freshness signal did:dht never offered, but only against a recognized-independent witness set, and the reject-lower gap itself remains until a first observation seeds the baseline. The resolver-side policy deciding which witness sets count as controller-independent (the independence rider above) also rides here. SCP drops KERI's OOBI mechanism, not the first-contact function. The substrate spec settles the exact KEL discovery surface and the witness-set-acceptance policy (Track S2 resolution, Track U4 spec amendment) before any Track S implementation lands; this ADR records these as open items, not resolved mechanisms.

## Which authority signs which key event

The compromise model follows directly from which authority signs which kind of event. SCP fixes that assignment here.

| Event or signed artifact | Signing authority |
|---|---|
| Inception event (fixes `#0`, the pre-rotation commitment, and the initial witness set; the identifier is derived from the event, not carried in it) | `#0` (root), at inception |
| Operational-key rotation (replace an operational signing key, currently `#active` or `#agent`) | `#0` (root) |
| Key-status assertion (`Superseded`, `Retired`, `Compromised{from:N}`) | `#0` (root) |
| `#0` recovery (install the pre-committed key as the new root) | authorized by a signature from the pre-rotation private key over the recovery event, whose public half's SHA-256 equals the commitment fixed by the prior `#0` event (see root recovery below) |
| Content signature (broadcast authorship) | an operational signing key (currently `#active` / `#agent`), never `#0` |
| KeyPackage attestation (`09-security-model.md` §9.5.2) | an operational signing key (currently `#active` / `#agent`), never `#0` |
| Cosigned log head (Layer B): the triple of identifier, sequence, and head digest, plus the witness's own timestamp | a witness relay — evidence, not identity authority |

The matrix is the compromise model. Because `#0`, not an operational key, signs every rotation and every status assertion, an attacker who compromises only an operational signing key (currently `#active`/`#agent`) cannot rotate a key and cannot assert or clear a key's status; it cannot equivocate the log head either, because a fork is a pair of divergent `#0`-signed heads and this attacker does not hold `#0`. That attacker can sign content and mint KeyPackage attestations under the compromised operational key only until `#0` signs a rotation event that retires it, at which point the security-model spec's current-key-only rule (`09-security-model.md` §9.7.1 check 1) revokes it. Operational-key compromise is therefore self-contained and recovered by an ordinary `#0`-signed rotation, exactly as the compromise-recovery protocol already specifies (`09-security-model.md` §9.12 steps 1–4). Compromise of `#0` is the severe case that the root-recovery section below handles: an attacker holding the compromised `#0` can sign a fork, but the legitimate owner recovers with a pre-rotation-authorized recovery event, which a verifier prefers deterministically and offline (the root-recovery section states the precedence rule) — so `#0`-compromise recovery does not depend on Layer B witnesses. A Layer B watcher's surfacing of a `#0` fork is an additional asynchronous signal, not the mechanism that resolves the recovery. This matrix scopes key events in the log; the security-model spec's `KeyDestructionAttestation` (§9.15) is a per-context artifact that `#0` or an operational key may sign, outside this matrix.

## Root recovery and the stable identifier

`#0` recovery installs the revealed pre-committed key as the new `#0` **root** authority. The recovery event is signed by the pre-rotation private key and reveals its public half, whose SHA-256 equals the pre-rotation commitment fixed by the previous `#0` event (`09-security-model.md` §9.12 Identity-Key compromise; the preimage-reveal-and-sign proof of ADR-003 §4b). Authorization is the signature, not the reveal alone: a revealed public key is public the instant it appears, so a matching value by itself is replayable, and the signature by the corresponding private key is what authorizes. Recovery therefore does not depend on the secrecy of the compromised `#0` key — it depends on control of the independently-held pre-rotation private key. **A recovery event supersedes any conflicting event at the same or a higher sequence signed by the superseded `#0`, and the precedence is deterministic and offline-checkable**: a verifier confirms the recovery reveals a preimage whose SHA-256 equals the standing pre-rotation commitment while the old-`#0`-signed fork does not, and prefers the recovery on that check alone — so a `#0`-compromise fork is resolved with no dependency on Layer B witnesses (Layer B detection of the fork is an additional signal, not the resolver). Rotating an operational (currently `#active`/`#agent`) signing key is a **separate** key event signed by `#0` (the matrix above); the two events are distinct, and `#0` recovery is stated only here.

**Reveal-on-recovery depends on independent pre-rotation custody.** Revealing the pre-committed key is sound against a compromised current key **only if** the pre-rotation key resides in a custody substrate whose compromise is independent of operational-custody compromise — the recovery-authority principal-distinctness rule (`09-security-model.md` §9.7.4.1 item 3a). If the pre-rotation key were reachable from operational custody, an attacker who compromised `#0` through operational custody could also reveal the pre-rotation key and complete the recovery as the identity's owner, so the reveal would protect nothing against that adversary. The realization of that independent custody is the pre-rotation recovery custody design proposed in RFC #2130 (pre-rotation recovery custody) and the substrate-isolation rule of ADR-054, pre-rotation key custody substrate isolation (`.docs/adrs/ADR-054-pre-rotation-custody-substrate-isolation.md`); this ADR names the dependency and does not realize it. Retention is part of this dependency's contract: the pre-rotation public key's preimage and its private key are retained from the moment the commitment is fixed until a recovery event reveals and uses them, on every reachable code path — the commitment-lifetime rule two shipped defects taught (`.docs/lessons/hash-commitment-preimage-lifetime.md` and `.docs/lessons/pre-rotation-key-must-be-stored-at-creation.md`) — and because the recovery ceremony has fallible steps after the irreversible reveal, its implementation returns a typed recovery handle on a post-reveal failure rather than a bare error that strands the caller (`.docs/lessons/migration-publish-recovery-handle.md`).

**The identifier is stable, so migration disappears.** ADR-003 modeled recovery as `migrate_identity`, which revealed the pre-rotation key, derived a *new* DID string from it, wrote an `alsoKnownAs` link into the old document, published both documents, and forced every per-context reference to migrate through a `DidRotationEvent`. Under the KEL the inception-derived identifier is stable for the identity's whole life: `#0` recovery appends one key event that installs the revealed key as the new root, and the identifier — derived from the inception event, which recovery does not rewrite — does not change. No new identifier is derived, no `alsoKnownAs` forwarding record is published, and no per-context reference migrates. Migration as a rename of the identifier does not exist in this substrate; recovery is one more key event in the log. Because the identifier does not change across recovery, the identifier itself no longer signals that the root moved, so a relying party re-verifies key continuity (`09-security-model.md` §9.11) on a `#0` recovery event — that re-verification is the signal the stable identifier no longer carries.

## Clauses of ADR-003 this decision retires

Each clause below is retired by this decision. The clause text stays in ADR-003's retained body as the historical record; this ADR states that it no longer governs SCP.

1. **The did:dht-only mandate.** ADR-003's Context named did:dht "the primary and only planned DID method" and named did:web "a contingency fallback." Neither governs: did:dht is not selected, and did:web is cut (clause 7 below).
2. **The DID-method trait whose purpose was a did:web swap.** ADR-003's Decision abstracted the DID method behind a trait "so the contingency did:web fallback could be swapped in without changing any calling code." The substrate is the inception-derived KEL; the trait survives only as the `IdentityBackend` seam (the identity-substrate execution plan, Track S3), whose purpose is backend evolution inside the KEL, not a did:web swap.
3. **The pkarr dependency and the DNS-record encoding.** ADR-003's Implementation depended on the `pkarr` crate and on roughly 300 lines of DID-document-to-DNS-resource-record encoding. SCP uses neither pkarr, BEP44, the Mainline crate, the z-base-32 DID string, nor any DNS-record encoding. The identifier derives from the inception event in SCP's own encoding.
4. **Mainline publish and republish.** ADR-003 published each DID document to the Mainline DHT as a BEP44 signed mutable item and ran a background task that republished every two hours with exponential backoff, emitted a `DhtPublishDegraded` warning after six consecutive failures, and marked stale resolutions past a republish window. Identity is the key-event log on the relay network, resolved by log replay. SCP runs no Mainline-DHT expiry-republish loop and no Mainline expiry handling; what survives is the substrate-agnostic propagation the highest-sequence-wins rule depends on — a relay or resolver heals a stale replica from a fresher one (Layer A). The distinction is between periodic *signing* (removed: no key signs on a schedule) and periodic *propagation* of the already-signed head (kept, as relay healing).
5. **The `did:dht:z` self-certification bindings.** ADR-003's migration verification enforced three invariants that bound a z-base-32 `did:dht:z` string to a public key — the self-cert binding of the old document to the old DID, the self-cert binding of the old DID, and the self-cert binding of the new DID. All three are retired: SCP's self-certifying binding is the binding of the identifier to its inception event under SCP's encoding, not a z-base-32 encoding of a public key.
6. **The retired-key retention bound of two.** ADR-003 retained at most the two most recent retired active keys and the two most recent retired agent keys, pruning older ones on rotation to hold the DID document within DHT size constraints. The DHT size constraint that motivated the pruning bound is gone; the append-only KEL retains the full key-event history by construction, so no retention bound applies.
7. **The did:web contingency and its acceptance criterion.** ADR-003's Context and its acceptance criterion 6 named a `DidWeb` implementation as a contingency the DID-method trait could swap in. did:web is cut outright; no did:web code is authorized. The trait survives only as `IdentityBackend` (clause 2).

## Surviving rulings this decision re-homes onto the KEL

Two rulings that ADR-003 stated over the did:dht document survive. This ADR re-homes each onto the KEL key-status model rather than dropping it.

- **A content signature verifies against a retired key, with a compromise carve-out; an attestation verifies against the current key only.** ADR-003 retained a rotated-away active key as a historical verification method so a signature over content it once signed stayed verifiable after rotation, while the security-model spec requires a KeyPackage attestation to verify against the identity's *current* `#active` or `#agent` verification method only and to reject any retired key, so that rotation revokes the attesting key group-wide (`09-security-model.md` §9.7.1 check 1). This asymmetry survives over the KEL, with the compromise carve-out made explicit: a relying party verifying a content signature accepts a key the log later retired as `Superseded` or `Retired`, but **rejects** a key retired `Compromised{from:N}` for content the compromise boundary places at or after the compromise, because a compromised key otherwise lets an attacker forge backdated content. The ordering the carve-out compares against is neither a self-asserted timestamp an attacker could backdate nor one global sequence: an application message is not itself a key event and, under the causal-DAG content model (`09-security-model.md` §9.8), carries causal head-references — a partial order within its context — not a position in a single total commit order. The carve-out therefore rejects content that is causally at or after a per-context **compromise anchor** — the point in that context where the compromised key's retirement took effect — and it cannot order content that is causally concurrent with the anchor. That anchor **must be a value that converges across honest members** of the context (for example, the context frontier at which the `#0`-signed retirement propagated in as a convergent event), so that two honest verifiers derive the same boundary and agree on a given content signature; §9.8's convergence requirement binds every field a soundness test consults. The boundary N is `#0`'s asserted first-compromised sequence in the key-event log; how N maps onto a convergent per-context compromise anchor, and the exact causal-reachability rule, is an open model question Track U4 settles, not merely a byte layout. Content committed after the actual compromise but before the anchor is the residual an asserted boundary cannot recover, so the carve-out is a deliberate, root-signed judgment, not a guarantee. A relying party verifying an attestation consults the current key status only and rejects any retired key.
- **The root verification method `#0` is a distinct root authority.** SCP keeps `#0` as a root authority in the key-event log, distinct from the rotating operational signing key, and `#0` asserts each key's status. A distinct root authority asserting status decouples status-assertion from the operational key: a status assertion is signed by `#0`, so it survives compromise of the operational `#active`/`#agent` key without that key's cooperation, and it can name a reason — `Superseded`, `Retired`, or `Compromised{from:N}`, where N is the sequence from which compromise is asserted — that an assertion signed by the retiring key itself could not make once that key is the thing being disavowed. Root-asserted status is strictly more expressive than retiring-key-asserted status for this reason. (Whether KERI's rotation model can or cannot express equivalent reason codes is UNVERIFIED against KERI primary sources and is not relied on here; the decision rests on the decoupling argument, not on a KERI comparison.) The identity specs realize the named status vocabulary across the spec corpus under the identity-substrate execution plan's Track U4; this ADR states the model and its reason codes and edits no spec.

## Implementation constraints this decision fixes

The dedicated architecture review (time-of-check-to-time-of-use, locking, and cross-tier placement) and the two research dossiers named in the provenance chain fixed the following constraints at the ADR level, because each one forecloses a defect class this repository has already paid for. Track S realizes them; Track U4 states the spec-level ones.

- **One hash implementation.** The KEL leaf hash, the event-type tag, and the inception derivation each have exactly one implementation in one module. A second copy that drifts breaks verification silently — proofs return false and no error is raised — the failure the hash-deduplication lesson records (`.docs/lessons/hash-pair-deduplication.md`).
- **RFC 9162 proof machinery, adopted verbatim.** Where the substrate needs inclusion or consistency proofs beyond the hash chain's own predecessor links — a relay's multi-identity overlay, compact bundle proofs — it adopts the constructions of RFC 9162, Certificate Transparency version 2.0, and invents no Merkle profile. The runtime event log's recorded divergence from the older RFC 6962 profile is a Track U4 convergence item, not an obligation of this ADR.
- **Determinism across compilation targets.** No KEL preimage contains a `usize`, a float, or a value dependent on map-iteration order; integers are big-endian and fixed-width. A native-versus-wasm32 known-answer test pins byte identity, in the deterministic build-and-compare modality that Prerequisite 5 of ADR-057, the in-browser client, defines for constructions that draw no randomness.
- **An injected clock for every time-dependent decision.** A witness's cosigning interval and a gating party's staleness evaluation take an injected clock (the `scp-clock` port), never a direct system-time read, so every time-dependent decision is deterministic under test — the rule the nonce-tracker clock lesson states (`.docs/lessons/in-memory-nonce-tracker-system-clock.md`).
- **Lock-free cross-identity resolver state.** The resolver's mutable state — the per-identity reject-lower watermark and the equivocation flag — is cross-context by nature, so it lives outside the actor-per-context ownership model of ADR-049, actor-per-context, and on the read path uses only the primitives that ADR's §12 admits: a `DashMap` keyed by identifier, holding an `AtomicU64` watermark advanced by `fetch_max` and an `ArcSwap`-published equivocation status. No read path acquires a `RwLock` or a `Mutex`.
- **A wasm-safe pure-sync leaf crate owns the KEL logic.** The KEL data model, canonical serialization, replay, and all pure verification — event signatures, chain links, cosignature checks, bundle verification — live in a wasm-safe leaf crate named for the capability it owns (extending `scp-did`, or a new `scp-kel`; Track S2 names it), with no tokio, IO, or thread edge and no `scp-dht` dependency. The rationale is Alec's ruling of 2026-08-31: servers never target wasm — wasm32 is the browser client's target only; wasm32-compilability is the mechanical purity fence proving the leaf has no tokio, IO, or thread edge, and every native tier links the same crate natively — one shared pure sync core, consumed two ways. Asynchronous fetch, publication, witness cosigning, and lifecycle stay in the tokio-coupled native identity crate (`scp-identity`), and cosigning runs only on relays. The fence is a dependency-direction invariant the wasm32 compile job enforces, not prose.

## Alternatives considered

- **Keep did:dht as SCP's method — rejected.** The did:dht-only mandate rested on a widened, misattributed decision that Alec repudiated (the Context above). did:dht cannot rotate its root key, which forced the identifier-renaming migration this decision removes, and it depends on the Mainline DHT that this decision removes.
- **Adopt KERI's code — CESR, OOBIs, witness and watcher pools — rejected.** SCP takes KERI's inception-derived append-only-log shape because that shape gives rotation, pre-rotation, and self-certification. SCP does not adopt KERI's encoding or its discovery and pool infrastructure, which would couple SCP to CESR and to witness and watcher pools it does not run; SCP encodes the log in its own format, carries it on its own relay network, and provides the freshness-and-corroboration function with the log's own sequence rules (Layer A) and a witness-and-watcher layer over that same relay network rather than dedicated pools (Layer B of the key-status-resolution section).
- **Per-event first-seen witness receipts as the witness attestation — rejected; drafts through the fifth carried them, and this draft replaces them.** A per-event receipt proves a witness saw one event. It does not prove the witness holds the whole log, it gives a quiet log no freshness signal, and duplicity detection then rests on watchers exchanging everything they ever saw. A cosigned head subsumes all three: the extension check the witness performs before cosigning covers every earlier event transitively, the witness timestamp gives freshness without warming any owner key, and two cosigned heads of which neither extends the other are a self-contained fault proof. Per-event receipts are KERI's mechanism and shipped at no scale comparable to the head-witnessing transparency systems; the first-seen rule survives as the watcher's comparison rule, not as the witness attestation (the external patterns dossier grounds the comparison).
- **Keep did:dc, the bespoke digest-chain method — rejected.** did:dc is abandoned and its repository is deleted. The inception-derived KEL replaces it.
- **Adopt KERI-pure rotate-everything key status — rejected.** SCP keeps `#0` as a distinct root authority so status is root-asserted and decoupled from the operational key, which lets a status assertion name a reason (`Superseded`, `Retired`, `Compromised{from:N}`) and survive operational-key compromise without that key's cooperation (the surviving-rulings section). Whether a KERI-pure model can express equivalent reason codes is UNVERIFIED against KERI primary sources; the rejection rests on the decoupling argument, not on that comparison. Alec confirmed keeping `#0` as root on 2026-08-30.
- **Build the `did:scp` DID-string facade now — deferred, not foreclosed.** No concrete external-verifier demand exists today, so building a DID-string facade would ship an interface with no consumer. The facade stays deferred — not built, not designed, not specified (the identity-substrate execution plan, Track S6); this decision does not foreclose it.
