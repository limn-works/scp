# ADR-060: Monetary Value Wire Representation

**Status:** Accepted (2026-07-05).

**Relates to:** ADR-033 (economic governance — defines `Amount`/`Coefficient`/`CostSchedule`/`PricingFormula`), ADR-048 §7 (per-SDK idiom over the JSON FFI), ADR-055/058/059 (typed SDK surfaces — structured value types projected to/from the canonical serde wire shapes), spec §19 (economic governance) and §19.15.1 (wire format tables). Supersedes the "JSON Amount serialization" paragraph in spec §19.8.

## Context

SCP is a crypto-settling, reimplementable interchange protocol: the same economic values (`Amount`, `Coefficient`) cross the wire between independent implementations in Rust, TypeScript, Python, Swift, and Kotlin, and settle against real payment rails (x402/USDC, SPL, Lightning). The canonical serde shapes in `scp-protocol` are the single source of truth (ADR-055/058/059); every SDK and bridge round-trips against them.

The economy types were originally specified to serialize monetary values as **JSON numbers** (`Amount` → unsigned integer, `Coefficient` → signed integer; spec §19.15.1, §19.8). That choice is out of step with how a crypto-settling, multi-language protocol represents money, for reasons that are structural, not a latent bug:

- **Crypto-rail interchange norm.** The rails SCP settles against represent on-wire amounts as **decimal strings over big-integer smallest-units**, precisely to avoid float/precision hazards at language boundaries: USDC and SPL token amounts are base-units-as-strings, and Lightning/BOLT11 carries millisatoshi integers as strings. A protocol that interchanges with these rails should speak the same representation at its own boundary rather than inventing a number-typed dialect that every adapter must reconcile.

- **Reimplementation-safety across language number models.** A JSON *number* is not safely round-trippable as a 64-bit integer in every target. JavaScript `JSON.parse` deserializes numbers into IEEE-754 doubles — integers above 2⁵³ silently lose precision, and there is no hook to intercept the parse. The napi bridge already narrows JS numbers through `i64` at the boundary. A wire form that a first-class SDK target cannot faithfully parse is a defect in the wire form, not in the SDK.

- **Wire/core decoupling in the human-readable path (no-DOA).** In JSON specifically, encoding money as a bare *number* couples the wire representation to a fragile JS-`parse` numeric model; the string sidesteps that and is also width-agnostic. This decoupling motivates the JSON string but is NOT a reason to string-encode the binary path: MessagePack already carries an exact 64-bit integer, and a future `u64` → `u128` widening (if ever taken) is a deliberate cross-encoding wire revision, not a silent event this ADR must pre-purchase by degrading the compact binary form today. Per the no-DOA tenet we avoid a representation we would have to *replace*; the native MessagePack integer is not such a representation.

This is a deliberate adoption of the standard enterprise money-representation discipline (integer smallest-units, string on the wire, never floats), aligned to a crypto-settling protocol — **not** a fix for a specific reachable collision. In particular, this decision is **not** justified by any ">2⁵³ JCS hash collision": SCP's currencies and scales keep real amounts far below that bound, so that scenario is unreachable and is not the rationale. The rationale is interchange norms, reimplementation-safety, and wire/core decoupling.

## Decision

**Monetary values serialize on the wire as a canonical base-10 decimal string of their smallest-unit integer.**

- **Wire form: split by encoding class (`is_human_readable`).** `Amount(u64)` and `Coefficient(i64)` pick their wire form from `Serializer::is_human_readable()`, everywhere they appear in a wire-crossing structure:
  - **Human-readable encodings (JSON)** — a canonical decimal string: plain ASCII digits, no `+`, no leading zeros (except the lone `"0"`), a single optional leading `-` for `Coefficient` only, no separators/underscores, no whitespace, no decimal point, no exponent, no hex. Examples: `Amount(1000000)` → `"1000000"`, `Amount(0)` → `"0"`, `Coefficient(-500000)` → `"-500000"`. The string encodes the **smallest-unit integer**, not a human decimal — `"1.50"` is invalid; the scale stays with `currency` / `COEFFICIENT_SCALE`.
  - **Binary encodings (MessagePack)** — the **native integer** (`serialize_u64` / `serialize_i64`), e.g. `Amount(1000000)` → MessagePack `uint 1000000`.

- **Why the split (not uniform string).** The string form exists to solve exactly one problem: a JSON *number* is not safely round-trippable as a 64-bit integer in every target (JS `JSON.parse` widens to an IEEE-754 double, corrupting values above 2⁵³, with no parse hook). MessagePack has no such hazard — it encodes an exact 64-bit integer natively — so forcing a string there buys nothing and costs the idiomatic, compact binary representation. Keeping MessagePack native also keeps every binary KAT and signature preimage (notably the `DataProvenance` provenance-hash Vector 35, `SHA-256(rmp_serde::to_vec(DataProvenance))`) byte-identical to its pre-ADR-060 value. Wire/core width-decoupling is not a reason to string-encode the binary path: SCP's smallest-unit `u64`/`i64` covers its currencies with vast headroom, and a future `u128` widening — should it ever happen — is a deliberate wire revision made across encodings at once, not a silent property this ADR must pre-purchase by degrading the binary form now (no-DOA is about not choosing a representation you must *replace*; the native binary integer is not such a representation).

- **Strict, injective JSON decode.** In the human-readable path, deserialization accepts ONLY that canonical string and rejects empty, leading zeros, `+`, `-0`, whitespace, separators, non-digit, decimal point, exponent, hex, a bare JSON number, and (for `Amount`) any leading `-`. Encode∘decode is the identity and re-encode is byte-identical, so the JSON representation is reproducible across independent reimplementations. In the binary path the value is the native integer, which is inherently exact and reproducible.

- **Core width unchanged.** The Rust core keeps `Amount(u64)` / `Coefficient(i64)`. Arithmetic (checked/saturating add/sub/mul, coefficient evaluation) is unchanged. The wire form is purely a serde boundary concern.

- **SDK surface: per-language idiom, converting at the FFI boundary (ADR-048 §7).** Each SDK exposes money in its natural integer type — TypeScript `bigint`, Python `int`, Swift `UInt64`, Kotlin `ULong` — and converts to/from the canonical decimal string at the FFI boundary, mirroring the typed-value-type convention of ADR-055/058/059. Each SDK additionally provides a `format(currency)` **display** helper that renders the human decimal (applying the currency's scale) for UIs — display is an SDK concern, never the wire form.

- **Enforcement: closed by construction, no gate.** Enforcement is entirely structural: the custom `Serialize`/`Deserialize` (with the `is_human_readable` split) live ON the `Amount` and `Coefficient` newtypes, and every monetary field is typed `Amount`/`Coefficient` — including `OutletCost.amount`, which is retyped from `u64` to `Amount`. Every monetary field therefore inherits the exact same encoding-class split — decimal string in JSON, native integer in MessagePack — with no per-field freedom to diverge. No source-scanning or AST gate is added (that would be a redundant, non-convergent denylist re-checking a property the type system already enforces soundly — see the over-engineering tenet).

The OUTLET-REGISTRATION canonical preimage (`compute_outlet_registration_canonical_bytes`) continues to hash `OutletCost.amount` as its raw `u64` big-endian bytes (via `amount.0.to_be_bytes()`), NOT the wire string, so that signature preimage — and its KAT — is byte-identical to the pre-ADR-060 preimage.

## Alternatives Considered

- **JSON integer for the human-readable path (rejected).** The originally-specified JSON number form. Rejected for JSON: not round-trippable through JS `JSON.parse` (>2⁵³ precision loss; napi narrows through `i64`) and out of step with crypto-rail decimal-string+bignum interchange. (For the *binary* path the native integer is retained deliberately — see the Decision — because MessagePack has no such parse hazard.)

- **Widen the core to `u128`/`i128` now (deferred, not rejected).** Widening the core integer would raise the numeric ceiling but does not, by itself, solve JS round-tripping or interchange-representation mismatch, and a number-typed `u128` wire is *worse* for JS. The string wire form makes a future core widening a non-breaking change, so widening is deferred rather than rejected — this decision removes the pressure to decide it now.

- **Arbitrary-precision / bignum type in the core (rejected).** A non-`Copy`, heap-allocating big-integer type is FFI-hostile (no flat value across bindings), complicates the `Copy` arithmetic surface, and is unnecessary — smallest-unit `u64`/`i64` more than covers SCP's currencies. The string wire form already gives width-independence without changing the core type.

- **String only at the wire but string in the SDK surface too (rejected).** Exposing money as strings in the public SDK APIs pushes parsing/formatting onto every caller and contradicts ADR-048 §7's per-language-idiom rule. SDKs use native integers and convert at the boundary.

- **Uniform decimal string across JSON *and* MessagePack (rejected).** A single string form in every encoding (the first-cut implementation). Rejected: it degrades the binary path — MessagePack has no `JSON.parse` hazard to mitigate, so a string there is purely wasteful (larger, non-idiomatic bytes) and it needlessly churns every binary KAT / signature preimage that hashes a monetary value (e.g. provenance-hash Vector 35). The only cited justification for uniformity was wire/core width-decoupling, which does not hold up (see the Decision's "Why the split"): SCP's `u64`/`i64` smallest-units have vast headroom, and a hypothetical future widening is a deliberate cross-encoding revision, not something to pre-pay for by making the binary wire worse now. The `is_human_readable` split applies the string only where it earns its cost.

- **Human-decimal string on the wire, e.g. `"1.50"` (rejected).** A scaled human decimal reintroduces locale/format ambiguity, is not injective (`"1.5"` vs `"1.50"`), forces scale knowledge into the parser, and contradicts ADR-033's smallest-unit-integer model. The wire string encodes the raw smallest-unit integer only.

- **Bespoke source-scanning / AST enforcement gate (rejected).** A check that scans for number-typed money fields would redundantly re-verify, in weaker source-text form, a property the type system already guarantees (serde on the newtype + every field typed `Amount`/`Coefficient`). Per the over-engineering / non-convergent-enforcement tenet, the newtype + `OutletCost` retype IS the enforcement; no gate is added.

## Consequences

- **Wire change, pre-release, no back-compat.** SCP is pre-release with no deployed data. For JSON, the string form is the ONLY accepted form; there is no dual number-or-string acceptance, no migration, no deprecation window. For MessagePack the native integer is the ONLY accepted form (a string in the binary path is rejected). Any economy KAT / test fixture / JCS preimage vector is regenerated to the correct per-encoding form by running the code — JSON fixtures become strings; binary KATs (e.g. provenance-hash Vector 35) stay byte-identical to their pre-ADR-060 values because the binary path is unchanged.

- **Spec.** Spec §19.1.1 gains an explicit wire-form note (JSON string / MessagePack native integer); §19.15.1's `Amount`/`Coefficient` rows are canonical decimal string for JSON and native `uint64`/`int64` for MessagePack; the §19.8 relay-config JSON example uses quoted amounts; and the §19.8 "JSON Amount serialization" paragraph is reversed for JSON (it previously declared integers-only and strings-invalid — this ADR supersedes it for the human-readable path).

- **Core.** `Amount` and `Coefficient` carry hand-written `Serialize`/`Deserialize` that branch on `is_human_readable()` — decimal string out / strict string parse in for JSON, native integer out/in for MessagePack — instead of derived number serde; all other derives, the `.0` field, and all arithmetic are unchanged. `OutletCost.amount` is retyped `u64` → `Amount`.

- **OUTLET-REGISTRATION KAT unchanged.** The registration signature preimage still hashes the raw `u64` bytes, so that vector is byte-identical; verified by test.

- **FFI (bridge phase).** The bridges consume the canonical serde shapes and compile against the retyped `OutletCost` (their internal construction wraps the native integer in `Amount`). Per the SDK-surface decision above, money crosses the FFI as each language's **native integer**, converted to/from `Amount`/`Coefficient` at the boundary — never as the wire string. This phase: (a) marshals amount-carrying napi params/returns as JS `bigint` (napi `BigInt`) so a full `u64` round-trips exactly (JS `number` would narrow through `i64`); PyO3 (`int`), UniFFI Swift (`UInt64`) and Kotlin (`ULong`) are already exact and stay native, wrapping into `Amount` at the bridge; and (b) quotes the bridge unit-test JSON fixtures that deserialize an economic policy, since JSON amounts are now strings. The per-language `format(currency)` display helpers and the SDK wrapper methods remain the next phase, tracked with the SDK slice.
