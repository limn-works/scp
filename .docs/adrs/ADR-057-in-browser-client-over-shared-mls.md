# ADR-057: In-Browser SCP Clients Over a Shared `scp-mls` Crate (Keys On-Device)

**Status:** Accepted (2026-06-30). Feasibility proven by a wasm32 compile spike; implementation staged across slices (see below). **Amended 2026-06-30** — see [Amendment: Dissolve `scp-primitives`; extract `scp-did`](#amendment-2026-06-30-dissolve-scp-primitives-extract-scp-did), which supersedes Prerequisite 3.

**Amends:** ADR-055 (Remove the WASM Bridge; Browser Clients Are Remote Thin Clients) — specifically its *browser-deployment conclusion*. ADR-055's removal of the WASM **bridge** stands unchanged; this ADR revises only its claim that a browser must therefore be a *remote thin client with no in-browser protocol execution*.

## Context

ADR-055 removed the WASM FFI bridge because it was a parallel **re-implementation** of the protocol that had to stay byte-identical to native for §9.9.3 Merkle convergence — a perpetual maintenance tax and a proven security-bug source. That removal was and remains correct.

ADR-055 then concluded that browser clients must be **remote thin clients** to a server-side `scp-node`, with "no in-browser client-side MLS or protocol execution." That conclusion rested on an unstated premise: that running the protocol in a browser necessarily means *re-implementing* it (the tax) or *delegating* it to a server (custodial). A feasibility audit and a wasm32 compile spike (2026-06-30) disproved that premise:

- The blocker that killed the WASM bridge is **`scp-runtime`'s orchestration** — multi-thread `tokio` + the ADR-049 actor/supervisor model — which cannot compile to `wasm32-unknown-unknown`. It is *not* the cryptography and *not* the keys.
- The MLS group state machine (at the time of the audit, `crates/scp-runtime/src/crypto/mls/{group,encrypt,ratchet,credential,key_package}.rs`, ~3,057 lines — since lifted to `crates/scp-mls/src/` — Slice 1) was **fully synchronous** and depended only on `openmls` (RustCrypto backend) plus an in-memory provider. It was *liftable*, not trapped.
- The participant hot path — §9.16 double-encryption seal/open, MLS epoch advance, event-log leaf + inclusion/absence proofs — is entirely synchronous, and the runtime provider traits it needs (`transport`, `event_log`, `persistence`) are **sync `dyn` traits a browser implements directly**. The actor/supervisor is native-concurrency machinery *wrapping* these sync calls; it is not a participant requirement.
- A wasm32 `cargo check` of the lifted MLS machine **succeeded (exit 0)**.

Therefore a browser can run the protocol in-tab over **shared code compiled to wasm32** — the same `scp-protocol`/`scp-mls` the native runtime uses — with the DID signing key and MLS group secrets held **on-device**. This is categorically different from the deleted bridge: it shares one codebase compiled to two targets, so the parity tax does not return.

Confidentiality and accountability are preserved at the *protocol* layer by construction: the browser decrypts locally, the server never sees plaintext and never holds keys, and every operation traces to the on-device human DID. This satisfies the protocol tenets (encryption-as-access-control, relays-are-untrusted, every-agent-traces-to-a-human-DID) that a custodial remote-thin-client would violate. (The trust boundary *moves* rather than vanishes — see Consequences: the browser tab becomes the platform-layer custody/plaintext boundary, where the server was in the custodial alternative.)

"Shared code compiled to two targets produces byte-identical output" holds specifically for *deterministic* artifacts — the convergent §9.9.3 leaves and the wire encoding of identical inputs — and for concrete reasons: MLS wire uses TLS-presentation serialization (RFC 9420, big-endian, length-prefixed, target-independent); convergent leaves hash explicit `to_be_bytes()` with `u32` length prefixes (no `usize` in any preimage, no float); the MessagePack body is name-tagged (`rmp_serde` by field/variant name, width-/endianness-independent); and the crypto provider is `openmls_rust_crypto`'s **pure-Rust** RustCrypto (no platform crypto, so none of the CryptoKit/Keystore divergence the cross-platform pseudonym work proved is real here). It does *not* extend to freshly-randomized key material (key generation, HPKE encapsulation, GCM nonces are non-deterministic by design). The invariant is only real if tested — see Prerequisite 5 (cross-target KAT).

## Decision

**Browser SCP clients run the protocol in-tab over a shared `scp-mls` crate, with keys on-device. The server is untrusted and never holds key material or plaintext.**

Components:

1. **`scp-mls` crate** — lift the synchronous MLS state machine out of `scp-runtime` into a `wasm32`-safe crate consumed by **both** `scp-runtime` (native node) and the browser client. One MLS implementation, two compile targets — no re-implementation, no byte-match maintenance. Liftable unit = the 9 sync files (`group`, `encrypt`, `ratchet`, `credential`, `key_package`, `error`, `wrapping_extension`, `epoch_grace`, and the `InMemoryMlsProvider = openmls_rust_crypto::OpenMlsRustCrypto` alias).
2. **Single-threaded browser driver** (~1.5–2.5K lines) over `scp-mls` + `scp-protocol`, implementing the participant operations (create/join/send/receive-decrypt/process-commit/close/leave, event-log leaves + proofs). It restores the deleted bridge's proven **shape** — a single global manager accessed via closure, with a pull-based `drain_events` model — but its bodies call shared `scp-protocol`/`scp-mls` types rather than re-deriving them.
3. **Browser platform infra**, restored/adapted from the deleted bridge: JS-callback key custody (the key stays in JS/WebCrypto and never enters wasm memory — *target design*; see Consequences for the as-built status), IndexedDB-backed storage (the in-memory MLS provider snapshots out-of-band, reusing the existing `snapshot`/`restore` path), the relay transport (the surviving `webtransport-wasm`/WebSocket pipe — refined in Slice 3 to an injected `JsSocket` port with WebSocket as the baseline, see [Amendment (2026-07-15)](#amendment-2026-07-15-ts-sdk-two-package-delivery-slice-3); the routing model that rides on that port — real §9.10.4 zeroed-`routing_id` per-member fan-out, not the shared channel — is [Amendment (2026-07-16)](#amendment-2026-07-16-slice-3-transport--real-9104-pseudonyms-shared-invitation-join-injected-jssocket)), and the hardened time source (mitigating attacker-overridable `Date.now()` → UCAN-expiry bypass).
4. **The node continues to run `scp-runtime`'s orchestration unchanged** (actors, sagas, recovery, durable async storage). The browser is a participant, not a node.

The deleted bridge is recoverable at commit `1a3b41a5e^` (pinned in ADR-055) and is used as a restoration source for the infra and the driver shape — **not** for its re-implemented protocol bodies, which shared `scp-protocol`/`scp-mls` now obsolete.

### Prerequisites (from the spike + cryptographer review)

1. **openmls `js` feature + a single hardened clock.** `openmls` must carry its `js` feature (KeyPackage `Lifetime`s need wall-clock time on wasm) plus the `getrandom` `wasm_js` backend. **The `js` feature wires `fluvio_wasm_timer::SystemTime`, which reads a *live, un-captured* `Date.now()` — a *different* clock than the SCP-layer hardened time source, and fully attacker-overridable in-tab.** Left as-is this lets a hostile same-origin script mint/accept KeyPackages with forged `Lifetime`s (expiry/`not_before` manipulation). Prerequisite: route openmls's `Lifetime` clock through the same injected/hardened `Clock` as the rest of the client, so there is *one* clock, not a hidden unhardened second one. In the in-browser model the wall clock is attacker-controllable in principle; the deferred presence ADR specifies which properties may depend on local time.

   **Implementation status (Prereq-1 landed).** openmls 0.8 exposes no clock-injection seam on `Lifetime`, so the seam used is `Lifetime::init(not_before, not_after)` — a pure constructor that takes caller-supplied bounds — plus SCP-side validation against the injected `Clock`. `scp-mls` gained a `lifetime` module (`key_package_lifetime` / `validate_key_package_lifetime`, mirroring openmls's private constants: 84-day lifetime, 1h margin, and the RFC 9420 max-range bound openmls's own `validate` never applies). Coverage:
   - **Generation — fully routed.** `create_group`/`generate_key_package` (and the `_with_wrapping_key` variants) mint the creator-leaf / KeyPackage `Lifetime` from the injected clock via `.lifetime(...)` / `.key_package_lifetime(...)`, never `Lifetime::default()`. Threaded through `ProductionMlsBackend`, `MlsCryptoProvider`, and the browser `ScpClient` driver (whose injected clock is the hardened captured-`Date.now` `WasmClock`).
   - **Accept side — bracketed.** Every accepted `Lifetime` is re-validated against the injected clock wherever openmls exposes it: post-`KeyPackageIn::validate` in `add_member` / `key_package_in_did` / the backend's `validate_key_package`, and pre-`merge_staged_commit` on each staged-commit Add proposal in `decrypt_with_sender_did` / `decrypt_with_membership_changes` (fail-closed: reject without merging). This runs *in addition to* openmls's own internal check, never in place of it. **Committer/receiver divergence is not a new attack.** The SCP max-range (and clock) check is *not* inside openmls's `process_message`, so a malicious committer can merge an Add whose leaf its honest receivers refuse — the committer's view then diverges from theirs. This reduces to the **pre-existing** MLS insider-equivocation property: a malicious committer could always fork receivers (send different commits to different members). It does not break honest-honest consistency, because the range check is a **clock-independent pure function of the KeyPackage's own `not_before`/`not_after` fields** — all honest receivers compute an identical verdict — and the temporal half's 84-day window + 1h margin absorbs realistic honest clock skew, so honest members never diverge on an honestly-issued leaf.
   - **Residual (V3, upstream).** openmls's internal `Lifetime::is_valid` on the *Welcome tree-leaf* validation path is not injectable and not bracketable — but *not* for the reason once recorded here. `LeafNode::life_time()` is `pub(crate)`; however `leaf_node_source()` **is** public and its `LeafNodeSource::KeyPackage(Lifetime)` variant **is** public, so a `LeafNode` in hand *does* yield its `Lifetime`. The real blocker is that a *joined* `MlsGroup` exposes no public way to reach another member's `LeafNode`: `members()`/`member_at()` return `Member` (index, credential, keys — **no** lifetime); `export_ratchet_tree()` returns a `RatchetTree` whose only field is private, with no public node/leaf iterator; `public_group()` is `pub(crate)`; and only `own_leaf_node()`/`own_leaf()` are public — and that own leaf is SCP-minted anyway, so bracketing it is *possible but pointless* (it is not the attacker-supplied Welcome-leaf). (`JoinBuilder::skip_lifetime_validation` was deliberately NOT used — it weakens rather than hardens.) Closing it requires an upstream openmls time-provider seam on `OpenMlsProvider` covering `Lifetime::new`/`is_valid`, requested upstream. Until then, same-origin page integrity (CSP/SRI/COOP/COEP) remains load-bearing for that one check, exactly as for the wall clock generally. Native bindings inject `SystemClock` (the hardened wall clock); there is no unhardened second clock on the SCP paths — the only remaining internal-clock read is this Welcome-leaf residual.
2. **`epoch_grace.rs` Clock injection.** It hard-wires `tokio::time::Instant`/`SystemClock` and sits on the ratchet path (`process_commit` takes `&mut EpochGraceStore`); it takes an injected `Clock` (wall-clock millis; the 30s grace window is behavior-equivalent) so it ships with the machine. Native injects `SystemClock` → identical behavior. (The `Clock` port moves to `scp-clock` per the Amendment.)
3. **~~`scp-identity` → `scp-protocol` factoring (an `IdentityError` split).~~ SUPERSEDED by the [Amendment (2026-06-30)](#amendment-2026-06-30-dissolve-scp-primitives-extract-scp-did).** The interim shipped in Slices 1/1a — `DidDocument`/`VerificationMethod`/`decode_multibase_key` moved into `scp-protocol`, `scp-identity` re-exporting them, and `SigningKeyId`/`DID` left in `scp-primitives` — was itself the smell it was meant to solve: it parked identity domain types in `scp-protocol` (and left them in the `scp-primitives` junk drawer) and relied on a re-export shim, both forbidden (no dumping grounds, no back-compat re-exports). The Amendment replaces it: dissolve `scp-primitives` into capability crates and give the DID data model one honest home in a new wasm-safe `scp-did` (moving it out of both `scp-primitives` and `scp-protocol`); `scp-identity` keeps its native DHT/resolution/lifecycle subsystem and imports the DID model from `scp-did`. (The DID-**method** layer was *not* split into a separate crate — the type graph rejects that seam; the DHT **transport** layer *is* separable and is the approved T1c-a slice — see the Amendment's rejected alternative 5.) The compile-ordering fact that motivated this prerequisite — `credential.rs` is a compile dependency of `group/encrypt/key_package`, so its identity types must be wasm-reachable — still holds; only the *destination* changes (`scp-did`, not `scp-protocol`).
4. **Fail-closed on tampered ciphertext via the `--release` build (NOT `panic=unwind`).** *(Reframes the original Prereq-4, which required a browser `panic=unwind` build so `catch_unwind` would convert an openmls decrypt panic into a recoverable error. That premise was wrong on both counts — `panic=unwind` is both infeasible for the shipped wasm artifact and unnecessary — and is replaced here; human-approved 2026-07-16.)* The concern is real: a malicious relay that delivers a *tampered or malformed ciphertext* must surface a **typed** `DecryptionFailed` at the JS boundary, never abort the tab. But the mechanism is not `panic=unwind`, for two independent reasons.

   **(a) `panic=unwind` is infeasible for the shipped artifact under the stable pin.** `wasm32-unknown-unknown` ships a precompiled `std` built with `panic=abort`; a `panic=unwind` wasm build would require nightly **+** `-Z build-std=std,panic_unwind` **+** the `+exception-handling` target feature **+** a `wasm-pack` flag wrapper for the *shipping* artifact — none of which is available under the `.mise.toml` stable toolchain pin, and all of which is unnecessary. **(b) It is not needed, because no other release-mode panic has been *found* on the openmls 0.8.1 decrypt path** — the one known panic is a `debug_assert!` (`openmls-0.8.1/src/framing/private_message_in.rs`, `"Ciphertext decryption failed"`) that is **compiled out of `--release` builds**. This is evidenced (not proven in the formal sense) by the `fuzz_mls_decrypt` decrypt-path fuzz target and pinned to openmls 0.8.1; a future openmls version bump could introduce a new panic, which the nightly fuzz job is positioned to catch. The shipped browser artifact is a `--release` (`wasm-pack build --release`) build, so on a tampered/malformed ciphertext `process_message` **returns a typed `Err`** rather than panicking; `scp-mls` already maps that to `MlsError::DecryptionFailed`, which `scp-client-wasm` maps to `ClientError::Mls` → the `[SCP-CRYPTO-4010]` error thrown at the JS boundary (`crates/scp-client-wasm/src/error.rs`). The untrusted-relay fail-closed-typed-error guarantee therefore already holds **in release, by construction** — the browser is not "worse than native" here; both surface a typed error on tampered input (native additionally catches the debug-build `debug_assert` via `catch_unwind`, a path the release wasm build never reaches).

   **Threat-model scope: untrusted RELAY, not malicious member.** This prerequisite addresses the *untrusted-relay* wire only — the tampered/malformed outer ciphertext a relay can inject. A relay cannot forge an AEAD-passing frame, so the deeper StagedCommit / tree-KEM (HPKE path-secret) panic surface — reachable only *after* the outer `PrivateMessage` AEAD succeeds, i.e. only from a valid frame authored by a malicious authenticated **member** (an insider) — is a distinct threat model that Prereq-4 does not cover, and that `fuzz_mls_decrypt` (which feeds relay-shaped tampered ciphertext to the decrypt entry points) does not exercise. Insider equivocation is the pre-existing MLS property discussed under Prereq-1; it is not in the untrusted-relay scope this prerequisite closes.

   This is made **true-by-premise, pinned, and evidenced**: (i) `debug-assertions = false` is set explicitly on `[profile.release]` (root `Cargo.toml`) — the load-bearing anchor that keeps openmls's decrypt `debug_assert` compiled out of shipped builds (it is also the cargo release *default*, so this changes no behavior; the explicit line makes the invariant greppable and guards against a future `[profile.release] debug-assertions = true` override silently re-arming the panic); (ii) a decrypt-path fuzz target (`fuzz/fuzz_targets/fuzz_mls_decrypt.rs`, built with debug-assertions **off** — cargo-fuzz `-O`/`--release` — so it exercises the *shipped* path, not the debug-only assert) drives arbitrary and tampered-AEAD ciphertext through the `scp-mls` decrypt entry points and asserts they never panic; (iii) **the browser SDK MUST build `--release`** — a `wasm-pack build --dev` (debug-assertions on) would re-arm the `debug_assert` and re-introduce the tab-abort, so the packaging slice's build config is `--release`-only (that `scp-ts-wasm` package does not exist yet, so the requirement is documented here and in the `encrypt.rs` `catch_unwind` notes; the mechanical `--release`-only build-flag check is a **scheduled Slice-3 deliverable** that lands with the `@limn-works/scp-ts-wasm` package — tracked in planning-session-09's *Mechanical guards & cleanups* list, `.docs/planning-sessions/planning-session-09-adr057-slice3-ts-sdk-packaging.md`). The `catch_unwind` sites in `scp-mls`'s `encrypt.rs` are retained as **defense-in-depth for native/debug builds** (where the `debug_assert` *can* fire) and are harmless no-ops in the release wasm build; they are **not** the load-bearing guarantee — the release build is.
5. **Cross-target determinism KAT.** Add a native-vs-wasm32 known-answer test asserting byte-equality of (i) a sample MLS commit/welcome wire blob and (ii) a checkpoint Merkle root over a fixed event sequence — *and* (iii) a credential **and** a KeyPackage from the same fixed DID on both targets (covering the prereq-3 move). Leg (iii) spans **two modalities** — do not conflate them. The **credential** is an RNG-free deterministic **construction** byte-pin: it is *built fresh* on each target from the fixed DID + `SigningKeyId` and its exact bytes are pinned to a golden — a construction comparison is valid *here precisely because* the credential draws no randomness (positional `MessagePack`, no key material). The **KeyPackage** — like the (i) Commit/Welcome legs — is a **wire-encoding round-trip**: deserialize and re-serialize *one committed golden blob* on both targets and assert byte-equality against the golden, **not** a comparison of two independent constructions (which differ by design: per the Context §determinism caveat, freshly-randomized key material / HPKE encapsulation / nonces are non-deterministic, so building a KeyPackage/Commit on each target and diffing would be wrong). The TLS-presentation codec is canonical (one encoding per value), so this round-trip is well-defined and needs no seeded provider. "Byte-identical by construction" is an *invariant only if tested*: shared code can still diverge on `usize`/`as` width (wasm32 is 32-bit) or `HashMap` iteration order feeding a hash, especially in the new ~2K-line driver. This codebase already has precedent (three divergent canonical forms from "shared intent") — the KAT is the guard.

### Scope fence (mandatory)

The browser driver covers the **participant** path only. Economy/payment validation, governance coordination, broadcast hosting, cross-context saga **coordination**, and always-on presence stay in `scp-runtime` or are node-delegated. The browser *participates* (signs its own steps) but does not *coordinate* — coordination requires always-on hosts. These were ~13K of the deleted bridge's 15.5K `manager.rs`; fencing them is what keeps the driver at ~2K and the parity-tax argument intact. The fence is **mechanically enforced, not prose-policed** (prose-policed parity *is* the tax ADR-055 killed): `scp-mls` and the browser driver MUST NOT depend on `scp-runtime` — a dependency-direction invariant the build enforces. Anything that needs `scp-runtime` is, by construction, node-side.

### Liveness / presence

MLS membership is an active relationship that **decays** when a member is absent — missed §9.9.2 heartbeats (peers cannot distinguish absence from relay suppression), lapsed PCS Update commits, exhausted KeyPackage pre-keys. These obligations are periodic **and** key-touching. The v1 model is **cold presence**: the browser participates while open and catches up / re-proves liveness when it returns, the same way the group already tolerates any frequently-offline member. **Always-on presence** (something keeping a member alive while the tab is closed) would require an **attenuated keep-alive delegate** that can *only* heartbeat / Update / replenish pre-keys and *cannot* read plaintext or send as the member. Whether MLS+SCP can express a delegation that narrow is an **open cryptographic question** (a delegate able to send a heartbeat — an MLS application message — can generally also decrypt), deferred to its own ADR + cryptographer analysis. **Confidentiality never requires custody** under any presence model; only always-on availability does.

## Consequences

**Positive:**
- True self-sovereign in-browser SCP clients (keys on-device, server sees only ciphertext) — high product value.
- One MLS state machine shared by node and browser; ADR-055's parity-tax avoidance is preserved because the browser runs shared code, not a re-implementation.
- Unblocks #1951 (browser examples) with a real foundation.

**Costs / risks:**
- A new `scp-mls` crate, a browser driver, and restored browser infra to build and maintain (bounded by the scope fence).
- The prerequisite factorings (openmls `js`, `epoch_grace` `Clock` injection, and the crate-topology split of the Amendment — dissolve `scp-primitives` into `scp-clock`/`scp-crypto`, extract the DID model into `scp-did`) touch core crates and must keep the native runtime working. The topology split has a wide but purely mechanical blast radius (pre-execution estimate: ~640 `Clock`/`SystemClock` and ~61 `DID` import sites) and is enforced by acyclicity/fence checks, not prose.
- Browser members are frequently offline → liveness degradation is expected; the protocol's offline-member handling must tolerate it.
- Forward secrecy means a fresh tab without local state cannot decrypt history it was absent for (lose-device-lose-history). Acceptable for a self-sovereign client; the custodial alternative trades it for plaintext-at-the-server.
- A single-tab driver needs its own crash/consistency story to replace the actor's bounded-crash-persist + per-context send serialization (snapshot cadence to IndexedDB; the §9.9.3 checkpoint compare is sync-available).
- **The browser tab becomes the platform-layer custody and plaintext boundary.** The model removes *server-side* custody risk and replaces it with *client-side browser-surface* risk: decrypted plaintext and the MLS ratchet/group secrets live in JS-reachable tab memory, so XSS, a single compromised supply-chain dependency in the page, or absent cross-origin isolation can exfiltrate them with no server compromise. Page hardening (CSP, SRI, COOP/COEP, no `eval`) is therefore *load-bearing for confidentiality* in this model — it must be a requirement of the browser SDK, not an afterthought. The signing key stays in JS/WebCrypto and never enters wasm memory (component 3); the group secrets and plaintext necessarily do. **As-built caveat (Slice 3):** this keys-never-in-wasm property is *aspirational* for the MLS signing key today — the ed25519 `SignatureKeyPair` is generated and held inside `scp-mls` in wasm linear memory; the JS-custody `sign`/`dhAgree` callbacks exist as a typed seam with no signing call site yet. Routing the MLS signing key through WebCrypto (so it never enters wasm) is the browser custody-signing slice. Until then it is defense-in-depth that is *not yet realized*, not a property confidentiality currently rests on (in the tab threat model an attacker able to read wasm memory can already read plaintext + group secrets regardless).
- **Local wall-clock is attacker-controllable in-tab** (`Date.now()` override). The hardened time source *narrows* the window (to script running before wasm init) but does not close it; any security property that depends on local time (KeyPackage `Lifetime`s, UCAN expiry/nbf, nonce freshness) is only as strong as the page's same-origin integrity. The deferred presence ADR specifies which properties may depend on local time at all.

## Alternatives Considered

1. **Remote thin client with node-held keys (ADR-055's stated direction).** Rejected as the *primary* model: the node holds the user's keys and group secrets, sees plaintext, and can impersonate — custodial, violating encryption-as-access-control / relays-are-untrusted / human-accountability. It remains a valid *secondary, opt-in* option for users who explicitly choose convenience over self-sovereignty (a documented custodial mode), but it is not the default and not what "browser client" means.
2. **Re-implement the protocol in wasm (the deleted WASM bridge).** Rejected: this is exactly the parity tax ADR-055 removed. Shared code via `scp-mls` achieves in-browser execution without it.
3. **Leave the browser unsupported.** Rejected: in-browser SCP clients are high-value, and the feasibility work shows the cost is bounded.

## Implementation Slices (forward-only)

1. **`scp-mls` extraction** — create the crate (9 sync files + the 3 prerequisite fixes); compiles native **and** wasm32; `scp-runtime` adopts it (no behavior change on native). Tests on both targets.
2. **Browser driver MVP** — one context end-to-end in-tab: create/join, send+encrypt, receive+decrypt, process commit. Over shared `scp-mls`/`scp-protocol`.
3. **Browser platform infra + TS SDK browser backend** — restore key custody / storage / transport / time; wire the browser backend behind the existing `@limn-works/scp-ts` API. *(Delivery refined — see [Amendment (2026-07-15)](#amendment-2026-07-15-ts-sdk-two-package-delivery-slice-3): two packages, `@limn-works/scp-ts` (native) + `@limn-works/scp-ts-wasm` (wasm participant subset); "the existing … API" = the shared API shape, not a single package.)* *(Transport rulings — real §9.10.4 pseudonyms, shared invitation join, injected `JsSocket`, and the §9.10.4-logic extraction to `scp-protocol::context::pseudonym` — see [Amendment (2026-07-16)](#amendment-2026-07-16-slice-3-transport--real-9104-pseudonyms-shared-invitation-join-injected-jssocket).)*
4. **Re-add browser examples** (closes the intent behind #1951) as in-browser-client demos.
5. **Presence** — a separate ADR (cold-presence semantics now; attenuated keep-alive delegate as open research).

Slices 1–3 shipped with the interim Prerequisite-3 factoring. Corrective slices, forward-only, address it (see the Amendment) — **T1, T1c-a (the DHT transport extraction), and T1c-b (the did:dht parser consolidation)** landed earlier; **T2 lands in this change set**:

- **T1 — Crate-topology split (landed earlier).** Dissolve `scp-primitives` into `scp-clock` / `scp-crypto`; move the DID data model into a new wasm-safe `scp-did` (out of `scp-protocol` and `scp-primitives`); `scp-identity` keeps its native DID-method/resolution/lifecycle subsystem unchanged, now importing the DID model from `scp-did` (the DID-method layer is not separable; see the Amendment's rejected alternative 5). Delete every re-export shim (including `scp-runtime/src/crypto/mls/mod.rs`'s `pub use scp_mls::*`). Behavior-preserving **except** the z-base-32 canonicality hardening of the `did:dht:z…` parsers — the port into `scp_did::extract_public_key_from_did` (see T1c-b), and the follow-on parser-parity fixes bringing the three remaining native did:dht decoders (the UCAN-validation resolver `scp_ffi_common::BridgeDidResolver`, `scp_identity::dht::DidDht::verify`'s self-certification check, and `scp-runtime`'s `app_sandbox` app-declaration verifier) onto the same guard — `BridgeDidResolver` and `app_sandbox` by delegating to the `scp-did` parser, `DidDht::verify` by delegating to the same-file native authority `scp_identity::dht::extract_public_key`; i.e. onto one of the **two** parity-tested authority parsers, not (yet) a single one — consolidation to one parser is T1c-b. Two of the three are fail-closed strictness only: `BridgeDidResolver` and `DidDht::verify` reject strictly more (non-canonical spellings that decode to a valid key) and nothing less. The `app_sandbox` change is a different kind — a fail-**open** functional repair: it fixes a prefix bug that had rejected *every* valid did:dht DID, so it now *accepts* valid canonical DIDs it previously wrongly rejected (and picks up the canonicality guard in the same pass). Separately, `BridgeDidResolver` re-asserts a local, fail-closed `did:key` gate against this crate's own `testing` feature, so that `scp-did/testing` — reachable *transitively* through orthogonal custody opt-ins (e.g. `allow_in_memory_custody`) — cannot widen the production DID-format acceptance surface; this preserves the original acceptance surface exactly (shipped artifacts, built with default features, still accept only did:dht), so it is behavior-preserving, not new behavior. acyclicity + fence enforced.
- **T1c-a — DHT transport slice (landed earlier).** Extracted the DHT **transport** layer (`scp-identity/src/dht_client/`: the `DhtClient` trait, `DhtRecord`, and the pkarr + in-memory impls) into a new `scp-dht` crate. The transport layer had **two** couplings back to `scp-identity`, both severable: (a) `IdentityError` in the two `DhtClient` method signatures (`publish`/`resolve`), and (b) the pkarr impl (`dht_client/pkarr_client.rs`) called `crate::dht::verify_bep44_signature(...)` to validate gateway responses (which in turn uses the `bep44_signable` helper). The slice therefore: moved `dht_client/` into `scp-dht`; moved the pure BEP44 transport-verification helpers `verify_bep44_signature`/`bep44_signable` into `scp-dht` (their **parameters** carry no identity types — only bytes, a seq, and an Ed25519 key; `bep44_signable` returns `Vec<u8>`, and `verify_bep44_signature`'s sole identity coupling was its `Result<(), IdentityError>` error channel — exactly what the new `DhtError` replaces); gave `scp-dht` its own `DhtError` and added `IdentityError: From<DhtError>` so the dependency flows one way (`scp-identity` → `scp-dht`). The DID-method layer (`dht.rs`: `DidDht`/`DidMethod`/`ScpIdentity`/`MigrationPartialState`) and its resolution siblings (`resolution.rs`, `resolver.rs`) stay in `scp-identity` and import the two BEP44 helpers **back** from `scp_dht` — a one-way edge, no cycle. No behavior change; acyclicity enforced. **Cross-crate consumers retargeted.** Every out-of-crate caller that reached `scp_identity::dht::bep44_signable` now imports it from `scp_dht::` **directly** — re-exporting it through `scp-identity` would be exactly the banned shim. The retargeted FFI/node call sites are: production `crates/scp-ffi/src/identity.rs` and `crates/scp-ffi/napi/src/identity.rs`, plus the test sites `crates/scp-ffi/uniffi/src/bridge.rs`, `crates/scp-ffi/common/src/resolvers.rs`, `crates/scp-ffi/napi/src/outlets.rs`, and `crates/scp-node/src/self_host.rs`. `scp-identity`'s own public API also re-exported the moving helper: the `pub use dht::{…, verify_bep44_signature, …}` block in `crates/scp-identity/src/lib.rs` surfaced `verify_bep44_signature` as `scp_identity::verify_bep44_signature`; that entry was **removed** from the re-export — *not* repointed through `scp-identity` (repointing it at `scp_dht::verify_bep44_signature` would be exactly the banned shim) — and its consumers import `scp_dht::verify_bep44_signature` directly. This slice also extended the no-shim gate's closed crate set (`scripts/check-no-shim-reexports.sh`) with `scp_dht` — the sanctioned expand-coverage edit.
- **T1c-b — did:dht parser consolidation (landed earlier).** Collapsed the last duplicate `did:dht:z…` decoder onto the single hardened `scp-did` authority. `scp_identity::dht::extract_public_key` was rewritten as a **thin wrapper**: an unconditional `did:dht:z` prefix gate, then delegation to `scp_did::extract_public_key_from_did` (which owns the sole workspace-wide `zbase32::decode`, the 32-byte length check, and the canonicality round-trip). The private `DidDht::extract_public_key` delegate method was deleted and all callers (two production — DHT publish and resolve — and seven test sites) retargeted to the free function. `DidDht::verify` was left untouched: it reaches the authority transparently through the wrapper it already calls via `is_ok_and`, so the whole native surface now has exactly one z-base-32 authority. **Context (why this mattered):** the wasm/browser stack reaches **only** the `scp-did` parser (`scp-event-log`'s `tree.rs` signature-verify and `scp-protocol`'s `bridge/claiming.rs`), while the native hardened parser is unreachable from wasm; the canonicality round-trip was ported into `scp_did::extract_public_key_from_did` in T1 (byte-exact re-encode-and-compare) so browser and native reject identical inputs. T1c-b is the consolidation that removes the last inline re-derivation, so there is no second decoder left to drift. **The two semantic blockers resolved as follows.** (1) **Error taxonomy.** `scp_did::extract_public_key_from_did` returns `Result<[u8; 32], String>` while the native parser returned `Result<[u8; 32], IdentityError>`, with decode failures on the typed `IdentityError::ZBase32DecodeError`. That variant was **deleted**: decode, length, and canonicality failures now fold into the single `IdentityError::InvalidDidFormat` channel carrying the authority's message text. This was verified safe — all thirteen callers consume the error via `?` / `map_err`-Display / `is_ok_and` / `expect` and none branch on the variant, and the FFI `From<IdentityError>` impls collapsed `ZBase32DecodeError` to the `IDENT_*` catch-all either way, so no bridge behavior changed. Error *message* text now changes on decode/length/canonicality failures (adopting the authority's wording under `InvalidDidFormat`); nothing asserts the old strings, and the sole surviving message assertion (`msg.contains("not canonical")`) is satisfied by the authority's message. (2) **did:key test-scope divergence.** The authority accepts a `did:key:{hex}` convenience under `scp-did/testing`. Crucially, the gate that protects the native surface from that is **unconditional** — a positive `did:dht:z` prefix whitelist — **not** the `#[cfg(not(any(test, feature = "testing")))]` spelling used by the `BridgeDidResolver` local `did:key` gate in T1. The reason is twofold: `scp-identity`'s own `testing` feature is enabled **transitively** through the custody chain (`scp-ffi/allow_in_memory_custody → scp-testing → scp-identity/testing`), so a cfg-gate keyed on it would be OFF in exactly the custody builds it must protect; and `scp-did/testing` itself is unified ON by sibling crates (`scp-protocol/testing`, `scp-mls/testing`, `scp-event-log/testing`, `scp-ffi-common/testing`) in any workspace or CI build with those testing features active that also compiles `scp-identity`, so the authority's `did:key` branch is live in those builds regardless of anything `scp-identity` does. The unconditional prefix check keeps the native surface `did:dht`-only in **every** build — which is also precisely the pre-consolidation behavior (native never accepted `did:key` in any build). Pinned by tests: a renamed re-fork guard (`wrapper_delegates_to_scp_did_authority_on_accept_and_reject`) that feeds the same canonical/non-canonical fixtures through both symbols so a future inline re-fork of the wrapper that drifts from the authority fails the build; a `did:key`-rejection test with an honest caveat that the load-bearing execution is the feature-unified CI run where the authority's `did:key` branch is live and the gate alone rejects; and a decode-failure test pinning the `InvalidDidFormat` taxonomy. `scp-did` itself is untouched; the `scp-identity → scp-did` dependency edge already existed, so no `Cargo.toml` change.
- **T2 — Client storage wiring (landed in this change set).** Make `scp-client`'s `Storage` a real, caller-chosen, wired dependency with an actual snapshot/restore read path (in-memory and IndexedDB both valid production backends — in-memory is a legitimate production choice for an ephemeral, no-persistence client, not merely a dev/test affordance); close the unwired-read-path gap. **As landed:** the driver writes one per-context snapshot (and, for an unconsumed key package, one pending-join blob) after each state-mutating op, and restores them all by key-prefix enumeration in its constructor — the single restore path, fail-closed and atomic. A persist that fails *after* the in-memory MLS ratchet has advanced leaves durable and live state diverged; that context is **poisoned** (every further op refuses it) and the client recovers by reconstructing from the last durable snapshot, rather than emitting ciphertext/leaves no peer will see. The pending-join blob is bound to its owning identity **and** context id, both verified on restore (a swapped/mislabeled blob is rejected fail-closed). Browser storage error codes occupy `SCP-STORAGE-8010–8013`; the low `8001–8003` block is reserved for `scp-kt-android`'s `AndroidStorage`. **Runtime snapshot consolidation was deliberately NOT attempted:** the `scp-mls` out-of-band snapshot byte-format is intentionally distinct from the native runtime's flat `MlsCryptoSnapshot` layout, which is byte-incompatible with committed legacy KAT fixtures — the two are kept as separate formats on purpose, and a future refactor must not fold them together on the assumption they are the same shape.
- **T3 — Convergent committer-timestamp authentication (landed in this change set; closes #1975).** Slice 2 transported a *convergent committer timestamp* — the value a member stamps on its mirrored event-log leaf so the §9.9.3 Merkle logs converge byte-for-byte — as a **loose, unauthenticated `u64`** carried beside the ciphertext, and stamped it on **both** the `MessageSent` and the `MemberJoined` leaf. Two defects, one governing upstream cause. **(a) `MessageSent` is not a convergent leaf at all.** Per the ADR-011 amendment exclusion taxonomy §2 (`.docs/adrs/phase-2.md`, ~956–969), an application message is **per-author application activity** with no total delivery order over a real relay: each member's log holds only its own author's `MessageSent` events, so honest members *diverge at equal count* — it is EXCLUDED from the canonical Merkle log and is a local `ContextEvent` until ADR-051 (exactly as on the native path, whose `finalize_send` returns a local event, not a leaf). The browser driver was wrongly appending it as a durable convergent leaf; the leaf hash mixes in the per-member arrival-order `sequence`/`prev_hash`, so a `MessageSent` leaf diverges across members *regardless of any timestamp*. **(b) The loose `u64` on the surviving (membership) path was a forgery seam.** For the `MemberJoined` leaf — which *is* convergent (commit-ordered) — the loose transported `u64` violated the ADR's "relays are untrusted dumb pipes" tenet: a hostile relay could deliver a valid Commit with an altered timestamp and fork the receiver's Merkle root from the honest committer's. This was a **named blocker on wiring a real (untrusted) relay/transport** (the Slice-3 browser-backend work). **T3 is primarily a subtraction that fixes both.** It excludes `MessageSent` from the Merkle log (the driver now buffers it as a local `MessageSent` `ContextEvent` for `drain_events`, matching native — the event log and its root are unchanged by a send/receive); and it retains the AAD authentication **only** for the commit-ordered `MemberJoined` leaf, adopted verbatim. Application messages are plain MLS-encrypted and bind no AAD.

  **Mechanism.** Only the **add-Commit** stamps a convergent membership leaf, so only it binds a timestamp. The committer binds it into the Commit's `FramedContent.authenticated_data` (AAD) immediately before the one add-member call, via the `scp-mls` entry point `add_member_with_convergent_timestamp` (the pre-existing `add_member`, consumed by the native runtime whose timestamp rides inside a signed SCP envelope, is left untouched). The application-message counterpart `encrypt_with_convergent_timestamp` is **deleted**: an application message is not a convergent leaf, so `encrypt_message` now uses the plain `scp-mls` `encrypt` and binds no AAD. openmls folds the Commit AAD into the frame, where it is covered by (a) the committer's **leaf signature** over the `FramedContentTBS` (RFC 9420 §6.1) — so no member other than the committer can author a frame carrying it — and (b) the **`PrivateMessage` AEAD tag** under the SCP `PURE_CIPHERTEXT` policy — so a relay that flips the timestamp breaks the tag and the frame is rejected at decrypt. A receiver recovers the value from openmls's *verified* `ProcessedMessage::aad()` (i.e. **after** signature + AEAD verification) and stamps that authenticated value on each mirrored `MemberJoined` leaf. The loose transported parameter/fields are therefore **deleted, not validated**: `SendOutput` / `WasmSendOutput` are removed (`send_message` returns the ciphertext bytes only), the `committer_timestamp_secs` field is removed from `AddMemberOutput` / `WasmAddMemberOutput`, and `receive_message` / `receiveMessage` lose the timestamp parameter (the forgery seam is gone *by construction* — a fresh caller cannot supply a mismatched value). A **no-add Commit** (e.g. a self-update) stamps no membership leaf, so it binds no AAD and the receiver decodes none (`InboundChange::Commit` carries `committer_timestamp_secs: Option<u64> = None`); the receive path decodes the AAD **iff** the Commit adds members, which also fixes a self-update that the pre-reframe unconditional decode would have failed closed.

  **Wire format.** A fixed **13-byte** AAD blob: `b"SCPT"` (4-byte magic) ‖ version `u8 = 1` ‖ `timestamp_secs` as `u64` big-endian. Big-endian, fixed-width, no `usize`, so a native and a wasm32 member produce byte-identical AAD for the same timestamp (cross-target determinism). Decoding fails closed on empty AAD (`ConvergentTimestampMissing`), wrong length / wrong magic / unrecognized version (`ConvergentTimestampMalformed`).

  **Adopted verbatim — no window, no floor.** Every receiver adopts the authenticated `MemberJoined` timestamp **verbatim**; there is no receiver-side plausibility window and no monotonic floor. The value is **convergent by construction**: MLS imposes a single total order on commits, and the AAD binding fixes exactly one authenticated value per Commit that every honest receiver reads identically — so verbatim adoption is what makes the mirrored leaves byte-identical. A receiver-side clock verdict would itself be a **§9.9.3 violation**: two honest members whose clocks straddled the same authenticated value would reach opposite accept/reject verdicts and diverge (and, on an add-Commit, partition on the epoch advance) — the exact non-convergence this leaf must avoid. The earlier "reject, never clamp" plausibility window (a `MAX_FUTURE_SKEW_SECS` / `MAX_AGE_SECS` bound on a *lying-but-authenticated* committer) is therefore **removed**, not tightened. A **monotonic floor** (adopt only if ≥ the last leaf's timestamp) was considered and rejected for the same reason: it makes a leaf's acceptance depend on per-receiver arrival history, which can differ across honest members. What survives is fail-closed decoding: a missing or malformed AAD on an add-Commit rejects it **pre-merge** (after the Remove-refusal and the KeyPackage-`Lifetime` bracket, before the merge), so a rejected add-Commit leaves the MLS epoch, SCP membership, and event log mutually consistent (fail-closed, not half-applied). These decode failures surface at the browser boundary as a distinct **`SCP-CRYPTO-4040`** error code. **One per-receiver clock verdict does remain on the membership path — by MLS necessity, not SCP choice.** Removing the plausibility window strips every *SCP-layer* clock verdict on the timestamp, but openmls's internal KeyPackage `Lifetime` check (§Prereq-1) still gates whether an add-Commit merges at all, so in principle two honest members whose clocks straddle a KeyPackage's `not_after` could diverge on the epoch advance. This residual is neither reintroduced nor removable here: openmls validates `Lifetime` inside `process_message` regardless, so suppressing it would disable MLS lifetime enforcement entirely — the upstream openmls time-provider seam (tracked as #1965) is the only real remedy — and KeyPackage lifetimes are coarse (~84 days) against the removed ±5-min / 7-day plausibility window, so realistic honest skew cannot straddle them. It is a known, bounded, upstream-tracked residual, not a gap this slice closes with a new receiver-side check.

  **AAD is authenticated, not confidential.** `authenticated_data` is transmitted in the clear (it is *authenticated* additional data, not encrypted). This is correct: the committer timestamp is a public event-log leaf field, not a secret, and the AAD carries **only** the timestamp.

  **One residual, out of this slice's scope (named, not hidden).** **Joiner-trusts-adder replay.** A *new* joiner adopts the adder's replayed event-log stream verbatim on join; independently re-verifying each historical leaf against a per-leaf committer signature is the leaf-signing / custody slice (§23.13 paragraph 1, per-event signature verification), not this one. The **authenticated committer lie** the removed window nominally bounded is *not* a residual introduced here: a malicious committer that binds a false-but-authenticated value is the pre-existing MLS insider-equivocation class (a malicious committer can already fork receivers by sending different commits to different members), and it is bounded once per-leaf committer signatures land (§23.13), not by a receiver re-adjudicating an authenticated value — which, as above, would break honest-honest convergence. Adopting the AAD value verbatim is the correct end state; per-leaf signing is the strictly-additive hardening that lands with the custody slice.

- **T4 — In-tab HPKE sender-key distribution over the `scp_wrapping_key` extension (landed in this change set; closes #1976).** Slice 2's participant `send_message` emitted only the §9.16 double-ciphertext; members exchanged their §9.16 sender keys **out-of-band** via `local_sender_key_bytes`/`install_sender_key` test seams (caller-trusted). T4 closes that distribution gap: each member HPKE-seals its per-member AES-256 sender key to peers' **stable** X25519 wrapping keys (§9.16.1) — published in the `scp_wrapping_key` MLS leaf extension by `generate_key_package_with_wrapping_key` / `create_group_with_wrapping_key` — and delivers each sealed key as an MLS-authenticated **management** message (SCPM-prefixed, §9.16.1, disjoint from application frames because an application header's first 4 bytes are the high bytes of a sender-key epoch ≥ 1 = `00 00 00 00`, never `SCPM`). The seal/open primitives (`hpke_seal_sender_key` / `hpke_open_sender_key`, RFC 9180 Base mode) are the **shared** `scp_protocol::crypto::sender_keys` code the native runtime uses, so a native and a browser member interoperate by construction — no wasm-local re-implementation. The distribution rides outside the convergent §9.9.3 Merkle log entirely: it is neither a `MemberJoined` leaf nor a `ContextEvent`, so an install returns `application == false`, buffers nothing for `drain_events`, and leaves the event-log root unchanged (INVARIANT 4).

  **Mechanism — the wrapping-key directory IS the member set (INVARIANT 1).** The driver holds one `member_wrapping_keys: HashMap<did, [u8;32]>` per context; there is no parallel `members: Vec<String>` that could drift, so a member is never recorded without the key a peer needs to seal to it (`member_dids` reads the directory keys). Distribution fires on **three** triggers forming a topologically-complete push mesh: (1) the **adder** seals its key to the joiner (`AddMemberOutput.sender_key_distributions`), because as the committer no bystander mirrors the add for it; (2) the **joiner** seals its key to every existing member it adopts from the transported directory (`join_context_encrypted` return); and (3) — the make-or-break trigger (INVARIANT 2) — every **bystander** existing member seals its key to each newly-added member when it processes the add-Commit in `receive_message` (Alice seals HER key to Carol when she processes Bob's add-Carol Commit). Without (3), a bystander's messages are undecryptable by later joiners. The transported directory travels beside the Welcome as `AddMemberOutput.wrapping_keys` (not in the `MemberJoined` leaf payload, which stays `Vec::new()` — INVARIANT 4); each Add proposal's published wrapping key is recovered from the joiner's `KeyPackage` leaf **pre-merge** by `scp-mls` (`key_package_in_wrapping_key` on the adder side, `decrypt_with_membership_changes` → `InboundChange::Commit.added_wrapping_keys` on the bystander side).

  **Fail-closed on a missing wrapping extension (INVARIANT 3).** An SCP add whose `KeyPackage` leaf carries no `scp_wrapping_key` extension is **rejected** — on the adder side `add_member` returns an `ExtensionError` before any leaf is stamped, and on the bystander side the whole Commit is dropped pre-merge (the group stays on its current epoch, MLS + SCP state consistent). A member no peer can HPKE-seal a sender key to must never be admitted.

  **Receive-side security invariants.** Installing a distribution enforces, in order and all **before** any store mutation: (a) **sender-DID binding** — the sealed key's claimed `sender_did` must equal the frame's authenticated MLS credential DID, so a member cannot attribute a key to a DID it does not control; (b) the **epoch-poisoning ceiling** ([`MAX_EPOCH_ADVANCE`] above the stored high-water) — a `u64::MAX` epoch cannot wedge future rotations; (c) **HPKE open** with the member's wrapping secret — fails closed for a distribution sealed to a different recipient; (d) **monotonic install** (`set_checked`) — a stale/replayed epoch is rejected. A management payload over the §9.16.1 64 KiB bound is refused. `rotate_sender_key` (§9.16.5) mints a fresh key, checked-increments the epoch, and re-seals to the whole directory; recipients accept the higher epoch and reject the stale earlier-epoch key.

  **Snapshot v3 (INVARIANT 5).** `SNAPSHOT_FORMAT_VERSION` advances 2→3 to persist the stable wrapping keypair (`wrapping_public` + a zeroized `wrapping_secret`) and the wrapping-key directory. Without the persisted secret a reopened tab could not HPKE-open the next distribution; without the directory it could not seal on the next add/rotate. A pending-join blob likewise carries the published wrapping keypair, so a join interrupted by a tab close resumes with the SAME key peers already seal to. Pre-release: no migration; a v2 blob is rejected as an unknown version.

  **Residuals, out of this slice's scope (named, not hidden).** (1) **Offline-during-push.** Rotation and add distributions are unsigned **pushes** over the management channel; a peer offline during the push does not receive the new key until a future push. Re-driving it needs the demand-driven **pull** path (`SenderKeyRequest`/`SenderKeyResponse`, §9.16.2) — gated on #1980 — which this slice does not implement (it uses the `SenderKeyDistributionMessage` PUSH variant, with a zeroed `request_nonce`). (2) **Block protocol excluded.** The signed `SenderKeyEpochAdvance` / block-notification auto-rotation (§9.16.3) is node-side and out of the participant fence. (3) **Self-certifying directory.** The wrapping-key directory is transported adder→joiner and trusted like the replayed event-log stream; independently re-deriving each member's wrapping key from a per-leaf-signed source is the leaf-signing / custody slice (§23.13), the same residual T3 names for the convergent timestamp.

## Amendment (2026-06-30): Dissolve `scp-primitives`; extract `scp-did`

**Supersedes Prerequisite 3.** The interim factoring (Slices 1/1a) that made the DID types wasm-reachable did so by parking them in the wrong homes: `DidDocument`/`VerificationMethod`/`decode_multibase_key` in `scp-protocol`, `DID`/`SigningKeyId` in `scp-primitives`, and `scp-identity` re-exporting the moved types for back-compat. Each of those is a violation the project forbids — a *generality-tier* crate (`scp-primitives`) used as a dumping ground, identity **domain** types living in `scp-protocol`, and a re-export shim standing in for real import updates. It solved the compile-ordering problem while *reproducing* the architectural smell it was meant to fix.

**Root cause.** A crate named for a generality tier (`primitives`/`common`/`core`/`util`) has no refusal criterion — anything "low-level enough" qualifies, so unrelated capabilities accrete. That is the exact mechanism that put `DID` in `scp-primitives`: the crate could not say *no*, because "primitive" is not a domain. The fix is structural, not a relocation: **every crate is named for the capability it owns; a universal type lives in its domain crate, because universality is not a domain.**

**Scope of the naming principle.** The principle targets *generality-tier* names (`primitives`/`common`/`core`/`util`) — names with no refusal criterion. It does **not** condemn every broadly-scoped crate: `scp-platform` passes, because "the host-platform-varying provider surface (custody, storage, attestation)" *is* a refusal criterion — a type that does not vary by host platform does not belong there. A known tension sat inside that boundary: `scp-platform`'s `kdf.rs` and `pseudonym.rs` were *pure-crypto* members that do **not** vary by platform, and were therefore candidates for a future factoring into `scp-crypto`. That factoring was flagged as a **separate decision**, not part of the topology-split slice — surfaced here so the principle is applied honestly rather than selectively. As of the [Amendment (2026-07-16 — Option A)](#amendment-2026-07-16--option-a-browser-pseudonym-derivation-ruling), the **`pseudonym.rs`** half is **DONE**: the §9.10.4.A derivation now lives in wasm-safe `scp-crypto::pseudonym` (native custody delegates to it), so native and browser can share one implementation. **`kdf.rs`** (the Argon2id passphrase→key derivation) remains the still-open future candidate — it has no browser consumer yet, so its factoring stays deferred. A symmetrical residue sits one layer up: `scp-protocol/src/identity/attestation.rs`'s `IdentityLinkAttestation` (the §3.5.1 identity-link wire message) imports `scp_did::DID` and is identity-domain-shaped, yet is defensibly a *protocol wire type* that stays in `scp-protocol` — flagged here for the record rather than silently passed.

**Decision.** Dissolve `scp-primitives` into capability crates and give the DID **data model** one wasm-safe home (`scp-did`). `scp-primitives` (`crypto.rs` = `verify_ed25519_signature`; `time.rs` = the `Clock` port; `identity.rs` = `DID`/`SigningKeyId`) is three unrelated capabilities under one name — split them into `scp-crypto` / `scp-clock` / `scp-did`. The DID document types (`DidDocument`, proofs, attestation) — moved into `scp-protocol` by the interim Slice-1a — join `scp-did`, so the DID model lives in exactly one place. `scp-identity`'s native DHT/resolution/lifecycle subsystem stays a single crate (the type graph shows it is not separable — see rejected alternative 5); it simply imports the DID model from `scp-did` instead of hosting or re-exporting it.

```
                                 ├─ scp-event-log

                                       └─ scp-runtime → scp-core → scp-ffi                   [native]
```

*The diagram foregrounds `scp-did`'s consumer edges for readability; `scp-clock` and `scp-crypto` are not consumer-less. They are likewise depended upon by `scp-protocol`, `scp-event-log`, and `scp-runtime` (and, for `scp-clock`, most native crates) — those edges are omitted from the drawing, not absent from the graph.*

**Mechanical rules.** The enforcement map is: the **load-bearing** invariants are fully enforced by construction — **acyclicity** by `rustc` itself (a crate cycle does not compile), the **wasm fence** by the `wasm32-unknown-unknown` compile job (the browser stack failing to build for wasm if it reaches a native-only crate is the check), and the **banned-dependency** rules by `scripts/check-protocol-deps.sh`. The **no-shim rule** is backstopped by `scripts/check-no-shim-reexports.sh` (added by this slice); its exact scope, and the canonical-vs-exotic-laundering split, are the first bullet below — the single ADR-level statement.
- **No back-compat / shim re-exports of moved or dissolved types, anywhere.** Every consumer imports the owning crate (`scp_clock::Clock`, `scp_crypto::verify_ed25519_signature`, `scp_did::DID`, …). This bans *shims standing in for real import updates* — it is **not** a blanket ban on re-exports: the `scp-core` facade remains the one sanctioned aggregation surface (it exists to be the SDK-facing façade and is unchanged by this amendment). The rule also **deletes** the `scp-runtime/src/crypto/mls/mod.rs` `pub use scp_mls::{…}` shim left by Slice 1 — `scp-runtime` call sites import from `scp_mls` directly. The gate `scripts/check-no-shim-reexports.sh` catches the canonical spellings — `pub use [::]scp_{clock,crypto,did,mls}` in whole-crate, `::Item` path, and `as`-rename forms, across every `src/` tree under `crates/` — outside the owning crate or the sanctioned `scp-core` facade; the load-bearing acyclicity/fence invariants above do not rely on it.
- **Acyclicity.** `scp-did` is a pure leaf — it reaches no other SCP crate (only `ed25519-dalek` + serialization). If any rotation/migration proof reaches a `scp-protocol` type, that type moves into `scp-did` or the reference was wrong — it is *not* resolved by a back-edge.
- **Fence unchanged.** `scp-mls`/`scp-client` still must not reach `scp-runtime`/`scp-identity`/tokio (`cargo tree`), now also expressible as: the browser stack depends only on the wasm-safe leaves + `scp-did`.
- **Pre-release** — no migration/deprecation code; consumers are updated in place.

**Alternatives considered (and why rejected):**
1. *Keep the DID types in `scp-protocol` (the interim).* Rejected: `scp-protocol` is protocol logic, not the identity domain; parking identity types there is the same class of smell as the junk drawer, one layer up.
2. *Fold the DID types into `scp-primitives` / keep `DID` there.* Rejected: this **is** the root cause — a generality-tier crate accreting domain types.
3. *Make `scp-identity` itself the wasm-safe leaf and bolt on a native sibling for the DHT.* Rejected: it inverts the graph (protocol depending on a would-be-leaf identity crate) and renames/guts the existing crate rather than decomposing by responsibility; the clean cut is three single-responsibility crates.
4. *A single `scp-primitives`/`scp-common` retained for the leftovers (`Clock`, crypto).* Rejected on the naming principle above — small **capability** crates (`scp-clock`, `scp-crypto`) are the correct shape; crate count is not the cost, the dumping ground is.
5. *Split the DHT into its own `scp-dht` crate (the original three-way hypothesis).* Rejected **at the DID-method layer**, approved **at the transport layer** — implementation ground-truth shows they are two distinct seams, not one:
   - The **DID-method layer** (`dht.rs`: `DidDht`, the async `DidMethod` trait impl, `ScpIdentity`, `MigrationPartialState`) is *not* separable. `DidDht` `impl`s the async `DidMethod` trait, embeds/constructs `ScpIdentity` (custody `KeyHandle`s), and returns `IdentityError` (`scp_platform`-coupled), while `IdentityError`/`config` reference `DidDht`/`MigrationPartialState` and `MigrationPartialState` *structurally embeds* `ScpIdentity` — a hard crate cycle Rust rejects. Extracting it is impossible without either moving async/`scp_platform`-coupled types into the wasm-safe `scp-did` (defeating its purpose) or a logic change (out of scope for a behavior-preserving split). This layer is one native capability and stays in `scp-identity`.
   - The **transport layer** (`dht_client/`: the `DhtClient` trait, `DhtRecord`, and the pkarr + in-memory impls) *is* separable, and was extracted into a new `scp-dht` crate (landed earlier). The full coupling enumeration and the extraction mechanics — the two severable couplings, the `DhtError`/`From<DhtError>` seam, and the one-way `scp-identity` → `scp-dht` edge — live in the **T1c-a** slice bullet above (§Implementation Slices) and are not repeated here.

   *The type graph decides crate boundaries — an aesthetically-appealing split the compiler rejects is not a boundary; a split the compiler accepts, once the one coupling type (`IdentityError`) is given its own home, is.*

## Amendment (2026-07-15): TS SDK two-package delivery (Slice 3)

**Refines the delivery of Slice 3** ("wire the browser backend behind the existing `@limn-works/scp-ts` API," line 84). Slice 3 ships the in-browser client as **two npm packages**, not one:

- **`@limn-works/scp-ts`** — the shared core (error hierarchy, types, wire marshalling) **+** the NAPI-backed, **full-capability** `ScpClient`. The unqualified base package; keeps its `@limn-works/scp-ts-napi-*` optional-dependency binaries.
- **`@limn-works/scp-ts-wasm`** — the same shared core **+** the wasm-backed, **participant-subset** `ScpClient` **+** opt-in `WebCryptoCustody` / `IndexedDbStorage` adapters. The adapters are **exports the embedder injects**, not silent defaults: a Workers/Deno/edge runtime (no `IndexedDB`) supplies its own custody/storage/socket ports, consistent with the injected-port model below and the "no silent security defaults" tenet.

**Reconciliation with line 84.** "the existing `@limn-works/scp-ts` API" denotes the shared **developer API *shape*** — the `ScpClient` participant surface, identical method shapes across tiers — delivered per tier. It never mandated a single npm package. The two-package split therefore **refines** the delivery; it does not contradict the ADR's intent. Line 84's text is unchanged; this amendment records how it is delivered.

**Key properties:**
- **Naming.** Native is the unqualified base (`scp-ts`); wasm is the mechanism-suffixed tier (`scp-ts-wasm`). This keeps the deliberate cross-language `scp-{lang}` family (so `-ts` stays — not a bare `scp`) and matches the external convention for native+wasm-of-the-same-code (`esbuild`/`esbuild-wasm`, `duckdb`/`@duckdb/duckdb-wasm`, napi-rs `-wasm32-wasi`).
- **Explicit tier opt-in; NO transparent native→wasm fallback.** The wasm tier is a **capability SUBSET**, barred from `scp-runtime` by the mechanical scope fence (§Scope fence + the 2026-06-30 Amendment's "Fence unchanged" restatement): governance, economy/payment validation, cross-context saga **coordination**, media, DHT, and broadcast **hosting** cannot exist in-browser. A silent fallback would hand a browser dev the subset under the full-surface import — "same import, different capability by environment." The reduced tier must be a knowing choice, which is why it is its own legible package.
- **Each package bundles its own copy of one in-repo core module.** Harmless: cross-tier co-load is structurally possible (a test harness or a Node process importing both), but its **only** residual is a bounded `instanceof` papercut — SDK error classification is by string code-**prefix** (`mapBridgeError` → `code.startsWith(prefix)`), not by cross-package object identity, so errors classify correctly across tiers. There is **no** third `-core` package; the wire byte-format that must agree across tiers is pinned in Rust (`scp-protocol` + relay-client, the cross-target KAT), not in the duplicated TS.

**Component 3 refinement (transport).** The browser relay transport (component 3, line ~32) is delivered as an **injected `JsSocket` port** — the same extern-injection pattern as `JsKeyCustody` / `JsStorage` — **NOT** a direct `web_sys::WebSocket` binding or a ported `webtransport-wasm` pump inside the Rust crate. This keeps `scp-client-wasm` honestly portable-non-native (an embedder in Deno/Bun/Workers/edge supplies the socket) and keeps the wasm fence trivially clean (no `web-sys` transport features). **WebSocket is the baseline** (spec §10.15.3); **WebTransport is a follow-on** behind the same injected-port interface.

**Decision record:** planning-session-09 (`.docs/planning-sessions/planning-session-09-adr057-slice3-ts-sdk-packaging.md`, decisions D1–D4).

## Amendment (2026-07-16): Slice-3 transport — real §9.10.4 pseudonyms, shared invitation join, injected JsSocket

**Governs the in-browser relay-transport slice** (Slice 3, component 3 — the `scp-client-wasm` transport code that carries app-data and the join bootstrap over an untrusted relay). It composes with, and does not supersede, the [Amendment (2026-07-15)](#amendment-2026-07-15-ts-sdk-two-package-delivery-slice-3) (that amendment's D4/Component-3 note fixed the transport *seam* — an injected `JsSocket`; this amendment fixes what the browser *puts on that seam* — the real routing model and the join wire). The governing principle is the ADR-055 / D5 / `scp-mls` **anti-parity-tax discipline**: the browser transport implements the REAL protocol models and **shares, never forks, every crypto / wire / pseudonym primitive**. Three rulings (T-1..T-3), each verified against the native code and approved 2026-07-16.

**T-1 — Real §9.10.4 per-context-pseudonym routing; no shared-channel shortcut.** The browser routes app-data **exactly as native routes it** (`scp-runtime/src/context/messaging_helpers.rs`): the outer-envelope cleartext `routing_id` is **zeroed** (`[0u8; 32]`) and one sealed blob **fans out to N per-member pseudonym transport addresses**. The browser MUST NOT publish app-data to `context_routing_id` — native treats that value as **RESERVED** (`is_reserved_pseudonym`, §9.10.4; the shared bootstrap RID is announcement-only), so publishing app-data there would (a) **add** a direct relay-readable per-context correlator — on top of the *pre-existing* known-limitation residual that the same MLS ciphertext is fanned to every pseudonym address, so a relay can already blob-match (`messaging_helpers.rs` §9.10.4 KNOWN LIMITATION, ~line 1092); per-member fan-out gives **reduced, not full**, unlinkability, and the shared-RID correlator would erode even that — and (b) break native↔browser interop, since a native member rejects a reserved-RID announcement and never fans app-data onto the shared channel. A **shared-channel MVP is REJECTED**: it would require an ADR carve-out sanctioning reduced unlinkability, against the privacy-paramount and no-DOA tenets. To honor share-don't-fork rather than duplicate §9.10.4 across native and browser, the **pure** §9.10.4 logic is **EXTRACTED** from native-only `messaging_helpers.rs` into the wasm-safe **`scp-protocol::context::pseudonym`** submodule (architecture-reviewed + approved): `is_reserved_pseudonym`, `is_pseudonym_announcement_payload`, `pseudonym_collides_with_other_did`, the `PseudonymAnnouncement` wire struct + `PSEUDONYM_ANNOUNCEMENT_TAG`, and a new pure **`classify_pseudonym_announcement`** decision core. Native and browser consume ONE copy; the stateful ingest (peer-registry insert + `PseudonymAnnounced` event emit, the `&mut` runtime path) stays native-async and wraps the shared classifier. The pseudonym-derivation **algorithm** (§9.10.4.A HKDF-SHA-256) is shared and — per the [Amendment (2026-07-16 — Option A)](#amendment-2026-07-16--option-a-browser-pseudonym-derivation-ruling) — now lives in the wasm-safe `scp-crypto/src/pseudonym.rs` (factored out of `scp-platform`; native custody delegates to it via the `KeyCustody::derive_pseudonym` port). At the time of this extraction slice, only **native** had a CALL SITE; the algorithm became reachable from the browser here, but wiring the browser call site was the transport slice's job, not this factoring. The **browser's reach to it was a prerequisite NOT YET BUILT at that point**: `scp-client-wasm`'s `JsKeyCustody` had no `derivePseudonym` seam (only did/sign/getPublicKey/generateKeypair/destroyKey/dhAgree, all unwired), `scp-client-wasm` did not depend on `scp-platform`, and there were zero pseudonym references in the browser stack. **(The transport slice has since wired the browser call site — via `ScpMlsGroup::derive_pseudonym` over the wasm-held MLS key — see the A1 as-built note below.)** Because the browser MUST derive its own per-context pseudonym to announce it and to be addressed in peers' fan-out, adding a browser derivation seam was a **structural prerequisite of the transport slice** (see Sequencing). **How** that seam is satisfied was an open design point coupled to #1980 (the browser key-custody model): with the key currently in wasm memory the browser could derive in Rust via the shared §9.10.4.A algorithm (**Option A**), or a JS-side `JsKeyCustody.derivePseudonym` seam could re-derive off-wasm (**Option B** — a §9.10.4.A re-implementation to be pinned by the §25.19 KAT). This is now **DECIDED = Option A** (human-approved 2026-07-16; see [Amendment (2026-07-16 — Option A)](#amendment-2026-07-16--option-a-browser-pseudonym-derivation-ruling)): the derivation is factored into wasm-safe `scp-crypto::pseudonym`, so native and browser run ONE implementation (byte-parity by construction, pinned by the §25.19 cross-target KAT). This T-1 slice extracted the §9.10.4 pure LOGIC; the Option-A derivation factoring is its companion; wiring the browser CALL SITE was the transport slice's job (since done — see the A1 as-built note below). The browser custody's byte-parity obligation is validated by the existing §25.19 KAT vectors — a **custody-model** obligation, **not** part of this pure-logic extraction. **Scope this precisely** (as the Option-A Decision and the A1 as-built note below do): the KAT pins **cross-target ALGORITHM determinism** — the same §9.10.4.A recipe yields the same bytes on native and `wasm32` for the *same input key*. It does **NOT** assert **same-human native↔browser pseudonym equality**, which does **not** hold pre-#1980 (the browser keys on the per-context MLS key, native on the identity key — see the A1 as-built deviation). "Identical pseudonyms native vs. browser for a given human" is a #1980 outcome (aligning the key-source), not a property of this seam.

**T-2 — Native↔browser join over the already-shared §5.12.3 invitation bundle.** The browser join bootstrap uses the shared `hpke_seal_invitation` / `hpke_open_invitation` / `InvitationBundle` / `derive_invitation_routing_id` in `scp-protocol` (`crypto/envelope_seal.rs`, `context/invitation_bundle.rs`) — the same crate/primitives `scp-client` already consumes for `hpke_seal_sender_key` (T4, #1976) — **NOT** a plaintext `JoinBundle`. Full native↔browser join interop lands **in the transport slice, not deferred**: deferring it would ship a half-client that cannot join native contexts. No extraction is needed — the primitives are already shared and wasm-reachable.

**T-2 re-slice as-built (2026-07-17; human-ruled, coupled to #1980).** The shipped transport slice is the **#1980-independent half only**. The invitation **join** path and the invitation **HPKE-open** custody are **DEFERRED pending #1980**: opening an `InvitationBundle` requires a Diffie-Hellman against the invitee's on-device custody key (`hpke_open_invitation_with_external_dh` / `JsKeyCustody.dhAgree`), and that seam is **unwired** in the browser pre-#1980 — the browser holds no custody key it can DH-agree with. T-2's premise above — "*nothing external blocks it; the primitives exist and are wasm-reachable*" — is therefore **FALSIFIED as-built**: the seal/open *primitives* are wasm-reachable, but HPKE-**open** needs a browser custody key that **does not exist pre-#1980**, which is a genuine external block (not a self-imposed scope cut). What ships is the #1980-independent transport machinery (real §9.10.4 zeroed-`routing_id` fan-out, the announce mesh, and the inbound pump); native↔browser join over the shared `InvitationBundle`, and the HPKE-open custody it needs, land with the #1980 browser-custody model. This is a human ruling recorded down into the artifact — a re-slice of the shipped scope, not a code-driven revision of the T-2 ruling itself.

**T-3 — Injected `JsSocket` port; the only per-target code is sync orchestration.** Transport is an injected `JsSocket` extern (outbound `send(frame: Vec<u8>)` sink), **NOT** a `web_sys::WebSocket` call — this keeps `scp-client-wasm` portable-non-native and the wasm fence trivially clean (refining the 2026-07-15 amendment's Component-3 note, D4). Inbound frames are JS-pumped into a **synchronous** `handleRelayFrame` method: the driver is a sync `&mut self` machine and cannot hold an `onMessage` callback. **WebSocket is the baseline** (spec §10.15.3); **WebTransport is a follow-on** behind the same port. The browser's sync **fan-out / announce / pump orchestration** is genuinely new code, but it is orchestration **over shared primitives** — the ADR-057 sync-driver-over-shared-machine pattern, identical in kind to how `scp-client` already re-orchestrates send/receive over the shared `scp-mls` state machine — **not** a crypto/wire fork. **No dev/test transport stand-in on the production path**: an in-memory loopback socket is `#[cfg(test)]` only and is never exported (per the no-dev/test-stand-in-in-production tenet).

**Sequencing:** (1) the §9.10.4 pseudonym-logic **extraction** slice (behavior-preserving; native adopts the shared copy; adds a cross-target byte-parity KAT) → (2) a **named prerequisite of the transport slice — the browser pseudonym-derivation seam** (the browser must be able to derive its own per-context pseudonym at all, to announce it and be addressed in fan-out; mechanism is the open, #1980-coupled design point above, to be scoped when the transport slice is planned — a peer of the D5 wire-types and D6 `panic=unwind` prerequisites) → (3) the **`JsSocket` transport** slice (fan-out orchestration + shared invitation join + inbound pump) → (4) the `@limn-works/scp-ts-wasm` package (2026-07-15 amendment) → (5) Slice-4 examples. This composes with, and precedes the transport-code half of, the 2026-07-15 amendment's sequencing (which numbered the transport as its execution step 3).

**Announce-mesh as-built (2026-07-17).** The transport slice wires the §9.10.4 pseudonym-announcement mesh in the browser. This is the authoritative as-built design (documented here as T4's sender-key distribution is documented above), governed by the same "relays are untrusted dumb pipes" and forward-secrecy constraints:

- **No announce at context creation.** A creator has no peers, and a §9.16 frame sealed at the creator's MLS epoch cannot be decrypted by a member who later joins at a higher epoch (MLS forward secrecy) — so a create-time announcement would be a **dead, undecryptable frame**. The creator instead learns and announces via the reciprocal mechanism below once a peer appears.
- **Seed trigger.** The **joiner** announces its pseudonym on `join_context_encrypted` — the one proactive announce.
- **Mesh completion = reciprocal-announce.** When a member records a **new** peer's pseudonym (a DID not previously in its registry) it **re-announces its own** pseudonym. This is guarded to **first-time-per-peer** so the cascade **CONVERGES** (no storm): joiner-announce → existing members reciprocate → joiner reciprocates → quiescent. It works over **live delivery** and does **not** consume relay backfill (`since:Some`), which the client does not use. **This is a limitation, not a virtue:** because there is no backfill and no reorder buffer, an announcement that arrives before the receiver can decrypt it is **lost** (see the ordering residual below); relying on live-only delivery is a deliberate scope cut for this slice, not a security property.
- **Self-echo handling.** The untrusted relay delivers every PUBLISH to **all** subscribers of the routing id **including the publisher** (`scp-transport/src/relay/subscription.rs` `deliver_to_subscribers` — no publisher exclusion), so each member receives the echo of its own announcement on the shared `context_routing_id`. The shared `scp-mls` decrypt maps openmls `ValidationError::CannotDecryptOwnMessage` to the typed `MlsError::CannotDecryptOwnMessage`, and the receive loop **DROPS it benignly** (symmetric with an unknown-routing_id drop).
- **Native-parity flag (recorded honestly, not a silent fork).** The native runtime (`scp-runtime`) has the **same two latent gaps**: its `ingest_pseudonym_announcement` does **not** reciprocal-announce, its decrypt did not distinguish own-messages (now fixed at the shared `scp-mls` layer, which native inherits), and it wires no live relay-receive pump today. The shared `scp-mls` self-echo fix is shared (native inherits it); the **reciprocal-announce** mechanism currently lives only in the **browser** ingest — **native must adopt the same in `ingest_pseudonym_announcement` when it wires its live receive pump**. This is a known **native-parity follow-up** — tracked in **#2179** — recorded here so it is not a silent fork of the announce logic across targets. The follow-up is gated on a **genuine external constraint**, not a deferral dressed as a decision: native wires **no live relay-receive pump** today, so a native reciprocal has nothing to drive against and is presently **untestable end-to-end**; the reciprocal trigger must land **together** with the receive pump that exercises it. A `#[ignore]`d scaffold test (`native_reciprocal_announce_on_new_peer_is_a_follow_up` in `messaging_helpers.rs`) exercises the first-time-new-peer trigger condition and pins the contract until #2179 wires the pump.

**Residuals, out of this slice's scope (named, not hidden — coherent with T4's residuals above).** The announce mesh converges *only* once every member holds every other member's §9.16 sender key and is at a decryptable MLS epoch. Two ordering-dependent residuals remain:

- **(1) Epoch/sender-key ordering residual.** An announcement is a §9.16 double-encrypted frame: to decrypt it the receiver must already hold the **announcer's sender key** and be at an MLS epoch the frame's sender-key epoch does not exceed. Because there is no backfill and no reorder buffer, an announcement **pumped too early** — before the announcer's key distribution (T4's push) has landed, or at the wrong epoch — cannot be opened and is a **benign drop** (`handle_relay_frame` counts it in `dropped_undecryptable`; a self-echo counts in `dropped_self_echo`). The frame's outer MLS generation is **consumed** by that failed decrypt (forward secrecy), so that exact announcement is spent — re-delivering it can never recover it. **Recovery is a partial self-heal:** every existing member re-announces on learning the *next* joiner (the reciprocal cascade), so a later membership change re-drives a *fresh* announcement (new generation) that succeeds once the key has arrived. This is **best-effort**, not guaranteed: in a static group with no further joins, a member that missed a peer's announcement stays **permanently** unable to address that peer — the pseudonym is **lost**, with no trigger to re-drive it. Full closure needs a **demand-driven pseudonym recovery** path — a *pseudonym-pull* (a member missing a peer's pseudonym explicitly requests it) OR a non-join-triggered re-announce — which is currently **UNSPECCED** and part of the same #1980-gated demand-pull era (tracked in **#2180**), and **not implemented in this slice**. **This is NOT closed by §9.16.2.** §9.16.2's `SenderKeyRequest`/`SenderKeyResponse` is a demand-driven pull for **sender keys, not pseudonyms** — `SenderKeyResponse` carries `hpke_sealed_key` (the sealed sender key) and no pseudonym. Pulling a missed sender key lets a member finally *decrypt* future frames from a peer, but it does **not** re-deliver the missed pseudonym announcement: in a static group with no further joins the reciprocal cascade never re-fires, so pulling a sender key never re-delivers the spent pseudonym announcement and the pseudonym stays permanently lost. §9.16.2 is therefore **necessary-but-not-sufficient** for announce-mesh convergence — it must complete for a frame to *decrypt at all* (the dependency premise below), but closing the pseudonym-loss residual additionally requires the distinct pseudonym-pull / re-announce mechanism above (#2180). The dependency premise is explicit: **announce-mesh convergence presupposes T4's key distribution has completed**; when it has not (offline-during-push), the announce mesh inherits T4's incompleteness.
- **(2) Offline residual (restore does not re-announce).** A tab restored from storage (ADR-057 T2) re-derives its own pseudonym and re-subscribes (via `resubscribeAll` on socket open), but it does **not** proactively re-announce, and peers that learned it before the restart still hold its (unchanged) pseudonym. A restored member that had *not* yet completed the mesh with some peer relies on the same reciprocal-re-announce-on-next-join path, or the deferred pull path, to complete it — identical in kind to residual (1). No create-time or restore-time announce is added (a restore-time announce sealed at the restored epoch would be a dead frame for any peer already past it, the same forward-secrecy hazard that bars a create-time announce).

Neither residual is closed here by design: building a reorder buffer, the §9.16.2 sender-key pull, or the distinct demand-driven pseudonym recovery (#2180) is out of this slice (all #1980-gated demand-pull-era work). What this slice guarantees is that a too-early or undecryptable frame **fails safe** (benign drop + observability counter, never a throw or a poisoned replay floor), so the window is survivable and self-heals on the next membership change.

**Decision record:** planning-session-10 (`.docs/planning-sessions/planning-session-10-adr057-transport-pseudonym.md`, decisions T-1–T-3).

## Amendment (2026-07-16 — Option A): browser pseudonym-derivation ruling

**Resolves the open design point named by the [Amendment (2026-07-16)](#amendment-2026-07-16-slice-3-transport--real-9104-pseudonyms-shared-invitation-join-injected-jssocket) T-1 note** (and by planning-session-10) — *how* the browser reaches the §9.10.4.A per-context pseudonym derivation. That note left the mechanism to-be-decided between **Option A** (derive in Rust over the wasm-held signing key, via the shared §9.10.4.A algorithm) and **Option B** (a JS-side `JsKeyCustody.derivePseudonym` seam re-deriving off-wasm). **Human-approved 2026-07-16: the mechanism is Option A.**

**Decision.** The §9.10.4.A software-custody derivation (`derive_pseudonym_secret` = HKDF-SHA-256 over the private seed; `derive_pseudonym_keypair` = HMAC-SHA-256 keying + Ed25519 keygen) is **factored, verbatim, out of `scp-platform` into the wasm-safe `scp-crypto::pseudonym` module** (unconditional `pub mod` — its HKDF/HMAC/SHA-256 primitives are already in the wasm tree). Native custody backends (`InMemory` / `File` / `SQLite`) delegate to it through the unchanged `KeyCustody::derive_pseudonym` port (behavior-preserving), and the browser — with its signing key currently in wasm memory — will derive its own per-context pseudonym by calling the **same** Rust function. Native and browser therefore run **ONE** implementation: **cross-target algorithm byte-parity by construction** — the same derivation recipe yields the same output bytes on native and `wasm32` for the *same input key* — not by a re-implementation that a test must chase. **Scope this claim precisely.** "Byte-parity by construction" here means **cross-target algorithm determinism** (same recipe → same bytes on native and wasm32 for a given input key), which holds and is KAT-pinned below. It is **explicitly distinct from same-human native↔browser pseudonym equality** — that does **not** hold pre-#1980, because the browser's *input key* differs from native's (native keys on the identity key; the browser keys on the per-context MLS key — see the A1 as-built note). The *algorithm* is byte-identical across targets; the *pseudonym a given human gets* is not, until #1980 aligns the key-source. Algorithm parity is pinned by the §25.19 KAT (vectors 30/31), which passes byte-identically in `scp-crypto`, plus a new native + `wasm32` cross-target KAT (`crates/scp-client-wasm/tests/pseudonym_derivation_cross_target_kat.rs`).

**Why Option A over Option B.** Option B would fork the §9.10.4.A recipe into JavaScript — a second implementation of a security-critical derivation, kept honest only by the KAT (share-don't-fork / anti-parity-tax discipline, ADR-055 / D5). Option A keeps a single Rust source of truth, so a future change to the recipe cannot silently diverge native from browser.

**Interim, coupled to #1980.** Option A presupposes the key is in wasm memory (the current as-built browser custody; the non-extractable-WebCrypto custody model of #1980 is punted). This is a coherent interim: if #1980 later moves the signing key to non-extractable WebCrypto, the pseudonym derivation moves out **with** the key (it must run wherever the private key lives), and the derivation seam follows the custody model then. Recording Option A now does not pre-empt #1980 — it fixes the mechanism for the current key location.

**Scope of the executing change.** This ruling is executed by the derivation-extraction slice ONLY: move the algorithm to `scp-crypto`, retarget `scp-platform`'s native custody consumers, drop `scp-platform`'s now-dead direct `hkdf` dependency, and add the cross-target KAT. It does **not** wire the browser CALL SITE (`JsKeyCustody.derivePseudonym` / the fan-out address computation) — that is the transport slice (Sequencing step 2/3 above). This slice makes the algorithm *reachable* from wasm; the transport slice *reaches* it.

**A1 as-built — the browser derives over the MLS key, NOT the DID identity key (interim deviation from §9.10.4.A).** *(Recorded 2026-07-17, when the transport slice wired the browser call site; human-ruled, coupled to #1980.)* Option A said "derive in Rust over the wasm-held signing key." When the transport slice reached to wire it, the *only* Ed25519 private key the browser holds in wasm is the **per-context MLS `SignatureKeyPair`** (generated inside `scp-mls` at `create_group` / `generate_key_package`); there is **no DID identity key in wasm** in this slice (the `Signer` trait exposes only `did()` / `signing_key_id()` — see `scp-client/src/signer.rs`, and the friction note in `scp-client-wasm/src/custody.rs`). So the browser derives its per-context pseudonym over the **MLS key** via `ScpMlsGroup::derive_pseudonym` (which feeds the MLS signing key's 32-byte seed to the shared `scp_crypto::pseudonym::derive_pseudonym_keypair`). §9.10.4.A, by contrast, derives a native member's pseudonym over its **identity** signing key. Consequence: **the browser's per-context pseudonym does NOT byte-match a native member's pseudonym for the same human/context.** This is *acceptable* under the **device-local-pseudonym model** the routing already assumes — each member **announces its own** per-context routing id and peers **record** it from the authenticated announcement (`classify_pseudonym_announcement`); no member (native or browser) ever *recomputes* a peer's pseudonym, so byte-parity across a human's devices is **not a routing requirement**. It is nonetheless a **knowing deviation from §9.10.4.A's key-source**, recorded here (not silently), and it **resolves with #1980**: when the identity signing key moves to on-device custody reachable by the browser, the derivation moves onto the identity key (per the "Interim, coupled to #1980" note above), restoring the §9.10.4.A key-source and, with it, **same-human native↔browser pseudonym equality** (the cross-target *algorithm* parity already holds today — see the Option-A Decision's scoped byte-parity claim — so #1980 changes only the key-source, and thus the same-human pseudonym, not the recipe). Until then the shared *algorithm* (recipe, domain separators, seed interpretation) is byte-identical native vs. browser — only the *key it is keyed on* differs — pinned by the `scp-mls` `derive_pseudonym` unit test (cross-checked against the `test-utils` private-seed accessor) and the §25.19 cross-target KAT.

**Decision record:** planning-session-10 (resolved 2026-07-16, Option A); this amendment; A1 as-built deviation recorded 2026-07-17.

## Amendment (2026-08-01): Ephemeral MLS leaf key + DID attestation (leaf-binding)

**Human-approved (CRYPTO-22 / [#2187](https://github.com/limn-works/scp/issues/2187)).** Resolves the leaf-key ↔ DID binding question for the shared `scp-mls` machine. Spec home: §9.7.1 (rewritten), §9.5.2 (`KeyPackageAttestation` signed structure + `0xFF03` extension body wire-format), §9.18.7 (`scp_keypackage_attestation` extension type `0xFF03`), §9.18.2 (`"SCP-KEYPACKAGE-ATTESTATION-V1:"` domain separator), §25.22 Vector 37 (byte-exact KAT). This amendment records the decision and its rationale; the spec is the normative surface.

**Decision.** The MLS leaf `signature_key` is an **ephemeral, context-scoped Ed25519 key** (unchanged from as-built — `scp-mls` generates it via `SignatureKeyPair::new()`, see the A1 note above). A member's DID is bound to that leaf's key material by a separate **KeyPackage attestation**: a statement signed by the DID's `#active`/`#agent` key over `{ DID, leaf signature_key, leaf encryption_key, init_key, wrapping_key, signing_key_id, issued_at, expires_at }` — binding **all** of the leaf's public keys: the Ed25519 `signature_key` and the **three distinct** X25519 HPKE keys (the LeafNode ratchet-tree `encryption_key`, the KeyPackage `init_key`, and the `scp_wrapping_key` `0xFF01` `wrapping_key`). Binding the whole leaf, not a subset, is the CRYPTO-22 post-compromise fix (§9.5.2): a thief holding only the leaf `signature_key` must not be able to substitute any of the leaf's decryption keys. The decisive one is `init_key` — **`init_key != encryption_key`** (RFC 9420: the Welcome's `EncryptedGroupSecrets` is HPKE-sealed to the KeyPackage `init_key`, not the LeafNode `encryption_key`), so binding only `signature_key` + `encryption_key` still let a thief craft a KeyPackage with an attacker-chosen `init_key` and read the Welcome as the victim. The attestation is carried **in the leaf as an MLS LeafNode extension** (`scp_keypackage_attestation`, `0xFF03`) — mirroring the existing `scp_wrapping_key` LeafNode extension. The attestation is **context-agnostic** (no `context_id`): a KeyPackage is pre-published for offline add before any group is known, so context scope is unknowable at mint time and is instead bound redundantly by the `0xFF02` `scp_context_params` GroupContext extension. This **replaces** the previously-written "leaf `signature_key` IS the DID `#active`/`#agent` key" rule (former §9.7.1).

**Why this, not leaf==DID.**
- **Per-message identity is already the inner envelope, not the leaf.** SCP authenticates every message by the inner-envelope `#active`/`#agent` signature (§9.8.1), verified against the DID document. The MLS leaf key never carried per-message identity; making it equal the DID key bought no message-authentication property SCP did not already have.
- **§9.7.1's real goal is admission/attribution-binding.** The property that mattered was: *when a leaf is added to a group, that leaf provably belongs to the DID it claims.* An attestation delivers exactly that, verified when a member-leaf is **introduced or replaced** — at add/join, and again whenever that member changes its own leaf via an Update / Commit-with-UpdatePath — which is where admission is decided. A Commit that does **not** change the committer's leaf carries no new attestation and is **not** re-verified (its leaf and attestation are byte-for-byte the already-verified ones), so steady-state processing does not depend on re-resolving each committer's DID.
- **leaf==DID was a non-standard conflation — and was never implemented.** RFC 9420 (§5.3 leaf self-signature, §10.1 KeyPackage) models identity in the leaf **`Credential`**, distinct from the leaf `signature_key`; binding an external identity to the leaf key is conventionally done *through* the credential, not by making the two keys equal. SCP's own key hierarchy (§9.7.4) declares the MLS leaf **signature** key ephemeral and separate from the identity keys (`#0`/`#active`/`#agent`). The written leaf==DID rule contradicted that hierarchy, and `ScpCredential::resolve_signing_key` (`crates/scp-mls/src/credential.rs:157` — the `scp-mls` credential method, NOT the same-named `scp-ffi` free function at `crates/scp-ffi/src/context.rs:1499`) — the function that would enforce it — has **zero production call sites** (tests only). We are reconciling the spec to the as-built key hierarchy, not changing shipped behavior.
- **Precedent.** Binding a long-term identity to an ephemeral/session key via a signed statement is the standard construction: Signal's identity key signs the (rotating) signed-prekey; an X.509 CA signs a subject's key; an SSH CA signs a host/user key. The attestation is SCP's instance of that pattern, and the direct in-protocol analog is `IdentityLinkAttestation` (§3.5.1–3.5.2).

**Signer.** Produced **once at KeyPackage generation**, and re-issued on leaf rotation (PCS Update, §9.7.3), via the identity custody `KeyCustody::sign` — a **single async signature, no raw key export**, so it is hardware-custody-compatible and needs **no `openmls` change** (the leaf self-signature stays the synchronous ephemeral-key operation openmls already does). This is the decisive advantage over signing MLS's per-message content with `#active`/`#agent`, which is blocked by openmls's sync-only per-message `Signer` wall (see rejected alternative B).

**Verifier.** Verification is triggered by **leaf introduction or change** — an Add/join, or a member's own Update / Commit-with-UpdatePath — **not** by every message: a Commit that leaves the committer's leaf unchanged carries no new attestation and is not re-verified (this is the BLACK-C22-10 fix — steady-state Commits do not depend on re-resolving each committer's DID, so an attacker degrading one member's DID resolution cannot get their Commits rejected group-wide). On a triggering event, resolve the DID's **current** `#active`/`#agent` verification method (via `ScpCredential::resolve_signing_key` — the `scp-mls` method above, now given a production call site) and verify the attestation against **that current key only** (never a `#retired-*` key — this is what makes rotation revoke; §9.7.1 check 1). Verification is **fail-closed for all production DIDs** as a **positive whitelist**: the sole exemption is the `testing`-feature-gated `did:test:` / `did:key:` carve-out — **no** production method (neither `did:dht:z*` nor `did:web:*`) is exempt, and enforcement MUST NOT be keyed on a single prefix. The **resolution-failure policy depends on the trigger** (§9.7.1 "Resolution failure policy"): on a new member's **Add** a resolution failure is itself a **REJECT** with **no stale fallback** — the verifier MUST NOT fall back to a pre-rotation cached DID document, because an attacker who *induces* resolution failures could otherwise pin verifiers onto a cached document in which the retired key still resolves, defeating revocation-by-rotation up to the cache TTL; on an already-admitted member's **Update** a *transient resolution failure* instead falls to a **bounded last-known-good grace** (bounded by §9.10.7 retention under the same rollback-resistance assumption, degrading toward the `MAX_KEYPACKAGE_ATTESTATION_LIFETIME` backstop against a rollback-capable attacker; so a DID-resolution outage cannot fork the epoch or censor an existing member), while a resolution *success* returning a rotated key still rejects and genuine compromise of an admitted member is a governance Remove (which presupposes a governance authority other than the compromised member — in a **SingleAdmin** context whose sole admin's MLS state is fully compromised, no other party can issue the Remove, so that is a context-re-creation event, not a grace-recoverable one; §9.7.1). For the Add path the resolver cache is retained only as a positive **same-or-fresher** optimization for this current-key check, with a TTL **hard-bounded to `MAX_ATTESTATION_KEY_RESOLUTION_STALENESS` (§9.18.7 — 300s / 5 min, tied to the §9.14 clock skew; §9.7.1 check 2)** — decoupled from and far tighter than the §9.10.7 privacy cache TTL (24h / 7d), which MUST NOT satisfy the current-key check beyond this bound; rotation therefore revokes outstanding KeyPackages (the Add path) within 5 minutes — near-immediate, not instantaneous. The ≤ 5-min freshness bound assumes rollback-resistant DID resolution (did:dht `seq` monotonicity §9.6.1 / did:web fetch integrity §9.6.2), enforced at the resolution layer, not re-checked by the attestation verifier. The verifier enforces the full check set in §9.7.1 Verification (MUST) — current-key resolution, current-key resolution **freshness** (the resolved document ≤ `MAX_ATTESTATION_KEY_RESOLUTION_STALENESS` old), signature validity, `leaf_signature_key == leaf.signature_key`, `leaf_encryption_key == leaf.encryption_key` (ratchet-tree HPKE key — this binding, with `init_key` at Add time, is what closes the read-as-victim-at-join vector; the `init_key != encryption_key` check is the RFC 9420 §10.1 malformed-KeyPackage guard, defense-in-depth, not that closure), `wrapping_key == leaf 0xFF01 extension` (checked on every triggering leaf verification — Add and Update), `init_key == KeyPackage.init_key` and `init_key != encryption_key` (**both Add/Welcome time only** — `init_key` lives solely in the KeyPackage, is consumed at join, and is not on the ratchet tree, so they are not re-checked on an Update; the Add-time checks are gated by the handshake structure, not by any attestation field-value comparison), `attestation.did == credential.did`, `attestation.signing_key_id == credential.signing_key_id`, `expires_at == leaf Lifetime.not_after` / `issued_at == leaf Lifetime.not_before`, the lifetime cap (`expires_at - issued_at <= MAX_KEYPACKAGE_ATTESTATION_LIFETIME`, §9.18.7), and freshness (`issued_at < expires_at`, unexpired, `issued_at` not future beyond the §9.14 5-minute skew). The testing carve-out mirrors the existing `validate_creator_identity` prefix carve-out (`crates/scp-runtime/src/crypto/mls/provider.rs`).

**Preimage.** Follows §9.5.1 exactly — `SHA-256("SCP-KEYPACKAGE-ATTESTATION-V1:" || fields)`, 4-byte BE length prefix on variable-length bytes (`did`, `signing_key_id`), raw fixed 32 bytes for the leaf `signature_key` and raw fixed 32 bytes for each of the three X25519 HPKE keys (`encryption_key`, `init_key`, `wrapping_key`), BE u64 for `issued_at`/`expires_at` (see the §9.5.2 table for the exact eight-field order). The `0xFF03` LeafNode extension body is the same eight fields in preimage order (deterministic length-prefixed binary, NOT MessagePack/JCS — byte-identical across all four bindings) followed by the raw 64-byte Ed25519 signature; §9.5.2 defines the exact layout and §25.22 Vector 37 pins it byte-for-byte. A **new** domain separator — deliberately NOT the trust-layer `"SCP-ATTESTATION-V1:"` (§7.4 `Attestation`), which is a different artifact.

**Rejected alternatives.**
- **(A) leaf==DID via raw key export (`from_raw`).** Rejected: to make the leaf `signature_key` *be* the `#active`/`#agent` key, custody would have to hand the raw private key to `scp-mls` to build the leaf signer. That reverses the custody-delegation direction established by [#1671](https://github.com/limn-works/scp/issues/1671) / [#810](https://github.com/limn-works/scp/issues/810) (keys live behind a `sign` port; raw material never leaves custody) and **breaks hardware custody** outright (a Secure Enclave / Keystore key cannot be exported at all). The attestation model touches the private key only through `KeyCustody::sign`, so it is custody- and hardware-compatible.
- **(B) leaf==DID via async `KeyCustody::sign` for the leaf/per-message signer.** Rejected: openmls's per-message signing is a **synchronous** `Signer` trait; there is no seam to await a custody signature inside MLS message production. Making the leaf key the DID key would force every MLS signature through that sync wall, which an async hardware-custody `sign` cannot satisfy without an upstream openmls change (an `#1965`-class async-signer effort). The attestation is signed **out of band, once**, at KeyPackage generation — entirely outside openmls's sync per-message path — so no upstream change is needed.

**Relationship to component 3 (browser custody).** Attestation signing is a **custody operation** (`KeyCustody::sign` by `#active`/`#agent`), so it lands on the same custody seam described for the browser signing key in the Decision (component 3, [line 32](#decision)) and the Consequences as-built caveat ([line 77](#consequences)). Today that identity key is not yet reachable from the browser (A1 note; the browser holds only the ephemeral MLS `SignatureKeyPair` in wasm), so **browser-side attestation issuance is coupled to the same identity-custody-in-browser work as #1980** — until the `#active`/`#agent` key is reachable on-device from the tab, a browser client cannot mint its own KeyPackage attestation and joins with an attestation minted by a custody-capable surface. This is the identical interim boundary the pseudonym-derivation Option-A/A1 ruling already sits behind; it resolves with the same on-device-identity-custody slice.

**Code seam (why this matters beyond tidiness).** MLS handshake actions (Add/Update/Remove proposals, Commits) are authenticated by the leaf `signature_key`, which — being ephemeral — carries **no DID attribution on its own**. Before this decision, the handshake-action → DID mapping was **unauthenticated**: nothing cryptographically tied a leaf (and thus a membership change or Commit) to the DID in its credential, precisely because `resolve_signing_key` was never called. Routing MLS handshake attribution through **credential + KeyPackage attestation** (verified when a member-leaf is introduced or replaced — at Add, and again on that member's own Update / Commit-with-UpdatePath — not on a Commit that leaves the leaf unchanged) **closes that gap**: every leaf in the tree now provably belongs to the DID it names, so handshake actions attribute to a real, DID-document-verifiable identity.

**Decision record:** CRYPTO-22 / #2187 (human-approved); spec changes in §9.7.1 / §9.5.2 / §9.18.7 / §9.18.2 / §25.22 land with this amendment; code (production `resolve_signing_key` call site + attestation mint/verify) is the follow-on implementation PR that closes #2187.
