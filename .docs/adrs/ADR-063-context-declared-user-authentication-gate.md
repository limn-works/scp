# ADR-063: Context-Declared User-Authentication Gate

**Status:** Proposed (2026-08-28). §Open questions names what a human decides before this ADR moves to Accepted. §Decision 5 states what a verifier does until then, and it is a rejection rather than an admission rule.

**Extends:** ADR-039, the shared-DID human-agent identity model (`.docs/adrs/phase-1.md:1231`), whose Permission Model section carries four Category C mechanisms. This ADR adds a fifth.

**Relates to:** ADR-006, platform abstraction traits (`.docs/adrs/phase-1.md:1017`), declares the `DeviceAttestation` trait. ADR-021, the UniFFI bridge definitions (`.docs/adrs/phase-4.md:855`), declares the `DeviceAttestationProvider` callback interface. ADR-025, the Apple platform adapter (`.docs/adrs/phase-5.md:381`), decides Apple's `BiometricPolicy`. ADR-027, the Android platform adapter (`.docs/adrs/phase-6.md:217`), decides `AndroidDeviceAttestation`. Specs: §4.9.3 Category C of `.docs/specs/04-agents.md`; §5.3.1 exhaustive capability categories, §5.7 metadata, and §5.9 governance of `.docs/specs/05-contexts.md`; §9.3 Sybil resistance and identity uniqueness of `.docs/specs/09-security-model.md`; §27.3.4 and §27.4.4, the key-custody attestation family, of `.docs/specs/27-attestations.md`.

## Context

A context declares a capability ceiling, a set of roles, a governance model, and a set of parameters that bound what happens inside it (§5.3 capability ceiling, §5.5 roles, and §5.9 governance of the contexts spec). ADR-039 adds four Category C mechanisms: three parameters — `agent_keys_allowed`, `agent_rate_limit`, and `agent_cosign_required` — and an agent-restricted role (`.docs/adrs/phase-1.md:1289`). No parameter lets a context say that a named action requires a person to authenticate on a device first.

**The request.** Alec asked for one, verbatim on 2026-08-28: "I would like for SDKs, and more specifically, contexts, to be able to specify which actions require biometric gating if they so choose."

**Two of his earlier rulings bear on it, and I state my reading of each separately from his words.** Alec ruled, verbatim: "having to auth every action biometrically is not going to fly. so platform." He also ruled, verbatim: "just let users decide" and "LET PEOPLE CHOOSE." My reading of the first: it forbids a gesture on every action, and a parameter that names a subset of actions is a case his sentence does not reach. That reading is mine, and open question 1 puts it to him. My reading of the second: it is a general clause about who decides, and this mechanism cuts against it in one direction, because a context that lists a capability takes that capability from a member who chose a custody model the context does not accept. Open question 2 puts that to him as well.

**A declaration that nothing checks is a false guarantee.** The "no dev/test-only stand-ins in production" tenet of `CLAUDE.md` states the reason: "Masking a missing production backend with a dev construct ships a *false guarantee*, which is strictly worse than the capability being honestly absent (absence is detectable; a nullifier lies)." A context parameter that every SDK may ignore is such a false guarantee. So this ADR adds the parameter only alongside a statement of what a verifier does, and §Decision 5 states that a verifier rejects.

**What the shipped code and the vendors' documentation offer a verifier.** I checked each of the following before writing this ADR.

1. **The per-request assertion has no verifier and no Rust caller.** `DeviceAttestationProvider` declares `assert_request(request_hash) -> Vec<u8>` (`crates/scp-ffi/uniffi/src/lib.rs:573`) and declares no verification method. A workspace search finds the name in three places and no Rust call site: the trait declaration (`crates/scp-ffi/uniffi/src/lib.rs:556`), a module doc comment (`:36`), and `crates/scp-ffi/uniffi/README.md:36`. §27.3.3 of the attestations spec derives the same absence and its open question OQ-22 records it. OQ-22 also asks which of two shipped traits is normative, because `scp_platform::DeviceAttestation` (`crates/scp-platform/src/traits.rs:795`) does declare a `verify`. This finding therefore holds against the trait the platform adapters implement, and a human who answers OQ-22 the other way changes it.

2. **Neither vendor's assertion reports that a person authenticated.** Apple documents `DCAppAttestService.generateAssertion` as producing "a block of data that demonstrates the legitimacy of an instance of your app running on a device" (https://developer.apple.com/documentation/devicecheck/dcappattestservice/generateassertion(_:clientdatahash:completionhandler:)), and the decoded object Apple publishes carries a signature and an authenticator-data block (https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server). Apple's stated verification steps for that object read the relying-party-identifier hash and the counter, and Apple documents no meaning for the flags byte the structure carries. Google's Play Integrity payload carries `requestDetails`, `accountDetails`, `appIntegrity`, `deviceIntegrity`, and `environmentDetails`, and Google defines the `deviceIntegrity` verdict `MEETS_DEVICE_INTEGRITY` as "The app is running on a genuine and certified Android device. On Android 13 and higher, there is hardware-backed proof that the device bootloader is locked and the loaded Android OS is a certified device manufacturer image." (https://developer.android.com/google/play/integrity/verdicts). Neither vendor documents a field reporting a user-authentication event. The Android adapter states the same conclusion in its own code, at the inline comment inside `assertRequest`: "Play Integrity does not have a per-request assertion flow equivalent to App Attest assertions" (`bindings/kotlin/scp-kt-android/src/main/kotlin/works/limn/scp/android/platform/AndroidDeviceAttestation.kt:127`), and the method body calls `attest` with the request hash as the challenge (`:130`).

3. **Both verification paths a per-request assertion could take are closed to a peer.** §9.3 of the security spec records both: "Play Integrity requires Google's servers, introducing an operator dependency the protocol otherwise avoids", and "App Attest is per-bundle-ID, but SCP is a protocol, not an app — different SCP apps on one device get different attestation keys" (`.docs/specs/09-security-model.md:187`). A peer running a different SCP app holds no public key against which to check an App Attest assertion, and the "protocol requires no operator" tenet of `CLAUDE.md` weighs against routing verification through Google.

4. **One primitive carries a user-authentication policy to a remote reader, on Android alone.** An Android Key Attestation certificate's `KeyDescription` extension encodes `noAuthRequired`, `userAuthType`, and `authTimeout` (https://source.android.com/docs/security/features/keystore/attestation), a Trusted Execution Environment signs the enclosing chain, and a reader validates that chain against a Google attestation root. `AttestationPlatform::AndroidKeyAttestation` is the variant `PlatformAttestation` already names for that chain (`crates/scp-did/src/attestation.rs:130`). Two limits qualify the primitive. Google's stated verification procedure includes a revocation check against a Google-hosted status list (https://developer.android.com/privacy-and-security/security-key-attestation), so a verifier validates offline only by skipping that step, and finding 3's operator argument therefore weighs against this primitive as well — open question 5 carries how far. And Apple publishes no counterpart: Apple defines the `biometryCurrentSet` access-control flag as a "Constraint to access an item with Touch ID for currently enrolled fingers, or from Face ID with the currently enrolled user" and `biometryAny` as a "Constraint to access an item with Touch ID for any enrolled fingers, or Face ID" (https://developer.apple.com/documentation/security/secaccesscontrolcreateflags), and documents no certificate through which a remote reader learns which flags a key carries.

**Finding 2 decides what this feature may be called, and decides nothing about what the mechanism requires.** No shipped primitive proves to a remote verifier that a biometric gated an operation, so this ADR names the parameter for user authentication. The narrowing of the *name* is mine, not Alec's. The narrowing of the *requirement* is not mine to make: whether the gate accepts only a biometric, accepts any hardware-backed user authentication, or lets each context choose is open question 2, and this ADR answers it nowhere.

## Decision

### 1. A fifth Category C mechanism, `user_authentication_required`

A context declares `user_authentication_required` on `ContextParams`: the list of capabilities that the context requires a member to exercise under a signing key whose platform releases it only to a signer who has passed a device-local authentication gesture. The interval between the gesture and the signature is open question 3. The default is the empty list. §4.9.3 of `.docs/specs/04-agents.md` states the normative text; this ADR records the evidence and the reasoning.

### 2. The granularity is one entry per capability

A context names capabilities rather than setting a boolean. Alec's ruling that authenticating "every action" will not fly rules out a boolean directly, and a capability is the vocabulary a context already uses to name what happens inside it.

Four candidate vocabularies exist and three cannot express what a context must declare:

- **`ActionCategory`** (`crates/scp-protocol/src/trust/custody_violation.rs:84`) carries two variants, and `classify_action` reads the `{resource}` segment of a capability URI alone (`:302`), so it cannot separate `governance:vote` from `governance:propose`. It also has no `CategoryC` variant and takes none: §4.9 of the agents spec states that Category C partitions nothing and is a second axis.
- **A role name** names the capabilities a member holds, and a member's role assignment carries one role name (`crates/scp-protocol/src/context/membership.rs:111`), so a role names no subset of a member's capabilities as gated. §4.9.3's agent-restricted role is the nearest existing shape, because it selects a role by which key signed, and open question 6 asks whether refining that mechanism beats adding a fifth.
- **A boolean** contradicts Alec's ruling.
- **`Capability`** (`crates/scp-protocol/src/context/roles.rs:74`, 21 built-in variants plus `Custom`) is what a capability ceiling lists, what a role grants, what a UCAN attests, and what §5.3.1's "Gated by" column names for each governance action. `Capability::new` is the canonical parser §5.3.1.1 names, and it bars a custom entry from denoting a built-in. It does not bound an entry to a context's ceiling — §5.3.1.1 says so of the type alone — so §4.9.3 and story SCP-AB-037 require that check separately at creation.

§4.9.3 specifies `agent_cosign_required` as a list of capabilities for the first of these reasons, and no struct declares either field yet.

**The entry's own type is not settled.** Open question 2 asks whether an entry may name an authentication modality and open question 3 asks whether it may name an interval. An affirmative answer to either adds a field to the entry, so a bare `Capability` is the entry type only if a human answers both in the negative. Story SCP-AB-037 states the same condition.

### 3. The parameter lives on `ContextParams` and in structural metadata

`agent_keys_allowed`, `agent_rate_limit`, and `agent_cosign_required` are specified as `ContextParams` fields projected into the structural metadata §5.7 of the contexts spec makes visible before joining, and changed through the `metadata:edit` governance path §5.9 describes. This parameter takes the same three placements, and §9.18.B of the security spec carries its row alongside the other three.

Structural metadata is not optional here. Under finding 4 only an Android member can satisfy this parameter, and under §Decision 5 no member can satisfy it today. §9.3 of the security spec records that macOS, Linux, and Windows have "no App Attest or Play Integrity equivalent" (`.docs/specs/09-security-model.md:189`), and finding 4 records that Apple attests no access-control policy to a remote reader. A member who could not read the list before joining would consent to a context that silently forecloses capabilities to them, which the "legibility before opt-in" tenet of `CLAUDE.md` forbids.

### 4. The exclusion binds per action, not at admission

A member whose platform publishes no such attestation joins the context and never exercises a listed capability. Three facts decide against an admission-time exclusion:

- **A DID names a keypair, not a device.** §9.3 of the security spec states: "The protocol cannot distinguish hardware at the network level; a DID is a keypair, and the protocol sees bytes, not devices" (`.docs/specs/09-security-model.md:187`). A member admitted from a phone signs from a laptop an hour later, so an admission-time check certifies a property that has stopped holding by the time the action arrives.
- **A member may change the checked property after admission along a sanctioned path.** §3.2.1 of the identity spec specifies custody migration, which moves `#active` between custody providers without changing the DID.
- **The parameter names capabilities, not members.** A member who holds `messages:write` and `governance:vote` in a context that lists only `governance:vote` keeps the first and loses the second. An admission-time rejection takes both, which restricts more than the context declared.

The one admission-time gate that exists could not carry the exclusion in any case: `evaluate_sybil_resistance` satisfies `policy.require_device_attestation` when `assessment.signals` contains the `DeviceAttestation` key (`crates/scp-protocol/src/trust/sybil.rs:773`), with no token, no signature, and no DID binding. §27.4.3 of the attestations spec records that in its paragraph "A second shipped consumer gates on the signal without reading a token" (`.docs/specs/27-attestations.md:547`).

Per-action binding has a consequence this ADR does not resolve. The verdict then depends on a DID document the signer republishes at will, so two verifiers reading at different times reach different verdicts on one signed artifact, and §9.9.3 of the security spec requires every field of a canonical event-log leaf to be convergent. Open question 4 carries it.

### 5. No admission rule exists, so a verifier rejects

A conformant verifier rejects an action on a listed capability, whatever the signer's DID document declares. This ADR states no condition under which a verifier admits one, and §4.9.3 states none either.

Four things a verifier would need are undecided: which `KeyCustodyModel` values satisfy the requirement (open question 2), what a platform attestation must bind and contain (open question 5), at which DID-document version the verdict is taken (open question 4), and where in the pipeline the check runs (open question 5). Writing an admission rule before those answers would produce one that admits the wrong artifacts, and two concrete failures show it. `PlatformAttestation` carries a platform discriminant and opaque bytes, and names no verification method, no public key, and no challenge (`crates/scp-did/src/attestation.rs:109`), so a rule that admitted on chain validity alone would admit a chain copied out of any other member's public DID document. And `KeyCustodyModel::HardwareBiometric` is a value its own subject writes (`crates/scp-did/src/attestation.rs:86`), so a rule that read it as satisfied would accept a caller-asserted value as a security guarantee — the substitution the "no dev/test-only stand-ins in production" tenet forbids, and the one `require_device_attestation` already performs.

Two absences make the rejection the only honest state today, and §27.4.4 of the attestations spec derives both. `DidDocument::set_custody_attestation` (`crates/scp-did/src/document.rs:671`) has no production caller, which its open question OQ-23 records. And no artifact states a verification procedure for `platform_attestation`, whose own documentation says its "format and verification procedure are platform-specific and outside the scope of the SCP protocol itself" (`crates/scp-did/src/attestation.rs:106`), which its open question OQ-3 records. The three shipped bridges answer a device-attestation verification request with the typed error `SCP-IDENT-1016` (`crates/scp-ffi/src/identity.rs:985`, `crates/scp-ffi/uniffi/src/bridge.rs:4042`, `crates/scp-ffi/napi/src/scp.rs:4640`), and issue #2171, the production device-attestation backend, tracks the work that replaces those errors.

One further stand-in reaches a shipped path, and open question 5 must account for it. The Apple adapter returns a synthetic `"software-attestation-<UUID>"` when App Attest is unsupported, on a shipped path with no test gate (`bindings/swift/Sources/SCP/Platform/AppleDeviceAttestation.swift:141`), and open question OQ-33 of the attestations spec records that divergence. Any future admission rule rejects that token.

## Rejected alternatives

**A per-action assertion carried on the inner envelope, verified against the signer's device attestation.** This is the mechanism `agent_cosign_required` uses for the human co-signature, and it does not carry over. Finding 2 shows the assertion carries no evidence of a gesture on either platform, and finding 3 shows a peer verifies neither vendor's assertion without either the same app bundle or Google's servers. Adding the field would give a verifier bytes it cannot turn into a verdict.

**A boolean `biometric_required` on `ContextParams`.** Rejected against Alec's ruling on authenticating every action, and against §5.3.1's capability vocabulary: a boolean names no action, so a context could not gate `governance:vote` while leaving `messages:write` alone.

**Excluding the member at admission.** Rejected on the three facts in §Decision 4.

**Naming the parameter for a biometric.** Rejected on finding 2: no shipped primitive proves a biometric to a remote verifier, and Android's `userAuthType` is the only attested field that distinguishes a fingerprint from a passcode. A parameter named for a biometric would state a guarantee the value a verifier reads does not carry. This rejection governs the name alone, and open question 2 carries what the requirement requires.

**Adding a fourth verification method to the DID document, bound to an authentication-gated key.** Rejected because ADR-039 fixes the key set at `#0`, `#active`, and `#agent` and states the structural constraint "Exactly one `#agent` verification method per DID document" (`.docs/adrs/phase-1.md:1274`). Widening the key set is a decision for ADR-039 rather than for an ADR downstream of it. ADR-039 also states a document-size constraint, but against per-context keys — "Per-context agent keys would exceed document size constraints at scale" (`.docs/adrs/phase-1.md:1276`) — and one additional key is not that case, so the first reason carries this rejection alone.

**WebAuthn and FIDO2.** Not rejected, and not evaluated far enough to adopt. W3C Web Authentication Level 3 defines a User Verified flag in the authenticator data an authenticator signs on every ceremony (https://www.w3.org/TR/webauthn-3/), which is the only per-operation user-verification signal any of these families puts in front of a remote verifier, and it works on macOS, Windows, and Linux, where finding 4's primitive does not. Two documented limits bound it. W3C states that user verification "MAY be instigated through various authorization gesture modalities; for example, through a touch plus pin code, password entry, or biometric recognition", so the flag names no modality. And W3C states that user verification "does not give the Relying Party a concrete identification of the user". The corpus already names the family: §3.2.1 of the identity spec lists `Passkey` as a custody-migration target (`.docs/specs/03-identity.md:37`), and §11's prior-art table names "Passkeys, WebAuthn" under key custody. Open question 5 asks a human whether this family is the one the mechanism reads.

**Refining `agent_cosign_required` with a custody axis rather than adding a fifth parameter.** Not rejected, and not evaluated. The two parameters share a vocabulary, a placement, a metadata projection, and a governance path, and §4.9.3 records that a capability on both lists makes `agent_cosign_required` unreachable for it. Open question 6 asks a human whether one parameter with a custody axis beats two parameters.

## Open questions

Each entry states what no artifact decides, which artifact should decide it, and what breaks while it stays open. This ADR answers none of the eight. Issue #2417, the ADR-063 open questions, carries them to a human, and story SCP-AB-037 of `.docs/prds/agent-binding.json` names that issue in `blockedByIssues`. The Category C entry in `.docs/specs/00-open-questions.md` indexes them.

### Whether the mechanism is permitted, and whether it is the right mechanism

**1. Does the protocol permit a context to require a device-attested custody policy per action?** *Undefined:* §9.3 of the security spec licenses a context to set admission thresholds from attestation signals — "Contexts set their own admission requirements from available signals… A high-trust financial context might require multiple attestation types" (`.docs/specs/09-security-model.md:195`) — and says of device attestation that "Its absence is expected… and is not penalizing" (`:187`). This parameter gates a named action rather than admission, and §9.3 contemplates no such case. *Decides it:* §9.3, stating whether its context-threshold license reaches a per-action gate. *Breaks meanwhile:* an implementer who reads §9.3 and §4.9.3 together cannot tell whether the parameter is permitted.

**2. What does the requirement require — a biometric, any hardware-backed user authentication, or a choice each context makes?** *Undefined:* Alec asked for biometric gating. Android Key Attestation encodes `userAuthType` as `FINGERPRINT` or `PASSWORD` and is the only primitive that attests a modality to a remote reader; Apple attests no access-control policy remotely; and `KeyCustodyModel` offers `HardwareBiometric` and `HardwarePin` as values a subject declares about itself with no proof behind either (`crates/scp-did/src/attestation.rs:86`). A parameter that names a modality is satisfiable on Android alone, and one that names no modality admits a passcode where a context asked for a fingerprint. The same answer decides whether a context may override a member's own custody choice, which is where this mechanism cuts against Alec's "LET PEOPLE CHOOSE". *Decides it:* Alec, then the key-custody spec section that open question OQ-3 of the attestations spec asks a human to place. *Breaks meanwhile:* the entry type is undecided, so no story can add the field.

**6. Does Category C cover a restriction that binds `#active`, and is a fifth parameter the right mechanism?** *Undefined:* ADR-039 defines Category C as "Per-context restrictions on agent actions" (`.docs/adrs/phase-1.md:1289`), and this parameter rejects an `#agent` signature and then constrains which `#active` signatures pass. Separately, `agent_cosign_required` shares this parameter's vocabulary, placement, metadata projection, and governance path, and §4.9.3 records that a capability on both lists makes `agent_cosign_required` unreachable for it, so a custody axis on that one parameter may beat two. *Decides it:* ADR-039's Permission Model section. *Breaks meanwhile:* §4.9.4 states the verifier's rule over "the effective authority of an agent key in a context", and that sentence does not reach the human's own key.

### What the requirement means

**3. Per signature or per session, and what bounds the interval?** *Undefined:* `KeyCustodyModel::HardwareBiometric` states no interval (`crates/scp-did/src/attestation.rs:88`) while layer 1 of ADR-039's enforcement stack reads "session-based biometric unlock" (`.docs/adrs/phase-1.md:1298`). Android's `authTimeout` tag encodes an interval and its absence encodes per-operation authentication; no SCP artifact carries either. *Decides it:* the same key-custody section. *Breaks meanwhile:* a verifier cannot tell whether an admitted signature followed a gesture by one second or by eight hours.

**7. Is `#active` hardware-backed?** *Undefined:* ADR-039's key-properties table gives `#active` the Backing value "Software" (`.docs/adrs/phase-1.md:1269`), while its enforcement stack layer 1 reads "`#active` in hardware (Secure Enclave / Android Keystore) with session-based biometric unlock" (`:1298`). *Decides it:* ADR-039. *Breaks meanwhile:* if the table governs, this parameter is unsatisfiable by construction on every platform.

### What a verifier does

**4. At which DID-document version is the verdict taken, and does it enter the convergent event log?** *Undefined:* the verdict reads a DID document its own subject republishes at will, so two honest verifiers reading at different times reach different verdicts on one signed artifact. §9.9.3 of the security spec requires "*every field* of a canonical leaf" to be convergent and names governance among the convergent event types (`.docs/specs/09-security-model.md:910`), and `governance:vote` is §4.9.3's own example. *Decides it:* §9.9.3. *Breaks meanwhile:* two honest members compute different Merkle roots at equal event count, which the equal-count/equal-root test reports as equivocation with none present.

**5. What must a platform attestation bind and contain, where does the check run, and which evidence family should it read?** *Undefined:* `PlatformAttestation` carries a platform discriminant and opaque bytes, and names no verification method, no public key, and no challenge (`crates/scp-did/src/attestation.rs:109`), so a rule that checked chain validity alone would admit a chain copied out of any other member's public DID document beside a software-held `#active`. A rule also needs an enforcement point, and no single artifact carries both inputs it reads: `signing_key_id` is an inner-envelope field, a UCAN names its method in `kid`, and `SignedVote` carries neither (`crates/scp-protocol/src/context/governance/mod.rs:991`). The evidence family is unsettled too — see the WebAuthn entry under §Rejected alternatives, and finding 4's revocation limit on the Android chain. *Decides it:* §9.3 of the security spec together with the key-custody section OQ-3 asks for; open questions OQ-2 and OQ-48 of the attestations spec carry the DID-binding and `did:web` halves. *Breaks meanwhile:* no verifier can admit a listed capability, and any rule written before the answer admits the wrong artifacts.

### What stops a context from bricking itself

**8. What guard prevents a context from making the parameter permanent?** *Undefined:* `metadata:edit` is a capability (§5.3.1 of the contexts spec), and §5.9 gates a change to the parameter on it, so a proposal that lists `metadata:edit` makes the capability that changes the parameter subject to the parameter and no member can propose the change back. A proposal listing `governance:vote` locks the tally the same way. The sibling parameter `agent_keys_allowed: false` carries no such hazard, because members keep acting through `#active` (§4.9.3). *Decides it:* §4.9.3, choosing between barring those capabilities from the list and rejecting a proposal that would leave no member able to exercise `metadata:edit`. *Breaks meanwhile:* one approved proposal makes a context permanently ungovernable.

Question 1 can retire the mechanism, and question 7 can make it unsatisfiable, which is why this ADR's status is Proposed.
