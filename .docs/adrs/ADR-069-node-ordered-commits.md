# ADR-069: Node-Ordered Commits

**Status:** Accepted 2026-11-02. Alec settled the design on 2026-10-25 (decisions D1 to D3 and question Q4 of the context-operation plan), and ruled "Rewrite now" on 2026-11-02 for the artifacts that ADR-067 had shaped. **Amended 2026-11-02:** decision 10 (priority holds) records Alec's ruling that the node's order must stop starvation, decision 8 records his answer on how an external re-seater learns that its re-seat lost, and decision 9 records his rejection of an openmls patch.

**Supersedes:** ADR-067, Concurrent Commits and fork merge, in `phase-6.md`. ADR-067's status flips to `Superseded by ADR-069`, and its body stays as the historical record.

**Amends:** ADR-066 decisions 5, 10, 32 and 40 and its acceptance-criteria paragraph; ADR-031 §7 and its 2026-10-17 amendment; ADR-029 §5b, §5c and §6 step 4, and its rationale paragraph on conflict resolution; ADR-001 criterion 6; ADR-051 §3, "No trusted sequencer". Each amended record carries a dated amendment that names this record.

**Spec:** `07-trust-validation-and-capabilities.md` §7.3.1 and §7.3.1.1 ("Competing Commits", "Commit order"), `05-contexts.md` §5.13.3 rules 11 and 16, `09-security-model.md` §9.5.2, §9.7.1, §9.7.2, §9.9.3, §9.14 and §9.18, `10-infrastructure-and-self-hosting.md` §10.2, §10.3 and §10.8.1, `23-sync-and-offline-strategy.md` §23.4, §23.5 and §23.7, and `25-test-vectors.md` §25.33.

## Context

`admit_and_merge_own_commit` (`crates/scp-mls/src/group.rs`) merges the committer's own Commit before anyone orders it. When two members commit at one epoch N, each merges its own Commit, and each member's openmls then rejects the other Commit as `WrongEpoch`, so the group splits.

ADR-066 decision 5 had answered the race with "Epoch order decides conflicts": a Commit that loses the race for an epoch never merges, and its executor re-checks it and sends it again. That rule needs one order of Commits that every member reads. On 2026-10-24 no party could give that order, because Alec had ruled "We can’t rely on daily presence" and the relays were untrusted store-and-forward services. ADR-067 therefore let every member keep both children of an epoch, choose one by the least (rank, cth), and re-apply the losing child's changes through fork records, imports and a merge function G. It needed sixteen mechanisms (M1 to M16), a fifth body item `merge` in the governance block, a journal, a key ledger, an epoch table, branch retention for up to seven days, a PPRF over child init secrets, two signed notice records, and ten accepted residuals.

On 2026-10-25 Alec settled how a context runs (`~/.claude/plans/context-operation-plan.md`, rulings 1 to 10):

- "Contexts most certainly have operators, and in fact, require them." "Nodes are pieces of infrastructure that operate many things. One of those things could absolutely be a specific context."
- "if a context runs on a single node and that node is off then the context is unreachable. Se la vie."
- "The context is the engine for finalization." "Why would governance be involved? It's an immutable part of the protocol".
- D1: "One node runs a context and is its MLS Delivery Service: it totally orders submitted Commits, one per epoch. Members verify every Commit."
- D2: members submit Commits directly to the context's node, with the priority class (Remove, re-join, other) as a field of the submission outside the MLS message, ordered "Remove first, then re-join, then arrival."
- D3: "The node holds no MLS group secrets."
- Q4: the node signs each chain entry (position, item hash, previous hash) and returns a signed receipt that assigns a position to each accepted submission, under a key the operator binds to its identifier when the context is instantiated.

A node that runs the context is online whenever the context is reachable, so the ordering party that ADR-067 lacked exists. The question this record answers is how members turn the node's order into one Commit per epoch when the node cannot read a Commit.

## Options considered

1. **Keep ADR-067 and add the node as a relay.** Every mechanism of ADR-067 stays, and the node only delivers. This lost because the node already gives a total order, so every mechanism that exists to merge two orders protects against a case the node removes. ADR-067's own necessity table justifies each mechanism by a fork, and a fork needs two Commits that two members both merge.
2. **The node accepts one Commit per epoch and refuses the rest.** The node reads the epoch from the `PrivateMessage` framing (RFC 9420 §6.3, which leaves `epoch` in the clear), appends the first Commit it receives for the current epoch, refuses the rest, and then expects the next epoch. This lost because of D3: the node holds no group secret, so it cannot verify a Commit. A member that sends a malformed Commit for epoch N would take epoch N's place, every member would reject it, and the node would refuse every honest Commit for epoch N as stale, so the context would stop. The node also cannot prove a refusal (Q4: "Refusal to accept is provable to no one").
3. **The node orders every submission, and members take the first valid Commit for each epoch.** The node appends every submission it accepts to one signed chain. Every member processes the chain in position order, and the canonical Commit for epoch N is the first Commit in the chain that names epoch N and passes the member's verification at epoch N. This option is chosen. It meets D1 ("one per epoch", "Members verify every Commit") and D3, because the choice reads only the chain order and each member's own verdict, and ADR-066 decision 10 makes that verdict a function of the Commit's bytes and the state every member holds identically.
4. **A member quorum or a witness set signs the order.** Members or witness nodes would sign which Commit comes first. This lost because Alec ruled on 2026-10-25 that "The context is the engine for finalization" and asked of governance "Why would governance be involved? It's an immutable part of the protocol", so no member, witness or governance action takes part in ordering.

### Options considered for the hold rule (decision 10, 2026-11-02)

A Remove built for epoch N loses to a committer's Commit for N, is rebuilt for N + 1, and arrives after the committer's Commit for N + 1, because the committer builds its next Commit while the remover is still processing the chain. Any rule that leaves the node appending on arrival lets a fast committer win every epoch.

1. **Append on arrival, with no hold.** The node holds at most one submission at a time, so D2's priority order never acts, and a member that commits nonstop starves every Remove. This lost to Alec's ruling of 2026-11-02.
2. **A fixed batching window on the node's clock.** The node collects submissions for a fixed time and appends each batch in D2's order. This lost because the window bounds nothing: a remover whose rebuild takes longer than the window loses every epoch to a committer whose next Commit arrives inside the window.
3. **A member-verified rule.** Members would treat an other-class Commit as invalid when the chain holds, after the previous epoch's Commit, a valid Remove that lost that epoch. This lost for two reasons. Members would verify a Commit at an epoch they already merged past, so they would keep that epoch's secrets after the merge, which breaks RFC 9420's deletion schedule (invariant I8). A remover that never rebuilds would also block every other-class Commit forever, because no clock-free event ends the block.
4. **A hold that any later priority submission ends.** The node cannot verify a submission's class, so a committer that wants to starve a Remove sends one malformed Remove-class submission, the hold ends, and the committer's Commit is appended first. This lost for that reason.
5. **A hold that only the lost submission's own submitter ends, capped by the node's clock.** The submitter proves it is the same party by revealing the secret behind the commitment its lost submission carried, and the node's clock caps the hold so that a submitter that never returns delays lower-class submissions by at most `PRIORITY_HOLD_SECS`. This option is chosen.

## Decision

1. **The node orders.** The node that runs a context is its MLS Delivery Service, the role RFC 9750 (the MLS architecture) gives the service that orders and delivers a group's messages. A member sends each Commit it makes to that node, at the address the context's `ContextNodeAddress` names. The node appends every submission it accepts to the context's chain at the next position, signs the chain entry, and returns a signed receipt naming the position (Q4). The node holds no MLS group secret (D3), so it never decides whether a Commit is valid.
2. **Priority.** Each submission carries its class outside the MLS message: Remove, re-join, or other (D2). Among the submissions it holds and has not yet appended, the node appends Remove-class submissions first, then re-join-class submissions, then the rest in arrival order. A Commit is Remove-class when its derived leaves include a `MemberLeft` leaf, re-join-class when it is an external re-seat or its derived leaves include a `MemberReset` leaf and no `MemberLeft` leaf, and other-class otherwise. The chain item is the submission as received (`item_hash` and the receipt's `submission_hash` hash the same bytes), so every member reads the class, and every member treats a Commit whose class differs from the class its content gives as invalid at its position. The node appends a submission when it arrives unless a priority hold blocks it, and decision 10 states when the node holds a submission and in what order it appends the held ones.
3. **One Commit per epoch.** Every member processes the chain in position order. At epoch N, the canonical Commit is the first chain item that is a Commit naming epoch N and that passes steps 1 and 2 of `07-trust-validation-and-capabilities.md` §7.3.1.1 "Receiver processing" in the member's state at epoch N. A member skips every other Commit: a Commit naming an epoch below its current one, and a Commit naming its current epoch that fails verification. A skipped Commit changes no member's state. Because every member's verdict reads only the Commit and state that every member holds identically (ADR-066 decision 10), every honest member merges the same Commit at every epoch.
4. **The committer merges its own Commit at its position.** A committer keeps its own Commit staged and unmerged after it submits it. It merges the staged Commit when, processing the chain in order, it reaches the position its receipt names and its group is still at the epoch the Commit names. When an earlier chain item moved its group past that epoch, it discards the staged Commit, re-checks its action against the new state, and submits it again or reports the proposal `Invalidated`, as ADR-066 decision 5 states. The committer never merges a Commit that the chain does not hold.
5. **Conflicts are serial.** "Committed first" in ADR-031 §7 means earlier in the chain. The conflict rule of §7.3.1.1 "Conflicts" and the executed-proposal set settle every pair of actions in chain order, and no merge function runs. The `member:X` conflict key stays: the governance state keeps `change_seq["member:X"]` after X leaves, so an Add of X anchored before a Remove of X loses to that Remove, and an invitation anchored after the Remove passes.
6. **The governance block has four body items.** The body loses item 5, `merge`, and with it the fork record, the import leaves, the re-applications and the carried re-seats. The body bound returns to 1 + 168 + 3 + 16,224 + 15,616 + 1 = 32,013 bytes, 751 bytes below the 32,764-byte body (`07-trust-validation-and-capabilities.md` §7.3.1.1, "Why 32,768 bytes and 96 approvals").
7. **No merge state.** The journal, the key ledger, the epoch table, the fork records, the imports, the pending joiners and the re-seat windows leave the governance state, and `merge_state_hash` leaves the `0xFF02` extension (`05-contexts.md` §5.13.3 rule 16 is withdrawn). A Commit with an empty block again carries the GroupContextExtensions proposal with its extensions unchanged (ADR-066 decision 32).
8. **The re-join.** An external re-seat (`09-security-model.md` §9.7.1) is a Commit like any other in the chain: the identity submits it with the re-join class, and the first valid Commit for the epoch wins. When another Commit for that epoch is earlier in the chain, the identity sends a new re-seat request and re-seats at the epoch it is answered from, which keeps Alec's ruling of 2026-10-21 that the re-joiner "rebuilds its Commit against the new epoch and sends it again". Rank −1, the re-seat window, the `D_MAX` send rule, the carried re-seat and the unused carried seat are removed.
   - **How the re-seater learns it lost.** A re-seating identity holds no secret of the epoch it joins, so it cannot verify the chain items before its re-seat. The node's signed receipt tells it instead: the receipt's `lost` flag says that a Commit-typed chain item before the re-seat's position names the epoch the re-seat names (decision 10). A re-seater whose receipt says lost sends a new re-seat request at once. Alec answered "Ok" on 2026-11-02 to the recommendation: "the node's signed receipt tells [the external re-seater] 'your submission lost; the epoch is now N+1', and the re-seater retries. Every member already trusts the node for ordering, and a lying node can only delay the re-seater, because the re-seater's next attempt is verified in full."
   - **A receipt that says lost about a re-seat that merged.** The node sets `lost` from the epoch an earlier item names and cannot tell whether that item was a valid Commit. A malformed item that names the same epoch therefore makes an honest node report lost for a re-seat that every member merged. The re-seater keeps its staged re-seat until the answer to its new request arrives. When the tree of that answer's GroupInfo holds the leaf the staged re-seat placed, the re-seat merged, and the re-seater merges its staged re-seat and processes the chain from the epoch after it.
9. **Verdicts read no clock, and SCP carries no openmls patch.** The choice of decision 3 requires every member that processes a Commit to reach one verdict on it. openmls reads the receiver's system clock when it validates a received KeyPackage's or LeafNode's lifetime, and offers no switch for that check (`09-security-model.md` §9.7.1, "openmls's own receive-side clock check"). Alec answered on 2026-10-04 how SCP handles that check: "no patch, bound, leave us a note for the happy future path". On 2026-11-02 he rejected a patch again: "you offered me a solution that did not rely on a patch. What has changed since then that makes you feel like we need one?" SCP bounds the check:
   - An adder refuses a KeyPackage with less than `KEY_PACKAGE_MIN_REMAINING_LIFETIME` (7 days + 1 hour) of lifetime left under its clock (`09-security-model.md` §9.7.1, check 13), and a Commit's blob requests at most `MAX_BLOB_TTL` (7 days, `09-security-model.md` §9.18.11).
   - openmls therefore refuses an honest Commit at only two kinds of member: a member whose clock runs more than one hour ahead of the adder's clock, and a member that processes the Commit more than 7 days after the adder sent it.
   - `23-sync-and-offline-strategy.md` §23.5.1 resets a member that has been offline for more than 7 days, so that member never merges another Commit for the refused Commit's epoch, and its refusal changes no verdict that a merging member reaches.
   - **Residual.** A member whose clock runs more than one hour ahead of the adder's clock refuses the Commit while every other member merges it. One hour is twelve times the 5-minute clock-skew tolerance of `09-security-model.md` §9.14. That member stays at the epoch before the Commit and recovers through Welcome-based fast-forward (`23-sync-and-offline-strategy.md` §23.4.1, source 3) or a group state reset (§23.5).
   - **Open dependency.** The third bullet needs every member that processes a Commit more than 7 days after it was sent to have reset first, and two gaps leave that unenforced. No artifact bounds how long the context's node keeps chain items, so a member can fetch a Commit older than 7 days from the chain. §23.5.1 trigger 1 counts from the member's last successful interaction with infrastructure, not from the age of the oldest Commit the member has not processed. `00-open-questions.md` lists the dependency ("openmls lifetime check under node order").
10. **Priority holds.** Alec ruled on 2026-11-02, when the starvation case was presented to him as an open question: "the whole point of context driven commit ordering and processing is to STOP starvation. No." The node therefore holds lower-class submissions while a Remove or re-join that lost its epoch is rebuilt.
   - **Lost.** The node reads the epoch and the content type of each submission from the `PrivateMessage` framing, which RFC 9420 §6.3 leaves in the clear. A submission is lost when a chain item before its position has the Commit content type and names the epoch the submission names. The node's receipt carries a `lost` flag that states this, and the node signs the flag with the rest of the receipt.
   - **Opening a hold.** A Remove-class or re-join-class submission may carry `hold_commitment`, the SHA-256 of a 32-byte random `hold_secret` that its submitter keeps. When the node appends such a submission and the submission is lost, the node opens a hold for it.
   - **Closing a hold.** A hold closes when a submission arrives whose `hold_opening` is the hold's `hold_secret`. That submission is the hold's opening. A hold also closes when `PRIORITY_HOLD_SECS` (120 seconds) have passed on the node's own clock since the node opened it. This rule reads the node's clock. Members never read or verify that clock, and no member's verdict depends on it, because the clock decides only how long the node waits before it appends a submission.
   - **Rank.** Open holds rank by class, Remove before re-join, and within a class by the time the node opened them, earliest first.
   - **Blocking.** An open hold blocks every submission the node has not appended whose class is the hold's class or a lower class, except the opening of a hold that ranks before it. Remove is the highest class and other the lowest.
   - **Appending.** The node appends one submission at a time and re-evaluates every hold after each append. When several submissions are unblocked at once, the node appends them in D2's order: Remove first, then re-join, then the rest. Within a class, openings come first in the rank of their holds, and the other submissions follow in arrival order. An opening may carry a new `hold_commitment`, so it opens a new hold when it is lost too.
   - **The submitter.** A member whose Remove-class or re-join-class submission is lost rebuilds the action on the epoch the chain reaches and submits the rebuilt Commit as the opening, or reports the proposal `Invalidated` under decision 4. An external re-seater sends a new re-seat request and submits the new re-seat as the opening (decision 8).
   - **The bound.** Let a Remove-class or re-join-class submission S be lost, let E be the epoch the chain has reached at S's position, and let S's opening arrive within `PRIORITY_HOLD_SECS` of the node opening S's hold. While S's hold is open, the node appends no other-class submission, so another member's other-class Commits add no epoch to S's wait, whatever rate that member commits at. S's opening is the first valid Commit for its epoch unless a valid Commit that ranks ahead of it is appended first. For a Remove, the Commits that can rank ahead of it are the openings of Remove holds the node opened before S's. For a re-join, they are the openings of re-join holds the node opened before S's, and Remove-class Commits. Each such Commit takes one epoch. No Add merges while S's hold is open, because an Add is other-class, so each valid Remove-class Commit ahead of a re-join removes a distinct member. A Remove therefore merges at an epoch no later than E + k, where k counts the Remove holds open when the node opened S's hold. A re-join merges at an epoch no later than E + k + m, where k counts the re-join holds open when the node opened S's hold and m is the number of the context's members at E.
   - **A submitter slower than the hold.** When S's opening arrives after S's hold closed, the node appends the opening as it appends any submission, and a lost opening that carries a new `hold_commitment` opens a new hold. The bound then counts from the first opening that arrives within `PRIORITY_HOLD_SECS` of its hold. A re-seater's opening waits for a member to answer its new re-seat request, so a re-seater that no member answers within 120 seconds gets no bound from this rule until an answer arrives in time.

## Invariants ADR-067 protected

Each row names an invariant ADR-067 protected and where it now lives, or why it no longer arises.

| # | Invariant | ADR-067 mechanism | Under node order |
|---|---|---|---|
| I1 | Two Commits at one epoch never split the group | M1, M2, M9 | Protected by decisions 1 and 3: every member reads one chain and merges the same first valid Commit per epoch. |
| I2 | Every device of every member chooses the same Commit | M2, M2r | Protected by decision 3; the choice reads the chain position and a verdict that ADR-066 decision 10 makes identical at every member. |
| I3 | A committer never merges a Commit that loses | M14 | Protected by decision 4: the committer merges only at its own chain position. |
| I4 | No change is lost silently, and its author learns the outcome | M3 obligations 1 and 3, `ConcurrentChangeExpired` | Protected by decision 4 and ADR-066 decision 5: a Commit that is not first executed nothing, and its executor re-checks it and submits it again or reports the proposal `Invalidated`. |
| I5 | A re-joiner and a Remove are not starved by a member that commits nonstop | M2r, M4 rank-0 window, rank −1 | Protected by decisions 2 and 10: a lost Remove or re-join opens a hold that blocks every other-class submission until its rebuilt Commit arrives, so it merges within the epochs decision 10's bound states, whatever rate another member commits at. |
| I6 | A removed member is not re-added by an Add anchored before the Remove | M3 obligation 1(d), `member:X` | Protected by decision 5: the `member:X` key is a serial conflict rule. |
| I7 | A change executes at most once | M6 collision rule, change identities | Protected by the executed-proposal set, the reset counter floor and the revocation set, because only one Commit per epoch executes anything. |
| I8 | Retained key material is bounded and consumed keys stay unrecoverable | M1, M12 | Does not arise: no member keeps a state that is not on its one path, so RFC 9420's deletion schedule applies as written, and a committer's discarded staged Commit holds no secret of a merged epoch. |

| I12 | A late release does not undo a merged re-join | Carried re-seat, M5a depth bound | Does not arise: the chain is append-only, so no Commit is released after members merged a later one. |
| I13 | A departure can be re-executed after the member uninstalls | M10 `DepartureRequest` | Does not arise: no losing branch exists to re-execute from. |
| I14 | A member a losing branch removed reads no message on the canonical path | M11 send barrier | Does not arise: a Remove is final when its Commit is canonical, at every member. |

| I16 | Two devices of one person converge | M9 | Protected by decision 1: both devices read one chain from one node. |
| I17 | A restrictive-only change (a Remove, a revocation) is never dropped | G, restrictive-only class | Protected by decisions 2 and 4: a Remove has first priority, and an executor whose Remove was not first submits it again. |
| I18 | A re-added member's KeyPackage is used once | M8 fresh KeyPackage | Does not arise: no Add is re-applied. |
| I19 | The tree's leaves match the governance membership | M8 tree reconciliation | Does not arise: one Commit per epoch changes both together, as before ADR-067. |

## Consequences

- Two members that commit at one epoch no longer split the group, and no member keeps parent states, branch stores, a PPRF over child init secrets, a journal, a key ledger or an epoch table.
- The governance block body has four items, and the body bound is 32,013 bytes. Spec 25's fork-merge vectors (§25.33, Vectors 71 to 79) are removed, and the `ForkNotice` and `DepartureRequest` preimages and the fork record leave `09-security-model.md` §9.5.2.
- A context with its node off makes no progress: no member can commit until the node returns (ruling 4).
- A malformed or stale Commit costs a chain position and changes no member's state.
- A member trusts the node for liveness and order, never for validity, because every member verifies every Commit. A node that equivocates or drops a receipted submission is proven by its own signatures (Q4) and answered by re-founding (plan D9).
- A lost Remove or re-join delays every lower-class submission by at most `PRIORITY_HOLD_SECS` (decision 10). The node cannot verify a submission's class or content, so a sender that submits Remove-class or re-join-class items and never opens their holds delays lower-class submissions by up to 120 seconds per such item, and no artifact bounds how many such items one sender submits. Members skip each such item as invalid at its position.
- A receipt carries the signed `lost` flag, and a submission carries the optional `hold_commitment` and `hold_opening` fields. The node checks only that a `hold_opening` hashes to an open hold's `hold_commitment`, and no member's verdict reads either field.
- Withdrawal and re-signing by key rotation (`05-contexts.md` §5.9.1, ADR-066 decision 10) still rest on an Update that rotates `signature_key`, and `propose_update` (`crates/scp-mls/src/ratchet.rs`) passes `LeafNodeParameters::default()`, so no Update rotates it yet.
- This record changes the order of Commits only. Plan decision D6 also has the node order application messages in place of ADR-051's causal DAG, and the artifacts that describe the DAG are not changed by this record.

## Acceptance Criteria

The stories that implement this record list their criteria in `.docs/prds/main.json` under the gate `gate-node-order`: SCP-357 (a Commit kept staged and unmerged until its chain position), SCP-351 (the first valid Commit per epoch, the committer's merge at its own position, and the hold fields a lost Remove or re-join carries) and SCP-361 (the `member:X` conflict key). The node side of decisions 1 and 10, the chain, its receipts, the holds and the submission transport, belongs to the execution of plan decision D1, which `~/.claude/plans/identity-artifacts/node-backend-execution-plan.md` records as having no story yet.
