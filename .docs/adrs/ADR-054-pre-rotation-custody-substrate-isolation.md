## Context

SCP's pre-rotation key is the recovery backstop for the entire identity system — the last resort after Identity Key compromise (spec §9.12). Spec §9.7.4.1 specifies its custody with the same rigor as the Identity Key. Two of its requirements are **substrate** requirements, not merely type requirements:

- **§9.7.4.1 §3 (Storage isolation):** "The pre-rotation private key MUST be stored separately from the Identity Key and Active Signing Key. It MUST NOT be accessible through the same custody provider or authentication flow used for daily operations."
- **§9.7.4.1 §4 (Approved custody methods):** the pre-rotation key MUST live in one of: a hardware security key (FIDO2/U2F), a secondary-device secure enclave, a platform-backed cloud key store, an encrypted offline backup (AES-256-GCM + Argon2id), Shamir 3-of-5, or a BIP39 paper backup.
- **§9.7.4.1 §5 (SDK presentation):** at identity creation the SDK MUST present the user with custody options, guide them through the selected method, verify the backup, and only then sign and publish the inception event, which carries the first pre-rotation commitment (item 5e as amended 2026-09-02).

The Rust core models this correctly: identity creation and `migrate_identity(...)` take a **separate** `PreRotationCustody` trait object from the operational `KeyCustody` (ADR-003 §4b), and the spec's two-substrate split is expressible at the trait boundary.

**The gap was at the FFI callback-custody boundary (state as of 2026-06-14; ADR-062, capability injection and prove-absent dev backends, §Decision 6 has since severed the mint — see the Forward note below).** When a mobile app supplied its own operational custody via the `KeyCustodyProvider` callback interface (the App-Attest / Keychain / Keystore path), the bridge minted the *pre-rotation* key into `scp_platform::testing::InMemoryPreRotationCustody`:

- PyO3: `crates/scp-ffi/src/identity.rs`, in `identity_create` and its `create_with_agent_key` / `create_with_custody` siblings.
- UniFFI: `crates/scp-ffi/uniffi/src/bridge.rs` — `generate_ephemeral_ed25519_seed` generated the seed locally via `OsRng` and routed it into `InMemoryPreRotationCustody`. The in-source comment named the limitation: type-level isolation held, and substrate isolation did not, because that backend co-resided in the same Rust process memory as the bridge, so one process-memory dump compromised both. That comment no longer describes the tree. `generate_ephemeral_ed25519_seed` returns the raw seed bytes, its caller mints the `InMemoryPreRotationCustody` only on an arm that `#[cfg(feature = "testing")]` selects, and the comment at the same site now states that no `PreRotationCustody` backend ships at all.

That routing violated §9.7.4.1 §3: the pre-rotation key sat in the **same process memory substrate** as the operational key-handle space, reachable without the separate authentication flow §3 mandates. It satisfied neither §4 (no approved backend) nor §5 (no SDK custody-selection ceremony) on the callback path.

A second, coupled defect blocks the **migration reveal** path for callback custody. Migrating an identity (ADR-003 §4b, spec §9.12) requires installing the revealed pre-rotation private bytes as the new operational `#0` key. *(This describes the reveal→import flow of the spec as it read before 2026-09-02; the amended `09-security-model.md` §9.7.4.2 R3 installs a fresh root and never installs the revealed key. The ADR-063 re-home of this ADR carries the disposition.)* The `KeyCustodyProvider` callback interface has no "import a known seed and return a handle" method — only `generate_keypair`, which mints a fresh random key. So UniFFI's `import_ed25519_signing_key` correctly fail-closes rather than silently corrupting the migration:

```
Err(PlatformError::Unsupported(
  "callback custody cannot import pre-rotation seed bytes; \
   KeyCustodyProvider has no import_ed25519_seed_bytes method. \
   Identity creation via callback custody is unaffected."))
```

Identity **creation** via callback custody works; **migration** via callback custody is unreachable. Both halves of this ADR are required for callback custody to meet §9.7.4.1 end-to-end.

This was surfaced during the 2026-06-13/14 cross-SDK audit. The existing code is honest about the limitation (detailed comments, fail-closed error, type-level isolation already enforced), but per the builder tenets "no deferral / completeness is the baseline," a self-admitted "separate workstream" is a gap to close, not a steady state. Per the artifact-flow invariant, the design is fixed in an ADR (and the spec, if §9.7.4.1 needs a callback-custody clause) **before** any code changes.

## Decision (proposed)

Close the gap by introducing a **dedicated pre-rotation custody callback interface** — distinct from the operational `KeyCustodyProvider`, exactly as §9.7.4.1 §3 demands — plus the SDK-side backends and selection ceremony §4/§5 require. Three parts:

### 1. A separate `PreRotationCustodyProvider` FFI callback interface

Define a new callback interface (UniFFI `[Trait, WithForeign]`, with the matching PyO3 `Py<PyAny>` and NAPI threadsafe-function adapters) that the SDK implements **independently** of its operational `KeyCustodyProvider`. Modeling it as a separate provider — not new methods on `KeyCustodyProvider` — is the mechanism that enforces §3's "MUST NOT be accessible through the same custody provider or authentication flow."

**Relationship to the existing core trait.** The Rust-core `PreRotationCustody` trait already exists (`crates/scp-platform/src/traits.rs`) and is consumed by identity creation and `migrate_identity`. This ADR does **not** rename it. *(Superseded 2026-10-20 by the SCP-345 amendment under Canonical method names: the callback interface routes into the core `NextSetCustody` trait)* The new FFI callback interface is the *foreign-facing* surface; a `CallbackPreRotationCustody` adapter implements the core trait by dispatching to the foreign provider. The interface therefore has four FFI-facing methods, three of which map onto existing core-trait methods and one of which is genuinely new:

- `generate() -> PreRotationKeyHandle` — generate the keypair **inside the separate substrate** (hardware key, secondary-device enclave, cloud key vault, or an encrypted-offline/Shamir/BIP39 wrapper), never in shared process memory. This is the only **new** capability: the core trait has no `generate` counterpart (it only ever *stores* an externally-supplied keypair via `store_committed_pre_rotation_key`). **`generate()` is required for backends that mint keys in-substrate (HSM, Secure Enclave, cloud vault). Import-only backends (BIP39 mnemonic restore, pre-generated offline backup) MUST return a typed error from `generate()` and the SDK MUST offer an alternative creation path (e.g., `from_mnemonic()` / `from_backup()`). Each SDK backend documents its capability set.**
- `public_key(handle) -> [u8; 32]` — read the 32-byte public key for the `SHA-256(public_key)` commitment. Maps to the core trait's existing **`reveal_public_key`**.
- `import_seed_bytes(seed: Zeroizing<[u8; 32]>) -> PreRotationKeyHandle` — install a known, externally-generated seed into the substrate and return a handle. This is the FFI-facing analogue of the core trait's existing **`store_committed_pre_rotation_key`** (see "import vs. store" below); it is the method whose absence at the *callback* boundary currently blocks migration, and it is the reveal-time inverse of `consume`, used when the new identity adopts the revealed bytes as its operational `#0` (ADR-003 §4b).
- `consume(handle) -> Zeroizing<[u8; 32]>` — destroy-and-export the private bytes atomically at migration time. Maps to the core trait's existing **`destroy_after_migration`** (the `migrate_identity` step-5 destroy-and-export described in the §9.7.4.1 "Partial-publish recovery" paragraph; the §9.7.4.1 "Partial-publish recovery" paragraph and item 6 "Post-rotation key cycling" as they read before 2026-09-02; the amended spec never installs the revealed key, and the ADR-063 re-home of this ADR carries the disposition). **Handle lifecycle invariant:** each `PreRotationKeyHandle` is single-use. The `CallbackPreRotationCustody` adapter MUST invalidate the handle in Rust immediately after `consume` returns — whether the callback succeeded or failed — so subsequent calls to `consume(same_handle)` or `public_key(same_handle)` return `Err(HandleNotFound)` regardless of what the foreign implementation does. This matches the core trait's documented contract that `destroy_after_migration` makes the handle return `HandleNotFound` thereafter; the adapter enforces it in Rust so foreign implementations cannot leak the backstop. *(Superseded 2026-10-20 by the SCP-345 amendment under Canonical method names: `import_seed_bytes` and `consume` are deleted, and no next-set private key leaves custody)*

**Canonical migration flow (reveal → import, ADR-003 §4b):** at `migrate_identity` step 5, the bridge calls `consume(pre_rotation_handle)` to destroy-and-export the 32-byte seed, wraps the seed in `Zeroizing`, then calls the operational `KeyCustody::import_ed25519_signing_key(seed)` to install the revealed pre-rotation bytes as the new `#0` signing key. The pre-rotation handle is invalidated in Rust before the operational import begins. A fresh pre-rotation handle is then generated via the selection ceremony (§9.7.4.1 item 5 and item 6 as they read before 2026-09-02; this reveal→import flow is the one the amended §9.7.4.2 R3 replaces with a fresh root, and the ADR-063 re-home of this ADR carries the disposition) before the migration transaction completes. *(Superseded 2026-10-20 by the SCP-345 amendment under Canonical method names: no method exports or imports a seed, so this flow has no callback path)*

The bridge's `generate_ephemeral_ed25519_seed` / `InMemoryPreRotationCustody` path on the callback flow is replaced by a `CallbackPreRotationCustody` adapter that dispatches to this provider. `InMemoryPreRotationCustody` is retained **test-only** (it already lives under `scp_platform::testing`), consistent with the in-memory-storage-is-dev-only stance.

### 2. Real SDK backends (§9.7.4.1 §4)

Each SDK ships at least one approved backend so the callback provider is not a hollow shell:

- **Swift (iOS/macOS):** Secure Enclave on a secondary device; iCloud Keychain with Advanced Data Protection (platform-backed cloud key store); FIDO2 via `ASAuthorization` security keys.
- **Kotlin (Android):** Android Keystore with StrongBox; a platform cloud key vault where available; FIDO2/CTAP2.
- **Cross-platform (all SDKs, incl. Python/TypeScript for server/test parity):** encrypted offline backup (AES-256-GCM, key via Argon2id memory=64 MiB/iter=3/parallelism=1 *(amended 2026-10-25, SCP-311: this line read parallelism=4, which contradicted the single parameterization `17-persistence-and-storage.md` §17.8 requires across the codebase)*, ≥128-bit auto-generated passphrase entropy) *(superseded for server rows — see Amendment 2026-07-14: auto-generated-passphrase encrypted-offline is not a conforming non-interactive-server floor)*; Shamir 3-of-5 over GF(2^8); BIP39 24-word mnemonic.

The encrypted-offline / Shamir / BIP39 codecs are pure and belong in `scp-protocol` (or `scp-platform` where they need platform RNG), shared across SDKs rather than re-implemented per language.

### 3. SDK custody-selection ceremony (§9.7.4.1 §5)

At identity creation the SDK presents custody options ordered by security, guides the user through the selected method, verifies the backup (re-entry/re-scan for offline methods), signs and publishes the inception event — which carries the first pre-rotation commitment (item 5e as amended 2026-09-02) — only after verification, and destroys the creating device's in-memory copy. This is SDK-layer UX wiring over part 1's provider; the protocol-level requirement is that creation does not complete (and the commitment is not published) until a §4 backend holds the key.

### Canonical method names (locked across bindings)

**Amended 2026-10-20 (SCP-345, one signer contract for key-event members).** The callback interface has five methods, rewritten for the `KeyEventSigner` contract scp-kel declares (`crates/scp-kel/src/key_event_signer.rs`), and the `import_seed_bytes` and `consume` rows and the paragraph that paired `import_seed_bytes` with `store_committed_pre_rotation_key` are deleted. The amended `09-security-model.md` §9.7.4.2 R3 installs a fresh root and never installs a revealed key (this ADR's own note in §Context), so the import and destroy-and-export flow serves nothing, and an export method lets any holder sign any digest with a next-set key. A callback host implements the raw arm only: it receives a 32-byte digest computed in Rust, `change.digest()` for `sign_change` and SHA-256("SCP-CUSTODY-PROBE-V1:" || nonce) for `sign_probe`, and never a nonce or a preimage. The assertion arm (passkey and FIDO2) and the headless copyable methods are implemented in the SDK by SCP-311, never across this callback. The amendment changes no host code: no adapter for this callback exists on main, and the callback path declines with `SCP-IDENT-1059`.

Per-binding casing of the five **FFI callback-interface** methods — these names are fixed and MUST NOT drift. The final column maps each FFI method to the core `NextSetCustody` method it routes through (`crates/scp-platform/src/traits.rs`); `sign_change` and `sign_probe` are the `KeyEventSigner` methods `NextSetCustody` takes as a supertrait.

**Key ids (amended 2026-10-25, SCP-345).** A callback host never reuses a key id within one adapter's custody-record namespace (`17-persistence-and-storage.md` §17.3, custody records). The adapter records each key id it gets from `generate` before it returns the handle, and refuses a record that differs from the one already stored, so a refusal over a stale record flags a host that broke this rule. A host key with no record, left when the process stops between the host's `generate` and the record write, is unusable: SCP never reads, signs with or destroys it, and the host alone removes it. SCP-345's callback-adapter PR adds the conformance check that a host returns no key id twice.

### Assertion-arm and store-set host interfaces

**Amended 2026-10-25 (SCP-311).** The 2026-10-20 amendment above leaves the assertion arm and the headless copyable methods to SCP-311, in the SDK and never across the raw-arm callback. Three more host interfaces carry what only a host reaches: the platform passkey or FIDO2 API, the pre-rotation credential's `largeBlob` store, and the platform account's synced store, the two synced members of the store set `09-security-model.md` §9.7.4.2 R10 names. Each is a provider of its own, separate from the operational `KeyCustodyProvider` for the reason part 1 of the Decision gives for the raw-arm callback. The ADR-057 in-browser client implements `KeyEventSigner` directly over `navigator.credentials` (`09-security-model.md` §9.7.4.2 R10, *What the signing rule cannot reach*), so a browser implements none of the three.

`assert_change` and `assert_probe` each return a record of three byte fields: `authenticator_data`, `client_data_json` and `signature_der` in UniFFI and PyO3, and `authenticatorData`, `clientDataJson` and `signatureDer` in NAPI, Swift and Kotlin. **`CredentialBlobProvider`** reaches the pre-rotation credential's WebAuthn `largeBlob` store:

| Concept | FFI method (canonical) | UniFFI | NAPI | PyO3 | Swift | Kotlin |
|---------|------------------------|--------|------|------|-------|--------|
| read the bytes the credential's `largeBlob` store holds, given the credential identifier, or report that it holds none | `read_blob` | `read_blob` | `readBlob` | `read_blob` | `readBlob()` | `readBlob()` |
| write bytes into the credential's `largeBlob` store, given the credential identifier, and return a `BlobWriteOutcome` reporting what the platform reported: `Landed`, `NotWritten`, `NoOutput`, or `VerificationDeclined` with the cause the platform reported, where it reported one | `write_blob` | `write_blob` | `writeBlob` | `write_blob` | `writeBlob()` | `writeBlob()` |

The bytes are the entry record `17-persistence-and-storage.md` §17.8 lays out. The Rust adapter encodes and decodes it, and the host passes its bytes through without reading them. Each method takes a credential identifier, and the host reads and writes that credential's store and no other. The Rust adapter holds no credential: the store set passes the credential of its own lease on every call, so no adapter reads or writes the store of a credential other than its set's.

The host reports what the platform reported, and the Rust adapter maps each report to the act that clears a write that did not land. The host never names an act.
- `Landed`: the platform reported `largeBlob: { written: true }`.
- `NotWritten`: the platform reported `largeBlob: { written: false }` with no error. The adapter maps it to `RemoveConsumingCredential`, because R10 reads that report as the authenticator's large-blob array at capacity.
- `NoOutput`: the assertion returned no `largeBlob` output, the report of a client or route that did not process the extension. The adapter maps it to `RetryThroughLargeBlobRoute`, the act R10 names for that cause: a retry through a route that processes the extension, which the read preceding the write proved the host has. It never maps to `RetryVerification`, because a retry through the route that dropped the extension clears nothing, and the distinct act keeps the cause in the outcome.
- `VerificationDeclined`: the user declined or cancelled the verification gesture, with the cause the platform reported, where it reported one. The adapter maps it to `RetryVerification`.
- Any other platform failure throws, and the adapter maps the throw to `RetryVerification` with the error's text as the cause.

`written: false` is also what a credential that does not support `largeBlob` reports. For that credential `RemoveConsumingCredential` names an act that clears nothing. That has no effect on safety: such a store never holds a handle or a marker, so it is never a member that stops a ceremony.

The host contract for `CredentialBlobProvider`:
- `write_blob` returns `Landed` only where the platform reports `written: true`. The store set reads no `largeBlob` write back, so a false `Landed` would leave a member at `Composed` while the ceremony believes it moved to `Signed`, the state R10 stops the ceremony in.
- A `largeBlob` output the platform does not return is `NoOutput`, never `Landed`.
- `read_blob` returns no bytes only where the platform reports that the store holds none, and every other failure throws, a read assertion that returns no `largeBlob` output included, so a store that failed to answer is never read as an empty one.

**`SyncedStoreProvider`** reaches the platform account's synced store, on a host where the host table of `09-security-model.md` §9.7.4.2 R10 marks that member present:

| Concept | FFI method (canonical) | UniFFI | NAPI | PyO3 | Swift | Kotlin |
|---------|------------------------|--------|------|------|-------|--------|
| read the bytes stored under a key, or report that none are stored | `get` | `get` | `get` | `get` | `get()` | `get()` |
| store bytes under a key | `put` | `put` | `put` | `put` | `put()` | `put()` |

The Rust adapter forms every key and encodes every value, each keyed on the credential under `recovery/{sha256_hex(credential_id)}/` (`17-persistence-and-storage.md` §17.8): the entry record, which holds the `RecoveryHandle` and the `LastRevealMarker`; the `StoreSetRecord`; and each signed event, keyed on its digest.

The host contract for `SyncedStoreProvider`:
- `get` returns no bytes only where the platform reports the item absent, and every other platform failure throws, so a store that failed to answer is never read as an empty one.
- `get` follows the freshness rule below.
- `put` returns only after the platform reports the item stored.

**One freshness rule for both interfaces.** Every read the store set makes, through `get` or `read_blob`, returns the value the platform holds when the call is made, read from the platform store on that call (for `read_blob`, through a `largeBlob` read assertion), and never a cache or the bytes of the host's last write. The store set merges every member's current value before it writes: a cached `read_blob` would let a composition proceed past a handle or marker another device wrote, and a cached `get` would also pass the read-back check after a platform write that failed.

On every interface in this section, a UniFFI host throws only `ScpError`: UniFFI panics on any other error a callback throws. A host that cannot answer a `CredentialBlobProvider` or `SyncedStoreProvider` call throws `ScpError.Storage` with the code `SCP-STORAGE-8016` and the platform's error text as the message. The Rust adapter reads only that text: a thrown read is a member not reached, a thrown `put` is a failed write, and a thrown `write_blob` is a write that did not land.

**Which bridges declare the three interfaces.** UniFFI alone declares all three, because the Swift and Kotlin SDKs are the hosts that reach a passkey API, a `largeBlob` store and a platform-account store. Alec ruled on 2026-10-26, "Ok uniffi only": PyO3 and NAPI declare none of the three and carry exemptions for them in the SDK capability matrix, `.docs/standards/sdk-capability-matrix.json`, alone, written in S8 PR 5b. The casing columns above bind every bridge that declares an interface.

## Consequences

- **Positive:** callback custody meets §9.7.4.1 §3-§6 end-to-end; a process-memory compromise no longer exposes the recovery backstop; callback-custody migration becomes reachable (closes the `import_ed25519_signing_key` block); the two-substrate model is structurally encouraged by the type system (a separate provider type prevents the same object from serving both roles), but hardware/OS-level substrate and auth-flow isolation remains a foreign-implementation obligation — the Rust type signature cannot verify that two distinct callback objects are not backed by the same Keychain access group or biometric prompt. The conformance test ("pre-rotation key NOT recoverable from the operational provider") is the primary observable enforcement.
- **Cost:** a new public FFI callback surface and per-platform keystore integrations — the largest single piece. The UX ceremony (§5) is real product work on mobile.
- **Risk:** key-handle lifecycle bugs across the FFI boundary are security-critical (a dropped/duplicated pre-rotation handle is a lost or leaked backstop). Mitigation: `Zeroizing` on all seed bytes at the boundary; a conformance test that a created identity's pre-rotation key is NOT recoverable from the operational custody provider; the existing partial-publish recovery handle (§9.7.4.1 "Partial-publish recovery", ADR-003) already covers migration interruption.
- **No migration burden:** SCP is pre-release with no deployed identities; the in-memory callback path is replaced outright (no back-compat shim), per the no-migration-pre-release stance.

## Alternatives considered

- **Keep `InMemoryPreRotationCustody` on the callback path (the status quo when this ADR was written).** Rejected: it violates §9.7.4.1 §3 substrate isolation, because the recovery backstop then shares the operational substrate. The code of the day flagged the requirement as not-yet-satisfied. ADR-062 §Decision 6 has since removed that path outright, so the callback path now declines with `SCP-IDENT-1059`.
- **Add `generate_pre_rotation` / `import_seed_bytes` methods to the existing `KeyCustodyProvider`.** Rejected: §9.7.4.1 §3 explicitly forbids the pre-rotation key being "accessible through the same custody provider or authentication flow used for daily operations." A combined provider re-introduces exactly the coupling §3 prohibits. A separate interface enforces the boundary structurally.
- **Generate the pre-rotation seed bridge-side and hand it to the SDK to store.** Rejected for the generation step on hardware-backed platforms: §9.7.4.1 §1 requires on-device CSPRNG generation, and for HSM/Secure-Enclave backends the key MUST be generated *inside* the substrate and never marshalled as raw bytes. The provider's `generate()` keeps generation in the substrate. (Bridge-side `OsRng` generation remains acceptable only for the software/offline backends that inherently hold raw bytes.)
- **Defer to a bare tracking issue with no design.** Rejected per the "Completeness is the baseline" builder tenet in AGENTS.md ("never file a tracking issue instead of doing in-scope work"): the design must be done, not parked in an empty ticket. This ADR *is* that design step — now **Proposed**, with its realization homed as a fully-specified proposal in RFC #2130 (tracked by #1729 / #1777). A designed-and-Proposed realization awaiting execution is not the rejected pattern; an undesigned deferral is.

## Amendment (2026-07-14): Recovery-authority residence — RULE canonical (spec §9.7.4.1 item 3a); realization PROPOSED (RFC #2130)

This amendment does not delete or contradict the design above; it sharpens the security property the design must satisfy and resolves OQ2 and OQ3 at the design level, but **leaves the ADR Proposed** — the realization is homed in RFC #2130, not accepted-canonical. The design is complete and review-converged; production pre-rotation custody is punted to a later e2e-collab stage, so this amendment's realization is recorded as PROPOSED in RFC #2130 rather than accepted-canonical; only the §3a residence rule is canonical (spec §9.7.4.1 item 3a). Provenance: the normative rule is authored spec-first as **§9.7.4.1 item 3a** in `../specs/09-security-model.md`; this ADR cites and realizes it, per the artifact-flow invariant. The rule is upstream; ADR-054 does not author it.

### The refinement: residence of the recovery authority, not the cipher

Call the **recovery authority** the minimal secret, key handle, or authorization capability sufficient to recover the pre-rotation private key. §3's adversary is one who has compromised **operational custody**. Substrate isolation is therefore a property of *where the recovery authority lives*, not of the cipher wrapped around the stored key:

- If the recovery authority is reachable from operational custody, the cipher gives **zero** protection against the §3 adversary — that adversary simply uses the reachable authority to decrypt. So §4's parameter checklist (AES-256-GCM, Argon2id, ≥128-bit entropy) does **not** by itself satisfy §3.
- Encrypted-offline backup **with an auto-generated passphrase** on a **non-interactive server** is **not** a valid standalone §3 backend: the auto-generated passphrase must be stored somewhere the unattended server can reach to decrypt, which is — by construction — reachable from operational custody. It is isomorphic to `InMemory`. It is §3-sound only if the passphrase / KEK itself resides in a §3-isolated substrate (e.g., KMS/HSM), in which case *that substrate* is the real backend.
- The load-bearing property is **principal-distinctness**, not human interaction. Migration is a rare, separately-authorized event, not a daily operation, so a non-interactive server **can** satisfy §3 if migration-time recovery is gated by an authorization principal **distinct** from the operational signing principal (e.g., a separate KMS role assumed only for migration; the operational path holds no grant to it). The fatal condition is "the daily operational auth flow can itself reach the pre-rotation key."

### OQ3 resolved — YES, a spec clause was required

§3's prose was insufficient: it constrained the custody-provider **object** ("MUST NOT be accessible through the same custody provider or authentication flow"), which a co-located encrypted-offline-auto-gen backend can satisfy at the object level while still placing the recovery **authority** within operational reach. The gap is the difference between constraining the provider object and constraining the secret's **residence**. The normative fix is **§9.7.4.1 item 3a (recovery-authority residence)**, added spec-first ahead of this amendment. This ADR cites §3a as its governing requirement; it does not restate the normative rule as its own invention.

### Strengthened conformance test (the PAIR)

The Risk-line conformance test ("a created identity's pre-rotation key is NOT recoverable from the operational custody provider") is strengthened from a single assertion to a **pair** that both MUST pass:

1. **Negative-reachability adversary test.** Hand the harness the **full operational surface**: every operational `KeyCustody` handle/key, and every artifact readable by the operational principal (config, environment, keychain/keystore entries, on-disk files) — plus every resource the operational principal can read, decrypt, or obtain via a remote API using its own credentials or IAM/role grants (KMS, Secrets Manager, cloud key vaults) — enumerated from the operational principal's **full grant set**, not only local artifacts — and any resource reachable by **assuming a role the operational principal is permitted to assume**, followed **transitively** through every key-wrapping / key-derivation link to the chain root — **plus** the publicly-stored encrypted-offline ciphertext. Assert the harness **CANNOT** reconstruct the 32-byte pre-rotation seed. The search MUST include *locating and using* any auto-generated passphrase from operational-reachable stores (so a co-located-passphrase encrypted-offline backend fails this test by construction).
2. **Principal-distinctness assertion.** Assert that the recovery-authority residence identifier (KMS key id / IAM role / keychain access-group / TPM policy handle) is **structurally distinct** from the operational principal, and that the operational grant set excludes **read, use, decrypt, or assume/delegate** over **every secret, key, KEK, or role in the recovery-authority derivation/wrapping chain** (the pre-rotation key, its KEK, each KEK up to the chain root, and any passphrase secret) — not merely the terminal pre-rotation KEK. For Shamir: assert **fewer than 3** shares are reachable from the operational blast radius.

The negative-reachability test replaces the weaker "not recoverable from the operational provider" phrasing everywhere it appears in the Consequences/Risk section below.

### At-rest caveat (added to Risk/Consequences)

§3a is an **at-rest / daily-operations** property. It cannot prevent the pre-rotation seed being live in operational process memory during an **authorized** migration: `consume()` by construction yields the plaintext seed, which is then imported as the new operational `#0` (ADR-003 §4b, §9.12). The Consequences claim "a process-memory compromise no longer exposes the recovery backstop" is therefore scoped to **at-rest / daily operations** — NOT the migration instant, during which the backstop is necessarily plaintext in operational memory for the duration of the rotation transaction. This is inherent to the reveal→import migration model and is out of scope for §3a to prevent; mitigation for the migration instant is the existing `Zeroizing` boundary discipline and the single-use handle invalidation (Decision part 1), which bound the exposure window to the migration transaction. *(This paragraph describes the reveal→import model as the spec read before 2026-09-02; under the amended `09-security-model.md` §9.7.4.2 R3 and R10 the pre-rotation key signs where it resides and is never imported, so the migration-instant exposure it describes no longer arises. The ADR-063 re-home of this ADR carries the disposition.)*
