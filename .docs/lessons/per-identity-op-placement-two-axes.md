# A Per-Identity Op's Axis Is Chosen by Its Caller, Not Its Return Type

**Rule**: Every per-identity operation in the `context/supervisor` layer sits on exactly ONE of two axes, and the axis is fixed by the operation's **caller**, never by the sensitivity of the data it returns:

- **(a) Actor-internal** — confined handler code inside a context actor, which reaches only the identity that owns it. This is a `SupervisorHandle` method taking `&OwnedIdentityDid` (the unforgeable ownership token). Name it with the `my_*` prefix.
- **(b) Bridge-external** — the trusted node/bridge orchestrator (the FFI layer). This is a `pub Supervisor` method taking a bare `DID`, with local-identity custody enforced at the bridge. Name it with a plain verb (`create_context`, `spawn_actor_from_welcome`, `reserve_key_package`).

Connotation: **never** choose the axis from "is the returned data secret?" — a PUBLIC read from inside an actor is still axis (a). The token `OwnedIdentityDid` gates `my_wrapping_public_key`/`my_key_package_store`, both of which return public bytes; they are gated because the discriminator is **caller-isolation** (*which identity is reachable*), not data-sensitivity.

**Context**: The token's `pub(in crate::context)` name-visibility keeps axis (a) off every crate-`pub` signature *by construction* — the compiler refuses to name `OwnedIdentityDid` in a `pub` method — so the type system holds that one direction soundly and there is deliberately NO bespoke CI gate (ADR-049 §5). What the compiler does NOT decide is *which axis a new per-identity op belongs on*: a bridge-callable op wrongly placed on the actor axis, or an actor-internal secret op wrongly exposed as a bare-`DID` method, both compile clean. That judgment is review-owned.

The invariant was implicit until it got mis-applied. The spawn-from-Welcome joiner seam — a bridge-initiated node-level bootstrap (the app receives a Welcome, or pre-publishes KeyPackages) — was first modeled as a `SupervisorHandle` method on the actor-internal axis. It does not belong there: it is called by the FFI orchestrator, takes a bare `DID`, and returns only public / context state (a `ReservationId` + public KeyPackage bytes, or a `ContextHandle`), never per-identity secret crypto. The mis-spec was carried in **two ADR passages at once** (the Decision-5 discussion and the deferred-work entry), so the ADR briefly contradicted itself on where the seam lived. Because the caller is the bridge, the correct home is a genuinely-`pub` bare-`DID` `Supervisor` entrypoint — the same shape and trust model as `create_context`.

**Fix**: Move the seam to `pub Supervisor::reserve_key_package` / `pub Supervisor::spawn_actor_from_welcome` (bare `DID`, custody at the bridge), reconcile BOTH ADR passages to the bare-`DID` framing, and codify the two-axis rule as a named invariant in ADR-049 §5 plus a naming convention (`my_*` = actor-internal, plain verb = bridge-external) in `.docs/standards/conventions.md`. The fix flowed spec→code, per the artifact-flow invariant. No mechanical gate and no compile-witness were added: the compiler already keeps axis (a) off `pub` signatures, and the "which axis" call is a legibility judgment a gate cannot make soundly.

**Lesson**: Three durable takeaways.

1. **Caller decides the axis, not the payload.** "This returns public data, so it needn't be gated" is the exact wrong instinct — an actor-internal accessor of public data is still on the `&OwnedIdentityDid` axis. Ask *who calls this*, not *how secret is the result*.
2. **A naming convention is the enforcement here — on purpose.** With the type system holding one direction and a gate rejected as non-convergent, legibility carries the rest: a `my_`-prefixed bare-`DID` method, or a plain-verb method taking the token, must read as wrong on sight. That is why the prefix rule is written down.
3. **When a spec self-contradicts across two passages, the invariant was never named.** The mis-spec surviving in two places at once is the tell that the rule lived only in reviewers' heads. Name it once, in the upstream artifact, and cross-reference every downstream mention to that name.
