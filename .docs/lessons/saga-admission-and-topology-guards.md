# A Saga Needs a Harmful Partial Commit and a Real Topology — Not Just "Two Contexts"

**Rule**: Before admitting any new saga, it MUST pass two guards. **(a) Harmful-partial-commit test** — a saga is justified ONLY by a *harmful* partial commit: a both-or-neither atomicity requirement across **2+ distinct contexts** that ordinary sequencing (do A, then B, with a benign or idempotent retry/rollback on each side) cannot satisfy. "It touches two contexts" is NOT sufficient. **(b) Topology guard** — no feature may assume content flows *through* an intermediate context to that context's members; that requires a decrypt-then-re-encrypt stage, which violates context-isolation and encryption-as-access-control (spec §5.11A.6). A proposed saga must pass BOTH: failing (a) means it is single-context or sequenceable work; failing (b) means it is a security violation, not a saga. Connotation: **never** scaffold a saga that fails either guard; **always** apply both at design time, before any code lands.

**Context**: ADR-049 originally enumerated four cross-context saga arms. Three of the four turned out to be category errors, each discovered only after scaffolding (types, journal variants, error codes, sometimes a full spec section) had already landed:

- **Custody handover** (ADR-049 §4, withdrawn): a 1-context/2-identity operation modeled correctly as single-context governance; also a §5.11A.6 violation (transferring group key material out-of-band).
- **Standing-pair creation** (spec §5.15.8, reclassified 2026-06-18): a 2-member MLS group is **one** context; replica sync is MLS + the event-log consistency layer, not a saga.
- **Broadcast hosting handshake** (formerly spec §5.14.13, withdrawn 2026-06-25): failed BOTH guards. (a) No harmful partial commit — the host's forwarding registry is benign on loss and B's accepted-host snapshot is a unilateral B-side write satisfiable by sequencing. (b) Phantom topology — it assumed broadcast content flowed *through* an intermediate host context to that host's members, which can only be achieved by decrypting B's content and re-encrypting it under the host's keys: a §5.11A.6 violation. Scale-out to a large audience is a transport/CDN concern (relays re-serving the already-public `BroadcastEnvelope`), needing no context mechanism — a relay re-serving ciphertext grants no new access; only an entity that independently joins B as a §5.14.3 subscriber can read B's content.

Only cross-context outlet invocation (spec §6.2.4) survived: it is the one arm with a genuine harmful partial commit (the caller's economy reservation and the target's outlet execution must be both-or-neither across two distinct contexts) and no phantom topology (no context relays another's plaintext).

The common failure mode was **counting contexts instead of testing atomicity**, and **assuming a relay/host topology** that the encryption model forbids. "As-built" scaffolding (a `SagaInput` variant, a `*Prepared` struct, journal snapshot mirrors, `SCP-SAGA-*` codes) created the *appearance* of a justified saga and made the category error look like settled design rather than a premise to interrogate.

**Fix**: Withdraw the arm, delete its scaffolding to completion (spec section, protocol file, `SagaInput` variant, prepared-state structs + snapshot mirrors, error-code band, FFI command variant, handler arms, and tests — re-pointing any test that exercised the generic FSM through the surviving saga's input rather than deleting the coverage), and record the generalized admission criteria in ADR-049 §3b so the next proposal is tested against the guards at design time, not after scaffolding.

**Lesson**: Three durable takeaways.

1. **"Touches two contexts" is not a saga criterion — a *harmful partial commit* is** (guard (a)). If either side's effect is benign on loss, or one side is a unilateral write the other never blocks on, sequence it. Most "cross-context" features are sequenceable; the saga is the rare exception.

2. **Content never flows *through* an intermediate context** (guard (b)). A context's content is readable only by an entity that independently joins it; any "X relays Y's content to X's members" design requires decrypt-then-re-encrypt (§5.11A.6 violation). Fan-out/scale-out is transport-layer re-serving of public ciphertext, never a context-level "hosting" relationship.

3. **As-built scaffolding is not justification.** A landed `SagaInput` variant, a spec section, and a registered error band describe a decision; they do not validate it. When 3 of 4 arms of an abstraction turn out to be category errors, the defect is in the admission criteria, not the individual arms — write the guard, then re-test every surviving and future member against it.
