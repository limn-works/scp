## Phase 1: Deep Verification — Specs 04, 05, 06

### 04 — Agents

**Requirements extracted:** 14
**Stories mapped:** SCP-018, SCP-019 (agent identity is implemented through the DID/identity system; no agent-specific stories exist beyond context membership)

**Verification results:**

- [CORRECT] 4.1 Every action traceable to human(s) — enforced by DID binding throughout: `crates/scp-core/src/identity/mod.rs` (DID type), `crates/scp-core/src/context/membership.rs` (MemberInfo.did), all tool invocations require invoker_did (`crates/scp-core/src/context/tools/invoke.rs:34-42`), all role assignments require DID (`crates/scp-core/src/context/roles.rs` RoleAssignment struct)
- [CORRECT] 4.2 Agent binding via cryptographic proof — implemented through Ed25519 key pairs bound to DIDs: `crates/scp-core/src/identity/` (DID resolution, key management). Institutional agents supported structurally via same DID mechanism.
- [CORRECT] 4.3 One agent per person per context — enforced in `crates/scp-core/src/context/membership.rs`: `MembershipState` uses `HashMap<DID, MemberInfo>` which prevents duplicate DID entries. `add_member()` rejects duplicates.
- [CORRECT] 4.4 BYOA (Bring Your Own Agent) — protocol defines communication/capability rules but not agent internals. No agent implementation type is assumed anywhere in the codebase.
- [MISSING] 4.4 Agent capability metadata (self-attested vs challenge-verified) — no implementation of structured capability profiles. Spec defines self-attested and challenge-verified capability metadata; neither has corresponding types or storage. No story covers this.
- [MISSING] 4.4 Challenge-response capability verification (7.3.4) — no implementation. Referenced in spec but no types or verification flow exist.
- [MISSING] 4.4 Context admission checks for capability levels — spec says "contexts can require specific capability levels for admission"; no implementation of capability-level admission gates exists.
- [CORRECT] 4.5 Human-agent pair as fundamental unit — structurally enforced: all protocol operations require a DID (human identity) and operate through agent actions. No bifurcation between "agent actions" and "human actions" in the API.
- [CORRECT] 4.6 Agents are consumers, not enforcers — protocol enforcement is cryptographic (MLS, UCAN capability tokens) not behavioral. SDK enforces rules; agents only invoke. Verified across `crates/scp-core/src/context/tools/invoke.rs` (UCAN checks), `crates/scp-core/src/context/roles.rs` (capability ceiling enforcement).
- [CORRECT] 4.7 Context-bound at protocol level — agent instances share no cross-context state at protocol level. Each context has independent membership, role state, key material. Verified in `crates/scp-core/src/context/manager.rs` (PerContextState is fully independent per context).
- [CORRECT] 4.7 No direct agent-to-agent primitive — no A2A mechanism exists. Cross-context communication uses tool interfaces (`crates/scp-core/src/context/tools/interface.rs`), nesting (`crates/scp-core/src/context/nesting.rs`), and standing channels (`crates/scp-core/src/context/standing.rs`).
- [CORRECT] 4.8 Agent fleet (one agent per context, many contexts per human) — structurally supported: `ContextManager` tracks per-context state independently. No per-human cross-context coupling.
- [MISSING] 4.8 Earned capacity (number of simultaneous contexts as earned resource) — spec notes "mechanism TBD". No implementation exists nor any story for this. The spec itself marks this as not yet designed.
- [CORRECT] 4.3 Institutional agents structurally identical to personal — both use the same DID/key binding. No separate institutional agent type; the difference is in key governance (multi-sig), which is outside protocol scope.

**Summary for 04:** 10 CORRECT, 0 INCORRECT, 4 MISSING (3 are unspecced features with no stories; 1 is explicitly TBD in spec)

### 05 — Contexts

**Requirements extracted:** 78
**Stories mapped:** SCP-018 (context state machine), SCP-019 (context manager), SCP-020 (context creation two-phase commit), SCP-021 (context membership), SCP-022 (context roles/UCAN), SCP-023 (context events), SCP-026 (tool schema validation), SCP-027 (tool lifecycle types), SCP-028 (tool registry/verification), SCP-029 (tool invocation engine), SCP-066 (TTL enforcement), SCP-067 (key destruction orchestration), SCP-068 (context promotion), SCP-069 (close orchestration), SCP-134 (context nesting), SCP-135 (auto-accept policy persistence), SCP-137 (standing channels), SCP-138 (invitation evaluation)

**Verification results:**

#### 5.1 Definition
- [CORRECT] Context is a bounded space with key material, event log, governance, membership, ceiling — `ContextParams` in `crates/scp-core/src/context/params.rs` contains all declared fields: mode, ceiling, ceiling_policy, promotion_policy, roles, tools, ttl, memory_scope, governance, template_id, economic_policy
- [CORRECT] Two modes: Encrypted and Broadcast — `ContextMode` enum at `crates/scp-core/src/context/params.rs:70-77` with exactly two variants
- [CORRECT] Mode immutable after creation — mode is part of `ContextParams` set at creation; no mutation API exists
- [CORRECT] Context is passive (spaces, not actors) — no `Context` struct has autonomous behavior; all actions require an external actor (DID) to initiate

#### 5.2 Creation
- [CORRECT] Only accountable identities can create — `create_context()` in `crates/scp-core/src/context/builder.rs` requires `ContextCryptoProvider::validate_creator_identity()` as Phase 1 step 1
- [CORRECT] Two-phase commit creation — `crates/scp-core/src/context/builder.rs` implements Phase 1 (validate, no side effects) and Phase 2 (execute with ordered rollback on failure). `CreationReceipt` tracks completed steps for rollback.
- [CORRECT] Creation branches on ContextMode — builder checks mode: Encrypted creates MLS group, Broadcast initializes broadcast key (`init_broadcast_key`). Both produce event log, governance, roles, transport.

#### 5.3 Capability Ceiling
- [CORRECT] Ceiling declared at creation — `ContextParams.ceiling: Vec<Capability>` in `crates/scp-core/src/context/params.rs:228`
- [CORRECT] Standard capability categories — `Capability` enum in `crates/scp-core/src/context/roles.rs` includes: MessagesRead, MessagesWrite, ToolInvoke(ToolId), ToolInvokeAll, ToolRegister, MemberInvite, MemberRemove, RoleAssign, GovernancePropose, GovernanceVote, ContextClose, ChildContextCreate, Custom(String)
- [MISSING] Media capabilities (media.voice, media.video, media.screenShare) — not present in Capability enum. Spec lists these as standard categories. No story covers media capabilities.
- [MISSING] Bridging capability — spec lists `bridging` as standard capability category; not in Capability enum
- [MISSING] toolInterface capability — spec lists `toolInterface` as standard capability for cross-context tool exposure; not in Capability enum
- [CORRECT] CeilingPolicy (immutable/governed) — `CeilingPolicy` enum at `crates/scp-core/src/context/params.rs` with Immutable and Governed variants
- [CORRECT] CapabilityCeiling with intersection logic — `crates/scp-core/src/context/roles.rs`: `CapabilityCeiling` struct with `contains()`, `is_subset()`, `intersection()` methods
- [CORRECT] Capability semantics uniform across modes — no mode-specific capability handling; same Capability enum used for both Encrypted and Broadcast

**Verification results:**

#### 7.1 Design Principle: Four-Layer Trust Model
- [CORRECT] 7.1 Four layers defined (Protocol Enforcement, Behavioral Validation, Attestation Authenticity, Trust Evaluation) — `TrustInput` in `crates/scp-core/src/trust/mod.rs:289-312` aggregates all four layers: `verified_attestations` (Layer 3), `behavioral_record` (Layer 2), `challenge_results` (Layer 3 challenge-response), `consequence_structure` (Layer 4), `threshold_counts` (Layer 3 threshold). The trust engine doc comment explicitly states "does not produce trust scores" matching the spec's agent-level evaluation principle.
- [CORRECT] 7.1 Trust engine provides validated inputs, not scores — module doc at `trust/mod.rs:1-7` explicitly states "provides validated inputs for agent-level evaluation — it does not produce trust 'scores.' Trust is contextual: each agent's evaluation logic consumes verifiable facts according to its own criteria."

#### 7.2 Layer 1: Protocol Enforcement (UCAN)
- [CORRECT] 7.2 Every action requires UCAN capability token — `crates/scp-core/src/crypto/ucan/validate.rs` implements 11-step validation pipeline: parse, signature, chain, root issuer, audience, capability match, attenuation, ceiling, nonce, revocation, expiry.
- [CORRECT] 7.2 Signature chain verified cryptographically — Step 2 in validate.rs verifies Ed25519 signatures via `ed25519_dalek`.
- [CORRECT] 7.2 Capability matches action — Step 6 via `check_capability_match()` in `capability.rs`.
- [CORRECT] 7.2 Context ceiling enforced — Step 8 via `verify_ceiling_compliance()` in `capability.rs` with O(1) HashSet check.
- [CORRECT] 7.2 Token revocation honored — Step 10 via `RevocationChecker` trait; `RevocationList` in `revoke.rs` with three-state model (Active -> RevocationPending -> Revoked), fail-closed on pending.
- [CORRECT] 7.2 Token expiry enforced — Step 11 checks `exp > now` and `nbf <= now`; `MAX_EXPIRY_SECS = 24 * 60 * 60` (24 hours) matching spec.
- [MISSING] 7.2 Spending UCAN AND-composition for paid actions — Spec says "Action UCAN + spending UCAN are AND-composed — both required." The `spending.rs` module implements `SpendingCapability` with AND-composition documented in module doc, but `validate_ucan()` in `validate.rs` does not check for a companion spending UCAN alongside the action UCAN. The spending module exists as types but the AND-composition enforcement point is not wired into the validation pipeline.

#### 7.3 Layer 2: Behavioral Validation
- [CORRECT] 7.3.1 Verifiable event logs (Merkle tree) — `crates/scp-core/src/event_log/tree.rs` implements append-only Merkle tree following RFC 6962 Certificate Transparency structure with domain separation (leaf: `SHA-256(0x00 || data)`, interior: `SHA-256(0x01 || left || right)`). - [CORRECT] 7.3.1 Events signed by acting agent and sequenced — `Event` struct in `event_log/mod.rs` includes `actor_did`, `sequence`, `signature`. `append()` in tree.rs verifies signature via `ed25519_dalek::Verifier`.
- [CORRECT] 7.3.1 Proof-of-inclusion and proof-of-absence — `crates/scp-core/src/event_log/proof.rs` implements Merkle proof operations.
- [CORRECT] 7.3.2 Behavioral record format — `BehavioralRecord` in `crates/scp-core/src/trust/behavioral.rs` includes: `context_count`, `total_duration_secs`, `tool_invocations` (HashMap by type), `governance_actions_against` (Vec<GovernanceActionSummary>), `governance_actions_by` (Vec<GovernanceActionSummary>), `role_transitions` (HashMap<String, Vec<RoleTransition>>), `attestation_references` (Vec<AttestationReference>), `context_creation_count`. All fields verifiable per spec.
- [CORRECT] 7.3.2 Behavioral records computed from event logs — `compute_behavioral_record()` in `behavioral.rs` takes a DID and list of events and produces a `BehavioralRecord`.
- [MISSING] 7.3.3 Tool verification via test vectors — Spec defines a process where agents verify tools by calling with test vector inputs, comparing outputs, and verifying implementation hash. No runtime verification logic exists. `ToolRegistration` in `context/tools/registry.rs` includes `test_vectors` and `implementation_hash` fields, but no `verify_tool()` function.
- [CORRECT] 7.3.4 Challenge-response verification — `crates/scp-core/src/trust/challenge.rs` implements `ChallengeRequest`, `ChallengeResponse`, `ChallengeVerification`, `ChallengeType` (standard + custom), `VerificationMethod` (SelfAttested/ChallengeVerified), `issue_challenge()`, `verify_challenge_response()`. ### 3.2 P0 Security-Critical Questions

#### 1. UCAN Revocation Mechanism (RESOLVED)

Previously listed as open. Actually fully resolved by ADR-016 and implemented in `crates/scp-core/src/crypto/ucan/revoke.rs` (SCP-055, done):
- **List format:** per-context `RevocationList` with `HashMap<String, RevocationState>`
- **Check frequency:** every UCAN validation (step 10 of 11-step pipeline)
- **Failure behavior:** fail-closed; MLS distribution failure triggers rollback
- Updated `00-open-questions.md` to mark as resolved.

#### 2. Sybil Resistance Enforcement (OPEN — needs design decisions)

§9.3 describes three layers but implementation is incomplete:
- **Layer 1 (Device attestation):** Implemented — App Attest (SCP-095) and Play Integrity (SCP-111) done
- **Layer 2 (Earned capacity):** Not specified — no algorithm, no signals, no thresholds
- **Layer 3 (Context thresholds):** Not specified — governance-level settings undefined

The Sybil block-list bypass (BLACK-006, #22) remains a known gap. Device attestation is the primary deterrent. Earned capacity and context thresholds need specification before they can be implemented. Classified as P1 (defense-in-depth, not blocking for launch).

#### 3. Commit Delivery Assurance Under Adversarial Relays (PARTIALLY RESOLVED)

§9.9.4 specifies the threat model and mitigation strategy. ADR-029 Tier 1 (epoch catch-up) handles missed Commits. The Relay Consistency Protocol (§9.9.3) detects divergence.

**Remaining gap:** No specified mechanism for peer-to-peer Commit fetch ("request missing Commit from other members"). Needs CommitRequest/CommitResponse wire types.

#### 4. Pseudonym Rotation and Traffic Analysis Resistance (OPEN — proposed approach)

Proposed epoch-based pseudonym rotation: derive `routing_id` with MLS epoch counter so pseudonyms change on every group operation. Grace period for dual-subscription during rotation. Cover traffic (SCP-225) addresses timing correlation separately.

Classified as P2 (defense-in-depth).
